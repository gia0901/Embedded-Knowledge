Sau module này bạn

  • Dựng được một thư viện C++17 dùng OpenSSL 3 đúng cách: RAII cho mọi handle, đọc error queue, dùng EVP API thay vì API đã deprecated.
  • Viết mTLS server bắt buộc client cert, đọc SPIFFE ID, tự nạp lại cert, và tránh các bẫy kinh điển của libssl.
  • Verify JWT ES256 với JWKS cache có thời hạn; xử lý chữ ký raw r‖s và allowlist thuật toán.
  • Cài đặt Milenage, 5G-AKA, SUCI bằng C++ và kiểm chứng bằng test vector 3GPP, đúng loại code của AUSF/UDM.
  • Tìm bug trong parser protocol bằng sanitizer và libFuzzer.
  • Thay orders-api của capstone bằng bản C++ và vẫn qua nguyên bộ test.sh.

Vì sao có module này, và học lúc nào

Module 00–16 dùng Python và Bash để học khái niệm nhanh. Nhưng service trong core network, kể cả phần security và authentication của platform, phần lớn viết bằng C/C++ và gọi thẳng OpenSSL. Phần khó khi viết C++ (quản lý handle, error queue, thread, bộ nhớ chứa secret, parser an toàn) là chung cho mọi bài, nên được gom vào một module. Lab 17.1 · Khung project, RAII và EVP

Cơ bảnC++17 · CMake · libcrypto90 phút

Dựng project CMake có thư viện tĩnh libnetsec, bật warning và tuỳ chọn sanitizer. Viết ossl.hpp (deleter cho mọi handle, hàm đọc error queue), crypto.cpp (hex, base64url, SHA-256, HMAC-SHA-256 bằng EVP_MAC, AES-128 ECB/CTR, KDF của 3GPP TS 33.220, X9.63 KDF, so sánh constant-time, xoá secret) và log.cpp (audit log JSON một dòng, giống capstone). Unit test với test vector chuẩn, chạy cả bản thường lẫn bản có ASan/UBSan.

Xong khi: ctest đạt ở cả hai bản build; không có warning nào; không có dòng *_free nào được gọi bằng tay ngoài deleter.

Gợi ý

template <auto Fn> struct Deleter (C++17) cho phép viết std::unique_ptr<EVP_MD_CTX, Deleter<EVP_MD_CTX_free>>. HMAC trong OpenSSL 3: EVP_MAC_fetch(nullptr, "HMAC", nullptr), tham số "digest" = "SHA256" qua OSSL_PARAM. Phần lớn hàm trả 1 khi thành công; hàm trả con trỏ thì nullptr là lỗi.

Lab 17.2 · mTLS server: client cert bắt buộc, SPIFFE ID, hot reload

VừaC++17 · libssl · socket120 phút

Viết tls.cpp: tạo SSL_CTX chỉ nhận TLS 1.3, server bắt buộc client cert có EKU clientAuth, client kiểm tra cert server có EKU serverAuth; lớp ReloadingTlsCtx tạo SSL_CTX mới khi file cert đổi (giữ ctx cũ nếu file mới hỏng); hàm peer_identity lấy đúng một SPIFFE ID trong SAN và thumbprint x5t#S256; vòng lặp serve_tls một thread mỗi connection, ghi log mọi lần từ chối kèm lý do verify. Viết mtls_hello: chào client có SPIFFE ID trong allowlist, từ chối client khác.

Xong khi: với PKI của Lab 10.2 và 11.3: svc-a được chào; svc-b bị từ chối ở tầng ứng dụng; không có cert và dùng server cert làm client cert đều bị từ chối ở TLS với lý do rõ ràng trong log; thay cert trên đĩa thì serial đổi mà không restart process.

Gợi ý

SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER | SSL_VERIFY_FAIL_IF_NO_PEER_CERT, nullptr), SSL_CTX_set_purpose(ctx, X509_PURPOSE_SSL_CLIENT). SAN: X509_get_ext_d2i(cert, NID_subject_alt_name, …) trả GENERAL_NAMES*; mục URI có type == GEN_URI. DER của cert: i2d_X509. Lý do verify thất bại: X509_verify_cert_error_string(SSL_get_verify_result(ssl)). std::filesystem::last_write_time đi theo symlink, giống cách kubelet cập nhật Secret.

Lời giải

Lý do verify: ok ở dòng "không có client cert" là đúng: không có cert nào để verify, handshake thất bại vì SSL_VERIFY_FAIL_IF_NO_PEER_CERT. Thử xoá cờ đó, build lại và chạy hello không cert: server chấp nhận connection với client rỗng. Đây là bẫy số 1 trong bảng. svc-b.crt được tạo ở Lab 11.3. Serial của bạn sẽ khác.

Lab 17.3 · Verify JWT ES256 và JWKS cache

VừaC++17 · libcrypto · nlohmann/json120 phút

Viết jwt.cpp: tạo public key EC P-256 từ JWK (EVP_PKEY_fromdata); JwksCache chọn key theo kid, tải lại khi gặp kid lạ (tối đa mỗi 10 giây) và định kỳ (5 phút), giữ cache cũ nếu tải lỗi; verify_es256 kiểm tra allowlist alg trước mọi thứ, chuyển chữ ký raw r‖s sang DER, verify, rồi kiểm tra iss, aud, exp/nbf có leeway và các claim bắt buộc. Dùng Python (PyJWT) sinh JWKS và 11 token mẫu; chương trình jwt_check phải cho cùng kết quả với kỳ vọng.

Xong khi: jwt_check báo đạt cả 11 token, gồm alg=none, HS256 giả mạo, chữ ký DER, sai key, kid lạ, hết hạn, sai aud, sai iss, thiếu cnf.

Gợi ý

Public key P-256 trong OpenSSL 3: OSSL_PARAM gồm OSSL_PKEY_PARAM_GROUP_NAME = "prime256v1" và OSSL_PKEY_PARAM_PUB_KEY = 04 ‖ x ‖ y, rồi EVP_PKEY_fromdata(…, EVP_PKEY_PUBLIC_KEY, …). Raw → DER: ECDSA_SIG_new, BN_bin2bn cho r và s, ECDSA_SIG_set0, i2d_ECDSA_SIG. Cache dùng std::chrono::steady_clock, không dùng giờ hệ thống (có thể bị chỉnh).

Lời giải

Token mẫu sống 5 phút: quá hạn thì chạy lại gen_tokens.py. Thử sửa return rc == 1; thành return rc; và đưa vào một chữ ký sai định dạng: bạn sẽ thấy vì sao dòng đó đáng một comment. JwksCache ở đây đã có TTL, nên lỗi ở M5 của capstone không lặp lại trong bản C++.

Lab 17.4 · Milenage, 5G-AKA và SUCI bằng C++

VừaC++17 · libcrypto120 phút

Viết fiveg.cpp: Milenage f1–f5* (TS 35.206), HE AV của ARPF, HXRES* và KSEAF của AUSF, phía USIM kiểm tra AUTN (MAC, SQN) rồi tính RES* và KSEAF, và SIDF giải SUCI Profile A (X25519, X9.63 KDF, AES-128-CTR, HMAC-SHA-256 cắt 8 byte). Unit test với Test Set 1 (TS 35.208) và các giá trị 5G-AKA đã đối chiếu ở module 15. Cuối cùng giải một SUCI do bản Python (Lab 15.4) tạo ra.

Gợi ý

Thuật toán giống hệt Lab 15.3, chỉ đổi ngôn ngữ; dùng lại aes128_ecb_block, kdf_3gpp, equal_ct của Lab 17.1. X25519: EVP_PKEY_new_raw_private_key(EVP_PKEY_X25519, …), EVP_PKEY_new_raw_public_key, rồi EVP_PKEY_derive_init, EVP_PKEY_derive_set_peer, EVP_PKEY_derive. Xoá CK, IK, KAUSF tạm bằng wipe() khi không cần nữa.

Lời giải

Lệnh read … < <(…) có một đoạn Python nhiều dòng; dán nguyên khối vào terminal. Dòng thay byte giả định byte thứ 36 không phải ff sẵn; nếu trùng thì đổi thành 00. Đây chính là code mà AUSF/UDM thật chạy, chỉ khác là K và private key của SIDF nằm trong HSM chứ không nằm trong RAM của process.

Lab 17.5 · Parser GTP-U: tìm bug bằng sanitizer và libFuzzer

Thử tháchC++17 · clang · ASan · libFuzzer90 phút

Parser cho protocol nhận từ mạng là nơi sinh ra những lỗi như Heartbleed. Bắt đầu từ parser GTP-U có lỗi cho sẵn dưới đây: nó đọc header bắt buộc 8 byte, 4 byte tuỳ chọn (sequence number, N-PDU, next extension type) và chuỗi extension header (TS 29.281). Viết unit test với packet mẫu, viết fuzz target, chạy libFuzzer với ASan/UBSan cho tới khi tìm ra bug, sửa parser, rồi biến input gây crash thành regression test.

Xong khi: fuzzer tìm ra crash trên bản có lỗi trong vòng vài giây; bản đã sửa chạy 60 giây không crash; mọi input gây crash đều thành ca âm tính trong test_gtpu.

Gợi ý

Liệt kê mọi chỗ đọc d[i] và hỏi: đã chắc i < len chưa? Trường length khai báo số byte sau 8 byte đầu, nên giới hạn đúng là 8 + length, và nó phải không vượt len. Extension có độ dài 0 thì vòng lặp không tiến. Build fuzz target: clang++ -std=c++17 -g -O1 -fsanitize=fuzzer,address,undefined -Iinclude fuzz/fuzz_gtpu.cpp src/gtpu.cpp -o fuzz_gtpu.

Lời giải

Byte gây crash, số lần chạy và dòng code trong stack trace của bạn sẽ khác: fuzzer ngẫu nhiên. Nếu nó tìm ra lỗi lặp vô hạn trước, libFuzzer báo ALARM: working on the last Unit for 2 seconds và lưu timeout-… thay vì crash-…. Trong project thật, mọi parser của NGAP, NAS, PFCP, Diameter, X.509 nên có fuzz target chạy trong CI.

Lab 17.6 · orders-api bản C++ trong capstone

Thử tháchC++17 · Docker · kind120 phút

Ghép mọi thứ: viết http.cpp (đọc request HTTP/1.1 có giới hạn kích thước, ghi response JSON, HTTPS GET qua mTLS có kiểm tra hostname để tải JWKS) và orders_api.cpp làm đúng những gì bản Python ở M3 của capstone làm: mTLS bắt buộc, verify token qua JWKS, kiểm tra cnf.x5t#S256 với cert của client, scope theo route, 401/403 với WWW-Authenticate, audit log cùng định dạng. Build image nhiều tầng, thay vào deployment orders-api trên kind.

Xong khi: test.sh của module 16 báo 10/10 mà không sửa một dòng test nào; bài diễn tập xoay cert ở M5 cũng đạt với bản C++ (log tls_context_loaded lần hai, không restart); và key k1 bị gỡ khỏi JWKS thì token k1 bị từ chối sau tối đa 5 phút.

Gợi ý

Đọc request tới \r\n\r\n, tối đa 8 KB, rồi bỏ. Tên header so sánh không phân biệt hoa thường. Phía client nhớ SSL_set_tlsext_host_name (SNI) và SSL_set1_host. Server Python của token-server đóng connection mà không gửi close_notify, nên SSL_read kết thúc bằng lỗi "unexpected eof": dữ liệu đã đủ, chỉ cần dọn error queue. Image runtime chỉ cần libssl3t64 (tên gói trên Ubuntu 24.04).

Lời giải

Image runtime khoảng 80 MB (Ubuntu + libssl); có thể giảm bằng distroless hoặc link tĩnh, nhưng khi đó phải tự lo cập nhật OpenSSL theo CVE. Con số log và thời gian của bạn sẽ khác (client ctx chỉ nạp lại ở lần tải JWKS kế tiếp). Muốn quay lại bản Python: kubectl apply -f ~/netlab/m16/k8s/30-orders-api.yaml.
