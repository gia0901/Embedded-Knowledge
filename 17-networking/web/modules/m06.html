Sau bài này bạn

  • Phân biệt forwarding (data plane) và routing (control plane).
  • Đọc được IPv4 header và IPv6 header: TTL, protocol, fragmentation, hop limit, next header.
  • Tính nhanh subnet từ CIDR, làm longest prefix match bằng tay, và nhận ra các dải address đặc biệt (private, CGNAT, link-local).

MTU, fragmentation và Path MTU Discovery

Mỗi link có MTU (Maximum Transmission Unit): kích thước IP datagram lớn nhất mà link chở được. Ethernet là 1,500 byte. Khi datagram lớn hơn MTU của link tiếp theo:

  • IPv4 không có DF: router cắt datagram thành nhiều fragment; host đích ghép lại nhờ Identification và Fragment offset. Mất một fragment là mất cả datagram.
  • IPv4 có DF (Linux đặt DF cho TCP) hoặc IPv6: router drop datagram và gửi về ICMP "Fragmentation Needed" (IPv6: "Packet Too Big") kèm MTU của link. Sender giảm kích thước gói. Đây là Path MTU Discovery (PMTUD).

IPv4 addressing

IPv4 address dài 32 bit, viết 4 số thập phân (dotted-decimal). Address gắn với interface, không gắn với host: router có nhiều interface nên có nhiều address §4.3.3.

Các interface nối với nhau mà không cần đi qua router tạo thành một subnet. Mọi address trong subnet có chung phần đầu gọi là network part (prefix). Ký hiệu CIDR a.b.c.d/x: x bit đầu là prefix, phần còn lại là host part.

Ghi nhớ
  • /24 → 256 address (254 host). Mỗi bớt 1 bit prefix thì số address gấp đôi: /23 → 512, /20 → 4,096, /16 → 65,536.
  • Address đầu (host part toàn 0) là network address, address cuối (host part toàn 1) là broadcast; không gán cho host. Riêng /31 (link point-to-point) và /32 (một address duy nhất) là ngoại lệ.
  • Đích nằm cùng subnet thì gửi thẳng (Q2: không có "via"); khác subnet thì gửi cho router (default gateway).

NAT

IPv4 chỉ có khoảng 4.3 tỷ address, không đủ cho mọi thiết bị. NAT (Network Address Translation) cho cả một mạng private dùng chung một (hoặc vài) public IP §4.3.4. Router NAT ghi lại mỗi lượt dịch vào NAT translation table, và dịch ngược khi reply quay về:

Loại NATViết lạiGặp ở đâu
SNAT / masqueradeSource address (và port) của traffic đi raRouter nhà (Q3), WSL2, Docker (Q5), pod gọi ra ngoài cluster
DNAT / port forwardingDestination address của traffic đi vàodocker run -p 8080:80; Kubernetes Service: kube-proxy DNAT từ ClusterIP sang IP của một pod
CGNATNAT nhiều tầng ở nhà mạngDải 100.64.0.0/10

Hệ quả của NAT:

  • Phá end-to-end principle (module 01): từ ngoài không thể chủ động mở connection vào host sau NAT nếu không cấu hình port forwarding.
  • NAT phải nhớ state cho từng connection (Linux: bảng conntrack). Bảng đầy thì connection mới bị drop.
  • NAT không phải firewall, dù nó tình cờ chặn được connection đi vào.
  • Server phía sau NAT/load balancer chỉ thấy IP của NAT, mất source IP thật của client.
Cạm bẫy security

Đừng dựa vào source IP để xác thực hay phân quyền: sau NAT, nhiều client có chung một IP; trong cluster, IP của pod đổi liên tục. Header X-Forwarded-For giúp lấy lại IP gốc cho mục đích log, nhưng client tự đặt header này được, nên chỉ tin khi nó do proxy của chính bạn thêm vào. Identity phải đến từ certificate hoặc token (module 10–12).

ICMP (Internet Control Message Protocol) là protocol báo lỗi và chẩn đoán của network layer. ICMP message nằm trong IP datagram (protocol 1) §5.6:

Ghi nhớ

Chặn toàn bộ ICMP không làm hệ thống an toàn hơn bao nhiêu mà làm hỏng PMTUD và khó debug. Chính sách hợp lý: cho phép type 3 (đặc biệt code 4), type 11, và echo trong nội bộ; rate-limit ICMP để chống flood. Với IPv6 càng không được chặn bừa: ICMPv6 lo cả việc tìm MAC address của neighbor (Neighbor Discovery), chặn là mất kết nối.

IPv6

IPv6 dùng address 128 bit, đủ để mỗi subnet có 264 address §4.3.5. Header được làm gọn để router xử lý nhanh:

So với IPv4IPv6
HeaderCố định 40 byte; option chuyển thành extension header nối nhau qua field Next header
ChecksumBỏ hẳn (link layer và transport layer đã có)
FragmentationRouter không fragment; chỉ host gửi làm, dựa vào ICMPv6 Packet Too Big
TTLĐổi tên thành Hop limit
NATThường không cần; mỗi host có global address

Viết tắt address: bỏ số 0 đầu mỗi nhóm, và thay một dãy nhóm toàn 0 liên tiếp bằng ::. Ví dụ 2001:0db8:0000:0000:0000:ff00:0042:8329 → 2001:db8::ff00:42:8329. Loại address: global unicast (2000::/3), link-local (fe80::/10, mọi interface đều có), unique local (fc00::/7, tương tự private), loopback ::1, multicast (ff00::/8).

Thế giới hiện chạy dual stack (cả IPv4 và IPv6). Đó là lý do getaddrinfo() ở module 03 trả về cả hai loại, và client nên thử cả hai (Happy Eyeballs). Mạng di động là nơi IPv6 phổ biến nhất: điện thoại 5G thường chỉ được cấp IPv6.

Lab 6.3 · Tái hiện MTU black hole và sửa bằng MSS clamping

Thử tháchDocker · ip · iptables60 phút

Dựng 3 container: client (10.10.1.10) — router — server (10.10.2.10). Server phục vụ một file 2 MB qua TCP. Sau đó:

  1. Tải file khi mọi thứ bình thường.
  2. Hạ MTU của interface phía client trên router xuống 1400. Tải lại: vẫn chạy nhờ PMTUD.
  3. Chặn ICMP "fragmentation needed" trên router. Tải lại: connection mở được nhưng dữ liệu không về.
  4. Sửa bằng MSS clamping trên router mà không cần bỏ chặn ICMP.

Xong khi: có 4 kết quả (đủ byte / đủ byte / gần 0 byte / đủ byte) và giải thích được vì sao MSS clamping sửa được.

Gợi ý

Router cần --sysctl net.ipv4.ip_forward=1 và --cap-add NET_ADMIN; client và server cần route tới subnet bên kia qua router. Interface của network đầu tiên trong router là eth0, network nối thêm bằng docker network connect là eth1. Rule chặn: iptables -A OUTPUT -p icmp --icmp-type fragmentation-needed -j DROP.

Lời giải

Vì sao MSS clamping chạy: router sửa field MSS trong gói SYN/SYN-ACK đi qua nó thành MTU của link hẹp nhất trừ 40 (ở đây 1,360). Server tin MSS đó nên ngay từ đầu không gửi segment quá lớn, không cần tới ICMP. Đây là cấu hình chuẩn trên VPN gateway và các tunnel trong core network. Nếu ở bước 3 bạn vẫn nhận đủ byte, hãy kiểm tra server đã xoá PMTU cache chưa, hoặc dừng và tạo lại container server.

Lab 6.4 · Viết ping bằng raw socket trong C

VừaC · raw socket45 phút

Viết myping: tự build ICMP echo request (type 8) kèm checksum, gửi bằng raw socket, nhận reply, tự parse IP header (dùng IHL để biết ICMP bắt đầu ở đâu), in TTL và RTT. Lọc đúng reply của mình bằng identifier và sequence number.

Xong khi: output tương tự ping thật, và bạn giải thích được vì sao chương trình cần sudo.

Gợi ý
  • socket(AF_INET, SOCK_RAW, IPPROTO_ICMP). Khi nhận, raw socket trả về cả IP header.
  • Checksum Internet (RFC 1071): cộng các word 16 bit vào số 32 bit, gấp phần tràn về, rồi đảo bit. Cùng thuật toán với checksum UDP/TCP ở module 05.

Lời giải

Raw socket cho phép tự dựng mọi loại packet (kể cả giả source IP), nên Linux chỉ cho process có capability CAP_NET_RAW. Trong Kubernetes, security best practice là drop capability này khỏi container của bạn. Mở rộng: đặt TTL tăng dần bằng setsockopt(s, IPPROTO_IP, IP_TTL, …) và xử lý ICMP_TIME_EXCEEDED để biến chương trình thành traceroute.
