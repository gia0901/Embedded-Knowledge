Socket API

Socket là "cánh cửa" giữa process và transport layer (module 02). API gần như mọi ngôn ngữ dùng là Berkeley sockets từ Unix những năm 1980. Trên Linux, một socket là một file descriptor: một con số, đọc ghi bằng read/write như file. Python, Go, Java… đều gọi xuống đúng các system call này.

Liên hệ job

Một proxy hoặc middleware gọi cùng một backend (cùng destination IP và port) chỉ còn đổi được source port, tức tối đa khoảng 28,000 connection đồng thời từ một IP. Mở rồi đóng connection liên tục, mỗi connection còn nằm trong TIME-WAIT 60 giây: hết ephemeral port, connect() báo EADDRNOTAVAIL. Đây là một lý do nữa để dùng connection pool (module 02).

TCP là byte stream: message framing

TCP đảm bảo đúng byte, đúng thứ tự, nhưng không giữ ranh giới giữa các lần send(). Bên nhận có thể nhận gộp hoặc nhận vụn:

Application phải tự đánh dấu ranh giới message. Ba cách phổ biến:

Cách framingVí dụ protocol thậtƯu / nhược
Delimiter (ký tự kết thúc)HTTP/1.1 header kết thúc bằng \r\n\r\n; Redis, SMTP dùng \r\nDễ debug bằng mắt; phải escape nếu dữ liệu chứa delimiter
Length-prefix (độ dài ở đầu)HTTP/2 frame (Length 24 bit), DNS over TCP (2 byte), TLS record (2 byte), gRPCNhanh, nhận binary tuỳ ý; phải giới hạn độ dài tối đa
Fixed sizeMột số protocol telecom cũ, header cố địnhĐơn giản nhất; lãng phí, kém linh hoạt
Cạm bẫy security
  • Đọc length-prefix 4 byte rồi cấp phát buffer đúng bằng số đó: kẻ tấn công gửi 0xFFFFFFFF và service của bạn cố cấp phát 4 GB. Luôn kiểm tra độ dài tối đa trước khi đọc tiếp.
  • send() cũng có thể gửi ít hơn số byte yêu cầu. Python có sendall(); trong C phải tự lặp tới khi gửi hết.
  • Không có timeout, một client mở connection rồi im lặng sẽ giữ thread/socket của bạn mãi. Tấn công Slowloris làm đúng điều này với hàng nghìn connection.

Concurrency model

Server thật phải phục vụ nhiều client cùng lúc. Các cách phổ biến:

ModelCách làmHợp khiGặp ở đâu
IterativeMột vòng lặp, phục vụ xong client này mới accept client sauDemo (như ví dụ trong sách §2.7)Không dùng thật
Thread-per-connectionMỗi connection một thread, code blocking dễ đọcVài trăm đến vài nghìn connectionPython ThreadingHTTPServer, Java servlet cũ
Event loop (I/O multiplexing)Một thread hỏi kernel "socket nào sẵn sàng?" bằng epoll (Linux), xử lý socket đó, lặp lạiHàng chục nghìn connection (bài toán C10K)nginx, Envoy, Netty, Node.js, Python asyncio, Go runtime
Event loop × N threadMỗi CPU core một event loopService hiệu năng caoEnvoy, Netty, Seastar; nhiều NF 5G viết bằng C++

Thread-per-connection tốn bộ nhớ (stack mỗi thread cỡ vài MB) và chi phí context switch. Event loop tốn ít tài nguyên nhưng mỗi handler không được block: chỉ cần một lệnh chậm (đọc file lớn, gọi DNS đồng bộ) là mọi connection khác cùng đứng. Lab 4.3 viết một event loop bằng epoll trong C.

Ghi nhớ: refused hay timeout?

Hai lỗi này trả lời hai câu hỏi khác nhau. Refused (nhanh): packet tới được máy đích, nhưng không ai nghe ở port đó, nên hãy kiểm tra service và port. Timeout (chậm): packet không tới được hoặc bị bỏ đi âm thầm, nên hãy kiểm tra route, firewall, NetworkPolicy. Chỉ riêng việc phân biệt hai lỗi này đã thu hẹp vùng cần debug đi một nửa.

Cạm bẫy: bind address
  • 127.0.0.1: chỉ process trên cùng máy (hoặc cùng pod) gọi được. Service "chạy ngon trên laptop" nhưng không ai trong cluster gọi tới được thường là do bind nhầm vào đây.
  • 0.0.0.0: nghe trên mọi interface. Tiện, nhưng một admin port hay debug port bind ở đây là lộ ra ngoài.
  • Container chạy non-root (khuyến nghị security) không bind được port dưới 1024: dùng 8443 thay cho 443, hoặc cấp riêng CAP_NET_BIND_SERVICE.

Lab 4.1 · UDP client có timeout và retry

Cơ bảnPython30 phút

Viết UDP server ở port 9000 trả lại câu nhận được dưới dạng chữ hoa (giống ví dụ UDPServer trong sách §2.7.1), nhưng có thêm tham số để cố ý bỏ một tỉ lệ datagram, giả lập packet loss. Viết client đọc từng dòng từ stdin, gửi đi, chờ tối đa 0.5 giây, gửi lại tối đa 3 lần, in RTT mỗi lần thành công.

Xong khi: với server bỏ 30% datagram, client vẫn nhận đủ câu trả lời (thỉnh thoảng phải retry), và bạn chỉ ra được một trường hợp client có thể nhận nhầm reply của câu trước.

Gợi ý

socket.settimeout(0.5) làm recvfrom() ném TimeoutError. Server dùng recvfrom() để biết address người gửi rồi sendto() trả về đúng address đó.

Lời giải

Lỗi tiềm ẩn: nếu reply của lần gửi thứ nhất chỉ đến muộn (không mất), client đã gửi lại và chuyển sang câu tiếp theo; reply muộn đó sẽ bị đọc như câu trả lời của câu sau. Cách sửa: gắn sequence number vào mỗi request và bỏ qua reply không khớp. DNS dùng đúng cách này với field ID (module 03). TCP giải quyết vấn đề này ở transport layer (module 05).

Lab 4.2 · Key-value server TCP với length-prefix framing

VừaPython60 phút

Viết một server TCP port 9100 lưu key-value trong bộ nhớ. Protocol tự thiết kế:

  • Mỗi message = 4 byte độ dài (big-endian) + JSON. Request: {"op":"set|get|del","key":…,"value":…}. Response: {"ok":true,…}.
  • Một connection gửi được nhiều request liên tiếp (persistent).
  • Thread-per-connection. Message dài quá 64 KB thì đóng connection. Client im lặng quá 30 giây thì đóng connection.

Viết thêm client kvcli.py. Rồi chứng minh framing đúng bằng ba phép thử: client gửi từng byte một; client gửi độ dài giả 0xFFFFFFFF; client mở connection rồi im lặng.

Xong khi: cả ba phép thử cho đúng kết quả trong log server, và ss -tnp | grep 9100 không còn socket nào treo sau khi client đi hết.

Gợi ý

Viết hàm recv_exact(conn, n) lặp recv() tới khi đủ n byte; recv() trả về b"" nghĩa là peer đã đóng. struct.pack("!I", n) cho 4 byte big-endian. Dùng with conn: để chắc chắn socket được close ở mọi nhánh (tránh CLOSE-WAIT).

Lời giải

Log server ở trên có thêm một cặp dòng +/− cho mỗi lệnh kvcli.py và slow_client.py. Mở rộng: thêm field "auth": token vào mỗi request và từ chối nếu sai; rồi capture bằng tcpdump để thấy token đi plaintext (giống Lab 2.3).

Lab 4.3 · Echo server một thread với epoll

Thử tháchC · epoll60 phút

Viết TCP echo server port 9200 bằng C, một thread duy nhất, dùng epoll để phục vụ nhiều client: listening socket và mọi connection socket đều non-blocking và đăng ký vào cùng một epoll instance. In log khi có client vào/ra. Sau đó dùng script Python mở 500 connection cùng lúc để kiểm tra.

Xong khi: 500/500 connection nhận echo đúng, ss -tn | grep -c 9200 cho thấy hàng trăm connection trong khi ps -T cho thấy server chỉ có 1 thread, và khi client đóng hết thì không còn socket CLOSE-WAIT nào.

Gợi ý
  • epoll_create1 → epoll_ctl(EPOLL_CTL_ADD, listen_fd) → lặp epoll_wait.
  • Sự kiện trên listening socket nghĩa là có connection mới: accept4(…, SOCK_NONBLOCK) trong vòng lặp tới khi gặp EAGAIN, rồi đăng ký fd mới.
  • Sự kiện trên connection socket: read; trả về 0 nghĩa là peer đã đóng → EPOLL_CTL_DEL và close.
Lời giải

Muốn thử vài nghìn connection, tăng giới hạn file descriptor trước: ulimit -n 8192 ở cả hai cửa sổ. Mở rộng: xoá dòng close(fd), chạy lại load test, rồi xem ss -tan state close-wait | wc -l.

Lab 4.4 · Bắt quả tang socket leak

VừaPython · ss · Bash25 phút

Đây là sự cố thật hay gặp với middleware: service dần dần "chết" vì hết file descriptor. Chạy server có bug dưới đây, tạo traffic, rồi dùng ss và /proc để chứng minh nó leak socket và chỉ ra state của các socket bị leak. Sau đó sửa bug.

Xong khi: có output ss cho thấy socket ở state CLOSE-WAIT, đếm được số file descriptor của process tăng theo traffic, và bản sửa làm số đó đứng yên.

Gợi ý

Tạo 20 client: for i in $(seq 20); do echo hi | nc -N 127.0.0.1 9300; done. Lọc state: ss -tan state close-wait. Số file descriptor của một process: ls /proc/PID/fd | wc -l.

Lời giải

Sửa: dùng with conn: (hoặc try/finally: conn.close()) quanh phần xử lý, và bỏ list leaked. Chạy lại: ss không còn CLOSE-WAIT, số fd đứng yên ở 4.

Ở công ty, cùng quy trình áp dụng cho pod: kubectl exec vào pod rồi chạy ss -tan, hoặc xem metric số file descriptor đang mở của process.
