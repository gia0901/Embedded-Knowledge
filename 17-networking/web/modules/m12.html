Sau bài này bạn

  • Phân biệt rõ authentication (bạn là ai), authorization (bạn được làm gì) và audit (ai đã làm gì); trả đúng 401 hay 403.
  • Lưu mật khẩu đúng cách (Argon2id, salt) và hiểu MFA, TOTP chạy thế nào.
  • Đọc, ký, validate JWT; biết các lỗi validate kinh điển (alg none, thiếu kiểm tra aud, exp).
  • Hiểu OAuth 2.0 (authorization code + PKCE, client credentials), OIDC, và cách 5G core dùng NRF làm authorization server.
  • Dùng LDAP để login và lấy group; map group → role → permission theo RBAC.

Toàn cảnh một hệ thống auth hiện đại:

Từ "I am Alice" tới nonce

Sách xây dựng authentication protocol từng bước, mỗi bước vá lỗ hổng của bước trước. §8.4 Chuỗi này giải thích vì sao mọi protocol hiện đại đều có nonce hoặc challenge:

ProtocolAlice chứng minh bằngTrudy phá bằng
ap1.0Nói "I am Alice"Nói y như vậy
ap2.0+ gửi từ IP của AliceIP spoofing (module 06)
ap3.0+ gửi kèm passwordNghe lén password
ap3.1+ password đã mã hoáReplay nguyên bản mã hoá: Bob không phân biệt được
ap4.0Bob gửi nonce R (dùng một lần), Alice trả về R mã hoá bằng shared keyReplay vô dụng vì lần sau R khác. Hạn chế: cần shared key trước.
Mở rộngNonce + chữ ký bằng private keyMan-in-the-middle nếu không biết public key thật → certificate (module 10)
Bạn đã gặp mẫu này ở đâu

TLS CertificateVerify (module 11) là "nonce + chữ ký": ClientHello.random đóng vai nonce. TOTP là ap4.0 với nonce là thời gian hiện tại. Passkey/WebAuthn là bản mở rộng: server gửi challenge, thiết bị ký bằng private key không bao giờ rời máy. Password gửi qua TLS về bản chất vẫn là ap3.0, chỉ được TLS che khỏi người nghe lén.

Lưu password

Server không bao giờ lưu password, chỉ lưu kết quả của một hàm một chiều, cố ý chậm, có salt. Khi login, server tính lại hàm đó với password vừa nhận rồi so sánh. Lý do phải chậm: khi DB bị lộ, kẻ tấn công đoán password offline với tốc độ của GPU. Với SHA-256, GPU đời mới thử được cỡ hàng chục tỷ lần mỗi giây; mọi password 8 ký tự chữ thường + số (36⁸ ≈ 2.8 nghìn tỷ khả năng) rơi trong vài phút. Hàm như Argon2id tốn vài chục ms và vài chục MB RAM cho mỗi lần thử, nên cùng việc đó mất hàng nghìn năm.

Pepper là một secret chung giữ ngoài DB (trong KMS), thêm vào trước khi hash: lộ DB mà không lộ pepper thì không đoán offline được.

Cạm bẫy ở endpoint login
  • User enumeration: trả "không có user này" khác với "sai password" (khác nội dung, hoặc khác thời gian phản hồi vì user không tồn tại thì bỏ qua bước hash) giúp kẻ tấn công biết user nào có thật. Luôn trả cùng một thông báo, và vẫn chạy hash giả khi user không tồn tại.
  • Credential stuffing: thử password lộ từ site khác. Chống bằng rate limit theo IP và theo account, MFA, kiểm tra password có trong danh sách đã lộ.
  • Lockout cứng (khoá vĩnh viễn sau 5 lần sai) biến thành công cụ DoS: ai cũng khoá được account admin. Dùng delay tăng dần và CAPTCHA/MFA thay vì khoá hẳn.

TOTP (RFC 6238), loại mã 6 số trong app authenticator, chính là HMAC (module 09): code = truncate(HMAC-SHA1(secret, floor(time / 30))). Server và điện thoại chung secret (QR code lúc đăng ký), cùng tính theo đồng hồ, nên mã đổi mỗi 30 giây. Lab 12.1 tự cài đặt TOTP và kiểm tra với test vector của RFC.

JWT

JSON Web Token (RFC 7519) gồm 3 phần base64url nối bằng dấu chấm:

ClaimNghĩaResource server phải kiểm tra
issAi cấp tokenĐúng issuer mình tin (và dùng đúng JWKS của issuer đó)
subToken nói về ai (user ID, client ID)Dùng làm identity cho authorization và audit log
audToken dành cho service nàoCó mình trong đó. Thiếu bước này, token cấp cho service A dùng được ở service B.
exp, nbf, iatHết hạn, chưa có hiệu lực trước, thời điểm cấp (Unix time)Theo đồng hồ của mình, cho phép lệch (leeway) vài chục giây

Hai họ thuật toán ký: HS256 (HMAC, cùng một secret để ký và verify, nên mọi service verify được cũng ký được) và RS256 / ES256 / EdDSA (ký bằng private key chỉ authorization server giữ, verify bằng public key công bố qua JWKS). Giữa nhiều service, luôn dùng loại thứ hai. Header kid chỉ key nào trong JWKS; nhờ vậy authorization server xoay vòng key được: công bố key mới bên cạnh key cũ, ký bằng key mới, gỡ key cũ khi token cũ đã hết hạn (Q2).

Thử verify JWT ngay trong trang. Widget chạy hoàn toàn trong browser của bạn, nhưng tập thói quen tốt: đừng dán token thật của production vào trang web nào.

Cạm bẫy khi validate JWT
  • alg: none. Library tin alg trong header, mà header do người gửi tự viết. Token alg: none không cần chữ ký vẫn được chấp nhận. Luôn truyền allowlist thuật toán cố định khi verify.
  • Algorithm confusion: server dùng RS256, kẻ tấn công gửi token HS256 ký bằng public key (ai cũng có) làm HMAC secret. Library ngây thơ đem public key ra verify HMAC → khớp. Cũng chữa bằng allowlist.
  • Không kiểm tra aud, iss, exp: chữ ký đúng chỉ chứng minh token do issuer cấp, không chứng minh nó dành cho bạn hay còn hạn.
  • kid hay jku trỏ tới URL hoặc file do kẻ tấn công kiểm soát: chỉ lấy key từ JWKS đã cấu hình sẵn, không theo URL trong token.
  • Access token sống nhiều ngày: không thu hồi được. Access token nên sống vài phút; dùng refresh token (được lưu và thu hồi được) để lấy token mới.

OAuth 2.0

OAuth 2.0 (RFC 6749) giải bài toán uỷ quyền: cho một client (app, service) lấy access token để gọi API, mà không đưa password của user cho client. Có 4 vai: resource owner (user), client, authorization server (cấp token), resource server (API). Cách lấy token gọi là grant:

GrantKhi nàoTrạng thái
Authorization code + PKCECó user ngồi trước browser hoặc appChuẩn cho mọi loại client
Client credentialsService-to-service, không có userChuẩn; 5G NRF dùng grant này
Refresh tokenLấy access token mới khi token cũ sắp hết hạnChuẩn; nên xoay vòng refresh token mỗi lần dùng
Device codeThiết bị không có browser: CLI, TVChuẩn (RFC 8628)
Implicit, PasswordToken trả thẳng qua URL / client cầm password của userĐã bị loại trong OAuth 2.1 và best practice hiện nay

Hai chi tiết đáng nhớ. Code đi qua browser (có thể lộ qua log, history) nhưng vô dụng nếu thiếu code_verifier, thứ chỉ client giữ: đó là PKCE. state buộc callback với đúng phiên login mà client đã khởi tạo, chống kẻ tấn công nhét code của họ vào phiên của nạn nhân.

OAuth không phải là authentication

Access token nói "client này được gọi API X", không nói chắc "người đang dùng là Alice", và nó được cấp cho resource server chứ không cho client. Dùng access token để login vào client là lỗi kinh điển. Login cần OpenID Connect.

OpenID Connect (OIDC)

OIDC là lớp authentication xây trên OAuth 2.0: thêm scope openid, và authorization server (lúc này gọi là OpenID Provider, IdP) trả thêm ID token, một JWT nói về việc user đã login. Discovery document /.well-known/openid-configuration (Q1) cho client biết mọi endpoint và JWKS để tự cấu hình.

Trong 5G SBA, NRF đóng vai authorization server. NF consumer (ví dụ AMF) authenticate với NRF bằng mTLS (module 11), dùng client credentials grant để xin access token với scope là tên NF service cần gọi (ví dụ nudm-uecm). Directory và LDAP

Trong doanh nghiệp và nhà mạng, user và group thường nằm trong một directory (OpenLDAP, 389 DS, Active Directory) truy cập bằng LDAP. Dữ liệu là một cây (DIT), mỗi entry có DN (Distinguished Name) duy nhất:

Cách một service login user qua LDAP (search-then-bind): (1) bind bằng service account chỉ có quyền đọc; (2) search DN của user theo username; (3) bind lại bằng DN của user và password vừa nhận, để chính LDAP server kiểm tra password; (4) search group của user để làm authorization. LDAP dùng port 389 (nên có StartTLS) và 636 cho LDAPS. Đừng bao giờ gửi bind password qua LDAP không mã hoá.

Cạm bẫy LDAP
  • Password rỗng: theo chuẩn LDAP, simple bind với DN có thật và password rỗng là "unauthenticated bind" và có thể trả success. OpenLDAP mặc định từ chối, nhưng không phải server nào cũng vậy. Code login phải tự chặn password rỗng trước khi bind.
  • LDAP injection: ghép username thẳng vào filter. Username * hay alice)(uid=* làm filter khớp nhiều entry. Luôn escape (escape_filter_chars trong ldap3).

Authorization: ai được làm gì

Sau khi biết identity, ta cần một mô hình quyết định. Phổ biến nhất là RBAC (Role-Based Access Control): gán permission cho role, gán role cho subject (user, group, service account). Kubernetes RBAC (module 14) là đúng mô hình này với Role/ClusterRole và RoleBinding.

Cạm bẫy authorization phổ biến nhất

Kiểm tra role nhưng quên kiểm tra object: user có quyền orders:read gọi GET /orders/1234 và đọc được đơn hàng của người khác chỉ bằng cách đổi ID. Lỗi này (BOLA, Broken Object Level Authorization) đứng đầu OWASP API Security Top 10. Mọi endpoint nhận ID phải kiểm tra subject có quyền với đúng object đó.

Liên hệ job

Kiến trúc thường gặp: gateway hoặc sidecar kiểm tra token (chữ ký, aud, exp, scope thô), service tự kiểm tra quyền chi tiết theo object. Mọi quyết định allow/deny quan trọng phải được ghi audit log có identity, action, resource, kết quả. Khi có sự cố, câu hỏi đầu tiên luôn là "ai đã làm gì, bằng credential nào".

Gợi ý

sudo apt install -y python3-argon2. PasswordHasher(time_cost, memory_cost, parallelism) với memory_cost tính bằng KiB. Lab 12.4 · Login qua LDAP và phân quyền RBAC

Thử tháchOpenLDAP · Python · ldap360 phút

Cài OpenLDAP (slapd) trong WSL với base dc=netlab,dc=local, tạo ou=people (alice, bob) và ou=groups (netops chứa alice, auditors chứa bob). Viết ldap_login.py user password action theo kiểu search-then-bind, lấy group, map group → role → permission như sơ đồ RBAC ở trên, rồi in ALLOW/DENY. Thử thêm username có ký tự đặc biệt và password rỗng.

Xong khi: alice được config:write, bob chỉ được config:read, sai password bị từ chối với cùng một thông báo như user không tồn tại, username alice)(uid=* và password rỗng đều bị chặn.

Gợi ý

Cài slapd không hỏi gì: điền trước câu trả lời bằng debconf-set-selections, rồi DEBIAN_FRONTEND=noninteractive apt install. Nếu slapd đã cài từ trước thì chạy sudo dpkg-reconfigure -f noninteractive slapd sau khi điền debconf. Thêm entry bằng ldapadd, đặt password bằng ldappasswd (server tự hash). Python: sudo apt install -y python3-ldap3; ldap3.utils.conv.escape_filter_chars.

Lời giải

Thử bỏ escape_filter_chars và chạy lại với username *: filter thành (uid=*), khớp cả alice và bob, và code chỉ không bị lừa nhờ dòng kiểm tra "đúng một entry". Ở đây vẫn dùng LDAP không mã hoá vì là lab trên localhost. Module 16 sẽ ghép LDAP, token server và mTLS thành một auth service hoàn chỉnh.
