Sau bài này bạn

  • Đọc được một HTTP request/response thô: request line, header, body, status code.
  • Tính được số RTT để tải một trang với non-persistent và persistent connection.
  • Phân biệt 401 và 403, biết method nào idempotent (retry an toàn) và vì sao response chứa token phải có Cache-Control: no-store.
  • Hiểu HTTP/2 khác HTTP/1.1 ở đâu: stream, frame, multiplexing, ALPN. Đây là protocol mà các network function của 5G core dùng để gọi nhau.
  • Tự viết được một REST service nhỏ có Bearer token authentication.

Làm trước (15 phút)

Application nói chuyện với nhau thế nào

Network application là các process chạy trên các host khác nhau trao đổi message. Có hai kiến trúc chính §2.1.1:

  • Client-server: server luôn chạy, có address cố định; client chủ động gửi request. Web, email, mọi microservice trong cluster của bạn.
  • P2P: các peer vừa là client vừa là server (BitTorrent). Ít gặp trong core network; đọc lướt §2.5 là đủ.

Application cần gì từ transport layer

Sách chia nhu cầu thành 4 loại §2.1.3: reliable data transfer (không mất byte nào), throughput, timing, security. TCP và UDP đáp ứng khác nhau:

HTTP và connection

HTTP là protocol request/response: client gửi request, server trả response §2.2.1. HTTP là stateless: server không nhớ gì về request trước. Muốn có "state" (đã login, giỏ hàng) thì client phải gửi kèm ở mỗi request: cookie hoặc token.

HTTP chạy trên TCP. Câu hỏi quan trọng về performance: mỗi object (HTML, ảnh, JSON) có cần một TCP connection riêng không? §2.2.2

Non-persistent: mỗi object ≈ 2·RTT + transmission time 1 RTT cho TCP handshake, 1 RTT cho request/response. Trang có 1 HTML + 10 ảnh, tải tuần tự: 11 × 2 = 22 RTT. Persistent (không pipelining): 1 + 11 = 12 RTT. Với HTTPS còn thêm 1 RTT cho TLS 1.3 handshake mỗi connection.
Liên hệ job

Trong cluster, middleware gọi nhau hàng nghìn lần mỗi giây. Mở connection mới cho mỗi request nghĩa là trả thêm TCP handshake + TLS handshake mỗi lần, cộng chi phí CPU cho cryptography. Vì vậy mọi HTTP client library tốt đều có connection pool (giữ connection để dùng lại). Bug "quên dùng lại connection" là nguyên nhân phổ biến khiến latency tăng và service xác thực bị quá tải.

Cạm bẫy
  • Header name không phân biệt hoa thường: content-type và Content-Type là một. HTTP/2 bắt buộc viết thường.
  • Thiếu dòng trống, hoặc dùng \n thay cho \r\n khi tự viết HTTP bằng tay, là lỗi kinh điển: server chờ mãi vì tưởng header chưa hết.
  • Host bắt buộc trong HTTP/1.1, vì một IP có thể phục vụ nhiều domain (virtual host). Ingress của Kubernetes cũng dựa vào Host để route request tới đúng service.

Ghi nhớ: 401 và 403

401 = "tôi không biết bạn là ai" (authentication thất bại). 403 = "tôi biết bạn là ai, nhưng bạn không được làm việc này" (authorization thất bại). Tên "Unauthorized" của 401 là nhầm lẫn lịch sử trong chuẩn; hãy nhớ theo nghĩa, đừng theo tên. Service của bạn trả sai hai code này thì client sẽ xử lý sai: gặp 401 client sẽ đi lấy token mới, gặp 403 thì lấy token mới cũng vô ích.

HTTP/2

HTTP/1.1 có vấn đề HOL blocking (head-of-line blocking): trên một connection, response phải trả lần lượt; một object lớn đứng trước sẽ chặn các object nhỏ phía sau. Browser né bằng cách mở 6 connection song song, tốn tài nguyên. HTTP/2 (RFC 9113) giải quyết bằng cách cắt message thành frame và đan xen chúng §2.2.6:

Khái niệm HTTP/2Ý nghĩa
Binary framingKhông còn là text. Mọi thứ là frame có header 9 byte (hình dưới)
StreamMột cặp request/response, có stream ID. Client mở stream ID lẻ: 1, 3, 5…
MultiplexingNhiều stream chạy song song trên một TCP connection
HPACKNén header; header lặp lại (như authorization) chỉ gửi index
Pseudo-headerRequest line thành :method, :path, :scheme, :authority; status line thành :status
Flow controlFrame WINDOW_UPDATE giới hạn bên gửi theo từng stream

Type hay gặp: DATA (0), HEADERS (1), RST_STREAM (3), SETTINGS (4), PING (6), GOAWAY (7), WINDOW_UPDATE (8).

  • ALPN: client và server thoả thuận dùng h2 hay http/1.1 ngay trong TLS handshake, không tốn thêm RTT. Đó là câu trả lời cho Q3.
  • h2c: HTTP/2 không có TLS. Đôi khi dùng bên trong cluster khi service mesh đã lo phần encryption.
  • HTTP/3: HTTP chạy trên QUIC (UDP), tránh nốt HOL blocking ở tầng TCP khi có packet loss. Học ở module 05.

Lab 2.1 · Nói HTTP bằng tay

Cơ bảnBash · nc · openssl20 phút

Không dùng curl. Dùng nc (HTTP) và openssl s_client (HTTPS) để:

  4. Gửi HEAD và so sánh với GET.
  5. Làm lại bước 1 qua HTTPS (port 443).

Xong khi: giải thích được vì sao request phải kết thúc bằng một dòng trống, và vì sao request cuối nên có Connection: close.

Gợi ý

Dùng printf để có \r\n đúng chuẩn (echo không đáng tin). Đếm số response bằng grep -c '^HTTP/1.1'. Với HTTPS: openssl s_client -connect host:443 -servername host -quiet đọc request từ stdin như nc.

Lời giải

Không có Connection: close, server giữ connection mở chờ request tiếp theo, nên nc treo đến khi server timeout. Dòng trống là cách duy nhất để server biết phần header đã hết.

Lab 2.2 · Mổ xẻ thời gian của một HTTPS request

Cơ bảnBash · curl -w25 phút

Viết httptime.sh URL in thời gian của từng phase: DNS lookup, TCP connect, TLS handshake, chờ server (TTFB), download. Chạy cho: một trang trong nước, một trang ở Mỹ, và cùng một trang qua http:// và https://.

Xong khi: chỉ ra được phase nào ≈ 1 RTT, phase TLS tốn mấy RTT, và trang nào chậm vì propagation delay chứ không vì server.

Gợi ý

Các biến của curl -w: time_namelookup, time_connect, time_appconnect (TLS xong), time_starttransfer (byte đầu tiên), time_total. Chúng cộng dồn từ lúc bắt đầu, đơn vị giây. Lấy hiệu để ra từng phase.

Lời giải

Đọc kết quả: với trang ở Mỹ, TCP connect, TLS và TTFB đều ở cỡ 200 ms: mỗi phase là một RTT, tức là propagation delay. Server nhanh đến đâu cũng không cứu được. Đây là lý do persistent connection và TLS 1.3 (giảm số RTT) quan trọng hơn tăng bandwidth.

Lab 2.3 · REST service có Bearer token authentication

VừaPython (stdlib)45 phút

Đây là phiên bản tí hon của thứ bạn sẽ làm ở công ty. Viết một HTTP server chỉ bằng thư viện chuẩn của Python, port 8080:

  • GET /health → 200 {"status": "ok"}, không cần token.
  • GET /api/v1/secrets cần header Authorization: Bearer <token>. Bảng token để trong code: tok-reader có scope secrets:read, tok-guest không có scope nào.
  • Thiếu token hoặc token lạ → 401 kèm header WWW-Authenticate: Bearer realm="netlab". Token đúng nhưng thiếu scope → 403.
  • POST /api/v1/secrets → 405 kèm header Allow: GET, HEAD. Path lạ → 404.
  • Mọi response là JSON, có Content-Length và Cache-Control: no-store. Server log mỗi request một dòng: method, path, status, identity (sub).

Xong khi: 5 lệnh curl trong phần lời giải cho đúng status code. Rồi chạy sudo tcpdump -i lo -A port 8080 trong lúc gọi API: bạn thấy gì trong packet? Ghi lại; module 11 (TLS) sẽ giải quyết.

Gợi ý

Kế thừa http.server.BaseHTTPRequestHandler, viết do_GET, do_POST. Header của request nằm ở self.headers. Đặt protocol_version = "HTTP/1.1" để hỗ trợ persistent connection; khi đó bắt buộc phải gửi Content-Length. Dùng ThreadingHTTPServer để phục vụ nhiều client cùng lúc.

Lời giải

Với tcpdump: bạn sẽ đọc được nguyên văn Authorization: Bearer tok-reader trong packet. Bất kỳ ai capture được traffic trong cluster đều lấy được token và giả danh svc-a. Đó là lý do bắt buộc phải có TLS.

Mở rộng: thêm scope secrets:write cho POST; viết thêm một script Bash gọi 5 lệnh curl trên và tự báo PASS/FAIL theo status code (bước đầu của automated test).

Lab 2.4 · Soi HTTP/2 frame bên trong TLS

Thử tháchnghttp · tcpdump · tshark40 phút
