Bài 0 · Từ mã nguồn tới file chạy được

Bốn bước của một lần build

Lệnh gcc main.c -o app trông như một bước, thực ra là bốn chương trình chạy nối tiếp:

 main.c ──[1. tiền xử lý: cpp]──▶ main.i ──[2. biên dịch: cc1]──▶ main.s
        ──[3. hợp dịch: as]──▶ main.o ──[4. liên kết: ld]──▶ app (ELF)
                                         ▲
                       các .o khác, thư viện .a/.so, startup, linker script
Bước Làm gì Xem kết quả bằng
1. Tiền xử lý Thay #include, mở macro, xử lý #if gcc -E main.c
2. Biên dịch C/C++ → assembly của kiến trúc đích; tối ưu diễn ra ở đây gcc -S main.c
3. Hợp dịch Assembly → mã máy trong object file (.o), còn các chỗ trống chờ địa chỉ gcc -c main.c
4. Liên kết Ghép các .o và thư viện, gán địa chỉ cuối cùng, điền các chỗ trống gcc *.o -o app

gcc -v in ra từng lệnh con được gọi; -save-temps giữ lại các file trung gian. Khi một macro "không chạy như mong đợi", xem file .i là cách nhanh nhất.

Mỗi file .c được biên dịch độc lập (một translation unit). Compiler không thấy file khác: nó chỉ biết read_raw() tồn tại nhờ khai báo trong header, và để lại một "chỗ trống" để linker điền địa chỉ sau. Đây là gốc rễ của hầu hết lỗi liên kết (Bài 2).

Toolchain và cross-compile

Firmware được build trên PC x86 nhưng chạy trên ARM: đó là cross-compile. Toolchain đặt tên theo bộ ba (target triplet) kiến-trúc-nhà-cung-cấp-hệ-điều-hành-abi:

Toolchain Đích
arm-none-eabi-gcc ARM bare-metal (Cortex-M/R), không OS, thư viện C là newlib
aarch64-linux-gnu-gcc ARM 64-bit chạy Linux, glibc
arm-linux-gnueabihf-gcc ARM 32-bit Linux, ABI dùng thanh ghi FPU để truyền số thực (hard-float)
riscv32-unknown-elf-gcc RISC-V 32-bit bare-metal

Với đích Linux, toolchain cần sysroot: bản sao header và thư viện của hệ thống đích (từ Yocto/Buildroot SDK, M11), để chương trình được biên dịch với đúng phiên bản glibc và thư viện mà thiết bị có.

Các cờ quan trọng cho Cortex-M: -mcpu=cortex-m4 -mthumb (bộ lệnh), -mfpu=fpv4-sp-d16 -mfloat-abi=hard (dùng FPU), và mọi file trong project phải cùng -mfloat-abi, nếu không linker báo lỗi không tương thích (hoặc tệ hơn, chạy sai khi trộn thư viện build sẵn).

Ý chínhÝ chính của Bài 0
  • Tiền xử lý → biên dịch → hợp dịch → liên kết; xem từng bước bằng -E, -S, -c, -v, -save-temps.
  • Mỗi file biên dịch độc lập; tham chiếu sang file khác là chỗ trống chờ linker.
  • Triplet chỉ đích; bare-metal dùng arm-none-eabi + newlib, Linux cần sysroot; thống nhất -mfloat-abi.

Bài 1 · Object file và định dạng ELF

Bên trong một file .o

Lấy file sau, biên dịch cho Cortex-M4 với -O2 -c:

#include <stdint.h>
int32_t read_raw(void);                 /* định nghĩa ở file khác */
static int32_t offset = 12;             /* static: chỉ thấy trong file này */
int32_t last_value;                     /* toàn cục, không khởi tạo */
const int32_t scale = 3;                /* hằng */

int32_t sensor_read(void) {
    last_value = read_raw() * scale + offset;
    return last_value;
}

Object file chia nội dung thành các section:

Section Chứa Nằm ở đâu khi chạy (MCU)
.text Mã máy Flash
.rodata Hằng (const, chuỗi literal) Flash
.data Biến toàn cục/static có giá trị khởi tạo khác 0 RAM (giá trị ban đầu lưu trong Flash, chép sang lúc khởi động)
.bss Biến toàn cục/static khởi tạo bằng 0 hoặc không khởi tạo RAM (xóa về 0 lúc khởi động; không chiếm chỗ trong file)

Xem bằng objdump -h sensor.o (kết quả thật, rút gọn):

Idx Name          Size      VMA       LMA       File off  Algn
  0 .text         00000018  00000000  00000000  00000034  2**2   CODE
  1 .data         00000000  00000000  00000000  0000004c  2**0
  2 .bss          00000004  00000000  00000000  0000004c  2**2
  3 .rodata       00000004  00000000  00000000  0000004c  2**2

.data rỗng dù có offset = 12? Compiler thấy offset là static và không bao giờ bị sửa, nên thay thẳng bằng hằng số 12 và bỏ biến đi. Tương tự scale: phép nhân với 3 được biến thành r0 + (r0 << 1). Biến scale vẫn được giữ trong .rodata vì nó không static (file khác có thể dùng).

Bảng ký hiệu

nm sensor.o:

00000000 B last_value      B: .bss, toàn cục
         U read_raw        U: undefined, chờ linker tìm ở nơi khác
00000000 R scale           R: .rodata
00000000 T sensor_read     T: .text, toàn cục

Chữ in hoa là ký hiệu toàn cục (file khác thấy được), chữ thường là cục bộ (static). W là ký hiệu yếu (weak, Bài 4). Mọi địa chỉ đều là 0: trong object file, địa chỉ chỉ là vị trí tương đối trong section; địa chỉ thật do linker quyết định.

Relocation: chỗ trống chờ linker

objdump -dr sensor.o:

00000000 <sensor_read>:
   0:  b508        push   {r3, lr}
   2:  f7ff fffe   bl     0 <read_raw>
               2: R_ARM_THM_CALL   read_raw        ← điền địa chỉ read_raw vào lệnh bl
   6:  4b03        ldr    r3, [pc, #12]
   8:  eb00 0040   add.w  r0, r0, r0, lsl #1       ← nhân 3
   c:  300c        adds   r0, #12                  ← cộng offset (đã thành hằng)
   e:  6018        str    r0, [r3, #0]             ← ghi last_value
  10:  bd08        pop    {r3, pc}
  14:  00000000    .word  0x00000000
              14: R_ARM_ABS32    .bss              ← điền địa chỉ của last_value

Mỗi dòng R_ARM_... là một relocation: "tại offset này, khi biết địa chỉ của ký hiệu kia, hãy điền theo cách này". Linker xử lý mọi relocation sau khi đặt các section vào địa chỉ cuối cùng.

ELF

Object file, file thực thi và thư viện chia sẻ trên Linux và trong hầu hết toolchain nhúng đều dùng định dạng ELF. Hai góc nhìn:

  • Section (dành cho linker, debugger): .text, .data, .symtab, .debug_*…; xem bằng readelf -S.
  • Segment / program header (dành cho bộ nạp): vùng nào nạp vào địa chỉ nào với quyền gì; xem bằng readelf -l. Trên MCU, công cụ nạp (OpenOCD, J-Link) dùng các segment có cờ LOAD để biết ghi gì vào Flash.

Firmware nạp lên chip thường là .bin hoặc .hex tạo bằng objcopy -O binary app.elf app.bin: chỉ còn byte thô, mất hết ký hiệu và thông tin debug. Luôn giữ lại file .elf của mỗi bản phát hành để giải mã địa chỉ khi có crash dump (M09 Bài 5).

Liên kết của ký hiệu và ODR

  • static ở phạm vi file (hoặc namespace không tên trong C++): ký hiệu cục bộ, hai file có thể cùng tên mà không xung đột. Mặc định nên dùng cho mọi thứ không cần xuất ra.
  • extern int x; trong header là khai báo; int x = 0; trong đúng một file .c là định nghĩa.
  • One Definition Rule: mỗi ký hiệu toàn cục chỉ được định nghĩa một lần trong toàn chương trình. Định nghĩa biến trong header (int count; không có extern) được include ở nhiều file sẽ vi phạm. Từ GCC 10, mặc định -fno-common biến lỗi này thành lỗi "multiple definition" (trước đó linker âm thầm gộp chúng lại).
  • C++17 có biến inline: inline int count = 0; trong header được phép, linker giữ một bản.
Tự kiểm traHai file cùng định nghĩa `static int buffer[256];`. Có lỗi liên kết không? Chương trình dùng bao nhiêu bộ nhớ cho chúng?

Không lỗi: mỗi buffer là ký hiệu cục bộ của file mình, hai biến hoàn toàn riêng biệt, tổng 2 × 256 × sizeof(int) byte trong .bss. Nếu ý định là dùng chung một buffer thì đây là bug thầm lặng: mỗi file thao tác trên bản riêng của nó.

Ý chínhÝ chính của Bài 1
  • .text, .rodata → Flash; .data → RAM (giá trị đầu ở Flash); .bss → RAM, xóa về 0.
  • nm: T/D/B/R/U/W, hoa toàn cục, thường cục bộ; địa chỉ trong .o chỉ tương đối.
  • Relocation là chỗ trống linker điền; objdump -dr để xem.
  • ELF: section cho linker, segment cho bộ nạp; giữ .elf của mỗi bản phát hành.
  • static mặc định cho thứ không xuất; một định nghĩa duy nhất; -fno-common.

Bài 2 · Linker và các lỗi liên kết

Linker làm gì

  1. Thu thập các object file và chọn object cần thiết từ thư viện tĩnh.
  2. Giải quyết ký hiệu: mỗi ký hiệu U phải khớp đúng một định nghĩa.
  3. Bố trí: ghép các section cùng loại từ mọi file (mọi .text thành một .text) và gán địa chỉ, theo linker script (Bài 3).
  4. Relocation: điền địa chỉ vào các chỗ trống.
  5. Ghi ra file ELF (và file map nếu được yêu cầu, Bài 6).

Thư viện tĩnh và thứ tự

Thư viện tĩnh .a chỉ là một kho chứa nhiều .o. Linker duyệt các tham số từ trái sang phải, và với mỗi thư viện chỉ lấy những .o giải quyết được ký hiệu đang còn thiếu tại thời điểm đó:

gcc main.o -lsensor -lhal       # main cần sensor_read, sensor cần hal_i2c_read: OK
gcc main.o -lhal -lsensor       # khi duyệt libhal, chưa ai cần hal_i2c_read → bỏ qua
                                #   → "undefined reference to hal_i2c_read"

Quy tắc: thư viện phụ thuộc đứng trước thư viện được phụ thuộc. Hai thư viện phụ thuộc lẫn nhau thì bọc trong -Wl,--start-group -lhal -lsensor -Wl,--end-group (linker duyệt lặp tới khi không còn gì mới). CMake tự lo thứ tự nếu khai báo target_link_libraries đúng.

Bỏ code không dùng

Mặc định, nếu dùng một hàm trong một file .o, cả file được giữ lại. Để linker bỏ từng hàm không dùng:

gcc -ffunction-sections -fdata-sections ...   # mỗi hàm, mỗi biến một section riêng
ld  --gc-sections                             # bỏ section không ai tham chiếu tới

Kết hợp LTO (-flto): compiler giữ biểu diễn trung gian trong .o, tối ưu lại toàn chương trình lúc liên kết (inline xuyên file, bỏ code chết). Thường giảm kích thước firmware 10–20%; đổi lại build chậm hơn và debug khó hơn một chút.

Vì --gc-sections xóa thứ không ai tham chiếu, những thứ chỉ được phần cứng dùng (bảng vector) hoặc chỉ được tìm qua tên section (bảng lệnh shell đăng ký bằng section riêng) phải được đánh dấu KEEP() trong linker script hoặc __attribute__((used)).

Giải mã lỗi liên kết

Thông báo Nguyên nhân hay gặp
undefined reference to 'foo' Quên file .c/thư viện; sai thứ tự thư viện; khai báo và định nghĩa khác chữ ký; gọi hàm C từ C++ thiếu extern "C" (tên bị mangle thành _Z3foov)
multiple definition of 'x' Định nghĩa biến/hàm không inline trong header; cùng hàm ở hai file
undefined reference to '__aeabi_...', memcpy, memset Build với -nostdlib nhưng compiler sinh lời gọi tới thư viện hỗ trợ (chia số nguyên, chép bộ nhớ); thêm -lgcc hoặc tự cung cấp (Bài 4)
region 'FLASH' overflowed by N bytes Firmware lớn hơn Flash: xem Bài 6
relocation truncated to fit Lệnh nhảy/tham chiếu xa hơn tầm với của lệnh (gọi hàm trong RAM từ Flash trên một số kiến trúc, mô hình bộ nhớ sai)
uses VFP register arguments, x.o does not Trộn -mfloat-abi=hard và soft

Với lỗi undefined reference trong C++, đọc tên đã bị demangle (c++filt _Z3foov → foo()) để thấy chữ ký linker đang tìm, rồi so với định nghĩa.

Tự kiểm traDự án C++ gọi hàm `hal_init()` viết trong `hal.c`, link báo `undefined reference to 'hal_init()'` dù `hal.o` có trong lệnh link. Vì sao, và sửa thế nào?

Thông báo có (), tức linker đang tìm phiên bản C++ đã mangle (_Z8hal_initv), còn hal.o (biên dịch bằng C) chỉ có ký hiệu hal_init. Header được include từ file C++ mà thiếu extern "C". Sửa trong hal.h: bọc các khai báo bằng #ifdef __cplusplus extern "C" { #endif ... #ifdef __cplusplus } #endif.

Ý chínhÝ chính của Bài 2
  • Linker: thu thập, giải quyết ký hiệu, bố trí, relocation.
  • Thư viện tĩnh duyệt trái sang phải: phụ thuộc đứng trước; vòng thì --start-group.
  • -ffunction-sections -fdata-sections + --gc-sections (+ LTO); KEEP cho thứ chỉ phần cứng dùng.
  • Đọc lỗi: undefined (thiếu, thứ tự, extern "C"), multiple definition, overflow, float ABI.

Bài 3 · Linker script cho MCU

Vì sao firmware cần linker script

Trên Linux, linker dùng script mặc định và hệ điều hành lo việc nạp. Trên MCU không có ai làm việc đó: linker script phải nói chính xác Flash ở đâu, RAM ở đâu, mỗi section đặt vào đâu, và xuất ra các ký hiệu (địa chỉ) mà startup code cần để chuẩn bị bộ nhớ. Các file dưới đây được dùng cho Cortex-M3 (LM3S6965, máy giả lập lm3s6965evb của QEMU) và đã chạy thật.

/* Bố cục bộ nhớ của MCU (ví dụ: LM3S6965, Cortex-M3: 256 KiB Flash, 64 KiB SRAM) */
MEMORY
{
  FLASH (rx)  : ORIGIN = 0x00000000, LENGTH = 256K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 64K
}

_stack_size = 4K;
_estack     = ORIGIN(RAM) + LENGTH(RAM);       /* stack đi xuống từ đỉnh RAM */

ENTRY(Reset_Handler)

SECTIONS
{
  .isr_vector : {
    KEEP(*(.isr_vector))                        /* KEEP: không để --gc-sections xóa */
  } > FLASH

  .text : {
    *(.text*)
    *(.rodata*)
    . = ALIGN(4);
  } > FLASH

  .init_array : {
    __init_array_start = .;
    KEEP(*(SORT(.init_array.*)))
    KEEP(*(.init_array))
    __init_array_end = .;
  } > FLASH

  _sidata = LOADADDR(.data);                     /* nơi giá trị khởi tạo nằm trong Flash */

  .data : {
    . = ALIGN(4);
    _sdata = .;
    *(.data*)
    *(.ramfunc*)                                 /* hàm muốn chạy từ RAM */
    . = ALIGN(4);
    _edata = .;
  } > RAM AT> FLASH                              /* VMA ở RAM, LMA ở Flash */

  .bss (NOLOAD) : {
    . = ALIGN(4);
    _sbss = .;
    *(.bss*)
    *(COMMON)
    . = ALIGN(4);
    _ebss = .;
  } > RAM

  .noinit (NOLOAD) : {
    *(.noinit*)                                  /* giữ nguyên qua reset mềm */
  } > RAM

  _end = .;                                      /* đầu heap */
  ASSERT(_end + _stack_size <= _estack, "RAM tràn: không còn đủ chỗ cho stack")

  /DISCARD/ : { *(.ARM.exidx*) *(.comment) }
}

Đọc từng phần

MEMORY khai báo các vùng nhớ vật lý với quyền (r, w, x). Chip thật thường có thêm vùng: CCM/DTCM (RAM nhanh không DMA được), backup SRAM, Flash nhiều bank. Lấy số liệu từ memory map trong datasheet (reference manual), không đoán.

Ký hiệu tự định nghĩa như _estack = ORIGIN(RAM) + LENGTH(RAM) không chiếm bộ nhớ; chúng chỉ là địa chỉ mà code C tham chiếu bằng extern uint32_t _estack; rồi lấy &_estack.

VMA và LMA. Mỗi section có hai địa chỉ: VMA (virtual/run address, nơi section nằm khi chương trình chạy) và LMA (load address, nơi nó được lưu trong ảnh nạp). Với .text hai địa chỉ trùng nhau (chạy thẳng từ Flash). Với .data, > RAM AT> FLASH nghĩa là: code tham chiếu biến ở địa chỉ RAM, nhưng giá trị khởi tạo được ghi vào Flash; startup code phải chép từ LMA (_sidata) sang VMA (_sdata…_edata). Đây là lý do biến .data tốn cả Flash lẫn RAM.

.bss (NOLOAD) chỉ chiếm RAM, không có gì trong Flash; startup code xóa nó về 0. Vì vậy uint8_t buf[4096]; không làm firmware to ra, còn uint8_t buf[4096] = {1}; thì tốn thêm 4 KB Flash.

KEEP(*(.isr_vector)): bảng vector không được code nào gọi tới, --gc-sections sẽ xóa nó nếu không có KEEP. Chip khởi động với bảng vector trống thì nhảy vào địa chỉ rác ngay lệnh đầu tiên.

.init_array: danh sách con trỏ hàm cần chạy trước main (constructor của đối tượng toàn cục C++, hàm __attribute__((constructor))). Script xuất __init_array_start/end để startup code duyệt.

.ramfunc: hàm muốn chạy từ RAM (nhanh hơn trên chip có Flash chậm, hoặc bắt buộc khi đang xóa/ghi chính Flash đó) được đặt trong .data: được chép sang RAM lúc khởi động cùng các biến.

.noinit: biến không bị startup xóa, giữ giá trị qua reset mềm; dùng cho bộ đếm reset, lý do crash (M09 Bài 5).

ASSERT: biến lỗi "chạy một lúc rồi stack đè lên dữ liệu" thành lỗi lúc build. Thêm ASSERT cho mọi giới hạn bạn biết (stack tối thiểu, heap tối thiểu, firmware không vượt vùng dành cho bootloader).

/DISCARD/ bỏ section không cần (bảng unwind của exception khi không dùng exception).

Trên chip có bootloader (M09 Bài 4), linker script của ứng dụng đặt FLASH bắt đầu sau vùng bootloader (ví dụ ORIGIN = 0x08008000), và ứng dụng phải trỏ VTOR tới bảng vector của mình.

Ý chínhÝ chính của Bài 3
  • MEMORY theo datasheet; ký hiệu linker là địa chỉ, dùng bằng &sym.
  • .data: VMA ở RAM, LMA ở Flash (AT>), startup chép; .bss NOLOAD, startup xóa.
  • KEEP bảng vector; .init_array cho constructor; .ramfunc, .noinit theo nhu cầu.
  • ASSERT để tràn bộ nhớ thành lỗi lúc build.

Bài 4 · Startup code Cortex-M

Cortex-M khởi động thế nào

Khi reset, lõi Cortex-M đọc hai word đầu tiên ở địa chỉ bảng vector (mặc định 0x00000000, chip STM32 ánh xạ Flash 0x08000000 về đó):

  1. Word 0 → nạp vào SP (stack pointer ban đầu).
  2. Word 1 → nhảy tới địa chỉ này (Reset_Handler), chế độ Thumb (bit 0 của địa chỉ là 1).

Không có gì khác được chuẩn bị: .data chưa có giá trị, .bss chứa rác, clock đang ở mặc định, FPU tắt. Startup code lo tất cả trước khi gọi main. Vì Cortex-M tự nạp SP từ bảng vector, startup có thể viết hoàn toàn bằng C (lõi Cortex-A thì cần assembly để đặt stack trước).

#include <stdint.h>

/* Ký hiệu do linker script định nghĩa: chỉ có địa chỉ, không có nội dung */
extern uint32_t _sidata, _sdata, _edata, _sbss, _ebss, _estack;
extern void (*__init_array_start[])(void);
extern void (*__init_array_end[])(void);

int main(void);
void Reset_Handler(void);
void Default_Handler(void);

/* Handler mặc định yếu: ISR nào không được định nghĩa ở nơi khác sẽ trỏ về đây */
void NMI_Handler(void)        __attribute__((weak, alias("Default_Handler")));
void HardFault_Handler(void)  __attribute__((weak, alias("Default_Handler")));
void SysTick_Handler(void)    __attribute__((weak, alias("Default_Handler")));
void UART0_IRQHandler(void)   __attribute__((weak, alias("Default_Handler")));

/* Bảng vector: phần tử 0 là SP ban đầu, phần tử 1 là địa chỉ Reset_Handler */
__attribute__((section(".isr_vector"), used))
const uintptr_t vector_table[] = {
    (uintptr_t)&_estack,
    (uintptr_t)Reset_Handler,
    (uintptr_t)NMI_Handler,
    (uintptr_t)HardFault_Handler,
    0, 0, 0, 0, 0, 0, 0,          /* MemManage, BusFault, UsageFault, reserved... (rút gọn) */
    0, 0, 0, 0,                   /* SVC, DebugMon, reserved, PendSV */
    (uintptr_t)SysTick_Handler,
    (uintptr_t)UART0_IRQHandler,  /* IRQ0 trở đi: theo datasheet của chip */
};

void Reset_Handler(void) {
    /* 1. Chép giá trị khởi tạo của .data từ Flash sang RAM */
    uint32_t *src = &_sidata;
    for (uint32_t *dst = &_sdata; dst < &_edata; ) *dst++ = *src++;
    /* 2. Xóa .bss về 0 */
    for (uint32_t *dst = &_sbss; dst < &_ebss; ) *dst++ = 0;
    /* 3. (SystemInit: clock, FPU... tùy chip) */
    /* 4. Chạy constructor của đối tượng toàn cục (C++) và hàm __attribute__((constructor)) */
    for (void (**f)(void) = __init_array_start; f < __init_array_end; ++f) (*f)();
    /* 5. Vào main; main không nên trả về trên MCU */
    main();
    for (;;) {}
}

void Default_Handler(void) { for (;;) {} }

Những điểm đáng chú ý

Handler yếu với alias. __attribute__((weak, alias("Default_Handler"))) tạo ký hiệu yếu trỏ về Default_Handler. Khi bạn viết void UART0_IRQHandler(void) {...} ở file khác, định nghĩa mạnh đó thắng và bảng vector trỏ tới nó. Hệ quả nguy hiểm: gõ sai tên ISR (USART2_IRQhandler) không gây lỗi biên dịch hay liên kết; ngắt rơi vào Default_Handler và chương trình treo trong vòng lặp vô hạn. Khi debug thấy CPU kẹt ở Default_Handler, đọc thanh ghi IPSR (số exception đang xử lý) để biết ngắt nào.

Compiler biến vòng lặp chép thành memcpy. Lần build đầu tiên của đoạn code trên với -O2 -nostdlib báo lỗi thật:

startup.c:34: undefined reference to `memcpy'
startup.c:36: undefined reference to `memset'

GCC nhận ra vòng lặp chép/xóa và thay bằng lời gọi memcpy/memset (tối ưu loop distribution). Trong startup code điều này còn nguy hiểm hơn lỗi liên kết: memcpy của thư viện có thể dùng biến toàn cục chưa được khởi tạo. Cách xử lý: biên dịch startup với -fno-tree-loop-distribute-patterns (như ở đây), hoặc viết vòng lặp bằng assembly, hoặc đảm bảo có memcpy/memset không phụ thuộc trạng thái.

Thứ tự: chép .data và xóa .bss trước mọi thứ khác, vì constructor C++ và cả SystemInit có thể dùng biến toàn cục. Một số SDK gọi SystemInit (cấu hình clock) trước khi chép .data để việc chép chạy nhanh hơn; khi đó SystemInit không được dùng biến toàn cục.

FPU: trên Cortex-M4F/M7, dùng lệnh số thực khi FPU còn tắt gây UsageFault. SystemInit phải bật: SCB->CPACR |= (0xF << 20); rồi __DSB(); __ISB();. Compiler có thể sinh lệnh FPU ngay trong code tưởng như không dùng số thực (chép struct bằng thanh ghi FPU), nên bật càng sớm càng tốt.

main trả về: trên MCU không có ai nhận giá trị trả về; vòng for (;;) sau main ngăn CPU chạy vào vùng nhớ rác.

Chạy thử trên QEMU

Chương trình kiểm tra từng bước của startup:

#include <stdint.h>
#define UART0_DR (*(volatile uint32_t *)0x4000C000u)    /* thanh ghi dữ liệu UART0 */

static void puts_uart(const char *s) { while (*s) UART0_DR = (uint32_t)*s++; }
static void put_hex(uint32_t v) { const char *h = "0123456789abcdef"; puts_uart("0x"); for (int i = 28; i >= 0; i -= 4) UART0_DR = h[(v >> i) & 0xF]; }

uint32_t counter = 42;                    /* .data: giá trị 42 nằm trong Flash, được chép sang RAM */
uint32_t zeroed;                          /* .bss: được xóa về 0 lúc khởi động */
const char banner[] = "hello from flash"; /* .rodata: chỉ nằm trong Flash */
__attribute__((section(".noinit"))) uint32_t boot_count;   /* không bị xóa khi reset */
static uint32_t ctor_ran;

__attribute__((constructor)) static void early_init(void) { ctor_ran = 0xC0FFEEu; }

__attribute__((section(".ramfunc"), noinline)) static uint32_t add_in_ram(uint32_t a, uint32_t b) { return a + b; }

static void semihost_exit(void) {                       /* báo QEMU thoát (semihosting) */
    register uint32_t r0 __asm__("r0") = 0x18, r1 __asm__("r1") = 0x20026;
    __asm__ volatile("bkpt 0xAB" : : "r"(r0), "r"(r1) : "memory");
}

int main(void) {
    puts_uart(banner); puts_uart("\n");
    puts_uart("counter="); put_hex(counter); puts_uart(" zeroed="); put_hex(zeroed);
    puts_uart(" ctor="); put_hex(ctor_ran); puts_uart("\n");
    puts_uart("ramfunc@"); put_hex((uint32_t)(uintptr_t)&add_in_ram); puts_uart(" -> "); put_hex(add_in_ram(40, 2)); puts_uart("\n");
    semihost_exit();
    return 0;
}

Mọi thứ khớp: counter có giá trị 42 (.data được chép), zeroed bằng 0 (.bss được xóa), constructor đã chạy trước main, hàm add_in_ram nằm ở địa chỉ RAM (0x20000004, bit 0 bằng 1 là dấu Thumb). Bảng ký hiệu (nm -n fw.elf, rút gọn) cho thấy bố cục cuối cùng:

00000000 R vector_table
00000048 T Default_Handler
00000048 W HardFault_Handler        ← các handler yếu cùng địa chỉ Default_Handler
0000004c T Reset_Handler
000001e8 t __add_in_ram_veneer      ← linker tự chèn "cầu nhảy": Flash tới RAM quá xa cho lệnh bl
00000254 A _sidata                  ← giá trị đầu của .data nằm ở đây trong Flash
20000000 T counter                  ← .data trong RAM
20000004 t add_in_ram

Dòng __add_in_ram_veneer là một chi tiết thú vị: lệnh bl của Thumb-2 chỉ nhảy được khoảng ±16 MB, còn khoảng cách Flash (0x0) tới RAM (0x20000000) là 512 MB, nên linker tự chèn một đoạn mã trung gian nạp địa chỉ đầy đủ rồi nhảy.

Tự kiểm traMột firmware chạy đúng khi debug bằng J-Link (nạp rồi chạy từ debugger) nhưng treo khi cắm nguồn lần đầu. Biến toàn cục `int mode = 2;` luôn đọc ra giá trị lạ. Nghi ngờ gì?

Startup không chép .data (hoặc chép sai địa chỉ do linker script đặt _sidata/LMA sai). Khi chạy từ debugger, RAM có thể còn giá trị từ lần nạp trước hoặc debugger tự nạp cả vùng RAM từ file ELF (nạp theo segment, kể cả .data ở VMA), nên lỗi bị che. Kiểm tra Reset_Handler, ký hiệu _sidata, _sdata, _edata trong file map, và chạy thử với một lần ngắt nguồn thật.

Ý chínhÝ chính của Bài 4
  • Reset: word 0 → SP, word 1 → Reset_Handler; không có gì khác được chuẩn bị.
  • Reset_Handler: chép .data, xóa .bss, SystemInit (clock, FPU), .init_array, main, vòng lặp vô hạn.
  • Handler yếu + alias: gõ sai tên ISR không báo lỗi mà rơi vào Default_Handler.
  • Compiler có thể biến vòng chép thành memcpy: -fno-tree-loop-distribute-patterns.
  • Bật FPU sớm; linker chèn veneer khi nhảy xa.

Bài 5 · Bố trí bộ nhớ, stack và heap

Bản đồ RAM của firmware

 0x20010000 ┌─────────────────────┐ ← _estack (SP ban đầu)
            │ stack ↓             │   một stack cho main + ISR (MSP);
            │                     │   với RTOS: mỗi task một stack riêng (cấp ở .bss hoặc heap)
            │ ...  vùng trống ... │
            │ heap ↑ (nếu dùng)   │
 _end       ├─────────────────────┤
            │ .noinit             │
            │ .bss                │
            │ .data               │
 0x20000000 └─────────────────────┘

Stack đi xuống, heap đi lên; nếu gặp nhau thì dữ liệu bị đè âm thầm. Trên MCU không có MMU, không có trang bảo vệ: tràn stack không gây lỗi ngay mà làm hỏng biến toàn cục hoặc heap, và triệu chứng xuất hiện ở chỗ khác hoàn toàn.

Ước lượng và đo stack

Tĩnh: -fstack-usage sinh file .su cho mỗi file nguồn, ghi số byte stack của từng hàm:

main2.c:7:13:put_dec   24    static
main2.c:8:17:deep      392   static
main2.c:10:5:main      16    static

static nghĩa là kích thước cố định (không có alloca, VLA). Tổng stack tệ nhất = đường đi sâu nhất trong đồ thị gọi hàm cộng với stack của các ISR có thể lồng nhau (Cortex-M đẩy thêm 32 byte, hoặc 104 byte có FPU, cho mỗi tầng ngắt). Đệ quy và con trỏ hàm làm phân tích tĩnh không đủ; công cụ như puncover, avstack.pl hoặc tính năng phân tích stack của các compiler thương mại tổng hợp đồ thị gọi. -Wstack-usage=256 cảnh báo hàm nào vượt ngưỡng.

Động: tô stack bằng một mẫu cố định, chạy hệ thống qua mọi kịch bản, rồi tìm chỗ sâu nhất mẫu bị ghi đè (stack painting / watermark). FreeRTOS làm vậy cho mỗi task (uxTaskGetStackHighWaterMark).

#include <stddef.h>
#include <stdint.h>
#include <errno.h>

extern uint32_t _ebss, _estack, _end;
extern uint32_t _stack_size;                     /* ký hiệu linker: dùng địa chỉ làm giá trị */
#define STACK_PATTERN 0xDEADBEEFu

/* Tô vùng từ cuối .bss tới gần SP hiện tại bằng mẫu; gọi sớm trong main */
void stack_paint(void) {
    uint32_t *p = &_ebss;
    uint32_t *sp;
    __asm__ volatile("mov %0, sp" : "=r"(sp));
    while (p < sp - 16) *p++ = STACK_PATTERN;    /* chừa 64 byte dưới SP hiện tại */
}

/* Số byte stack đã từng dùng (tính từ đỉnh RAM xuống chỗ mẫu đầu tiên bị ghi đè) */
size_t stack_high_water(void) {
    const uint32_t *p = &_ebss;
    while (p < &_estack && *p == STACK_PATTERN) ++p;
    return (size_t)((const uint8_t *)&_estack - (const uint8_t *)p);
}

/* _sbrk cho newlib: heap đi lên từ _end, không được đâm vào vùng dành cho stack */
void *_sbrk(ptrdiff_t incr) {
    static uint8_t *heap_end;
    uint8_t *const heap_limit = (uint8_t *)&_estack - (size_t)&_stack_size;
    if (!heap_end) heap_end = (uint8_t *)&_end;
    if (heap_end + incr > heap_limit) { errno = ENOMEM; return (void *)-1; }
    uint8_t *prev = heap_end;
    heap_end += incr;
    return prev;
}

Chạy trên QEMU (gọi stack_paint() đầu main, rồi gọi một hàm đệ quy 10 tầng):

before: 96 B
after deep(10): 1600 B
malloc(1000) ok, malloc(100000) NULL

Quy tắc thực tế: đặt kích thước stack bằng mức đo được cộng biên an toàn (thường 25–50%), kiểm tra lại sau mỗi thay đổi lớn, và báo high-water mark như một metric trong bản debug.

Phát hiện tràn khi chạy: đặt một vùng MPU không có quyền ghi ngay dưới đáy stack (tràn → MemManage fault thay vì đè dữ liệu); Cortex-M33 (ARMv8-M) có thanh ghi giới hạn stack MSPLIM/PSPLIM làm việc này bằng phần cứng; FreeRTOS có configCHECK_FOR_STACK_OVERFLOW. Một kỹ thuật đơn giản khác: đặt stack ở đầu RAM (đi xuống về phía địa chỉ 0x20000000), dữ liệu ở phía trên; tràn thì ghi ra ngoài vùng RAM và thường gây fault ngay (tùy bản đồ bộ nhớ của chip) thay vì đè dữ liệu.

Heap trên MCU

malloc của newlib xin bộ nhớ qua hàm _sbrk, do bạn cung cấp (hàm trong stack.c ở trên): heap tăng từ _end, không vượt vùng dành cho stack, hết thì trả lỗi để malloc trả NULL (thử nghiệm ở trên: xin 100.000 byte trên RAM 64 KB trả NULL đúng như mong đợi).

Nhiều chuẩn (MISRA, hàng không, y tế) cấm cấp phát động sau khi khởi động, vì: phân mảnh làm malloc thất bại sau nhiều ngày chạy dù tổng bộ nhớ trống còn nhiều; thời gian malloc không tất định; không an toàn trong ISR. Thay thế: cấp phát tĩnh mọi thứ, memory pool khối cố định (M06 Bài 4), hoặc chỉ cấp phát trong giai đoạn khởi tạo rồi "khóa" heap.

Bộ nhớ của process trên Linux

 địa chỉ cao   ┌──────────────────────┐
               │ kernel (không truy cập được từ userspace)
               ├──────────────────────┤
               │ stack ↓ (main thread, 8 MiB mặc định, có guard page)
               │ ...
               │ vùng mmap: thư viện .so, stack các thread, malloc lớn, file ánh xạ
               │ ...
               │ heap ↑ (brk)
               │ .bss, .data
               │ .text, .rodata
 địa chỉ thấp  └──────────────────────┘

Khác MCU: mỗi vùng có quyền riêng qua MMU (ghi vào .text gây SIGSEGV), có guard page dưới stack, và ASLR đặt các vùng ở địa chỉ ngẫu nhiên mỗi lần chạy. Xem bố cục thật của một process: cat /proc/<pid>/maps; tổng bộ nhớ thực dùng: /proc/<pid>/smaps_rollup (RSS, PSS).

Tự kiểm traThiết bị chạy ổn vài ngày rồi một biến cấu hình toàn cục tự đổi giá trị ngẫu nhiên. Code không có chỗ nào ghi vào biến đó. Hướng điều tra?

Nghi ngờ hàng đầu là tràn stack (hoặc tràn buffer) đè lên vùng RAM chứa biến. Xem file map để biết biến nằm cạnh gì; đo high-water mark của stack (và của từng task nếu dùng RTOS) dưới mọi kịch bản, đặc biệt đường lỗi hiếm (xử lý lỗi in log dài, ISR lồng nhau). Đặt watchpoint phần cứng (DWT) trên địa chỉ biến để bắt lệnh ghi. Phòng ngừa: MPU guard dưới đáy stack hoặc MSPLIM, tăng biên stack, -fstack-usage trong CI.

  • Đo stack: tĩnh (-fstack-usage, đồ thị gọi, cộng tầng ISR) và động (tô mẫu, high-water mark); thêm biên 25–50%.
  • Bắt tràn khi chạy: MPU guard, MSPLIM/PSPLIM, stack ở đầu RAM, kiểm tra của RTOS.
  • Heap qua _sbrk; tránh cấp phát động sau khởi động; pool khối cố định.
  • Linux: MMU, guard page, ASLR; /proc/<pid>/maps.

Bài 6 · File map và tối ưu kích thước firmware

Đọc file map

Thêm -Wl,-Map=fw.map khi link. File map trả lời ba câu hỏi: bộ nhớ được khai báo thế nào, mỗi section nằm ở đâu và to bao nhiêu, mỗi byte đến từ file/thư viện nào. Trích từ file map của firmware ở Bài 4:

Memory Configuration
Name             Origin             Length             Attributes
FLASH            0x00000000         0x00040000         xr
RAM              0x20000000         0x00010000         xrw

.isr_vector     0x00000000       0x44
 .isr_vector    0x00000000       0x44 startup.o
                0x00000000                vector_table
.text           0x00000048      0x208
 .text.Default_Handler
                0x00000048        0x4 startup.o
 ...
.data           0x20000000        0x8 load address 0x00000254
.bss            0x20000008        0x8 load address 0x0000025c

Dòng .data ... load address 0x00000254 thể hiện đúng VMA/LMA ở Bài 3. Phần Discarded input sections ở đầu file liệt kê những gì --gc-sections đã bỏ, hữu ích khi một hàm "biến mất".

Công cụ đọc nhanh:

Lệnh Cho biết
arm-none-eabi-size fw.elf text (Flash: code + hằng), data (vừa Flash vừa RAM), bss (RAM)

bloaty fw.elf -d compileunits Kích thước theo file nguồn
puncover Giao diện web: kích thước và stack theo hàm, đồ thị gọi

Flash dùng = text + data; RAM tĩnh = data + bss (chưa tính stack, heap).

Kẻ ăn Flash quen thuộc: printf

Đo thật trên Cortex-M4, -Os, cùng một chương trình nhỏ in một số ra UART:

Cách in Kích thước (text + data)
Tự đổi số thành chuỗi ~0,2 KB
snprintf("%d") với newlib-nano (--specs=nano.specs) ~4,1 KB
snprintf("%d") với newlib đầy đủ ~28,7 KB
snprintf("%.1f") với newlib-nano + -u _printf_float ~21,3 KB

newlib-nano bỏ hỗ trợ số thực trong printf mặc định (định dạng %f in ra rỗng!) để tiết kiệm; bật lại bằng -u _printf_float thì kéo theo cả thư viện số thực mềm. Trên MCU nhỏ, các lựa chọn thường gặp: newlib-nano không float, thư viện printf nhỏ chuyên cho nhúng (ví dụ mpaland/printf, nanoprintf), in số thực bằng số nguyên đã nhân tỉ lệ (fixed-point, M07), hoặc log dạng token (M09 Bài 6).

Bài 7 · Chương trình được nạp và chạy thế nào trên Linux

Từ execve tới main

 shell gọi execve("./app")
   └─▶ kernel đọc ELF header, ánh xạ các segment LOAD vào bộ nhớ
         └─▶ thấy segment INTERP: nạp dynamic linker /lib64/ld-linux-x86-64.so.2
               (trên ARM 64-bit: /lib/ld-linux-aarch64.so.1)
               └─▶ ld.so nạp các thư viện NEEDED (libc.so.6...), xử lý relocation
                     └─▶ nhảy tới _start của chương trình (từ crt1.o)
                           └─▶ __libc_start_main: khởi tạo libc, chạy .init_array
                                 └─▶ main(argc, argv, envp)
                                       └─▶ exit(): chạy .fini_array, atexit, destructor static

Xem bằng công cụ (kết quả thật trên một chương trình nhỏ):

$ readelf -h app | grep Type
  Type:     DYN (Position-Independent Executable file)
$ readelf -d app | grep NEEDED
  0x0000000000000001 (NEEDED)    Shared library: [libc.so.6]
$ readelf -r app | grep JUMP_SLO
  000000003fc0  ... R_X86_64_JUMP_SLO  puts@GLIBC_2.2.5
  000000003fc8  ... R_X86_64_JUMP_SLO  time@GLIBC_2.2.5

PIE, GOT, PLT

  • PIE (position-independent executable): chương trình có thể được nạp ở địa chỉ bất kỳ; kết hợp ASLR để mỗi lần chạy một địa chỉ khác, gây khó cho tấn công khai thác lỗ hổng. Mặc định trên các bản phân phối hiện đại.
  • Lời gọi tới hàm trong thư viện chia sẻ (puts, time) đi qua PLT (bảng các đoạn nhảy nhỏ) và GOT (bảng địa chỉ). Dòng JUMP_SLOT ở trên là ô trong GOT mà ld.so điền địa chỉ thật của puts. Có thể điền lười ở lần gọi đầu tiên (lazy binding) hoặc điền hết lúc khởi động (-Wl,-z,now, thường bật cùng -z relro để GOT thành chỉ đọc sau khi điền: chống ghi đè GOT).

Interposition và LD_PRELOAD

Vì ký hiệu được tìm lúc chạy theo thứ tự nạp, thư viện nạp trước có thể thay thế hàm của thư viện sau. Ví dụ thay time() của libc để test chương trình phụ thuộc thời gian (đã chạy thử):

/* faketime.c  →  gcc -shared -fPIC faketime.c -o libfaketime.so */
#include <time.h>
time_t time(time_t *t) { time_t v = 1700000000; if (t) *t = v; return v; }

$ ./app
constructor chạy trước main
time() = 1792666066
$ LD_PRELOAD=./libfaketime.so ./app
constructor chạy trước main
time() = 1700000000

Cùng cơ chế được dùng cho: thay allocator (jemalloc), đo đạc/trace (gọi hàm gốc qua dlsym(RTLD_NEXT, "time")), và cũng là một bề mặt tấn công (vì vậy với chương trình setuid, ld.so hạn chế chặt LD_PRELOAD).

Tìm thư viện chia sẻ

ld.so tìm theo thứ tự: RPATH/RUNPATH ghi trong file thực thi (-Wl,-rpath,'$ORIGIN/../lib'), biến LD_LIBRARY_PATH, cache /etc/ld.so.cache (cập nhật bằng ldconfig), rồi /lib, /usr/lib. ldd app liệt kê thư viện sẽ được nạp (đừng chạy ldd trên file không tin cậy: nó có thể thực thi code). LD_DEBUG=libs ./app in quá trình tìm kiếm.

Static hay dynamic trên thiết bị nhúng

  • Dynamic (mặc định với glibc): nhiều chương trình chia sẻ thư viện, cập nhật thư viện một chỗ.
  • Static: một file chạy được ở mọi nơi có cùng kiến trúc, không phụ thuộc thư viện trên máy đích. Với glibc, liên kết tĩnh có hạn chế (NSS, dlopen); musl (Alpine, nhiều image nhúng nhỏ) hỗ trợ liên kết tĩnh tốt và nhỏ gọn.
  • glibc, musl, uClibc-ng: Buildroot/Yocto cho chọn thư viện C; chương trình build cho glibc không chạy trên hệ thống musl và ngược lại (Bài 9).
Ý chínhÝ chính của Bài 7
  • execve → kernel ánh xạ segment → ld.so nạp thư viện, relocation → _start → __libc_start_main → .init_array → main.
  • PIE + ASLR; gọi thư viện qua PLT/GOT; -z now -z relro.
  • Interposition/LD_PRELOAD để thay hàm (test, allocator, trace).
  • Tìm thư viện: rpath/runpath, LD_LIBRARY_PATH, ld.so.cache; LD_DEBUG=libs.
  • Static với musl gọn cho nhúng; glibc và musl không thay thế nhau được.

Bài 8 · Build system

Make: những gì cần nắm

CC      := arm-none-eabi-gcc
CFLAGS  := -mcpu=cortex-m4 -mthumb -Os -g -Wall -Wextra -ffunction-sections -fdata-sections
DEPFLAGS = -MMD -MP                     # sinh file .d: object phụ thuộc những header nào
LDFLAGS := -T lm3s.ld -Wl,--gc-sections -Wl,-Map=$(BUILD)/fw.map

SRCS := startup.c main.c drivers/uart.c
OBJS := $(SRCS:%.c=$(BUILD)/%.o)

$(BUILD)/fw.elf: $(OBJS) lm3s.ld
    $(CC) $(CFLAGS) $(OBJS) $(LDFLAGS) -o $@

$(BUILD)/%.o: %.c
    @mkdir -p $(dir $@)
    $(CC) $(CFLAGS) $(DEPFLAGS) -c $< -o $@

-include $(OBJS:.o=.d)                  # sửa header thì build lại đúng file phụ thuộc

Hai lỗi kinh điển của Makefile tự viết: không theo dõi header (sửa .h mà file .c dùng nó không được build lại, sinh ra bug "chạy sai dù code đúng"; chữa bằng -MMD -MP), và không phụ thuộc vào linker script (sửa .ld mà không link lại).

CMake cho cross-compile

CMake tách cấu hình toolchain (một file dùng chung cho mọi project nhắm cùng chip) khỏi mô tả project:

# Toolchain file: dùng khi cấu hình, ví dụ
#   cmake -B build -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake
set(CMAKE_SYSTEM_NAME Generic)                     # không có hệ điều hành
set(CMAKE_SYSTEM_PROCESSOR arm)
set(CMAKE_C_COMPILER   arm-none-eabi-gcc)
set(CMAKE_CXX_COMPILER arm-none-eabi-g++)
set(CMAKE_ASM_COMPILER arm-none-eabi-gcc)
set(CMAKE_OBJCOPY      arm-none-eabi-objcopy)
set(CMAKE_SIZE         arm-none-eabi-size)
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)  # khi dò compiler, đừng thử link chương trình

set(CPU_FLAGS "-mcpu=cortex-m3 -mthumb")
set(CMAKE_C_FLAGS_INIT   "${CPU_FLAGS} -ffunction-sections -fdata-sections")
set(CMAKE_CXX_FLAGS_INIT "${CPU_FLAGS} -ffunction-sections -fdata-sections -fno-exceptions -fno-rtti")
set(CMAKE_EXE_LINKER_FLAGS_INIT "${CPU_FLAGS} -Wl,--gc-sections -nostartfiles --specs=nano.specs --specs=nosys.specs")

cmake_minimum_required(VERSION 3.20)
project(fw C)

add_executable(fw.elf startup.c main.c)
target_compile_options(fw.elf PRIVATE -Wall -Wextra -O2 -g)
set_source_files_properties(startup.c PROPERTIES COMPILE_OPTIONS -fno-tree-loop-distribute-patterns)
target_link_options(fw.elf PRIVATE
    -T${CMAKE_SOURCE_DIR}/lm3s.ld
    -Wl,-Map=${CMAKE_BINARY_DIR}/fw.map)
set_target_properties(fw.elf PROPERTIES LINK_DEPENDS ${CMAKE_SOURCE_DIR}/lm3s.ld)  # sửa .ld thì link lại

add_custom_command(TARGET fw.elf POST_BUILD
    COMMAND ${CMAKE_OBJCOPY} -O binary fw.elf fw.bin
    COMMAND ${CMAKE_SIZE} fw.elf
    COMMENT "Tạo fw.bin và in kích thước")

$ cmake -B build -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake
$ cmake --build build
[3/3] Linking C executable fw.elf
   text    data     bss     dec     hex filename
    596       4       8     608     260 fw.elf

(Đã chạy thử: build ra đúng firmware ở Bài 4 và chạy được trên QEMU.) Vài điểm: CMAKE_SYSTEM_NAME Generic báo không có hệ điều hành; CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY vì CMake mặc định thử link một chương trình để kiểm tra compiler, việc này thất bại khi chưa có linker script; LINK_DEPENDS để sửa .ld thì link lại. Cùng một CMakeLists.txt dùng được cho bản build test trên PC (không truyền toolchain file) nếu tách phần phụ thuộc phần cứng ra thư viện riêng (M08 Bài 7).

Thói quen build tốt

  • Hai cấu hình rõ ràng: debug (-Og -g, assert bật) và release (-Os/-O2 -g, assert theo chính sách); luôn giữ -g (thông tin debug không nằm trong .bin, không tốn Flash).
  • Cảnh báo ở mức cao và -Werror trong CI.
  • Build tái lập (reproducible): cùng mã nguồn cho cùng file nhị phân; cố định phiên bản toolchain (container, SDK), tránh nhúng thời gian build (SOURCE_DATE_EPOCH), dùng -ffile-prefix-map để đường dẫn tuyệt đối không lọt vào binary.
  • Nhúng phiên bản (git hash, số phiên bản) vào firmware ở vị trí cố định để đọc được từ thiết bị và từ file .bin.
  • ccache tăng tốc build lại; Ninja nhanh hơn Make cho project lớn.
  • Cho Embedded Linux: Yocto/Buildroot sinh cả toolchain, sysroot, rootfs (M11).

Toolchain và object file

01Các bước từ file .c tới file chạy được?Hay hỏi

Tiền xử lý (include, macro, #if) → biên dịch ra assembly (tối ưu ở đây) → hợp dịch ra object file có section, ký hiệu, relocation → liên kết: ghép object và thư viện, gán địa chỉ, điền relocation, ra ELF. Xem từng bước bằng -E, -S, -c, -v, -save-temps.

02.text, .rodata, .data, .bss nằm ở đâu trên MCU?Hay hỏi

.text và .rodata ở Flash. .data chạy ở RAM nhưng giá trị khởi tạo lưu ở Flash, startup chép sang (tốn cả hai). .bss chỉ ở RAM, startup xóa về 0, không tốn Flash.

03Relocation là gì?

Chỗ trống trong object file (địa chỉ hàm/biến ở file khác hoặc chưa biết địa chỉ cuối), kèm cách điền. Linker xử lý sau khi gán địa chỉ cho mọi section. Xem bằng objdump -dr hoặc readelf -r.

04Triplet arm-none-eabi nghĩa là gì? Khác arm-linux-gnueabihf thế nào?

Kiến trúc ARM, không nhà cung cấp cụ thể, không hệ điều hành (bare-metal), ABI nhúng; thư viện C là newlib. arm-linux-gnueabihf nhắm Linux với glibc và ABI hard-float, cần sysroot của hệ thống đích.

05static ở phạm vi file có tác dụng gì với linker?

Ký hiệu trở thành cục bộ (chữ thường trong nm), không xung đột với tên trùng ở file khác, compiler tối ưu mạnh hơn (có thể bỏ hẳn biến nếu không bị sửa). Mặc định nên dùng cho mọi thứ không xuất ra ngoài.

Linker

06Vì sao thứ tự thư viện tĩnh khi link lại quan trọng?Hay hỏi

Linker duyệt trái sang phải, từ mỗi .a chỉ lấy object giải quyết ký hiệu đang thiếu lúc đó. Thư viện phụ thuộc phải đứng trước thư viện được phụ thuộc; phụ thuộc vòng dùng --start-group ... --end-group.

07undefined reference khi gọi hàm C từ C++: nguyên nhân và cách sửa?Hay hỏi

C++ mangle tên (_Z8hal_initv), object C chỉ có hal_init. Bọc khai báo trong header bằng extern "C" (trong #ifdef __cplusplus). Dùng c++filt để đọc tên linker đang tìm.

08-ffunction-sections -fdata-sections và --gc-sections làm gì? Rủi ro?

Mỗi hàm/biến một section, linker bỏ section không ai tham chiếu: firmware nhỏ hơn nhiều khi dùng một phần thư viện. Rủi ro: thứ chỉ phần cứng dùng (bảng vector) hoặc được tìm theo tên section bị xóa nếu không có KEEP hoặc __attribute__((used)).

09LTO là gì?

Link-time optimization: object giữ biểu diễn trung gian, compiler tối ưu lại toàn chương trình lúc liên kết (inline xuyên file, bỏ code chết). Giảm kích thước và tăng tốc; build chậm hơn, debug khó hơn.

Linker script và startup

10VMA và LMA khác nhau thế nào?Hay hỏi

VMA là địa chỉ section khi chạy, LMA là nơi nó được lưu trong ảnh nạp. .data có VMA ở RAM, LMA ở Flash (> RAM AT> FLASH); startup chép từ _sidata sang _sdata..._edata.

11Linker script cho MCU cần những gì?Hay hỏi

MEMORY theo datasheet; SECTIONS đặt bảng vector (KEEP) đầu Flash, .text/.rodata, .init_array có ký hiệu đầu/cuối, .data với AT>, .bss NOLOAD, các vùng tùy chọn (.noinit, .ramfunc); ký hiệu cho startup (_estack, _sidata, _sdata, _edata, _sbss, _ebss, _end); ASSERT chống tràn; /DISCARD/.

12Cortex-M làm gì khi reset? Reset_Handler phải làm gì?Hay hỏi

Lõi đọc word 0 của bảng vector vào SP, word 1 là địa chỉ Reset_Handler rồi nhảy tới. Reset_Handler: chép .data, xóa .bss, SystemInit (clock, bật FPU), chạy .init_array (constructor C++), gọi main, vòng lặp vô hạn nếu main trả về.

13Vì sao gõ sai tên ISR không gây lỗi biên dịch?

Handler trong bảng vector là ký hiệu yếu alias tới Default_Handler. Hàm tên sai là một hàm khác không ai dùng; ký hiệu yếu không bị thay, ngắt rơi vào Default_Handler (thường vòng lặp vô hạn). Đọc IPSR để biết exception nào.

14Vì sao startup code đôi khi báo undefined reference to memcpy?

Compiler nhận ra vòng lặp chép/xóa và thay bằng memcpy/memset (loop distribution). Với -nostdlib không có hàm đó; và trong startup, gọi thư viện trước khi .data/.bss sẵn sàng là nguy hiểm. Dùng -fno-tree-loop-distribute-patterns hoặc tự cài đặt.

15Biến .noinit dùng để làm gì?

Không bị startup xóa nên giữ giá trị qua reset mềm: bộ đếm reset, lý do crash, thông tin cho bootloader. Phải kiểm tra tính hợp lệ (magic + CRC) vì sau mất điện nội dung là rác.

Bộ nhớ và kích thước

16Xác định kích thước stack cần thiết thế nào?Hay hỏi

Tĩnh: -fstack-usage từng hàm + đồ thị gọi tìm đường sâu nhất + stack các tầng ISR lồng nhau (32 B hoặc 104 B có FPU mỗi tầng). Động: tô stack bằng mẫu, chạy mọi kịch bản, đo high-water mark. Cộng biên 25–50%. Đệ quy và con trỏ hàm làm phân tích tĩnh không đủ.

17Phát hiện tràn stack trên MCU thế nào?

MPU region chặn ghi dưới đáy stack, MSPLIM/PSPLIM trên ARMv8-M, kiểm tra của RTOS (configCHECK_FOR_STACK_OVERFLOW), đặt stack ở đầu RAM để tràn ra ngoài vùng nhớ, watermark trong bản debug.

18Vì sao nhiều chuẩn cấm malloc trên MCU?

Phân mảnh làm cấp phát thất bại sau thời gian dài dù tổng trống còn nhiều; thời gian không tất định; không an toàn trong ISR; khó chứng minh không cạn bộ nhớ. Thay bằng cấp phát tĩnh, memory pool khối cố định, hoặc chỉ cấp phát lúc khởi tạo.

19Firmware vượt Flash: bạn làm gì?Hay hỏi

Đọc map/nm --size-sort/bloaty tìm thứ lớn nhất; thủ phạm hay gặp: printf (nhất là %f), số thực mềm, iostream, exception/RTTI C++, template bloat. Biện pháp: -Os, gc-sections, LTO, newlib-nano hoặc printf nhỏ, fixed-point, log token.

20size in text, data, bss: Flash và RAM dùng bao nhiêu?

Flash = text + data (giá trị khởi tạo của data); RAM tĩnh = data + bss; chưa tính stack và heap.

Linux runtime và build

21Chương trình trên Linux chạy tới main thế nào?Hay hỏi

execve → kernel ánh xạ segment LOAD, thấy INTERP thì nạp dynamic linker → ld.so nạp thư viện NEEDED, xử lý relocation → _start → __libc_start_main → .init_array (constructor) → main → exit chạy destructor/atexit.

22PLT và GOT là gì?

Lời gọi hàm thư viện chia sẻ nhảy qua PLT, đọc địa chỉ thật từ GOT mà ld.so điền (lười ở lần gọi đầu hoặc lúc khởi động với -z now). -z relro làm GOT chỉ đọc sau khi điền để chống ghi đè.

23LD_PRELOAD dùng làm gì?

Nạp thư viện trước các thư viện khác để thay thế hàm (interposition): giả lập thời gian khi test, thay allocator, trace lời gọi (gọi hàm gốc qua dlsym(RTLD_NEXT, ...)).

24Chạy chương trình báo "No such file or directory" dù file tồn tại?Hay hỏi

Dynamic linker ghi trong INTERP không tồn tại trên hệ thống: build cho glibc chạy trên musl, hoặc sai kiến trúc/đường dẫn. Kiểm tra readelf -l; build bằng toolchain + sysroot của đích hoặc liên kết tĩnh.

25Makefile tự viết hay mắc lỗi gì?

Không theo dõi header (sửa .h không build lại .c phụ thuộc) → dùng -MMD -MP và -include file .d; không phụ thuộc linker script; không tách thư mục build.

26Toolchain file của CMake cho bare-metal cần những gì?

CMAKE_SYSTEM_NAME Generic, compiler và công cụ (objcopy, size) của toolchain, CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY, cờ CPU trong *_FLAGS_INIT, cờ link (--gc-sections, specs). Linker script đưa vào bằng target_link_options và LINK_DEPENDS.
