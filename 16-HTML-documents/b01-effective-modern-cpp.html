Lvalue và rvalue

Mỗi biểu thức trong C++ có hai thuộc tính độc lập: kiểu (type) và value category (loại giá trị). Hai category quan trọng nhất:

  • Lvalue: biểu thức chỉ tới một object có danh tính, thường lấy được địa chỉ bằng &. Ví dụ: tên biến x, *p, arr[3], một hàm trả về tham chiếu T&.
  • Rvalue: giá trị tạm, không có tên, thường không lấy được địa chỉ. Ví dụ: literal 42, kết quả a + b, hàm trả về theo giá trị make_packet().

Cách kiểm tra nhanh nhất: lấy được địa chỉ thì là lvalue.

int x = 10;
int* p = &x;          // OK: x là lvalue
int* q = &(x + 1);    // lỗi: x + 1 là rvalue
int* r = &42;         // lỗi: literal là rvalue

Một điểm rất hay gây nhầm: kiểu và category độc lập với nhau. Một biến có kiểu "tham chiếu rvalue" vẫn là lvalue khi bạn dùng tên của nó, vì nó có tên và lấy được địa chỉ:

void consume(Packet&& p) {   // kiểu của p là Packet&& (rvalue reference)
    Packet* addr = &p;       // nhưng biểu thức "p" là lvalue: lấy được địa chỉ
}

Ghi nhớ câu này, vì Chương 5 dựa hoàn toàn vào nó: mọi tham số hàm đều là lvalue.

Template cơ bản

Một function template là khuôn để compiler sinh ra hàm thật. Khi bạn gọi, compiler suy luận (deduce) tham số template từ đối số truyền vào:

template<typename T>
T max_of(T a, T b) { return a > b ? a : b; }

max_of(3, 7);        // compiler suy ra T = int, sinh hàm int max_of(int, int)
max_of(2.5, 1.0);    // T = double
max_of(3, 1.0);      // lỗi: T là int hay double? Suy luận mâu thuẫn
max_of<double>(3, 1.0); // chỉ định tường minh: OK

Việc suy luận này có quy tắc chính xác, và đó là chủ đề của Item 1.

Const ở mức ngoài và mức trong

Với con trỏ, const có thể áp dụng cho chính con trỏ (top-level, mức ngoài) hoặc cho thứ nó trỏ tới (low-level, mức trong):

const char* a;          // mức trong: không sửa được *a, nhưng a đổi được
char* const b = buf;    // mức ngoài: b không đổi được, *b sửa được
const char* const c = buf; // cả hai

Khi copy một giá trị, const mức ngoài không còn ý nghĩa: bản sao là object mới, nó có hằng hay không là chuyện của bản sao. Nhưng const mức trong vẫn quan trọng: bản sao của const char* vẫn trỏ tới dữ liệu không được sửa. Quy tắc này giải thích trường hợp 3 của Item 1.

Decay: mảng và hàm biến thành con trỏ

Trong hầu hết ngữ cảnh, tên mảng tự chuyển thành con trỏ tới phần tử đầu, gọi là array-to-pointer decay. Tên hàm cũng tự chuyển thành con trỏ hàm. Đây là di sản của C, và tham số hàm kiểu mảng thực chất là con trỏ:

void f(int arr[16]);   // trình biên dịch hiểu là void f(int* arr)
void g(int* arr);      // cùng một chữ ký với f

Nhưng một tham chiếu tới mảng thì giữ nguyên kiểu mảng, kể cả kích thước: int (&ref)[16] = arr;. Item 1 tận dụng điều này.

C++98 chỉ có một bộ quy tắc suy luận kiểu, dùng cho function template. C++11 sửa đổi bộ quy tắc đó và thêm hai bộ mới: một cho auto, một cho decltype. C++14 mở rộng chỗ dùng được auto và decltype.

Vì sao chương này quan trọng? Suy luận kiểu giúp bạn không phải viết lại những kiểu đã rõ ràng, và khi thay đổi một kiểu ở một chỗ thì mọi chỗ khác tự cập nhật. Nhưng nếu bạn không biết compiler đang suy ra kiểu gì, code sẽ chạy khác điều bạn nghĩ: copy thay vì tham chiếu, mất const, hay tạo ra con trỏ treo. Chương này cho bạn mô hình chính xác để luôn đoán đúng.

Item 1 · Hiểu template type deduction Đọc kỹ tr. 9 · PDF 27

Đặt vấn đề

Hãy xét dạng tổng quát của một function template và lời gọi nó:

template<typename T>
void f(ParamType param);   // ParamType là một kiểu được viết dựa trên T

f(expr);                   // gọi f với một biểu thức

Lúc compile, từ expr compiler phải suy ra hai kiểu: kiểu của T, và kiểu của ParamType. Hai kiểu này thường khác nhau, vì ParamType thường có thêm "trang trí" như const hay &. Ví dụ:

template<typename T>
void f(const T& param);    // ParamType là const T&

int x = 0;
f(x);                      // T = int, ParamType = const int&

Ở đây T là int còn param có kiểu const int&. Rất tự nhiên: ta nghĩ T chính là kiểu của đối số. Nhưng không phải lúc nào cũng vậy. Kiểu suy ra cho T phụ thuộc vào cả kiểu của expr lẫn dạng của ParamType. Có ba trường hợp:

  1. ParamType là con trỏ hoặc tham chiếu, nhưng không phải universal reference.
  2. ParamType là universal reference (T&&).
  3. ParamType không phải con trỏ cũng không phải tham chiếu (truyền theo giá trị).

Trong các ví dụ dưới đây, ta dùng ba biến chuẩn:

int x = 27;          // int
const int cx = x;    // const int
const int& rx = x;   // tham chiếu tới x dưới dạng const int

Trường hợp 1: ParamType là tham chiếu hoặc con trỏ

Quy tắc gồm hai bước:

  1. Nếu kiểu của expr là tham chiếu, bỏ phần tham chiếu.
  2. Khớp mẫu (pattern-match) kiểu còn lại của expr với ParamType để tìm T.
template<typename T>
void f(T& param);

f(x);    // expr: int          → T = int,       param: int&
f(cx);   // expr: const int    → T = const int, param: const int&
f(rx);   // expr: const int&   → bỏ &: const int → T = const int, param: const int&

Hãy để ý hai điều.

Thứ nhất, const được giữ lại trong T. Khi truyền cx (một hằng) vào tham số kiểu T&, người gọi kỳ vọng hàm không thể sửa cx. Nếu T bị suy ra là int thì param có kiểu int& và hàm sửa được hằng, điều đó vi phạm an toàn kiểu. Vì vậy T phải là const int. Nhờ quy tắc này, truyền object const vào tham số T& luôn an toàn: tính hằng trở thành một phần của T.

Thứ hai, tính tham chiếu của rx bị bỏ qua. Bước 1 xóa nó đi trước khi khớp mẫu, nên rx cho cùng kết quả với cx.

Nếu đổi tham số thành const T&, phần const đã có sẵn trong ParamType, nên T không cần mang const nữa:

template<typename T>
void f(const T& param);

f(x);    // T = int, param: const int&
f(cx);   // T = int, param: const int&   (const đã nằm trong ParamType)
f(rx);   // T = int, param: const int&

Với con trỏ, mọi thứ diễn ra y hệt:

template<typename T>
void f(T* param);

const int* px = &x;
f(&x);   // expr: int*        → T = int,       param: int*
f(px);   // expr: const int*  → T = const int, param: const int*

Đến đây chưa có gì bất ngờ: các quy tắc hoạt động đúng như trực giác mà một người viết template mong muốn.

Trường hợp 2: ParamType là universal reference

Với tham số dạng T&& mà T được suy luận, quy tắc khác hẳn so với rvalue reference thông thường (chi tiết đầy đủ ở Item 24). Tóm tắt:

  • Nếu expr là lvalue: cả T lẫn ParamType đều được suy ra là lvalue reference. Đây là chỗ duy nhất trong template type deduction mà T được suy ra là một kiểu tham chiếu. Lạ hơn nữa: dù ParamType được viết bằng cú pháp rvalue reference T&&, kiểu cuối cùng lại là lvalue reference.
  • Nếu expr là rvalue: áp dụng quy tắc của trường hợp 1.
template<typename T>
void f(T&& param);         // universal reference

f(x);    // x là lvalue  → T = int&,        param: int&
f(cx);   // cx là lvalue → T = const int&,  param: const int&
f(rx);   // rx là lvalue → T = const int&,  param: const int&
f(27);   // 27 là rvalue → T = int,         param: int&&

Vì sao T&& lại thành int&? Khi T = int&, ParamType là int& &&, một "tham chiếu tới tham chiếu". Compiler áp dụng reference collapsing (Item 28): có một & thì kết quả là &. Cơ chế này cho phép một hàm duy nhất nhận được cả lvalue và rvalue, đồng thời ghi nhớ đối số ban đầu là loại nào (ghi vào T). Đây là nền tảng của perfect forwarding với std::forward.

Điểm cốt lõi: với universal reference, lvalue và rvalue cho kết quả khác nhau. Với các loại tham số khác thì không.

Trường hợp 3: truyền theo giá trị

template<typename T>
void f(T param);           // param là một bản sao

Vì param là một object mới, độc lập với đối số, quy tắc là:

  1. Nếu kiểu của expr là tham chiếu, bỏ phần tham chiếu.
  2. Sau đó, nếu còn const (mức ngoài), bỏ luôn. Nếu còn volatile, cũng bỏ.
f(x);    // T = int, param: int
f(cx);   // T = int, param: int   (const bị bỏ)
f(rx);   // T = int, param: int   (& và const đều bị bỏ)

Lý do: cx không sửa được, nhưng param là bản sao. Sửa bản sao không ảnh hưởng gì tới cx, nên không có lý do để param là hằng.

Cẩn thận với con trỏ. Chỉ const mức ngoài bị bỏ. const mức trong (thứ con trỏ trỏ tới) phải được giữ, nếu không hàm sẽ sửa được dữ liệu hằng qua bản sao của con trỏ:

const char* const name = "uart0";   // con trỏ hằng tới chuỗi hằng
f(name);   // T = const char*  (bỏ const mức ngoài của con trỏ,
           //                   giữ const của chuỗi)

Mảng làm đối số

Mảng và con trỏ thường dùng thay nhau được, nhưng chúng là hai kiểu khác nhau. const char banner[] = "BOOT v1.2"; có kiểu const char[10], không phải const char*.

Khi truyền theo giá trị, mảng decay thành con trỏ:

template<typename T> void by_value(T param);
by_value(banner);   // T = const char*

Nhưng khi truyền theo tham chiếu, không có decay, và T là kiểu mảng thật kể cả kích thước:

template<typename T> void by_ref(T& param);
by_ref(banner);     // T = const char[10], param: const char (&)[10]

Điều này cho phép viết một hàm tính số phần tử của mảng lúc compile:

template<typename T, std::size_t N>
constexpr std::size_t array_size(T (&)[N]) noexcept {   // không cần tên tham số
    return N;
}

uint8_t rx_buf[64];
uint8_t mirror[array_size(rx_buf)];                // 64, biết lúc compile
std::array<uint16_t, array_size(rx_buf)> stats;    // dùng được làm tham số template

constexpr (Item 15) cho phép dùng kết quả lúc compile, noexcept (Item 14) giúp compiler tối ưu. So với macro sizeof(a)/sizeof(a[0]) của C, hàm này không compile nếu lỡ truyền một con trỏ, nên an toàn hơn. Từ C++17, thư viện chuẩn có sẵn std::size(arr) làm đúng việc này.

Hàm làm đối số

Tên hàm cũng decay, thành con trỏ hàm:

void on_tick(int ms);
template<typename T> void reg1(T param);
template<typename T> void reg2(T& param);

reg1(on_tick);   // T = void (*)(int)     con trỏ hàm
reg2(on_tick);   // T = void (int),  param: void (&)(int)  tham chiếu tới hàm

Trên thực tế hai dạng này dùng gần như nhau, nhưng biết được nó giúp bạn hiểu thông báo lỗi.

Ý chínhÝ chính của Item 1

  • Universal reference: lvalue được xử lý đặc biệt, T thành lvalue reference.
  • Truyền theo giá trị: bỏ tham chiếu, bỏ const/volatile mức ngoài.
  • Mảng và hàm decay thành con trỏ, trừ khi tham số là tham chiếu.
Tự kiểm tra`template void f(T& p);` với `const std::array a{};` gọi `f(a)`. `T` là gì? Hàm có sửa được `a` không?

T = const std::array<int, 4>, p có kiểu const std::array<int, 4>&. Không sửa được: const được giữ trong T.

Tự kiểm tra`template void g(T p);` gọi `g(rx)` với `const int& rx`. `T` là gì? Vì sao?

T = int. Truyền theo giá trị: bỏ &, rồi bỏ const mức ngoài, vì p là bản sao độc lập.

Tự kiểm tra`template void h(T&& p);` gọi `h(x)` và `h(std::move(x))` với `int x`. Kiểu `T` và `p` trong mỗi trường hợp?

h(x): x là lvalue → T = int&, p: int&. h(std::move(x)): rvalue → T = int, p: int&&.

Tự kiểm traVì sao `array_size` viết bằng template an toàn hơn macro `sizeof(a)/sizeof(a[0])`?

Macro vẫn compile khi lỡ truyền con trỏ (cho kết quả sai, ví dụ 4/1 = 4). Template nhận T (&)[N] sẽ báo lỗi compile vì con trỏ không khớp với tham chiếu tới mảng.

Item 2 · Hiểu auto type deduction Đọc kỹ tr. 18 · PDF 36

auto chính là template deduction

Khi đã hiểu Item 1, bạn gần như đã hiểu auto. Quy tắc gần như một-một: trong khai báo auto, từ khóa auto đóng vai T của template, và toàn bộ phần kiểu được viết (ví dụ const auto&) đóng vai ParamType.

Hãy hình dung compiler làm như sau với mỗi khai báo:

auto x = 27;
// giống như: template<typename T> void tmp(T param);  tmp(27);     → T = int

const auto cx = x;
// giống như: template<typename T> void tmp(const T param); tmp(x); → T = int, cx: const int

const auto& rx = x;
// giống như: template<typename T> void tmp(const T& param); tmp(x); → rx: const int&

Vì thế cả ba trường hợp ở Item 1 áp dụng y nguyên:

auto x = 27;            // trường hợp 3 (giá trị):       int
const auto cx = x;      // trường hợp 3:                 const int
const auto& rx = x;     // trường hợp 1 (tham chiếu):    const int&

auto&& u1 = x;          // trường hợp 2, x là lvalue:    int&
auto&& u2 = cx;         // trường hợp 2, cx là lvalue:   const int&
auto&& u3 = 27;         // trường hợp 2, 27 là rvalue:   int&&

const char banner[] = "BOOT v1.2";
auto a1 = banner;       // const char*   (decay)
auto& a2 = banner;      // const char (&)[10]

void on_tick(int);
auto f1 = on_tick;      // void (*)(int)
auto& f2 = on_tick;     // void (&)(int)

Hệ quả thực tế quan trọng: auto (không có &) luôn tạo bản sao và bỏ const. Muốn tham chiếu thì phải viết auto& hoặc const auto&.

std::vector<Sample> samples = load();
for (auto s : samples) { s.value = 0; }        // sửa bản sao, samples không đổi, lại tốn copy
for (auto& s : samples) { s.value = 0; }       // sửa phần tử thật
for (const auto& s : samples) { use(s); }      // chỉ đọc, không copy

Ngoại lệ duy nhất: braced initializer

C++11 có bốn cách khởi tạo một biến int với giá trị 27:

int a = 27;
int b(27);
int c = {27};
int d{27};

Cả bốn cho cùng kết quả. Nhưng thay int bằng auto thì khác:

auto a = 27;     // int
auto b(27);      // int
auto c = {27};   // std::initializer_list<int>, chứa một phần tử 27
auto d{27};      // theo sách (C++11/14): std::initializer_list<int>
                 // từ C++17 (đề xuất N3922): int

Đây là quy tắc đặc biệt của auto: khi gặp dấu ngoặc nhọn, nó giả định bạn muốn std::initializer_list<T> (một danh sách tạm các giá trị cùng kiểu, dùng để khởi tạo container). Nếu các phần tử không cùng kiểu, suy luận thất bại:

auto e = {1, 2, 3.0};    // lỗi: không suy ra được T chung cho initializer_list<T>

Ngược lại, template không làm vậy:

template<typename T> void f(T param);
f({1, 2, 3});            // lỗi: không suy ra được T

template<typename T> void g(std::initializer_list<T> list);
g({1, 2, 3});            // OK: T = int, vì ParamType đã ghi rõ initializer_list

Đây là khác biệt duy nhất giữa suy luận của auto và của template. Lời khuyên thực tế: tránh dùng auto với {} trừ khi bạn thật sự muốn một initializer_list. Viết auto n = 27;.

Cẩn thậnBẫy khi chuyển code sang `{}`

Nhiều người được khuyên "dùng {} khắp nơi" (Item 7) rồi máy móc đổi int n = 0; thành auto n = {0};. Kết quả là n có kiểu std::initializer_list<int>, không còn là số, và thường chỉ lộ ra ở lỗi compile ở đâu đó rất xa.

auto ở kiểu trả về và tham số lambda (C++14)

C++14 cho phép auto làm kiểu trả về của hàm, và làm kiểu tham số của lambda (generic lambda). Ở hai chỗ này, compiler dùng quy tắc template, không phải quy tắc auto. Do đó braced initializer không được chấp nhận:

auto make_ids() {
    return {1, 2, 3};          // lỗi: không suy ra được kiểu từ {1, 2, 3}
}

std::vector<int> v;
auto reset = [&v](const auto& init) { v = init; };   // C++14 generic lambda
reset({1, 2, 3});              // lỗi: không suy ra được kiểu tham số
Ý chínhÝ chính của Item 2
  • auto dùng đúng quy tắc của template, với auto là T.
  • Khác biệt duy nhất: auto x = {…} suy ra std::initializer_list, còn template thì không suy ra được từ {…}.
  • auto ở kiểu trả về và tham số lambda dùng quy tắc template, nên không nhận {…}.
  • auto không có & luôn tạo bản sao.
Tự kiểm traKiểu của mỗi biến: `auto a = 1.5f;`, `auto b = {1.5f};`, `auto& c = a;`, `const auto d = c;`, `auto e{1.5f};` (C++17)?

a: float, b: std::initializer_list<float>, c: float&, d: const float, e: float (từ C++17).

Tự kiểm traVòng lặp `for (auto p : packets)` với `std::vector` có vấn đề gì nếu `Packet` lớn 256 byte?

Mỗi vòng copy một Packet 256 byte vào p. Nếu chỉ đọc, dùng const auto& p; nếu cần sửa phần tử thật, dùng auto& p.

Item 3 · Hiểu decltype Lướt tr. 23 · PDF 41

decltype cho kiểu "y nguyên"

decltype nhận một tên hoặc biểu thức và cho biết kiểu của nó, không thêm không bớt. Khác với template và auto, nó không bỏ tham chiếu hay const:

const int cx = 0;          // decltype(cx) là const int
const int& rx = cx;        // decltype(rx) là const int&
bool is_ready(const Uart& u);  // decltype(is_ready) là bool(const Uart&)
                               // decltype(is_ready(u)) là bool
struct Point { int x, y; };    // decltype(Point::x) là int
std::vector<int> v;            // decltype(v[0]) là int& (operator[] trả int&)

Ứng dụng chính: kiểu trả về phụ thuộc tham số

Giả sử bạn viết một hàm template truy cập phần tử container sau khi kiểm tra quyền truy cập. Hàm nên trả về đúng kiểu mà operator[] của container trả về. Với hầu hết container, đó là T&, nghĩa là người gọi sửa được phần tử. (Ngoại lệ là std::vector<bool>, trả về một proxy, xem Item 6.)

C++11 dùng trailing return type: kiểu trả về đặt sau danh sách tham số, nên dùng được tên tham số:

template<typename Container, typename Index>
auto checked_at(Container& c, Index i) -> decltype(c[i]) {   // C++11
    validate(i);
    return c[i];
}

auto ở đầu ở đây không suy luận gì, nó chỉ báo hiệu "kiểu trả về được viết ở phía sau".

C++14 cho phép bỏ phần đuôi và để compiler tự suy ra kiểu trả về từ câu return. Nhưng nếu viết auto, compiler dùng quy tắc template (Item 2), tức là bỏ tham chiếu:

template<typename Container, typename Index>
auto checked_at(Container& c, Index i) {   // C++14, sai ý
    validate(i);
    return c[i];        // c[i] là int&, nhưng auto bỏ & → trả về int (bản sao)
}

std::vector<int> regs(8);
checked_at(regs, 3) = 0xFF;   // lỗi compile: gán vào một rvalue int

Giải pháp của C++14 là decltype(auto): auto nghĩa là "hãy suy ra kiểu", còn decltype nghĩa là "dùng quy tắc của decltype để suy ra":

template<typename Container, typename Index>
decltype(auto) checked_at(Container& c, Index i) {   // C++14, đúng ý
    validate(i);
    return c[i];        // trả về đúng int&
}

decltype(auto) cũng dùng được khi khai báo biến:

const int& cref = x;
auto a = cref;            // int (bỏ const và &)
decltype(auto) b = cref;  // const int& (giữ nguyên)

Phiên bản hoàn chỉnh của hàm trên nên nhận cả container tạm (rvalue), ví dụ checked_at(make_table(), 5). Muốn vậy, tham số phải là universal reference và dùng std::forward (Item 25):

template<typename Container, typename Index>
decltype(auto) checked_at(Container&& c, Index i) {
    validate(i);
    return std::forward<Container>(c)[i];
}

Trường hợp đặc biệt: biểu thức lvalue không phải tên

Có một chi tiết của decltype bạn cần biết dù hiếm gặp. Với một cái tên, decltype cho kiểu đã khai báo. Nhưng với một biểu thức lvalue phức tạp hơn một cái tên, decltype luôn cho T&. Và chỉ cần bọc tên trong dấu ngoặc là đã thành "biểu thức phức tạp hơn một cái tên":

int x = 0;
decltype(x)   // int
decltype((x)) // int&   vì (x) là biểu thức lvalue, không phải tên

Với decltype(auto), sự khác biệt này có thể gây lỗi nghiêm trọng:

decltype(auto) good() {
    int local = 0;
    return local;      // decltype(local) là int → trả về int: OK
}

decltype(auto) bad() {
    int local = 0;
    return (local);    // decltype((local)) là int& → trả về tham chiếu tới biến cục bộ!
}                      // undefined behavior khi người gọi dùng kết quả

Chỉ thêm một cặp ngoặc mà hàm trả về tham chiếu treo. Bài học: dùng decltype(auto) cẩn thận và chỉ khi thực sự cần giữ nguyên tham chiếu.

Ý chínhÝ chính của Item 3
  • decltype gần như luôn cho đúng kiểu đã khai báo của tên hoặc biểu thức, không sửa đổi.
  • Với biểu thức lvalue không phải tên, decltype cho T&. decltype((x)) là int&.
  • decltype(auto) suy luận kiểu từ initializer nhưng theo quy tắc của decltype. Dùng cho hàm trả về đúng kiểu của biểu thức (thường là tham chiếu).
Tự kiểm traVới `int a[4];`, `decltype(a)` và `decltype(a[0])` là gì?

decltype(a) là int[4] (tên, kiểu khai báo). decltype(a[0]) là int& (biểu thức lvalue không phải tên).

Tự kiểm traMột hàm `auto get_cfg() { return cfg_; }` với `Config cfg_;` là thành viên. Người gọi viết `get_cfg().baud = 9600;`. Chuyện gì xảy ra?

auto bỏ tham chiếu nên hàm trả về bản sao Config. Phép gán sửa bản sao tạm, cfg_ không đổi (và với class, code vẫn compile, nên lỗi rất khó thấy). Muốn sửa được thì khai báo kiểu trả về Config&. Cũng có thể dùng decltype(auto) với return (cfg_);, nhưng viết rõ Config& dễ đọc hơn nhiều.

Item 4 · Biết cách xem kiểu được suy ra Bỏ qua tr. 30 · PDF 48

Khi không chắc compiler suy ra kiểu gì, có ba thời điểm để kiểm tra: lúc viết code, lúc compile, và lúc chạy.

Lúc viết: IDE

Hầu hết IDE (VS Code với clangd, CLion, Visual Studio) hiện kiểu khi di chuột lên biến. Với kiểu đơn giản thì chính xác; với kiểu phức tạp (template lồng nhau), IDE có thể hiển thị khó đọc hoặc không chính xác, vì nó chạy một phiên bản compiler nội bộ.

Lúc compile: ép compiler báo lỗi

Mẹo đáng tin cậy nhất: khai báo một class template không định nghĩa, rồi cố dùng nó với kiểu cần xem. Compiler báo lỗi và trong thông báo lỗi có tên kiểu:

template<typename T> class TypeDisplay;   // chỉ khai báo, không định nghĩa

auto y = &x;
TypeDisplay<decltype(y)> show_y;   // lỗi: "implicit instantiation of undefined
                                   //  template 'TypeDisplay<int *>'"

Lúc chạy: in ra

Cách hay được nghĩ tới là typeid(x).name(). Nó có hai vấn đề:

  • Kết quả phụ thuộc compiler. GCC và Clang in tên đã mangle (ví dụ PKi cho const int*), cần chạy qua c++filt -t để đọc.
  • Nó không chính xác: chuẩn quy định typeid xử lý kiểu như khi truyền theo giá trị vào template, tức là bỏ tham chiếu và const. Kiểu const Widget& sẽ được in là Widget.

Thư viện Boost.TypeIndex cung cấp boost::typeindex::type_id_with_cvr<T>().pretty_name() (chữ cvr nghĩa là giữ const, volatile, reference) cho kết quả chính xác và dễ đọc.

Lợi ích 1: không thể quên khởi tạo

Trong C và C++, biến cục bộ kiểu cơ bản không được khởi tạo sẽ chứa giá trị rác. Đây là nguồn bug kinh điển trong firmware: một cờ trạng thái lúc thì 0, lúc thì khác 0 tùy nội dung stack trước đó.

int status;          // giá trị rác, compile bình thường
auto status2;        // lỗi compile: auto cần initializer để suy ra kiểu
auto status3 = 0;    // OK: int, đã khởi tạo

Vì auto phải nhìn initializer để biết kiểu, không thể khai báo biến auto chưa khởi tạo.

Lợi ích 2: viết được những kiểu dài hoặc không viết được

Kiểu của iterator hay của giá trị mà iterator trỏ tới thường rất dài:

template<typename It>
void process_range(It begin, It end) {
    while (begin != end) {
        typename std::iterator_traits<It>::value_type current = *begin;   // C++98
        auto current2 = *begin;                                           // C++11
        ++begin;
    }
}

Quan trọng hơn, có những kiểu không thể viết ra: kiểu của một lambda (closure) chỉ compiler biết. Với auto, lưu một lambda vào biến là việc hiển nhiên:

auto by_priority = [](const Task& a, const Task& b) { return a.prio < b.prio; };

C++14 còn cho phép tham số lambda là auto, nên lambda trên có thể viết tổng quát cho mọi kiểu có trường prio:

auto by_priority = [](const auto& a, const auto& b) { return a.prio < b.prio; };

Lợi ích 3: auto rẻ hơn std::function

Không có auto, cách duy nhất để lưu một lambda vào biến là std::function, một class template của C++11 có thể chứa bất kỳ thứ gì gọi được (hàm, lambda, function object) có chữ ký phù hợp:

std::function<bool(const Task&, const Task&)> cmp =
    [](const Task& a, const Task& b) { return a.prio < b.prio; };

std::function vẫn có chỗ dùng: khi cần lưu nhiều loại callable khác nhau vào cùng một biến hay container (ví dụ một mảng callback đăng ký từ nhiều nơi). Nhưng khi chỉ cần một biến cục bộ giữ một lambda, auto tốt hơn về mọi mặt.

Lợi ích 4: tránh "sai kiểu ngầm" (type shortcut)

Đây là lợi ích ít ai nghĩ tới nhưng quan trọng nhất. Xét đoạn code rất bình thường:

std::vector<uint8_t> frame = receive();
unsigned len = frame.size();

Kiểu trả về chính thức của size() là std::vector<uint8_t>::size_type, một kiểu số nguyên không dấu mà chuẩn không quy định độ rộng. Trên MCU 32-bit, unsigned và size_type cùng 32-bit nên không sao. Trên Linux 64-bit, size_type là 64-bit còn unsigned là 32-bit: dữ liệu lớn hơn 4 GB sẽ bị cắt. auto len = frame.size(); luôn đúng.

Ví dụ thứ hai tinh vi hơn nhiều, và rất phổ biến:

std::unordered_map<std::string, int> counters;

for (const std::pair<std::string, int>& p : counters) {
    // ...
}

Trông hoàn toàn hợp lý. Nhưng kiểu phần tử của std::unordered_map<K, V> là std::pair<const K, V>: khóa là const (sửa khóa sẽ phá cấu trúc bảng băm). Vì std::pair<std::string, int> khác std::pair<const std::string, int>, compiler phải tìm cách chuyển đổi. Nó làm được, bằng cách tạo một object pair tạm (copy cả chuỗi), rồi gắn tham chiếu p vào object tạm đó. Cuối mỗi vòng lặp, object tạm bị hủy. Hậu quả:

  • Mỗi vòng copy một std::string: chậm, có thể cấp phát heap.
  • Nếu lấy địa chỉ &p để lưu lại, bạn đang trỏ vào object tạm đã chết.

Viết auto thì không có vấn đề gì:

for (const auto& p : counters) { }   // p: const std::pair<const std::string, int>&

Điểm chung của hai ví dụ: kiểu viết tay trông "đủ đúng", compile bình thường, nhưng không phải kiểu thật. auto luôn lấy đúng kiểu thật.

Lợi ích 5: refactor dễ hơn

Nếu một hàm đổi kiểu trả về từ int sang int64_t, các biến auto nhận kết quả tự đổi theo. Biến khai báo int vẫn compile được và âm thầm cắt dữ liệu.

Phản biện: "code khó đọc vì không thấy kiểu"

Đây là lo ngại hợp lý. Ba ý trả lời:

  • IDE hiển thị kiểu khi cần.
  • Nhiều ngôn ngữ khác (C#, Kotlin, Rust, Swift) đã dùng suy luận kiểu rộng rãi mà không gặp vấn đề lớn về khả năng bảo trì.

Đây không phải quy tắc tuyệt đối: nếu viết kiểu ra làm code rõ ràng hơn (ví dụ khi kiểu là thông tin quan trọng, như uint16_t cho một trường thanh ghi), cứ viết. Nhưng mặc định nên nghiêng về auto.

Item 6 · Dùng explicitly typed initializer khi auto suy ra kiểu không mong muốn Lướt tr. 43 · PDF 61

Một ví dụ bất ngờ

Giả sử có hàm trả về các cờ tính năng của một thiết bị dưới dạng std::vector<bool>, mỗi bit một tính năng:

std::vector<bool> features(const Device& d);

bool low_power = features(dev)[3];   // OK
apply_power_mode(dev, low_power);

Đổi sang auto:

auto low_power = features(dev)[3];   // compile được
apply_power_mode(dev, low_power);    // undefined behavior!

Cùng một biểu thức, chỉ khác cách khai báo, mà một bản đúng một bản có UB. Lý do nằm ở chỗ std::vector<bool> đặc biệt.

Proxy class

Thư viện chuẩn có một specialization riêng cho std::vector<bool>: nó nén mỗi bool thành một bit. Hệ quả: operator[] không thể trả về bool& như các vector<T> khác, vì C++ không có tham chiếu tới một bit. Thay vào đó, nó trả về một object kiểu std::vector<bool>::reference, một proxy class: object nhỏ đóng vai một bool&, bên trong chứa con trỏ tới word chứa bit và vị trí bit. Nó có toán tử chuyển ngầm sang bool để dùng như bool.

Bây giờ xét lại hai cách khai báo:

  • bool low_power = features(dev)[3];: proxy được chuyển ngay sang bool (đọc bit), rồi giá trị được lưu. Object vector tạm do features() trả về bị hủy cuối câu lệnh, nhưng ta đã có giá trị.
  • auto low_power = features(dev)[3];: auto suy ra đúng kiểu của biểu thức, tức là proxy. Proxy chứa con trỏ vào bộ nhớ của vector tạm. Cuối câu lệnh, vector tạm bị hủy, con trỏ trong proxy treo. Dùng low_power sau đó là UB.

Quy tắc chung

Proxy class được thiết kế để sống ngắn, chỉ trong một biểu thức. auto giữ chúng sống lâu hơn dự kiến. Vấn đề không nằm ở auto mà ở việc nó suy ra đúng một kiểu mà người viết không biết là tồn tại. Một số ví dụ proxy:

  • std::vector<bool>::reference, std::bitset<N>::reference.
  • Expression template trong thư viện đại số tuyến tính (như Eigen): auto sum = m1 + m2 + m3; không phải một ma trận mà là một object mô tả phép tính, tham chiếu tới các ma trận gốc. Thiết kế này giúp tránh tạo ma trận trung gian, nhưng lưu bằng auto có thể treo khi các ma trận gốc là object tạm.
  • Smart pointer (std::shared_ptr) về mặt kỹ thuật cũng là proxy, nhưng chúng được thiết kế để sống lâu nên không có vấn đề.

Làm sao nhận ra một proxy "vô hình"? Đọc tài liệu hoặc header: kiểu trả về của hàm sẽ lộ ra (reference operator[](size_type) trong vector<bool> thay vì bool&).

Cách sửa: explicitly typed initializer idiom

Không cần bỏ auto. Ép kiểu biểu thức sang đúng kiểu bạn muốn:

auto low_power = static_cast<bool>(features(dev)[3]);
auto total = static_cast<Matrix>(m1 + m2 + m3);

Idiom này còn có ích khi bạn cố ý muốn một kiểu khác với kiểu của biểu thức, và muốn người đọc thấy rõ điều đó:

double ratio = compute_ratio();            // trong [0, 1)
auto index = static_cast<std::size_t>(ratio * table.size());   // rõ ràng là đang cắt phần thập phân
float gain = static_cast<float>(calc_gain_double());           // cố ý giảm độ chính xác

So với std::size_t index = ratio * table.size();, cách viết với static_cast cho người đọc biết việc chuyển kiểu là có chủ đích chứ không phải sơ suất.

Ý chínhÝ chính của Item 6
  • Proxy class "vô hình" có thể khiến auto suy ra kiểu khác với kiểu người viết nghĩ tới.
  • Explicitly typed initializer idiom (auto x = static_cast<T>(expr);) buộc auto có đúng kiểu mong muốn, đồng thời ghi rõ ý định khi chuyển kiểu.
Tự kiểm traVì sao `bool b = flags()[0];` an toàn còn `auto b = flags()[0];` thì không, với `std::vector flags();`?

Bản bool chuyển proxy sang giá trị ngay trong câu lệnh. Bản auto giữ lại proxy, mà proxy trỏ vào vector tạm đã bị hủy cuối câu lệnh.

Tự kiểm traNếu `flags` là một biến `std::vector` (không phải hàm trả về object tạm), `auto b = flags[0];` có vấn đề gì?

Không treo, vì flags còn sống. Nhưng b là proxy, không phải bản sao: sửa b = true sẽ sửa phần tử trong vector, và nếu flags thay đổi kích thước thì proxy có thể bị vô hiệu. Hành vi khác hẳn bool b.

Item 7 · Phân biệt () và {} khi tạo object Đọc kỹ tr. 49 · PDF 67

Quá nhiều cách khởi tạo

Trong C++11 có thể khởi tạo một biến bằng dấu ngoặc tròn, dấu bằng, hoặc dấu ngoặc nhọn:

int a(0);       // ngoặc tròn
int b = 0;      // dấu bằng
int c{0};       // ngoặc nhọn
int d = {0};    // dấu bằng + ngoặc nhọn (thường được xử lý giống c{0})

Với kiểu cơ bản, khác biệt chỉ là hình thức. Với class thì khác: dấu = trong khai báo gọi copy constructor (hoặc move), còn dấu = trong câu lệnh riêng là assignment:

Sensor s1;          // default constructor
Sensor s2 = s1;     // copy constructor (không phải phép gán)
s1 = s2;            // copy assignment operator

Để có một cú pháp dùng được ở mọi nơi, C++11 đưa ra uniform initialization (khởi tạo thống nhất) dựa trên dấu ngoặc nhọn, gọi là braced initialization.

Những chỗ chỉ {} làm được

std::vector<int> v{1, 3, 5};          // khởi tạo container với danh sách giá trị

class Uart {
    uint32_t baud_{115200};           // OK: giá trị mặc định cho thành viên
    uint8_t  stop_bits_ = 1;          // OK
    uint8_t  parity_(0);              // lỗi: ngoặc tròn không dùng được ở đây
};

std::atomic<int> a1{0};               // OK
std::atomic<int> a2(0);               // OK
std::atomic<int> a3 = 0;              // lỗi trước C++17: atomic không copy được

{} là cú pháp duy nhất dùng được ở cả ba ngữ cảnh: khởi tạo thành viên trong class, khởi tạo object không copy được, và khởi tạo container theo danh sách. Đó là lý do nó được gọi là "uniform".

Ưu điểm 1: cấm narrowing conversion

Narrowing là chuyển đổi có thể làm mất thông tin, ví dụ double sang int, hay int sang uint8_t khi giá trị không vừa. Với {}, compiler từ chối narrowing; với () và = thì không:

double gain = 2.7;
int g1(gain);           // OK, âm thầm cắt thành 2
int g2 = gain;          // OK, âm thầm cắt
int g3{gain};           // lỗi compile: narrowing từ double sang int

uint8_t duty{300};      // lỗi compile: 300 không vừa uint8_t
uint8_t duty2{200};     // OK: hằng số vừa với kiểu đích
int32_t raw = read_adc();
uint16_t sample{raw};   // lỗi compile: int32_t → uint16_t có thể mất dữ liệu
Góc EmbeddedÁp dụng

Trong firmware, chuyển đổi số nguyên âm thầm là nguồn bug thường gặp (giá trị thanh ghi bị cắt, số âm thành số dương lớn). Khởi tạo bằng {} biến chúng thành lỗi compile. Khi thực sự cần cắt, viết static_cast để ghi rõ ý định.

Ưu điểm 2: không bị "most vexing parse"

C++ có một quy tắc: thứ gì đọc được như một khai báo thì là một khai báo. Hệ quả nổi tiếng:

Timer t1(10);   // tạo Timer với đối số 10
Timer t2();     // KHÔNG tạo object: đây là khai báo một HÀM tên t2, trả về Timer
Timer t3{};     // tạo Timer bằng default constructor

Lỗi này gọi là most vexing parse. {} không bao giờ bị hiểu nhầm thành khai báo hàm.

Nhược điểm: std::initializer_list được ưu tiên quá mức

Nếu {} tốt như vậy, tại sao không dùng ở mọi nơi? Vì nó có những hành vi bất ngờ, đến từ mối quan hệ giữa braced initializer, std::initializer_list và overload resolution của constructor.

Bất ngờ thứ nhất bạn đã gặp ở Item 2: auto x{…} hay auto x = {…} có thể suy ra initializer_list.

Bất ngờ thứ hai: khi một class có constructor nhận std::initializer_list, khởi tạo bằng {} sẽ ưu tiên constructor đó một cách cực đoan. Không có constructor initializer_list thì () và {} gọi cùng một constructor:

class Pwm {
public:
    Pwm(int channel, bool inverted);
    Pwm(int channel, double duty);
};
Pwm p1(1, true);    // gọi constructor thứ nhất
Pwm p2{1, true};    // cũng gọi constructor thứ nhất
Pwm p3(1, 0.5);     // gọi constructor thứ hai
Pwm p4{1, 0.5};     // cũng gọi constructor thứ hai

Thêm một constructor nhận initializer_list:

class Pwm {
public:
    Pwm(int channel, bool inverted);
    Pwm(int channel, double duty);
    Pwm(std::initializer_list<long double> duties);   // mới thêm
};
Pwm p1(1, true);    // vẫn gọi constructor thứ nhất
Pwm p2{1, true};    // giờ gọi constructor initializer_list! (1 và true được chuyển sang long double)
Pwm p3(1, 0.5);     // vẫn gọi constructor thứ hai
Pwm p4{1, 0.5};     // gọi constructor initializer_list

Compiler chọn constructor initializer_list bất cứ khi nào có thể chuyển đổi các phần tử sang kiểu của danh sách, kể cả khi constructor khác khớp hoàn hảo. Thậm chí nếu việc chuyển đổi là narrowing (bị cấm), compiler vẫn chọn constructor đó rồi báo lỗi, chứ không lùi về constructor khác:

class Pwm {
public:
    Pwm(int channel, bool inverted);
    Pwm(int channel, double duty);
    Pwm(std::initializer_list<bool> flags);
};
Pwm p{1, 0.5};      // lỗi: chọn initializer_list<bool>, nhưng 1 và 0.5 → bool là narrowing

Chỉ khi không có cách nào chuyển các phần tử sang kiểu danh sách (ví dụ initializer_list<std::string> với đối số số nguyên), compiler mới quay lại overload resolution bình thường.

Trường hợp {} rỗng

{} rỗng nghĩa là "không có đối số", nên gọi default constructor, không phải constructor initializer_list với danh sách rỗng. Muốn truyền danh sách rỗng thì viết thêm một lớp ngoặc:

Pwm a{};      // default constructor
Pwm b({});    // initializer_list rỗng
Pwm c{{}};    // initializer_list rỗng

Ví dụ thực tế ảnh hưởng nhiều nhất: std::vector

std::vector<int> có constructor (size, value) và constructor initializer_list<int>:

std::vector<int> a(10, 20);   // 10 phần tử, tất cả bằng 20
std::vector<int> b{10, 20};   // 2 phần tử: 10 và 20

Đây là ví dụ hay được hỏi trong phỏng vấn.

Bài học cho người viết class và người viết template

  • Người viết class: nếu thêm constructor initializer_list vào một class đã có người dùng, code đang dùng {} của họ có thể âm thầm đổi sang gọi constructor mới. Hãy thiết kế để () và {} không cho kết quả khác nhau khi có thể, hoặc thêm constructor initializer_list ngay từ đầu.
  • Người dùng class: chọn một kiểu làm mặc định ({} cho an toàn narrowing, hoặc () cho tương thích C++98) và chỉ dùng kiểu kia khi cần.
  • Người viết template: khi tạo object bên trong template từ các đối số được chuyển tiếp, phải chọn () hoặc {}, và kết quả có thể khác nhau tùy kiểu. std::make_unique và std::make_shared của thư viện chuẩn chọn () và ghi rõ trong tài liệu.
template<typename T, typename... Args>
T build(Args&&... args) {
    T a(std::forward<Args>(args)...);   // vector<int>(10, 20): 10 phần tử
    T b{std::forward<Args>(args)...};   // vector<int>{10, 20}: 2 phần tử
    return a;
}
Ý chínhÝ chính của Item 7
  • {} dùng được ở mọi ngữ cảnh khởi tạo, cấm narrowing và không bị most vexing parse.
  • Khi có constructor std::initializer_list, {} ưu tiên nó gần như tuyệt đối, kể cả khi constructor khác khớp tốt hơn.
  • std::vector<int>(10, 20) và std::vector<int>{10, 20} cho kết quả hoàn toàn khác nhau.
  • Trong template, chọn () hay {} để tạo object là quyết định thiết kế cần ghi tài liệu.
Tự kiểm tra`uint8_t level{adc_raw >> 4};` với `uint16_t adc_raw` có compile không?

Không: biểu thức có kiểu int (sau integer promotion) và không phải hằng số, chuyển sang uint8_t là narrowing. Viết uint8_t level = static_cast<uint8_t>(adc_raw >> 4); để ghi rõ việc cắt bit.

Tự kiểm tra`std::vector v{3, "x"};` tạo gì? Còn `std::vector w(3, "x");`?

w(3, "x"): 3 chuỗi "x". Với v{3, "x"}: compiler thử initializer_list<std::string> trước, nhưng 3 không chuyển được sang std::string, nên quay về overload thường và cũng tạo 3 chuỗi "x". Đây là trường hợp hiếm mà hai cách cho cùng kết quả.

Tự kiểm tra`Timer t();` rồi `t.start();` báo lỗi gì? Vì sao?

t là khai báo một hàm trả về Timer, không phải object, nên t.start() lỗi (không có thành viên của một hàm). Sửa bằng Timer t; hoặc Timer t{};.

Item 8 · Ưu tiên nullptr thay cho 0 và NULL Đọc kỹ tr. 58 · PDF 76

Vấn đề: 0 và NULL không phải con trỏ

Literal 0 có kiểu int. C++ cho phép dùng nó ở chỗ cần con trỏ, nhưng đó là quy tắc "miễn cưỡng": nó vẫn là int. NULL cũng vậy: implementation có thể định nghĩa nó là 0, 0L, hay một hằng số nguyên khác, nhưng không phải kiểu con trỏ.

Vấn đề lộ ra khi có overload giữa kiểu số nguyên và kiểu con trỏ:

void log_value(int v);
void log_value(bool v);
void log_value(void* p);

log_value(0);        // gọi log_value(int), không phải void*
log_value(NULL);     // có thể gọi log_value(int), hoặc báo mơ hồ; không bao giờ gọi void*

Người viết log_value(NULL) muốn gọi bản con trỏ, nhưng không bao giờ được như ý. Vì lý do này, hướng dẫn C++98 là tránh overload giữa số nguyên và con trỏ, và hướng dẫn đó vẫn còn giá trị trong C++11.

nullptr

nullptr có kiểu std::nullptr_t, một kiểu đặc biệt chuyển ngầm được sang mọi kiểu con trỏ (và con trỏ thành viên), nhưng không chuyển sang số nguyên:

log_value(nullptr);  // gọi log_value(void*)
int n = nullptr;     // lỗi compile

Rõ ràng hơn khi đọc code

auto result = find_device(id);
if (result == 0) { }         // result là con trỏ hay số? Không rõ
if (result == nullptr) { }   // rõ ràng là con trỏ

Lý do quan trọng nhất: template

Với template, 0 và NULL bị suy ra là kiểu số nguyên, nên không còn dùng được làm con trỏ null khi được chuyển tiếp qua template. Xét một hàm khóa mutex rồi gọi hàm xử lý với một con trỏ:

int  handle_a(std::shared_ptr<Frame> f);
bool handle_b(std::unique_ptr<Frame> f);
void handle_c(Frame* f);

template<typename Func, typename Ptr>
decltype(auto) locked_call(Func func, std::mutex& m, Ptr ptr) {
    std::lock_guard<std::mutex> g(m);
    return func(ptr);
}

locked_call(handle_a, m, 0);        // lỗi: Ptr = int, không chuyển được int sang shared_ptr
locked_call(handle_b, m, NULL);     // lỗi: Ptr = int hoặc long
locked_call(handle_c, m, nullptr);  // OK: Ptr = std::nullptr_t, chuyển được sang Frame*

Gọi trực tiếp handle_a(0) thì được, vì literal 0 có quy tắc đặc biệt. Nhưng khi đi qua template, 0 đã thành một biến int bình thường, và một biến int không chuyển được sang con trỏ. nullptr không gặp vấn đề này vì kiểu của nó vẫn là "con trỏ null".

MCU / bare-metalLiên hệ với C

Code C cho MCU dùng NULL khắp nơi. Khi chuyển sang C++ hoặc viết lớp C++ bọc API C, hãy dùng nullptr ở phía C++. Lưu ý trên Cortex-M, địa chỉ 0 là địa chỉ hợp lệ (đầu Flash), nên con trỏ null không gây crash khi đọc (xem Module 1). nullptr không thay đổi điều này, nhưng giúp code nói rõ ý định.

Ý chínhÝ chính của Item 8
  • Dùng nullptr thay vì 0 hoặc NULL.
  • Tránh overload giữa kiểu số nguyên và kiểu con trỏ.
Tự kiểm traVì sao `locked_call(handle_a, m, 0)` lỗi trong khi `handle_a(0)` gọi trực tiếp thì được?

Literal 0 được phép chuyển thành con trỏ null. Qua template, Ptr được suy ra là int, ptr là một biến int bình thường, không còn là literal, nên không chuyển sang con trỏ được.

Item 9 · Ưu tiên alias declaration thay cho typedef Lướt tr. 63 · PDF 81

Cú pháp using

C++11 có alias declaration, làm cùng việc với typedef nhưng dễ đọc hơn, nhất là với con trỏ hàm:

typedef void (*IrqHandler)(uint32_t);   // C/C++98: tên nằm giữa
using IrqHandler = void (*)(uint32_t);  // C++11: tên = kiểu, đọc từ trái sang phải

typedef std::unique_ptr<std::unordered_map<std::string, std::string>> UPtrMapSS;
using UPtrMapSS = std::unique_ptr<std::unordered_map<std::string, std::string>>;

Lý do thực sự: alias template

Alias declaration template hóa được, typedef thì không. Giả sử bạn có một allocator từ memory pool và muốn một tên ngắn cho "list dùng pool allocator, với kiểu phần tử bất kỳ":

template<typename T>
using PoolList = std::list<T, PoolAllocator<T>>;   // alias template

PoolList<Packet> rx_queue;                          // gọn

Với typedef, phải bọc trong một struct template:

template<typename T>
struct PoolListT {
    typedef std::list<T, PoolAllocator<T>> type;
};
PoolListT<Packet>::type rx_queue;                   // phải thêm ::type

Tệ hơn, khi dùng bên trong một template khác, cách typedef còn đòi thêm typename:

template<typename T>
class Driver {
    typename PoolListT<T>::type pending_;   // bắt buộc có typename
    PoolList<T> pending2_;                  // alias template: không cần
};

Lý do cần typename: PoolListT<T>::type là một dependent type (phụ thuộc tham số template T). Với một T cụ thể, ai đó có thể đã specialize PoolListT<T> mà type là một biến chứ không phải kiểu. Compiler không biết trước, nên bạn phải nói rõ "đây là một kiểu" bằng typename. Alias template thì chắc chắn là kiểu, không cần nói.

Type traits trong C++14

Thư viện <type_traits> của C++11 cung cấp các phép biến đổi kiểu dưới dạng struct có ::type (vì được viết trước khi alias template ra đời). C++14 bổ sung bản alias cho tất cả, có hậu tố _t:

std::remove_const<T>::type          // C++11:  const T → T
std::remove_const_t<T>              // C++14
std::remove_reference<T>::type      // C++11:  T& / T&& → T
std::remove_reference_t<T>          // C++14
std::add_lvalue_reference<T>::type  // C++11:  T → T&
std::add_lvalue_reference_t<T>      // C++14

C++17 thêm tiếp các biến hằng hậu tố _v: std::is_same_v<A, B> thay cho std::is_same<A, B>::value.

Ý chínhÝ chính của Item 9
  • typedef không template hóa được; alias declaration thì được.
  • Alias template không cần ::type và typename.
  • Dùng các bản _t (C++14) và _v (C++17) của type traits.
Tự kiểm traViết alias template `RegArray` cho `std::array`.

template<std::size_t N> using RegArray = std::array<volatile uint32_t, N>; (tham số template của alias có thể là giá trị, không chỉ kiểu).

Item 10 · Ưu tiên scoped enum thay cho unscoped enum Đọc kỹ tr. 67 · PDF 85

Vấn đề 1: tên enum tràn ra ngoài

Theo quy tắc chung, tên khai báo trong {} chỉ có hiệu lực trong phạm vi đó. Enum kiểu C++98 là ngoại lệ: các enumerator tràn ra phạm vi bao quanh:

enum Color { Black, White, Red };
auto White = false;            // lỗi: White đã được khai báo ở phạm vi này
enum LedState { Off, On, Blink };
enum PowerState { Off, Sleep, Run };   // lỗi: Off bị trùng

Đó là lý do code C hay đặt tiền tố: LED_OFF, PWR_OFF. C++11 có scoped enum, khai báo bằng enum class:

enum class LedState   { Off, On, Blink };
enum class PowerState { Off, Sleep, Run };   // OK
auto s = LedState::Off;                      // phải ghi rõ phạm vi

Vấn đề 2: chuyển ngầm sang số nguyên

Unscoped enum chuyển ngầm sang số nguyên (và từ đó sang số thực), cho phép những phép so sánh vô nghĩa:

enum Color { Black, White, Red };
Color c = Red;
if (c < 14.5) { }               // compile được: so sánh màu với số thực?

enum class Mode { Idle, Tx, Rx };
Mode m = Mode::Tx;
if (m < 14.5) { }               // lỗi compile
if (static_cast<int>(m) < 2) {} // muốn so sánh với số thì phải cast rõ ràng

Vấn đề 3: forward declaration

Forward declaration là khai báo tên mà chưa định nghĩa, giúp file header không phải #include định nghĩa đầy đủ, nhờ đó giảm phụ thuộc biên dịch. Scoped enum luôn forward declare được; unscoped enum chỉ được khi có ghi kiểu nền:

enum class Status;           // OK
enum OldStatus;              // lỗi
enum OldStatus : uint8_t;    // OK (C++11)

Lý do: mỗi enum có một kiểu nền (underlying type), kiểu số nguyên dùng để lưu nó. Với unscoped enum, compiler tự chọn kiểu nền vừa đủ cho các giá trị, nên phải thấy hết các giá trị mới biết kích thước. Với scoped enum, kiểu nền mặc định là int, nên compiler biết kích thước mà không cần định nghĩa.

Lợi ích thực tế: một header khai báo enum class Status; và các hàm dùng Status. Khi thêm một giá trị mới vào Status (định nghĩa nằm ở file khác), chỉ những file thực sự dùng giá trị mới phải biên dịch lại, thay vì cả hệ thống.

Chỉ định kiểu nền

Cả hai loại enum đều cho chỉ định kiểu nền, rất quan trọng trong Embedded khi enum nằm trong struct ánh xạ với frame hay thanh ghi:

enum class Cmd : uint8_t {
    Ping  = 0x01,
    Read  = 0x02,
    Write = 0x03,
};
struct __attribute__((packed)) FrameHeader {
    Cmd      cmd;     // đúng 1 byte
    uint16_t len;
};
static_assert(sizeof(FrameHeader) == 3, "layout");

Chỗ unscoped enum vẫn tiện hơn

Khi dùng enumerator làm chỉ số, unscoped enum gọn hơn vì chuyển ngầm sang số. Ví dụ truy cập các trường của một std::tuple:

using SensorInfo = std::tuple<std::string, uint32_t, float>;   // tên, id, nhiệt độ
enum InfoField { Name, Id, Temp };
SensorInfo info;
auto t = std::get<Temp>(info);                          // gọn

enum class InfoField2 { Name, Id, Temp };
auto t2 = std::get<static_cast<std::size_t>(InfoField2::Temp)>(info);   // dài dòng

Có thể viết một hàm nhỏ để chuyển enum sang kiểu nền. Hàm phải là constexpr vì kết quả dùng làm tham số template (phải biết lúc compile):

template<typename E>
constexpr std::underlying_type_t<E> to_underlying(E e) noexcept {
    return static_cast<std::underlying_type_t<E>>(e);
}
auto t3 = std::get<to_underlying(InfoField2::Temp)>(info);

C++23 đã đưa hàm này vào thư viện chuẩn với tên std::to_underlying.

Ý chínhÝ chính của Item 10
  • Enumerator của scoped enum chỉ thấy được trong enum; chỉ chuyển sang kiểu khác bằng cast.
  • Cả hai loại đều chỉ định được kiểu nền; scoped enum mặc định là int, unscoped không có mặc định.
  • Scoped enum luôn forward declare được; unscoped chỉ khi ghi rõ kiểu nền.
Tự kiểm tra`enum class Reg : uint8_t { Ctrl = 0x10 }; uint8_t addr = Reg::Ctrl;` có compile không?

Không: scoped enum không chuyển ngầm sang số nguyên. Viết static_cast<uint8_t>(Reg::Ctrl) hoặc to_underlying(Reg::Ctrl).

Tự kiểm traVì sao `enum OldStatus;` không forward declare được mà `enum class Status;` thì được?

Unscoped enum không có kiểu nền mặc định, compiler phải thấy mọi giá trị mới biết kích thước. Scoped enum mặc định kiểu nền int nên đã biết kích thước.

Item 11 · Ưu tiên deleted function thay cho private không định nghĩa Đọc kỹ tr. 74 · PDF 92

Bài toán: cấm một số cách dùng

Đôi khi bạn muốn cấm người dùng gọi một hàm. Ví dụ phổ biến nhất: cấm copy một object đại diện cho tài nguyên duy nhất (một bus SPI vật lý, một file descriptor). Compiler tự sinh copy constructor và copy assignment (Item 17), nên phải chặn chúng.

Cách của C++98

Khai báo hai hàm đó là private và không định nghĩa:

class SpiBus {
private:
    SpiBus(const SpiBus&);              // không định nghĩa
    SpiBus& operator=(const SpiBus&);   // không định nghĩa
};

Code bên ngoài gọi copy thì lỗi compile (hàm private). Code bên trong class hoặc friend gọi copy thì compile được nhưng lỗi link (không có định nghĩa), thường rất khó hiểu.

Cách của C++11: = delete

class SpiBus {
public:
    SpiBus(const SpiBus&) = delete;
    SpiBus& operator=(const SpiBus&) = delete;
};

Ưu điểm:

  • Mọi lời gọi, kể cả từ bên trong class, đều lỗi lúc compile.
  • Quy ước là khai báo deleted function ở phần public. Lý do: compiler kiểm tra quyền truy cập trước khi kiểm tra deleted. Nếu để private, thông báo lỗi có thể là "hàm này private" thay vì "hàm này đã bị xóa", gây hiểu nhầm.

Lợi thế lớn: delete được MỌI hàm

Mẹo private chỉ áp dụng cho member function. = delete áp dụng được cho mọi hàm, kể cả hàm tự do. Ứng dụng: chặn những chuyển đổi ngầm không mong muốn. Giả sử có hàm ghi một giá trị 32-bit vào thanh ghi:

void write_reg(uint8_t addr, uint32_t value);

write_reg(0x10, true);     // compile được: bool → uint32_t
write_reg(0x10, 'A');      // compile được: char → uint32_t
write_reg(0x10, 3.7);      // compile được: double → uint32_t (bị cắt thành 3)

Xóa các overload không mong muốn:

void write_reg(uint8_t addr, uint32_t value);
void write_reg(uint8_t addr, bool) = delete;
void write_reg(uint8_t addr, char) = delete;
void write_reg(uint8_t addr, double) = delete;   // chặn cả float (float → double)

write_reg(0x10, true);     // lỗi: dùng hàm đã xóa
write_reg(0x10, 3.7f);     // lỗi: float được promote sang double, khớp bản đã xóa

Deleted function vẫn tham gia overload resolution. Đó chính là cơ chế làm việc này hoạt động: compiler chọn bản khớp nhất, thấy nó đã bị xóa, và báo lỗi.

Xóa một specialization của template

Giả sử có hàm template gửi dữ liệu qua DMA từ một con trỏ, và bạn muốn cấm void* (không biết kích thước phần tử) và char* (thường là chuỗi, nên dùng hàm khác):

template<typename T>
void dma_send(const T* data, std::size_t count);

template<> void dma_send<void>(const void*, std::size_t) = delete;
template<> void dma_send<char>(const char*, std::size_t) = delete;

Với mẹo private của C++98, không thể làm vậy cho hàm template thành viên của class, vì specialization phải khai báo ở phạm vi namespace, không thể cho nó quyền truy cập khác với template gốc. = delete khai báo được ở phạm vi namespace nên không gặp vấn đề.

Ý chínhÝ chính của Item 11
  • Dùng = delete thay cho private không định nghĩa.
  • Bất kỳ hàm nào cũng xóa được, kể cả hàm tự do và specialization của template.
  • Khai báo deleted function là public để thông báo lỗi rõ hơn.
Tự kiểm traCó `void set_baud(uint32_t);` và `void set_baud(int) = delete;`. Gọi `set_baud(115200)` có compile không?

Không: literal 115200 có kiểu int, khớp chính xác với bản int đã bị xóa. Phải viết set_baud(115200u). Ví dụ này cho thấy deleted function tham gia overload resolution, nên cần cân nhắc kỹ khi xóa.

Tự kiểm traVì sao nên đặt deleted function ở `public`?

Compiler kiểm tra quyền truy cập trước khi kiểm tra deleted; để private có thể làm thông báo lỗi nói về quyền truy cập thay vì nói hàm đã bị xóa.

Item 12 · Khai báo hàm ghi đè với override Đọc kỹ tr. 79 · PDF 97

Nhắc lại: virtual function và overriding

Trong lập trình hướng đối tượng C++, class con ghi đè (override) một hàm virtual của class cha để gọi qua con trỏ hoặc tham chiếu tới class cha vẫn chạy bản của class con:

class Sensor {
public:
    virtual ~Sensor() = default;
    virtual void sample();
};
class Thermistor : public Sensor {
public:
    void sample() override;     // ghi đè
};

std::unique_ptr<Sensor> s = std::make_unique<Thermistor>();
s->sample();                    // gọi Thermistor::sample

Điều kiện để ghi đè

Muốn ghi đè thành công, hàm ở class con phải khớp tất cả điều kiện:

  1. Hàm ở class cha là virtual.
  2. Cùng tên (trừ destructor).
  3. Cùng kiểu tham số.
  4. Cùng const-ness.
  5. Kiểu trả về và exception specification tương thích.
  6. Cùng reference qualifier (điều kiện mới của C++11, giải thích bên dưới).

Sai bất kỳ điều kiện nào, hàm ở class con không ghi đè mà trở thành một hàm mới, che khuất hàm của class cha. Compiler không bắt buộc phải cảnh báo. Thử tìm lỗi trong đoạn sau:

class Base {
public:
    virtual void start();
    virtual void configure(int rate);
    virtual void read() &;
    void reset();
};
class Derived : public Base {
public:
    virtual void start() const;              // thêm const: khác chữ ký
    virtual void configure(unsigned rate);   // int → unsigned: khác kiểu tham số
    virtual void read() &&;                  // & → &&: khác reference qualifier
    virtual void reset();                    // Base::reset không virtual
};

Không hàm nào ghi đè, mà code vẫn compile. Gọi qua Base* sẽ chạy bản của Base, gây bug khó tìm.

override biến lỗi im lặng thành lỗi compile

class Derived : public Base {
public:
    void start() const override;          // lỗi: không ghi đè hàm nào
    void configure(unsigned) override;    // lỗi
    void read() && override;              // lỗi
    void reset() override;                // lỗi
};

Thêm lợi ích: khi đổi chữ ký hàm ở class cha, mọi class con có override sẽ báo lỗi, cho bạn biết chính xác những chỗ cần sửa. Không có override, bạn chỉ biết khi có bug.

override và final là contextual keyword: chỉ là từ khóa ở vị trí cuối khai báo hàm. Code cũ có biến tên override vẫn compile được.

Reference qualifier cho member function

Điều kiện thứ 6 cần giải thích. C++11 cho phép giới hạn một member function chỉ được gọi khi *this là lvalue (&) hoặc rvalue (&&), tương tự cách const giới hạn cho object hằng:

class Probe {
public:
    void run() &;    // chỉ gọi được trên lvalue
    void run() &&;   // chỉ gọi được trên rvalue
};
Probe p;
p.run();             // gọi bản &
make_probe().run();  // object tạm → gọi bản &&

Ứng dụng: một class giữ buffer lớn, có hàm trả về dữ liệu. Nếu object là lvalue, phải trả tham chiếu (hoặc copy). Nếu object là tạm sắp bị hủy, move dữ liệu ra sẽ rẻ hơn nhiều:

class Capture {
public:
    using Data = std::vector<uint16_t>;
    Data& samples() &  { return data_; }              // lvalue: trả tham chiếu
    Data  samples() && { return std::move(data_); }   // rvalue: move ra, không copy
private:
    Data data_;
};

Capture cap = record();
auto a = cap.samples();          // copy (cap còn dùng tiếp)
auto b = record().samples();     // move, không copy

Nếu chỉ có một bản Data& samples(), dòng cuối sẽ copy toàn bộ vector từ một object sắp chết.

Ý chínhÝ chính của Item 12
  • Luôn ghi override cho hàm ghi đè.
  • Reference qualifier (&, &&) cho phép xử lý khác nhau khi *this là lvalue hoặc rvalue, và là một điều kiện để ghi đè.
Tự kiểm tra`virtual void on_irq(uint32_t mask);` ở class cha, class con viết `void on_irq(uint16_t mask) override;`. Kết quả?

Lỗi compile: kiểu tham số khác (uint16_t khác uint32_t) nên không ghi đè gì cả, và override buộc compiler báo lỗi. Không có override, đây sẽ là một hàm mới và gọi qua con trỏ class cha vẫn chạy bản cũ.

Item 13 · Ưu tiên const_iterator thay cho iterator Bỏ qua tr. 86 · PDF 104

const_iterator là phiên bản "con trỏ tới hằng" của iterator: duyệt được nhưng không sửa được phần tử. Nguyên tắc "dùng const bất cứ khi nào có thể" nghĩa là: khi không cần sửa phần tử, dùng const_iterator.

Trong C++98, nguyên tắc này khó áp dụng: lấy const_iterator từ container không hằng rất vụng về, và các hàm như insert, erase chỉ nhận iterator. C++11 sửa cả hai: có cbegin()/cend(), và các hàm chèn/xóa nhận const_iterator:

std::vector<int> ids = load_ids();
auto it = std::find(ids.cbegin(), ids.cend(), 42);   // const_iterator
ids.insert(it, 41);                                   // C++11: insert nhận const_iterator

Trong code tổng quát tối đa (template phải chạy với cả container lẫn mảng C), nên dùng hàm không phải thành viên std::begin(c), std::cbegin(c) thay vì c.begin(), vì mảng C không có hàm thành viên. C++11 có std::begin/std::end; std::cbegin/std::cend có từ C++14.

Ý chínhÝ chính của Item 13
  • Dùng const_iterator khi không sửa phần tử.
  • Trong code tổng quát, ưu tiên std::begin, std::cbegin… không phải thành viên.

Item 14 · Khai báo noexcept khi hàm không ném exception Đọc kỹ tr. 90 · PDF 108

Từ C++98 đến C++11

C++98 có exception specification liệt kê các kiểu exception một hàm có thể ném (void f() throw(std::bad_alloc);). Trong thực tế chúng gây nhiều phiền phức hơn lợi ích: sửa cài đặt hàm có thể phải sửa danh sách, mà sửa danh sách có thể làm hỏng code của người gọi, và compiler không giúp kiểm tra. C++11 nhận ra thông tin thực sự có ý nghĩa chỉ là: hàm này có thể ném hay không bao giờ ném. Đó là noexcept.

int checksum(const uint8_t* p, std::size_t n) noexcept;   // hứa không ném

noexcept là một phần của interface

Người gọi có thể hỏi một hàm có noexcept không, bằng toán tử noexcept(expr) lúc compile, và đưa ra quyết định dựa trên câu trả lời. Vì vậy noexcept quan trọng ngang với const trên member function: không ghi noexcept cho một hàm bạn biết là không ném là thiết kế interface kém.

Lý do 1: compiler tối ưu tốt hơn

Khi exception thoát khỏi một hàm noexcept, chương trình gọi std::terminate. Điểm khác biệt với throw() của C++98: với noexcept, stack chỉ có thể (không bắt buộc) được unwind trước khi terminate. Điều này cho optimizer tự do hơn: không cần giữ stack ở trạng thái có thể unwind, không cần đảm bảo các object bị hủy đúng thứ tự ngược với lúc tạo nếu exception thoát ra.

Lý do 2 (quan trọng nhất): move trong container

Xét std::vector::push_back. Khi vector đầy, nó cấp phát vùng nhớ mới lớn hơn, chuyển các phần tử sang, rồi giải phóng vùng cũ. C++98 chuyển bằng copy. Cách này có strong exception guarantee: nếu copy một phần tử ném exception giữa chừng, vùng nhớ cũ còn nguyên, vector trở lại đúng trạng thái trước khi gọi push_back.

C++11 muốn dùng move thay copy để nhanh hơn. Nhưng nếu move phần tử thứ n ném exception, n−1 phần tử đầu đã bị "rút ruột" sang vùng mới, và move ngược lại cũng có thể ném. Không khôi phục được trạng thái cũ, tức là phá vỡ strong guarantee mà code cũ có thể đang dựa vào.

Giải pháp của thư viện chuẩn: chỉ move khi move constructor là noexcept, ngược lại vẫn copy. Cơ chế là std::move_if_noexcept. Nhiều hàm khác cũng hành xử vậy (vector::reserve, deque::insert…).

Hậu quả thực tế: nếu bạn viết move constructor mà quên noexcept, vector chứa class đó sẽ copy toàn bộ phần tử mỗi lần tăng dung lượng.

class Frame {
public:
    Frame(Frame&& other) noexcept               // có noexcept: vector sẽ move
        : data_{std::move(other.data_)} {}
    // ...
private:
    std::vector<uint8_t> data_;
};
static_assert(std::is_nothrow_move_constructible_v<Frame>);   // kiểm tra lúc compile

swap và conditional noexcept

swap thường được dùng trong cài đặt các thuật toán và trong copy assignment. Thư viện chuẩn khai báo swap noexcept có điều kiện: noexcept khi các phép swap bên trong noexcept:

template<class T, std::size_t N>
void swap(T (&a)[N], T (&b)[N]) noexcept(noexcept(swap(*a, *b)));

noexcept(...) bên ngoài là specifier (khai báo hàm có noexcept hay không, tùy giá trị bool bên trong); noexcept(...) bên trong là operator (hỏi biểu thức có noexcept không). Nhờ vậy, tính noexcept lan truyền từ kiểu thấp lên kiểu cao.

Đừng lạm dụng

  • Chỉ ghi noexcept khi chắc chắn lâu dài: nếu sau này cài đặt thay đổi và có thể ném, bỏ noexcept sẽ làm hỏng code người gọi đã dựa vào nó. Còn giữ noexcept thì phải bắt mọi exception bên trong, làm code phức tạp.
  • Phần lớn hàm là exception-neutral: bản thân chúng không ném, nhưng gọi hàm có thể ném và để exception đi qua. Những hàm này không nên là noexcept.
  • Mặc định đã noexcept: destructor và các hàm giải phóng bộ nhớ (operator delete) ngầm định là noexcept, trừ khi một thành viên có destructor được khai báo noexcept(false).
  • Wide và narrow contract: hàm wide contract không có tiền điều kiện (gọi với đối số nào cũng được), hợp với noexcept. Hàm narrow contract có tiền điều kiện (ví dụ "chuỗi không quá 32 ký tự"); vi phạm là UB. Người viết thư viện thường muốn hàm narrow contract ném exception khi phát hiện vi phạm trong bản debug, nên không ghi noexcept cho chúng.
  • Compiler không kiểm tra sự nhất quán: một hàm noexcept gọi hàm không noexcept vẫn compile. Đó là thiết kế có chủ ý, vì hàm được gọi có thể không ném trong ngữ cảnh đó (ví dụ hàm C).
MCU / bare-metalKhi build với -fno-exceptions

Nhiều dự án firmware tắt exception. Lúc đó lợi ích tối ưu của noexcept gần như biến mất (compiler biết không có exception nào). Nhưng type traits vẫn đọc noexcept: std::vector vẫn quyết định move hay copy dựa trên std::is_nothrow_move_constructible. Vì vậy vẫn phải ghi noexcept cho move constructor, move assignment và swap.

Ý chínhÝ chính của Item 14
  • noexcept là một phần của interface, người gọi có thể dựa vào nó.
  • Hàm noexcept được tối ưu tốt hơn.
  • Đặc biệt quan trọng cho move operation, swap, hàm giải phóng bộ nhớ và destructor.
  • Phần lớn hàm là exception-neutral, không nên ép noexcept.
Tự kiểm traMột `std::vector` tăng từ 1000 lên 2000 phần tử. `Frame` có move constructor không ghi `noexcept`. Điều gì xảy ra lúc realloc?

Vector dùng std::move_if_noexcept, thấy move có thể ném nên copy cả 1000 phần tử để giữ strong exception guarantee. Thêm noexcept thì các phần tử được move.

Tự kiểm traKhác biệt giữa `noexcept` dùng như specifier và như operator?

Specifier void f() noexcept(cond); khai báo hàm có noexcept khi cond là true. Operator noexcept(expr) là biểu thức bool lúc compile, cho biết expr có được khai báo là không ném không.

Item 15 · Dùng constexpr bất cứ khi nào có thể Đọc kỹ tr. 97 · PDF 115

constexpr cho object

Object constexpr là const và có giá trị biết được lúc compile (chính xác hơn là lúc dịch, gồm compile và link). Giá trị như vậy dùng được ở những chỗ C++ đòi hỏi integral constant expression: kích thước mảng, tham số template giá trị, giá trị enumerator, alignas…

int n = read_config();
constexpr auto a = n;         // lỗi: n không biết lúc compile
std::array<int, n> buf1;      // lỗi

constexpr auto kSize = 64;    // OK
std::array<int, kSize> buf2;  // OK

const thì không đảm bảo điều này: một object const có thể được khởi tạo bằng giá trị chỉ biết lúc chạy.

int n = read_config();
const auto c = n;             // OK: c là hằng, nhưng giá trị chỉ biết lúc chạy
std::array<int, c> buf3;      // lỗi

Tóm lại: mọi object constexpr là const, nhưng không phải mọi object const là constexpr.

constexpr cho hàm

Hàm constexpr có hành vi "hai trong một":

  • Gọi với đối số biết lúc compile và dùng ở ngữ cảnh cần hằng số: kết quả được tính lúc compile.
  • Gọi với đối số chỉ biết lúc chạy: chạy như hàm bình thường.

Nhờ vậy không cần hai bản hàm. Ví dụ tính số chia baud rate cho UART:

constexpr uint32_t uart_div(uint32_t clk_hz, uint32_t baud) noexcept {
    return (clk_hz + baud / 2) / baud;          // làm tròn
}

constexpr uint32_t kDiv = uart_div(84'000'000, 115'200);   // tính lúc compile: 729
static_assert(kDiv == 729, "sai hệ số chia");

void reconfigure(uint32_t baud_from_user) {
    UART1->BRR = uart_div(SystemCoreClock, baud_from_user);  // tính lúc chạy
}

(Dấu ' trong 84'000'000 là digit separator của C++14, chỉ để dễ đọc.)

Giới hạn của C++11 và C++14

  • C++11: thân hàm constexpr chỉ được có một câu return. Vẫn viết được nhiều thứ nhờ toán tử ?: và đệ quy:
constexpr int ipow(int base, unsigned exp) noexcept {      // C++11
    return exp == 0 ? 1 : base * ipow(base, exp - 1);
}
  • C++14: nới lỏng rất nhiều: cho phép biến cục bộ, vòng lặp, nhiều câu lệnh:
constexpr int ipow(int base, unsigned exp) noexcept {      // C++14
    int r = 1;
    for (unsigned i = 0; i < exp; ++i) r *= base;
    return r;
}
  • Tham số và kiểu trả về phải là literal type: kiểu mà giá trị có thể xác định lúc compile. Mọi kiểu cơ bản (trừ void trong C++11) là literal type. Class tự viết cũng có thể là literal type nếu constructor và các hàm thành viên liên quan là constexpr:
class Rgb {
public:
    constexpr Rgb(uint8_t r, uint8_t g, uint8_t b) noexcept : r_{r}, g_{g}, b_{b} {}
    constexpr uint16_t to565() const noexcept {
        return static_cast<uint16_t>(((r_ >> 3) << 11) | ((g_ >> 2) << 5) | (b_ >> 3));
    }
private:
    uint8_t r_, g_, b_;
};

constexpr Rgb kOrange{255, 165, 0};
constexpr uint16_t kOrange565 = kOrange.to565();   // tính lúc compile, nằm trong Flash

Trong C++11, member function constexpr ngầm định là const và không được trả void, nên không viết được setter constexpr. C++14 bỏ cả hai giới hạn.

Vì sao "bất cứ khi nào có thể"

  • Hiệu năng: chuyển việc tính toán từ lúc chạy sang lúc compile. Thời gian compile tăng một chút, chương trình chạy nhanh hơn.
  • Phạm vi dùng rộng hơn: object và hàm constexpr dùng được ở mọi nơi cần hằng số, còn non-constexpr thì không.
  • Lưu ý: constexpr là một phần của interface. Nó hứa "có thể dùng ở ngữ cảnh cần hằng số". Nếu sau này bỏ constexpr (ví dụ thêm log vào hàm), code của người dùng đang dùng hàm làm kích thước mảng sẽ hỏng. Hãy chắc chắn trước khi hứa.
Góc Embeddedconstexpr trong firmware

Đây có thể là tính năng C++ đáng giá nhất cho firmware: tính bảng tra CRC, bảng sin, mask thanh ghi, hệ số chia clock lúc compile. Kết quả nằm trong .rodata (Flash), không tốn thời gian khởi động và không tốn RAM. C++17 cho phép lambda constexpr và if constexpr; C++20 thêm consteval (bắt buộc tính lúc compile) và constinit (bắt buộc khởi tạo tĩnh, tránh "static initialization order fiasco").

constexpr std::array<uint16_t, 256> make_crc16_table() {
    std::array<uint16_t, 256> t{};
    for (unsigned i = 0; i < 256; ++i) {
        uint16_t c = static_cast<uint16_t>(i << 8);
        for (int b = 0; b < 8; ++b) c = (c & 0x8000) ? static_cast<uint16_t>((c << 1) ^ 0x1021) : static_cast<uint16_t>(c << 1);
        t[i] = c;
    }
    return t;
}
constexpr auto kCrc16Table = make_crc16_table();   // C++17: std::array::operator[] là constexpr
Ý chínhÝ chính của Item 15
  • Object constexpr là const và được khởi tạo bằng giá trị biết lúc compile.
  • Hàm constexpr cho kết quả lúc compile khi đối số biết lúc compile, và chạy như hàm thường khi không.
  • constexpr dùng được ở nhiều ngữ cảnh hơn, và là một phần của interface.
Tự kiểm tra`const int a = 10;` và `constexpr int b = 10;` khác nhau thế nào khi dùng làm kích thước `std::array`?

Trong trường hợp này cả hai đều dùng được, vì a là const int được khởi tạo bằng hằng số (quy tắc đặc biệt cho số nguyên). Nhưng const int c = read(); thì không dùng được, còn constexpr int d = read(); sẽ lỗi ngay ở khai báo. constexpr đảm bảo và kiểm tra điều đó; const thì không.

Tự kiểm traHàm `constexpr` có chắc chắn được tính lúc compile không?

Không. Chỉ khi đối số là hằng compile-time và kết quả được dùng ở ngữ cảnh cần hằng (hoặc compiler chọn tính sớm). Muốn bắt buộc, gán kết quả cho biến constexpr, hoặc dùng consteval (C++20).

Item 16 · Làm cho const member function thread-safe Lướt tr. 103 · PDF 121

Bối cảnh: mutable cache

Một const member function có thể cần sửa dữ liệu nội bộ không thuộc "trạng thái logic" của object, ví dụ một cache kết quả tính toán tốn kém. Từ khóa mutable cho phép điều đó:

class Calibration {
public:
    float coefficient() const {
        if (!valid_) {
            cached_ = expensive_fit(raw_);   // sửa trong hàm const
            valid_ = true;
        }
        return cached_;
    }
private:
    std::vector<float> raw_;
    mutable float cached_ = 0;
    mutable bool  valid_ = false;
};

Vấn đề: người dùng tin rằng const là an toàn khi đọc đồng thời

Về mặt khái niệm, gọi const member function là thao tác đọc. Nhiều thread cùng đọc một object mà không khóa là chuyện bình thường. Nhưng ở đây, hai thread cùng gọi coefficient() sẽ cùng ghi cached_ và valid_ mà không đồng bộ: đó là data race, undefined behavior.

Giải pháp

Mutex khi cần bảo vệ nhiều biến hoặc nhiều vùng nhớ như một khối:

float coefficient() const {
    std::lock_guard<std::mutex> g(m_);
    if (!valid_) { cached_ = expensive_fit(raw_); valid_ = true; }
    return cached_;
}
mutable std::mutex m_;   // mutable: lock/unlock là thao tác không const

std::atomic khi chỉ có một biến cần bảo vệ, thường rẻ hơn mutex. Ví dụ đếm số lần gọi:

mutable std::atomic<unsigned> calls_{0};
float value() const { ++calls_; return v_; }

Nhưng đừng dùng nhiều atomic riêng lẻ cho các biến phải cập nhật cùng nhau. Với cache ở trên, nếu cached_ và valid_ đều là atomic:

  • Nếu set valid_ = true trước khi ghi cached_: thread khác có thể thấy valid_ true và đọc cached_ cũ (sai).
  • Nếu ghi cached_ trước rồi mới set valid_: đúng, nhưng nhiều thread có thể cùng tính expensive_fit (lãng phí).

Hai biến liên quan với nhau cần một mutex.

Tác dụng phụ

std::mutex và std::atomic đều không copy và không move được. Thêm chúng vào class sẽ làm class mất khả năng copy/move (trừ khi tự viết các hàm đó).

Ý chínhÝ chính của Item 16
  • Làm const member function thread-safe, trừ khi chắc chắn object không bao giờ dùng đồng thời.
  • std::atomic có thể nhanh hơn mutex, nhưng chỉ phù hợp cho một biến hoặc một vùng nhớ.
Tự kiểm traVì sao `std::mutex` trong class phải khai báo `mutable` để dùng trong hàm `const`?

Trong hàm const, mọi thành viên được coi là const. lock() và unlock() không phải hàm const, nên phải đánh dấu mutex là mutable.

Special member function là gì

Đây là những hàm thành viên mà compiler có thể tự sinh nếu bạn không viết. C++98 có bốn: default constructor, destructor, copy constructor, copy assignment operator. C++11 thêm hai: move constructor và move assignment operator.

class Buffer {
public:
    Buffer(Buffer&& rhs);              // move constructor
    Buffer& operator=(Buffer&& rhs);   // move assignment
};

Các hàm tự sinh là public, inline, và không virtual (trừ destructor của class con khi class cha có virtual destructor).

Hàm move tự sinh làm gì

Move constructor tự sinh move từng thành viên non-static (và từng class cha) từ rhs. Move assignment tương tự. Chính xác hơn, đó là yêu cầu move: thành viên nào hỗ trợ move thì được move, thành viên nào không (kiểu C++98 không có move) thì được copy. Cơ chế là áp std::move lên từng thành viên rồi overload resolution chọn move hay copy.

Quy tắc sinh: điểm khác biệt quan trọng nhất

Hai hàm copy độc lập với nhau: khai báo copy constructor không ngăn compiler sinh copy assignment, và ngược lại (như C++98).

Hai hàm move không độc lập: khai báo một trong hai thì compiler không sinh cái còn lại. Lý do: nếu bạn tự viết move constructor, nghĩa là cách move mặc định (move từng thành viên) không phù hợp với class này, vậy rất có thể move assignment mặc định cũng không phù hợp.

Thêm nữa, khai báo copy operation thì compiler không sinh move. Lý do tương tự: bạn đã nói cách copy mặc định không phù hợp, nên cách move mặc định có lẽ cũng không. Và ngược lại, khai báo move operation thì copy operation bị xóa (= delete).

Cuối cùng là Rule of Three của C++98: nếu bạn phải tự viết một trong ba hàm destructor, copy constructor, copy assignment, thì gần như chắc chắn bạn cần cả ba, vì cả ba đều liên quan tới việc quản lý một tài nguyên. C++11 áp dụng một phần quy tắc này: khai báo destructor thì compiler không sinh move.

Bảng tổng hợp, áp dụng cho C++11 trở đi:

Hàm Được compiler sinh khi
Default constructor Class không khai báo constructor nào
Destructor Không khai báo destructor. Tự sinh là noexcept; là virtual nếu class cha có virtual destructor
Copy constructor Không khai báo copy constructor. Bị xóa nếu class khai báo move operation. Việc sinh khi có destructor hoặc copy assignment tự khai báo là deprecated
Copy assignment Không khai báo copy assignment. Bị xóa nếu class khai báo move operation. Việc sinh khi có destructor hoặc copy constructor tự khai báo là deprecated
Move constructor và move assignment Class không khai báo: copy operation nào, move operation nào, destructor

Bẫy kinh điển: thêm destructor làm mất move

class Telemetry {
public:
    ~Telemetry() { log("telemetry destroyed"); }   // chỉ thêm log để debug
private:
    std::vector<Sample> samples_;
    std::string device_;
};

std::vector<Telemetry> all;
all.push_back(make_telemetry());   // trước đây: move. Bây giờ: COPY toàn bộ samples_

Do khai báo destructor, compiler không sinh move constructor. Code vẫn compile vì copy constructor vẫn được sinh (deprecated nhưng hợp lệ), và rvalue gắn được với const Telemetry&. Mọi "move" âm thầm thành copy, hiệu năng giảm mạnh mà không ai biết.

Giải pháp: = default

Khi khai báo một special member function, hãy khai báo rõ cả những cái khác, dùng = default nếu cài đặt mặc định là đúng:

class Telemetry {
public:
    Telemetry() = default;
    ~Telemetry() { log("telemetry destroyed"); }
    Telemetry(const Telemetry&) = default;
    Telemetry& operator=(const Telemetry&) = default;
    Telemetry(Telemetry&&) noexcept = default;
    Telemetry& operator=(Telemetry&&) noexcept = default;
};

Đây là Rule of Five: khai báo một trong năm hàm (destructor, copy constructor, copy assignment, move constructor, move assignment) thì khai báo cả năm.

Tốt hơn nữa là Rule of Zero: thiết kế class sao cho không cần viết hàm nào. Dùng các thành viên tự quản lý tài nguyên (std::vector, std::string, std::unique_ptr với custom deleter) để các hàm tự sinh làm đúng việc. Chỉ những class "quản lý tài nguyên cấp thấp" mới cần viết các hàm này.

Member function template không ảnh hưởng

Một constructor template hay assignment template không bao giờ ngăn việc sinh special member function, kể cả khi nó có thể nhận đúng kiểu của class:

class Config {
    template<typename T> Config(const T& rhs);        // nhận mọi kiểu, kể cả Config
    template<typename T> Config& operator=(const T&);
};   // compiler vẫn sinh copy và move cho Config

Góc EmbeddedÁp dụng: class quản lý tài nguyên phần cứng

Class bọc một kênh DMA, một handle I2C hay một vùng nhớ trong pool thường là move-only: không copy được (tài nguyên là duy nhất), nhưng move được (chuyển quyền sở hữu). Mẫu chuẩn:

class DmaChannel {
public:
    explicit DmaChannel(int ch) : ch_{dma_acquire(ch)} {}
    ~DmaChannel() { if (ch_ >= 0) dma_release(ch_); }
    DmaChannel(const DmaChannel&) = delete;
    DmaChannel& operator=(const DmaChannel&) = delete;
    DmaChannel(DmaChannel&& o) noexcept : ch_{std::exchange(o.ch_, -1)} {}
    DmaChannel& operator=(DmaChannel&& o) noexcept {
        if (this != &o) { if (ch_ >= 0) dma_release(ch_); ch_ = std::exchange(o.ch_, -1); }
        return *this;
    }
private:
    int ch_;
};

std::exchange(a, b) (C++14) gán b vào a và trả về giá trị cũ của a: rất tiện để "lấy rồi xóa" khi move. Object bị move được đặt về -1 để destructor của nó không giải phóng kênh.

Ý chínhÝ chính của Item 17
  • Special member function là các hàm compiler có thể tự sinh: default constructor, destructor, copy operation, move operation.
  • Move operation chỉ được sinh khi class không khai báo copy operation, move operation và destructor.
  • Copy operation bị xóa khi class khai báo move operation; việc sinh copy khi có destructor tự khai báo là deprecated.
  • Member function template không bao giờ ngăn việc sinh special member function.

Move được (move tự sinh, move từng thành viên). Copy không được: copy constructor được sinh nhưng bị định nghĩa là deleted vì unique_ptr không copy được.

Không còn move operation tự sinh, vì đã khai báo destructor (kể cả = default). "Move" sẽ thành copy nếu copy được. Phải khai báo thêm Widget(Widget&&) = default; và move assignment.

Vì sao con trỏ thô khó dùng đúng

Con trỏ thô (T*) mạnh nhưng mang rất ít thông tin. Nhìn vào khai báo Frame* p, bạn không biết:

  1. Nó trỏ tới một object hay một mảng?
  2. Nó có sở hữu object không, tức là ai chịu trách nhiệm giải phóng?
  3. Nếu phải giải phóng, giải phóng bằng cách nào: delete, delete[], free, hay một hàm riêng như pool_release(p)?
  4. Nếu là delete, dùng dạng đơn hay dạng mảng? Dùng sai là undefined behavior.
  5. Làm sao đảm bảo giải phóng đúng một lần trên mọi đường đi của code, kể cả khi có return sớm hay exception? Sót thì rò rỉ, thừa thì UB.
  6. Con trỏ có đang treo (dangling) không, tức object đã bị hủy nhưng con trỏ vẫn trỏ tới?

Smart pointer là class bọc con trỏ thô, hành xử giống con trỏ (*, ->), nhưng mã hóa các thông tin trên vào kiểu và tự động giải phóng đúng lúc, đúng cách. Đây là ứng dụng trực tiếp của RAII (Resource Acquisition Is Initialization): tài nguyên gắn với vòng đời của một object; object bị hủy thì tài nguyên được giải phóng, và C++ đảm bảo destructor chạy trên mọi đường thoát khỏi scope.

C++11 có bốn smart pointer:

  • std::auto_ptr: di sản C++98, đã bị loại bỏ (removed trong C++17). Do C++98 không có move semantics, nó "mượn" phép copy để chuyển quyền sở hữu: copy một auto_ptr sẽ biến bản gốc thành null. Hành vi kỳ lạ này khiến không thể bỏ nó vào container. Thay bằng std::unique_ptr trong mọi trường hợp.
  • std::unique_ptr: sở hữu độc quyền.
  • std::shared_ptr: sở hữu chia sẻ.
  • std::weak_ptr: quan sát một object do shared_ptr quản lý mà không sở hữu.

Mặc định nên chọn unique_ptr

Khi cần một smart pointer, hãy nghĩ tới std::unique_ptr đầu tiên. Lý do:

  • Kích thước bằng con trỏ thô (với deleter mặc định), và các thao tác như dereference dịch ra đúng các lệnh của con trỏ thô. Bạn có thể dùng nó ngay cả khi bộ nhớ và chu kỳ CPU rất quý.
  • Ngữ nghĩa sở hữu độc quyền: một unique_ptr khác null luôn sở hữu object nó trỏ tới. Move một unique_ptr chuyển quyền sở hữu sang đích, nguồn thành null. Không copy được: nếu copy được, sẽ có hai unique_ptr cùng sở hữu một object và cùng giải phóng nó.
  • Khi bị hủy, nó giải phóng object (mặc định bằng delete).

Ứng dụng điển hình: factory function

Một factory function tạo object trên heap và trả về cho người gọi. Ví dụ: tạo driver phù hợp với loại cảm biến đọc được từ EEPROM:

class SensorDriver { public: virtual ~SensorDriver() = default; virtual float read() = 0; };
class Bme280 : public SensorDriver { /* ... */ };
class Sht31  : public SensorDriver { /* ... */ };

std::unique_ptr<SensorDriver> make_driver(SensorType type, I2cBus& bus) {
    switch (type) {
    case SensorType::Bme280: return std::make_unique<Bme280>(bus);
    case SensorType::Sht31:  return std::make_unique<Sht31>(bus);
    }
    return nullptr;
}

{
    auto drv = make_driver(read_type_from_eeprom(), bus);   // drv sở hữu driver
    float t = drv->read();
}   // drv bị hủy → driver bị delete, kể cả khi read() ném exception

Người gọi nhận quyền sở hữu, không phải nhớ delete. Đổi kiểu trả về thành SensorDriver* thì người gọi phải tự lo giải phóng, và mọi lỗi ở 6 câu hỏi trên lại xuất hiện.

Lưu ý: class cha phải có virtual destructor, vì unique_ptr<SensorDriver> gọi delete qua con trỏ class cha. Không có virtual destructor thì destructor của class con không chạy, đó là UB.

Custom deleter

Mặc định unique_ptr giải phóng bằng delete. Có thể truyền deleter riêng: bất kỳ thứ gì gọi được với con trỏ. Kiểu deleter là tham số template thứ hai của unique_ptr:

auto close_file = [](std::FILE* f) { if (f) std::fclose(f); };
std::unique_ptr<std::FILE, decltype(close_file)> log_file{std::fopen("/var/log/app.log", "a"), close_file};

Đây là cách bọc mọi loại tài nguyên có cặp hàm lấy/trả, không chỉ bộ nhớ: file, handle của HAL, khối trong memory pool, socket.

Một số quy tắc:

  • Deleter nhận con trỏ thô và chịu trách nhiệm toàn bộ việc giải phóng.
  • unique_ptr không nhận con trỏ thô qua phép gán ngầm (std::unique_ptr<T> p = raw; lỗi), để tránh vô tình chuyển quyền sở hữu. Phải dùng constructor tường minh, hoặc reset(raw).

Kích thước phụ thuộc deleter

Deleter Kích thước unique_ptr (trên máy 32-bit)
Mặc định (std::default_delete) 4 byte, bằng con trỏ thô
Lambda không capture 4 byte (closure rỗng, không tốn chỗ)
Con trỏ hàm 8 byte (lưu thêm con trỏ hàm)

Lambda không capture được ưu tiên hơn con trỏ hàm vì không tốn thêm bộ nhớ và gọi trực tiếp (dễ inline).

Hai dạng: object và mảng

std::unique_ptr<T> cho một object; std::unique_ptr<T[]> cho mảng (dùng delete[], có operator[], không có * và ->). Trong thực tế hiếm khi cần dạng mảng vì std::array, std::vector hay std::string hầu như luôn tốt hơn. Ngoại lệ hợp lý là khi nhận một mảng cấp phát bởi API kiểu C.

Chuyển sang shared_ptr dễ dàng

std::shared_ptr<SensorDriver> shared = make_driver(type, bus);   // chuyển từ unique_ptr

Đây là lý do unique_ptr là kiểu trả về lý tưởng cho factory: factory không biết người gọi muốn sở hữu độc quyền hay chia sẻ; trả unique_ptr thì người gọi tự chọn, chi phí bằng 0 nếu họ chọn độc quyền.

struct PoolReturn { void operator()(RxBuffer* b) const noexcept { rx_pool.release(b); } };
using RxBufferPtr = std::unique_ptr<RxBuffer, PoolReturn>;   // stateless: kích thước = 1 con trỏ

RxBufferPtr acquire_rx() { return RxBufferPtr{rx_pool.acquire()}; }

    auto buf = acquire_rx();

    if (!parse(*buf)) return;          // return sớm: buffer vẫn được trả về pool

Item 19 · Dùng std::shared_ptr cho sở hữu chia sẻ Lướt tr. 125 · PDF 143

Ý tưởng: không ai sở hữu một mình

Một số object có vòng đời không thuộc về một chủ duy nhất: ví dụ một bản cấu hình được nhiều module cùng dùng, sống cho đến khi module cuối cùng thôi dùng. std::shared_ptr cho phép nhiều con trỏ cùng sở hữu; object bị hủy khi shared_ptr cuối cùng trỏ tới nó bị hủy hoặc trỏ sang chỗ khác.

Cơ chế là reference count (bộ đếm tham chiếu): số shared_ptr đang trỏ tới object. Constructor tăng bộ đếm, destructor giảm, copy assignment a = b giảm bộ đếm của object a đang trỏ và tăng của object b trỏ. Khi bộ đếm về 0, object bị hủy.

Chi phí

Reference count có ba hệ quả về hiệu năng:

  • Kích thước gấp đôi con trỏ thô: một con trỏ tới object, một con trỏ tới control block chứa bộ đếm.
  • Bộ nhớ cho control block phải cấp phát động (thường trên heap).
  • Tăng giảm bộ đếm là thao tác atomic, vì nhiều thread có thể cùng copy và hủy các shared_ptr trỏ tới cùng object. Atomic chậm hơn thao tác thường (trên ARM là vòng LDREX/STREX kèm barrier).

Move một shared_ptr thì không cần thay đổi bộ đếm (nguồn thành null, đích nhận con trỏ), nên move nhanh hơn copy.

Control block

Control block chứa: reference count, weak count (cho weak_ptr, Item 20), bản sao của custom deleter và allocator nếu có.

shared_ptr<T>                         Object T
┌───────────────┐                  ┌────────────┐
│ ptr tới T     │ ───────────────▶ │            │
│ ptr tới CB    │ ──┐              └────────────┘
└───────────────┘   │   Control block
                    └─▶ ┌──────────────────────┐
                        │ reference count      │
                        │ weak count           │
                        │ deleter, allocator…  │
                        └──────────────────────┘

Khác với unique_ptr, kiểu của deleter không thuộc kiểu của shared_ptr: deleter được lưu trong control block. Nhờ vậy, hai shared_ptr<Frame> dùng deleter khác nhau vẫn cùng kiểu, có thể gán cho nhau và bỏ chung một container. Kích thước shared_ptr không đổi theo deleter.

Control block được tạo trong các trường hợp:

  1. std::make_shared (luôn tạo object mới nên luôn tạo control block mới).
  2. Tạo shared_ptr từ unique_ptr (unique_ptr không có control block).
  3. Tạo shared_ptr từ con trỏ thô.

Tạo từ một shared_ptr hoặc weak_ptr khác thì dùng chung control block có sẵn.

Bẫy 1: hai control block cho một object

Từ quy tắc 3 suy ra: tạo hai shared_ptr từ cùng một con trỏ thô sẽ có hai control block, hai bộ đếm, và object bị hủy hai lần:

auto raw = new Session(cfg);
std::shared_ptr<Session> a(raw);
std::shared_ptr<Session> b(raw);    // control block thứ hai → hủy hai lần: UB

Bài học: tránh tạo shared_ptr từ biến con trỏ thô. Dùng std::make_shared. Nếu bắt buộc (cần custom deleter), truyền thẳng kết quả của new: std::shared_ptr<Session> a(new Session(cfg), deleter);.

Bẫy 2: shared_ptr từ this

Một trường hợp bất ngờ hơn: object muốn đăng ký chính nó vào một danh sách các shared_ptr:

std::vector<std::shared_ptr<Session>> active;

void Session::activate() {
    active.emplace_back(this);    // tạo control block mới từ this!
}

Nếu ngoài kia đã có shared_ptr quản lý object này, thì đây là control block thứ hai, và object bị hủy hai lần. Thư viện chuẩn giải quyết bằng std::enable_shared_from_this:

class Session : public std::enable_shared_from_this<Session> {
public:
    template<typename... Args>
    static std::shared_ptr<Session> create(Args&&... args) {   // factory: buộc tạo qua shared_ptr
        return std::shared_ptr<Session>(new Session(std::forward<Args>(args)...));
    }
    void activate() { active.emplace_back(shared_from_this()); }   // dùng control block có sẵn
private:
    Session(Config cfg);   // constructor private
};

Mẫu class kế thừa từ một template có tham số là chính nó gọi là CRTP (Curiously Recurring Template Pattern, xem Module 4). shared_from_this() tìm control block hiện có và tạo shared_ptr dùng chung nó. Nếu object chưa có shared_ptr nào quản lý thì là lỗi (từ C++17 ném std::bad_weak_ptr). Vì vậy class kiểu này thường để constructor private và chỉ cho tạo qua factory trả shared_ptr.

Những gì shared_ptr không làm được

  • Không chuyển ngược về unique_ptr: một khi đã chia sẻ, không có cách lấy lại quyền độc quyền.
  • Theo sách (C++11/14), không hỗ trợ mảng (shared_ptr<T[]>). C++17 đã thêm.

Chi phí có đáng không?

Với deleter và allocator mặc định, control block chỉ khoảng ba word, dereference rẻ như con trỏ thô, thao tác tăng giảm bộ đếm là một hai lệnh atomic. Đó là cái giá hợp lý cho việc quản lý vòng đời tự động của object chia sẻ. Nhưng đừng dùng shared_ptr chỉ vì "an toàn hơn": nếu sở hữu độc quyền là đủ, unique_ptr rẻ hơn rõ rệt và nói rõ thiết kế hơn.

MCU / bare-metalshared_ptr trên MCU

Hiếm khi dùng: cần heap cho control block, thao tác atomic (Cortex-M0 phải tắt ngắt), và thời điểm hủy object khó dự đoán (có thể rơi vào một ISR hay một task ưu tiên cao nếu nó giữ bản sao cuối cùng). Phần lớn thiết kế firmware có chủ sở hữu rõ ràng; dùng unique_ptr, tham chiếu, hoặc chỉ số vào bảng tĩnh.

Ý chínhÝ chính của Item 19
  • shared_ptr quản lý vòng đời object chia sẻ gần như tự động.
  • So với unique_ptr: gấp đôi kích thước, có control block, bộ đếm atomic.
  • Deleter mặc định là delete, hỗ trợ custom deleter; kiểu deleter không ảnh hưởng kiểu shared_ptr.
  • Tránh tạo shared_ptr từ biến con trỏ thô.
Tự kiểm tra`std::shared_ptr a = std::make_shared(); std::shared_ptr b = a;` có bao nhiêu control block? Reference count bằng mấy?

Một control block (b dùng chung với a), reference count bằng 2.

Tự kiểm traVì sao không nên gọi `shared_from_this()` trong constructor?

Trong constructor, chưa có shared_ptr nào quản lý object (nó được tạo sau khi constructor chạy xong), nên không có control block để dùng chung.

Item 20 · Dùng std::weak_ptr cho con trỏ giống shared_ptr nhưng có thể treo Lướt tr. 134 · PDF 152

Vấn đề

Đôi khi cần một con trỏ hành xử như shared_ptr nhưng không tham gia sở hữu, tức không giữ object sống, và cần biết được khi object đã bị hủy. Con trỏ thô không biết được điều đó. std::weak_ptr làm được.

weak_ptr luôn được tạo từ một shared_ptr (hoặc weak_ptr khác). Nó trỏ cùng object nhưng không tăng reference count (nó tăng weak count, một bộ đếm riêng trong control block).

auto cfg = std::make_shared<Config>();   // ref count = 1
std::weak_ptr<Config> wcfg(cfg);         // ref count vẫn = 1
cfg = nullptr;                           // ref count = 0, Config bị hủy
bool gone = wcfg.expired();              // true

Dùng weak_ptr thế nào

weak_ptr không dereference được (không có *, ->). Lý do: nếu có, giữa lúc kiểm tra expired() và lúc dereference, một thread khác có thể hủy object. Thao tác "kiểm tra rồi truy cập" phải là atomic, nên phải đổi sang shared_ptr:

// Cách 1: lock() trả shared_ptr, null nếu object đã bị hủy
if (auto cfg = wcfg.lock()) {
    use(*cfg);                           // cfg giữ object sống trong khối này
}

// Cách 2: tạo shared_ptr trực tiếp, ném std::bad_weak_ptr nếu đã hủy
std::shared_ptr<Config> cfg2(wcfg);

Ba ứng dụng

1. Cache. Một hàm tải object tốn kém (ví dụ đọc và giải mã một bảng hiệu chuẩn từ flash ngoài) theo ID. Muốn tái sử dụng object đã tải nếu nó còn được dùng ở đâu đó, nhưng không muốn cache giữ nó sống mãi:

std::shared_ptr<const CalTable> load_cal(CalId id) {
    static std::unordered_map<CalId, std::weak_ptr<const CalTable>> cache;
    auto sp = cache[id].lock();          // còn sống thì dùng lại
    if (!sp) {
        sp = read_cal_from_flash(id);    // trả shared_ptr
        cache[id] = sp;                  // cache chỉ giữ weak_ptr
    }
    return sp;
}

(Bản này chưa thread-safe và không bao giờ xóa entry hết hạn khỏi map, đủ để minh họa ý tưởng.)

2. Observer. Trong mẫu Observer, subject giữ danh sách observer để thông báo. Subject không nên quyết định observer sống bao lâu, nhưng cần biết observer đã bị hủy để không gọi vào nó. Danh sách weak_ptr đáp ứng đúng nhu cầu.

3. Phá vòng tham chiếu. Hai object giữ shared_ptr tới nhau: reference count của cả hai không bao giờ về 0, cả hai bị rò rỉ. Ví dụ cấu trúc cây: cha giữ con bằng shared_ptr (hoặc tốt hơn unique_ptr), con giữ con trỏ ngược về cha bằng weak_ptr (hoặc con trỏ thô nếu chắc chắn cha luôn sống lâu hơn con).

 ┌──────┐ shared_ptr ┌──────┐
 │  A   │ ─────────▶ │  B   │
 │      │ ◀───────── │      │   shared_ptr cả hai chiều → rò rỉ
 └──────┘ shared_ptr └──────┘
                                  đổi một chiều thành weak_ptr → hủy đúng

Chi phí

weak_ptr có kích thước giống shared_ptr, dùng chung control block, và thao tác weak count cũng atomic. Object chỉ bị hủy khi ref count về 0, nhưng control block chỉ được giải phóng khi cả weak count về 0 (Item 21 cho thấy vì sao điều này quan trọng).

Ý chínhÝ chính của Item 20
  • Dùng weak_ptr cho con trỏ kiểu shared_ptr có thể treo.
  • Ứng dụng: cache, danh sách observer, phá vòng tham chiếu shared_ptr.
  • Truy cập qua lock(), không qua expired() rồi dereference.
Tự kiểm traVì sao `weak_ptr` không có `operator->`?

Kiểm tra còn sống và truy cập phải là một thao tác atomic. Nếu có ->, object có thể bị hủy bởi thread khác giữa lúc kiểm tra và lúc dùng. lock() trả về shared_ptr giữ object sống trong lúc dùng.

Item 21 · Ưu tiên std::make_unique và std::make_shared thay vì new trực tiếp Lướt tr. 139 · PDF 157

Ba make function

  • std::make_shared (C++11), std::make_unique (C++14), std::allocate_shared (C++11, giống make_shared nhưng nhận allocator).
  • Chúng nhận các đối số, chuyển tiếp hoàn hảo vào constructor của object được tạo trên heap, và trả về smart pointer tương ứng.

C++11 không có make_unique, nhưng viết rất dễ (bản đơn giản, không hỗ trợ mảng):

template<typename T, typename... Ts>
std::unique_ptr<T> make_unique(Ts&&... params) {
    return std::unique_ptr<T>(new T(std::forward<Ts>(params)...));
}

Lý do 1: không lặp tên kiểu

auto a = std::make_unique<Session>(cfg);          // Session viết một lần
std::unique_ptr<Session> b(new Session(cfg));     // Session viết hai lần

Lặp code là nguồn lỗi kinh điển: sửa một chỗ quên chỗ kia.

Lý do 2: an toàn với exception (trước C++17)

void process(std::shared_ptr<Session> s, int priority);
int compute_priority();

process(std::shared_ptr<Session>(new Session), compute_priority());   // có thể rò rỉ (C++11/14)

Để gọi process, compiler phải tính ba thứ: new Session, constructor của shared_ptr, và compute_priority(). Chuẩn C++11/14 chỉ đảm bảo new Session chạy trước constructor của shared_ptr (vì kết quả của nó là đối số). Compiler được phép xếp thứ tự:

  1. new Session
  2. compute_priority()
  3. constructor của shared_ptr

Nếu bước 2 ném exception, con trỏ từ bước 1 chưa được ai quản lý: rò rỉ. Dùng std::make_shared<Session>() thì việc cấp phát và việc giao cho smart pointer nằm trong một hàm, không thể bị chen ngang.

Ghi chúThay đổi trong C++17

C++17 quy định mỗi đối số hàm phải được tính xong hoàn toàn trước khi bắt đầu tính đối số khác, nên tình huống trên không còn rò rỉ. Lý do 1 và 3 vẫn đúng.

Lý do 3: make_shared nhanh và nhỏ hơn

std::shared_ptr<Session> s(new Session); thực hiện hai lần cấp phát: một cho Session (bởi new), một cho control block (bởi constructor của shared_ptr).

std::make_shared<Session>() thực hiện một lần cấp phát cho một khối chứa cả object lẫn control block. Ít cấp phát hơn, mã nhỏ hơn, ít phân mảnh hơn, và object nằm gần control block (tốt cho cache). allocate_shared cũng vậy.

Khi nào không dùng make function

  • Cần custom deleter: make function không nhận deleter.
  • Muốn khởi tạo bằng {}: make function dùng () để chuyển tiếp (Item 7). std::make_shared<std::vector<int>>(10, 20) tạo 10 phần tử bằng 20. Muốn danh sách {10, 20}, tạo một initializer_list trước bằng auto (Item 2) rồi truyền vào:
auto init = {10, 20};                                  // std::initializer_list<int>
auto v = std::make_shared<std::vector<int>>(init);     // vector chứa 10, 20

Với riêng make_shared, thêm hai trường hợp:

  • Class có operator new/operator delete riêng: các hàm đó thường được viết cho đúng kích thước sizeof(T), nhưng make_shared cấp phát khối lớn hơn (thêm control block) qua allocator chứ không qua operator new của class.
  • Object lớn và weak_ptr sống lâu hơn shared_ptr cuối cùng: vì object và control block chung một khối, bộ nhớ của cả khối chỉ được trả lại khi control block được giải phóng, tức khi weak count cũng về 0. Object đã bị hủy (destructor đã chạy) nhưng vùng nhớ của nó vẫn bị giữ. Với new + shared_ptr, hai khối tách rời: vùng nhớ của object được trả ngay khi ref count về 0, chỉ control block nhỏ còn lại.

Nếu buộc phải dùng new

Đưa kết quả của new vào smart pointer ngay trong một câu lệnh riêng, rồi truyền smart pointer đó đi:

std::shared_ptr<Session> s(new Session, session_deleter);   // câu lệnh riêng: không thể rò rỉ
process(std::move(s), compute_priority());                   // move để tránh tăng/giảm ref count
Ý chínhÝ chính của Item 21
  • So với new trực tiếp, make function bỏ lặp code, an toàn exception hơn, và make_shared/allocate_shared sinh code nhỏ và nhanh hơn.
  • Không dùng được make function khi cần custom deleter hoặc muốn khởi tạo bằng {}.
  • Với shared_ptr, cân nhắc không dùng make_shared khi class có operator new riêng, hoặc object lớn mà weak_ptr sống lâu.
Tự kiểm tra`make_shared` cấp phát mấy lần? `shared_ptr(new T)` cấp phát mấy lần?

make_shared: một lần (object và control block chung khối). shared_ptr<T>(new T): hai lần.

Tự kiểm traMột `shared_ptr` tới object 2 MB tạo bằng `make_shared`. Mọi `shared_ptr` đã bị hủy nhưng còn một `weak_ptr` trong cache. 2 MB đó đã được trả lại chưa?

Chưa. Destructor đã chạy, nhưng vùng nhớ chung với control block chỉ được giải phóng khi weak count về 0.

Item 22 · Với Pimpl, định nghĩa special member function trong file .cpp Đọc kỹ tr. 147 · PDF 165

Pimpl idiom là gì

Pimpl (pointer to implementation) là kỹ thuật giấu toàn bộ thành viên dữ liệu của class vào một struct riêng, class chỉ giữ con trỏ tới struct đó. Struct được khai báo trong header nhưng định nghĩa trong file .cpp.

Vấn đề nó giải quyết: class sau phải #include header của mọi kiểu thành viên:

// motor.h  (không dùng Pimpl)
#include "pid.h"
#include "encoder.h"
#include <vector>
class Motor {
public:
    Motor();
private:
    Pid pid_;
    Encoder enc_;
    std::vector<float> log_;
};

Mọi file #include "motor.h" cũng phải biên dịch pid.h, encoder.h. Sửa pid.h thì mọi file dùng Motor phải biên dịch lại, dù chúng không hề biết Pid là gì. Với Pimpl:

// motor.h
class Motor {
public:
    Motor();
    ~Motor();
private:
    struct Impl;          // khai báo, chưa định nghĩa: incomplete type
    Impl* p_;
};

// motor.cpp
#include "motor.h"
#include "pid.h"
#include "encoder.h"
struct Motor::Impl { Pid pid; Encoder enc; std::vector<float> log; };
Motor::Motor() : p_(new Impl) {}
Motor::~Motor() { delete p_; }

Header không còn phụ thuộc pid.h, encoder.h. Thay đổi chúng chỉ cần biên dịch lại motor.cpp. Pimpl còn giúp giữ ABI ổn định: kích thước Motor luôn là một con trỏ, thêm thành viên vào Impl không làm thay đổi layout của Motor mà người dùng thấy.

Một kiểu như Motor::Impl khi chỉ mới được khai báo gọi là incomplete type: compiler biết nó tồn tại nhưng chưa biết kích thước và thành viên. Có thể khai báo con trỏ tới nó, nhưng không thể tạo, hủy hay truy cập thành viên.

Dùng unique_ptr thay con trỏ thô và lỗi khó hiểu

Code trên dùng new/delete thủ công, đúng kiểu mà Chương 4 khuyên tránh. Thay bằng unique_ptr:

// motor.h
class Motor {
public:
    Motor();
private:
    struct Impl;
    std::unique_ptr<Impl> p_;
};

// motor.cpp
struct Motor::Impl { /* ... */ };
Motor::Motor() : p_(std::make_unique<Impl>()) {}

// main.cpp
#include "motor.h"
Motor m;      // lỗi compile!

Lỗi xuất hiện ở nơi dùng Motor, với thông báo về việc áp dụng sizeof hay delete lên incomplete type. Nguyên nhân:

  1. Motor không khai báo destructor, nên compiler tự sinh destructor. Destructor tự sinh là inline, nghĩa là nó được sinh ra trong mọi file dùng Motor, như main.cpp.
  2. Destructor đó gọi destructor của p_, tức gọi deleter mặc định của unique_ptr, tức delete lên Impl*.
  3. Deleter mặc định có static_assert kiểm tra Impl là complete type, vì delete một incomplete type là UB (destructor của nó không thể được gọi). Trong main.cpp, Impl chưa được định nghĩa, nên static_assert thất bại.

Cách sửa

Đảm bảo destructor được sinh ở chỗ Impl đã đầy đủ, tức trong motor.cpp. Khai báo destructor trong header, định nghĩa trong .cpp sau định nghĩa của Impl, dù chỉ là = default:

// motor.h
class Motor {
public:
    Motor();
    ~Motor();                                     // chỉ khai báo
private:
    struct Impl;
    std::unique_ptr<Impl> p_;
};

// motor.cpp
struct Motor::Impl { /* ... */ };
Motor::Motor() : p_(std::make_unique<Impl>()) {}
Motor::~Motor() = default;                        // Impl đã complete ở đây

Đừng quên move và copy

Khai báo destructor làm mất move operation tự sinh (Item 17). Pimpl rất hợp với move (chỉ cần chuyển con trỏ), nên khai báo chúng. Và vì cùng lý do như destructor (move assignment phải hủy Impl cũ, move constructor có thể cần hủy khi có exception), chúng cũng phải được định nghĩa trong .cpp:

// motor.h
    Motor(Motor&& rhs) noexcept;
    Motor& operator=(Motor&& rhs) noexcept;

// motor.cpp
Motor::Motor(Motor&& rhs) noexcept = default;
Motor& Motor::operator=(Motor&& rhs) noexcept = default;

Copy: unique_ptr không copy được nên copy tự sinh không dùng được. Nếu class cần copy, phải tự viết, thực hiện deep copy (copy nội dung Impl, không copy con trỏ):

Motor::Motor(const Motor& rhs) : p_(std::make_unique<Impl>(*rhs.p_)) {}
Motor& Motor::operator=(const Motor& rhs) { *p_ = *rhs.p_; return *this; }

Vì sao shared_ptr không gặp vấn đề này

Với unique_ptr, kiểu deleter là một phần của kiểu con trỏ, nên compiler sinh code gọi deleter ngay trong hàm hủy, ở nơi hàm hủy được sinh: chỗ đó cần Impl complete. Với shared_ptr, deleter được lưu trong control block lúc shared_ptr được tạo (trong motor.cpp, nơi Impl complete), nên destructor tự sinh ở main.cpp chỉ cần giảm bộ đếm, không cần biết Impl. Nhưng với Pimpl, sở hữu là độc quyền, nên unique_ptr vẫn là lựa chọn đúng.

Ý chínhÝ chính của Item 22
  • Pimpl giảm thời gian build bằng cách cắt phụ thuộc biên dịch giữa người dùng class và phần cài đặt.
  • Với unique_ptr cho Pimpl: khai báo special member function trong header, định nghĩa trong .cpp, kể cả khi chỉ là = default.
  • Điều này áp dụng cho unique_ptr, không áp dụng cho shared_ptr.
Tự kiểm traVì sao lỗi "incomplete type" xuất hiện ở `main.cpp` chứ không ở `motor.cpp`?

Destructor tự sinh là inline, được sinh ở mọi nơi dùng Motor. Ở main.cpp, Impl chưa được định nghĩa, nên static_assert trong deleter của unique_ptr thất bại.

Tự kiểm traĐã khai báo `~Motor();` trong header và `= default` trong .cpp, nhưng `std::vector` khi tăng dung lượng lại báo lỗi copy. Vì sao?

Khai báo destructor làm mất move tự sinh; vector cố copy, mà copy bị xóa do unique_ptr. Cần khai báo move constructor và move assignment (noexcept) trong header, định nghĩa = default trong .cpp.

Bức tranh chung

Ba tính năng trong chương này là lý do lớn nhất khiến C++11 được gọi là "ngôn ngữ mới":

  • Move semantics: cho phép thay thao tác copy đắt đỏ bằng thao tác move rẻ. Một std::vector một triệu phần tử được move chỉ bằng việc chuyển ba con trỏ, thay vì cấp phát và copy một triệu phần tử. Move semantics cũng cho phép tạo kiểu chỉ-move như std::unique_ptr, std::thread, std::future.
  • Perfect forwarding: viết được hàm template nhận đối số bất kỳ rồi chuyển tiếp chúng tới hàm khác mà giữ nguyên tính chất lvalue/rvalue, như thể hàm đích được gọi trực tiếp. Đây là nền tảng của emplace_back, make_unique, std::thread.
  • Rvalue reference (T&&) là "keo" nối hai tính năng trên.

Lúc đầu mọi thứ trông đơn giản: std::move để move, T&& là rvalue reference. Càng tìm hiểu càng thấy nhiều ngóc ngách: std::move không move gì, T&& không phải lúc nào cũng là rvalue reference, move không phải lúc nào cũng rẻ hơn copy. Chương này đi qua tất cả.

Câu cần khắc ghi trước khi đọc (đã gặp ở Chương 0): một tham số luôn là lvalue, kể cả khi kiểu của nó là rvalue reference.

void take(Frame&& f);   // f có kiểu Frame&&, nhưng bên trong hàm, biểu thức f là lvalue

Item 23 · Hiểu std::move và std::forward Đọc kỹ tr. 158 · PDF 176

Hai hàm này không làm gì lúc chạy

Cách dễ nhất để hiểu std::move và std::forward là bắt đầu từ những gì chúng không làm: std::move không di chuyển gì, std::forward không chuyển tiếp gì. Lúc chạy, chúng không sinh ra một lệnh máy nào. Chúng chỉ là phép ép kiểu (cast) lúc compile.

  • std::move ép đối số của nó thành rvalue, vô điều kiện.
  • std::forward ép đối số thành rvalue chỉ khi một điều kiện thỏa mãn.

Một bản cài đặt std::move (C++14, rút gọn):

template<typename T>
decltype(auto) move(T&& param) {
    using ReturnType = std::remove_reference_t<T>&&;
    return static_cast<ReturnType>(param);
}

Nó nhận một universal reference (Item 24), bỏ mọi tham chiếu khỏi T rồi thêm &&, và cast param sang kiểu đó. Kết quả là một rvalue. Có lẽ tên rvalue_cast sẽ chính xác hơn.

Vậy move xảy ra ở đâu?

Rvalue là thứ có thể được move. Việc move thực sự xảy ra khi rvalue đó được dùng để khởi tạo hoặc gán một object, và overload resolution chọn move constructor hoặc move assignment (vì chúng nhận T&&, khớp tốt hơn với rvalue so với copy nhận const T&). std::move chỉ biến biểu thức thành "ứng viên được move".

Bẫy: std::move một object const

class Annotation {
public:
    explicit Annotation(const std::string text)
        : value_(std::move(text)) {}      // tưởng là move, thực ra là COPY
private:
    std::string value_;
};

Phân tích:

  1. text có kiểu const std::string.
  2. std::move(text) cho ra const std::string&& (cast không bỏ const).
  3. std::string có hai constructor ứng viên: copy string(const string&) và move string(string&&).
  4. Move constructor nhận string&& (không const) nên không gắn được với const string&&: move constructor phải sửa nguồn (lấy ruột), không được phép sửa object const.
  5. Copy constructor nhận const string&, gắn được với mọi thứ, kể cả const string&&. Copy được chọn.

Code compile, chạy đúng, nhưng âm thầm copy. Hai bài học:

  • Đừng khai báo const cho object bạn muốn move. Yêu cầu move trên object const sẽ âm thầm thành copy.
  • std::move không đảm bảo có move xảy ra, cũng không đảm bảo kết quả đủ điều kiện để move. Điều duy nhất chắc chắn là kết quả là rvalue.

std::forward: cast có điều kiện

Ứng dụng điển hình của std::forward là hàm template nhận universal reference rồi chuyển tiếp cho hàm khác:

void process(const Frame& lval);   // xử lý lvalue
void process(Frame&& rval);        // xử lý rvalue (có thể lấy ruột)

template<typename T>
void log_and_process(T&& param) {
    log("processing");
    process(std::forward<T>(param));
}

Frame f;
log_and_process(f);              // phải gọi process(const Frame&)
log_and_process(std::move(f));   // phải gọi process(Frame&&)

Bên trong log_and_process, param (như mọi tham số) là lvalue. Gọi process(param) thì luôn chọn bản lvalue. Muốn gọi bản rvalue khi và chỉ khi đối số ban đầu là rvalue, ta cần cast có điều kiện. std::forward làm đúng việc đó.

Nhưng làm sao std::forward biết đối số ban đầu là gì? Thông tin được mã hóa trong T (Item 1, trường hợp 2): lvalue thì T = Frame&, rvalue thì T = Frame. std::forward<T> đọc T và cast sang rvalue chỉ khi T không phải tham chiếu. Item 28 giải thích cơ chế bằng reference collapsing.

Dùng std::forward thay luôn std::move được không?

Về kỹ thuật được: std::forward<std::string>(s) cho cùng kết quả với std::move(s). Nhưng std::move gọn hơn, không cần tham số template (bỏ sót hay viết sai tham số template là lỗi), và nói rõ ý định: "tôi muốn move". std::forward nói "tôi chuyển tiếp nguyên trạng". Hai thông điệp khác nhau, nên dùng đúng chỗ.

Ý chínhÝ chính của Item 23
  • std::move là cast vô điều kiện sang rvalue; tự nó không move gì.
  • std::forward cast sang rvalue chỉ khi đối số được gắn với rvalue.
  • Cả hai không làm gì lúc chạy.
Tự kiểm tra`const std::vector v = load(); auto w = std::move(v);` thì `v` sau đó còn dữ liệu không?

Còn: std::move(v) cho const vector&&, chỉ khớp copy constructor, nên w là bản copy và v không bị ảnh hưởng.

Tự kiểm tra`void f(Frame&& x) { g(x); }` với hai overload `g(const Frame&)` và `g(Frame&&)`. `g` nào được gọi?

g(const Frame&), vì x là lvalue. Muốn gọi bản rvalue phải viết g(std::move(x)).

Item 24 · Phân biệt universal reference và rvalue reference Đọc kỹ tr. 164 · PDF 182

T&& có hai nghĩa

Nhìn thấy T&&, ta nghĩ ngay đó là rvalue reference. Không hẳn:

void f(Frame&& param);              // rvalue reference
Frame&& var1 = Frame();             // rvalue reference
auto&& var2 = var1;                 // KHÔNG phải rvalue reference

template<typename T>
void g(std::vector<T>&& param);     // rvalue reference

template<typename T>
void h(T&& param);                  // KHÔNG phải rvalue reference

Nghĩa thứ nhất là rvalue reference thật: chỉ gắn với rvalue, mục đích là nhận diện object có thể move.

Nghĩa thứ hai là "hoặc rvalue reference hoặc lvalue reference". Nó gắn được với mọi thứ: rvalue, lvalue, const, không const, volatile… Scott Meyers gọi chúng là universal reference. Ủy ban chuẩn C++ sau này đặt tên chính thức là forwarding reference, vì chúng hầu như luôn đi với std::forward.

Cách nhận diện

Universal reference xuất hiện khi và chỉ khi hội đủ hai điều kiện:

  1. Có suy luận kiểu (type deduction).
  2. Dạng khai báo chính xác là T&& (với T là tham số được suy luận), hoặc auto&&.

Hai ngữ cảnh phổ biến:

template<typename T>
void h(T&& param);     // tham số function template

auto&& var2 = var1;    // khai báo auto

Thiếu điều kiện 1 thì là rvalue reference:

void f(Frame&& param);   // không có suy luận kiểu

Thiếu điều kiện 2 (dạng không đúng T&&) cũng là rvalue reference:

template<typename T> void g(std::vector<T>&& param);   // dạng std::vector<T>&&
template<typename T> void k(const T&& param);          // thêm const là đủ phá

Bẫy: có T mà không có suy luận

Trong một class template, member function dùng tham số T của class thì không suy luận gì cả, vì T đã được cố định khi class được tạo:

template<class T, class Allocator = std::allocator<T>>
class vector {
public:
    void push_back(T&& x);    // rvalue reference: T đã biết khi tạo vector<T>
};
std::vector<Frame> v;         // T = Frame, push_back(Frame&& x)

Ngược lại, emplace_back có tham số template riêng, được suy luận mỗi lần gọi:

template<class T, class Allocator = std::allocator<T>>
class vector {
public:
    template<class... Args>
    void emplace_back(Args&&... args);   // universal reference: Args được suy luận
};

Universal reference trở thành gì

Universal reference là tham chiếu, nên phải được khởi tạo. Initializer quyết định nó là loại nào: khởi tạo bằng rvalue thì thành rvalue reference, bằng lvalue thì thành lvalue reference.

template<typename T> void h(T&& param);
Frame f;
h(f);             // lvalue → param: Frame&
h(std::move(f));  // rvalue → param: Frame&&

auto&& trong thực tế

auto&& ít gặp hơn, nhưng xuất hiện trong C++14 với generic lambda khi cần nhận mọi thứ. Ví dụ một lambda đo thời gian chạy của bất kỳ hàm nào:

auto timed = [](auto&& func, auto&&... params) {
    auto start = std::chrono::steady_clock::now();
    std::forward<decltype(func)>(func)(std::forward<decltype(params)>(params)...);
    return std::chrono::steady_clock::now() - start;
};

func nhận được mọi thứ gọi được, kể cả lvalue và rvalue; params nhận mọi đối số. (Item 33 giải thích decltype ở đây.)

Đây là một mô hình đơn giản hóa

Tác giả nói rõ: "universal reference" là một trừu tượng hóa. Bên dưới, chúng là rvalue reference trong một ngữ cảnh đặc biệt: có suy luận kiểu phân biệt lvalue với rvalue, và có reference collapsing (Item 28). Nhưng mô hình "universal reference" giúp đọc code nhanh hơn nhiều so với lần nào cũng nghĩ qua reference collapsing.

Ý chínhÝ chính của Item 24
  • Tham số function template dạng T&& với T được suy luận, hoặc object khai báo auto&&, là universal reference.
  • Dạng không đúng T&&, hoặc không có suy luận kiểu, thì T&& là rvalue reference.
  • Universal reference khởi tạo bằng rvalue thành rvalue reference, bằng lvalue thành lvalue reference.
Tự kiểm traCái nào là universal reference? (a) `template void f(T&&);` (b) `template void f(const T&&);` (c) `template struct S { void f(T&&); };` (d) `auto&& x = y;` (e) `template void f(A&&...);`

Item 25 · std::move cho rvalue reference, std::forward cho universal reference Đọc kỹ tr. 168 · PDF 186

Quy tắc

  • Rvalue reference chỉ gắn với object có thể move. Khi chuyển nó cho hàm khác, hãy để hàm đó tận dụng điều này: cast thành rvalue vô điều kiện bằng std::move.
  • Universal reference có thể gắn với lvalue. Cast chỉ khi nó gắn với rvalue: dùng std::forward.
class Message {
public:
    Message(Message&& rhs)                       // rvalue reference
        : topic_(std::move(rhs.topic_)),
          payload_(std::move(rhs.payload_)) {}

    template<typename T>
    void set_topic(T&& t) {                      // universal reference
        topic_ = std::forward<T>(t);
    }
private:
    std::string topic_;
    std::shared_ptr<Payload> payload_;
};

Sai lầm: std::move trên universal reference

template<typename T>
void set_topic(T&& t) {
    topic_ = std::move(t);       // SAI
}

std::string get_topic_name();
Message m;
auto name = get_topic_name();
m.set_topic(name);               // name là lvalue, nhưng bị move mất
// name giờ có giá trị không xác định

Người gọi truyền một biến cục bộ và không hề nghĩ nó sẽ bị "rút ruột".

Vì sao không dùng hai overload thay cho universal reference?

Cách "an toàn" là viết hai bản:

void set_topic(const std::string& t) { topic_ = t; }               // copy
void set_topic(std::string&& t)      { topic_ = std::move(t); }    // move

Có ba nhược điểm:

  1. Nhiều code hơn để viết và bảo trì.
  2. Kém hiệu quả hơn: gọi m.set_topic("sensors/temp") với literal chuỗi. Với universal reference, T là const char(&)[13], và const char* được chuyển thẳng vào std::string::operator=: không tạo object tạm. Với hai overload, phải tạo std::string tạm từ literal, move nó vào topic_, rồi hủy object tạm.
  3. Không mở rộng được: hàm có n tham số cần 2^n overload. Với hàm nhận số lượng đối số không giới hạn (variadic) như make_shared, overload là không thể. Universal reference là cách duy nhất.

Chỉ cast ở lần dùng cuối cùng

Khi dùng một tham chiếu nhiều lần trong hàm, chỉ std::move/std::forward ở lần cuối. Các lần trước, object phải còn nguyên giá trị:

template<typename T>
void publish(T&& text) {
    audit_log(text);                           // dùng như lvalue, không bị động tới
    topic_table.add(std::forward<T>(text));    // lần cuối: chuyển tiếp
}

Một số trường hợp hiếm nên dùng std::move_if_noexcept thay vì std::move (Item 14).

Trả về theo giá trị

Hàm trả về theo giá trị một tham số là rvalue reference hoặc universal reference: áp std::move/std::forward khi return.

Matrix operator+(Matrix&& lhs, const Matrix& rhs) {
    lhs += rhs;
    return std::move(lhs);        // move lhs vào giá trị trả về
}

Bỏ std::move thì lhs (lvalue) bị copy vào giá trị trả về. Nếu Matrix không hỗ trợ move, std::move cũng không hại gì (sẽ copy). Nếu sau này Matrix thêm move, code tự động nhanh hơn.

Tương tự cho universal reference:

template<typename T>
Fraction reduce_and_copy(T&& frac) {
    frac.reduce();
    return std::forward<T>(frac);   // rvalue thì move, lvalue thì copy
}

Nhưng đừng std::move biến cục bộ khi return

Thấy lợi ích trên, nhiều người suy luận: "vậy cũng std::move biến cục bộ khi return để tránh copy":

Frame make_frame() {
    Frame f;
    // ...
    return std::move(f);   // SAI: làm chậm hơn
}

Đây là sai lầm. Chuẩn C++ từ lâu đã có RVO (Return Value Optimization): compiler được phép bỏ hẳn copy (và move) bằng cách tạo f trực tiếp tại vùng nhớ dành cho giá trị trả về. Gọi là copy elision. Điều kiện:

  1. Kiểu của object cục bộ trùng với kiểu trả về của hàm.
  2. Object cục bộ chính là thứ được return.

Với biến có tên, gọi là NRVO (Named RVO). return std::move(f); không thỏa điều kiện 2: thứ được return giờ là một tham chiếu tới f (kết quả của std::move), không phải f. Compiler buộc phải move, mất cơ hội bỏ hẳn thao tác.

Còn nếu compiler không thể áp dụng elision (ví dụ hàm có nhiều nhánh return các biến khác nhau)? Chuẩn quy định: khi điều kiện RVO thỏa mà compiler không elide, object được return phải được coi như rvalue. Tức là compiler tự động std::move cho bạn. Vậy std::move thủ công không bao giờ giúp được gì, chỉ có thể làm hại.

Áp dụng tương tự cho tham số truyền theo giá trị: return chúng sẽ được coi như rvalue (dù không được elide).

Ý chínhÝ chính của Item 25
  • std::move cho rvalue reference, std::forward cho universal reference, ở lần dùng cuối cùng.
  • Làm tương tự khi return theo giá trị một rvalue reference hoặc universal reference.
  • Không bao giờ std::move/std::forward một object cục bộ được return nếu nó đủ điều kiện RVO.
Tự kiểm traVì sao `return std::move(local);` chậm hơn hoặc bằng `return local;`?

return local; cho phép compiler bỏ hẳn copy/move (NRVO); nếu không elide được thì local tự được coi là rvalue và được move. return std::move(local); trả về một tham chiếu, không đủ điều kiện elision, nên luôn phải move.

Tự kiểm tra`template void store(T&& v) { cache_ = std::move(v); }` gọi với một biến `std::string s`. Hậu quả?

s bị move mất nội dung dù người gọi truyền lvalue. Phải dùng std::forward<T>(v).

Item 26 · Tránh overload trên universal reference Lướt tr. 177 · PDF 195

Một hàm ghi log tên

Giả sử ta có hàm nhận một tên, ghi log thời điểm, rồi thêm vào một tập toàn cục:

std::multiset<std::string> names;
void log_and_add(const std::string& name) {
    log(now(), "add");
    names.emplace(name);
}

std::string pet("Darla");
log_and_add(pet);                     // lvalue: copy vào names (không tránh được)
log_and_add(std::string("Persephone")); // rvalue: vẫn copy, dù có thể move
log_and_add("Patty Dog");             // tạo string tạm rồi copy, dù có thể tạo thẳng trong set

Dùng universal reference giải quyết cả hai lãng phí:

template<typename T>
void log_and_add(T&& name) {
    log(now(), "add");
    names.emplace(std::forward<T>(name));
}

Thêm một overload, mọi thứ hỏng

Giờ thêm khả năng tra tên theo chỉ số:

std::string name_from_idx(int idx);
void log_and_add(int idx) {
    log(now(), "add");
    names.emplace(name_from_idx(idx));
}

log_and_add(22);          // gọi bản int: OK
short idx = 22;
log_and_add(idx);         // lỗi compile!

Với đối số short, overload resolution so sánh:

  • Bản int: cần promotion short → int.
  • Bản template: suy ra T = short&, khớp chính xác.

Khớp chính xác thắng promotion, nên bản template được gọi, cố gắng emplace một short vào std::multiset<std::string>, và lỗi compile vì std::string không có constructor nhận short.

Bài học: hàm nhận universal reference là hàm tham lam nhất trong C++. Chúng khớp chính xác với gần như mọi kiểu đối số, nên kết hợp chúng với overload hầu như luôn là ý tồi: bản universal reference lấy về nhiều lời gọi hơn người viết dự đoán.

Perfect-forwarding constructor còn tệ hơn

Một cách dễ rơi vào bẫy là viết constructor chuyển tiếp hoàn hảo:

class Person {
public:
    template<typename T>
    explicit Person(T&& n) : name_(std::forward<T>(n)) {}   // perfect-forwarding ctor
    explicit Person(int idx) : name_(name_from_idx(idx)) {}
private:
    std::string name_;
};

Vấn đề với short ở trên vẫn còn, nhưng có vấn đề nghiêm trọng hơn. Item 17 nói compiler vẫn sinh copy và move constructor dù có constructor template. Vậy class thực sự có:

Person(const Person& rhs);   // copy ctor (compiler sinh)
Person(Person&& rhs);        // move ctor (compiler sinh)

Bây giờ:

Person p("Nancy");
auto clone_of_p(p);          // lỗi compile!

p là lvalue không const. Hai ứng viên:

  • Copy constructor nhận const Person&: cần thêm const.
  • Template với T = Person&: nhận Person&, khớp chính xác.

Template thắng. Nó cố khởi tạo std::string name_ từ một Person, và lỗi. (Nếu p là const Person, copy constructor khớp chính xác và quy tắc "ưu tiên hàm thường hơn template khi ngang nhau" chọn nó.)

Với kế thừa thì càng khó thấy:

class SpecialPerson : public Person {
public:
    SpecialPerson(const SpecialPerson& rhs) : Person(rhs) {}            // gọi template của Person!
    SpecialPerson(SpecialPerson&& rhs) : Person(std::move(rhs)) {}      // gọi template của Person!
};

rhs có kiểu SpecialPerson, không phải Person. Copy/move constructor của Person cần chuyển đổi class con sang class cha, còn template khớp chính xác. Template được gọi, và lỗi (hoặc tệ hơn, compile được với hành vi sai).

Ý chínhÝ chính của Item 26
  • Overload trên universal reference gần như luôn dẫn tới việc bản universal reference được gọi nhiều hơn mong đợi.
  • Perfect-forwarding constructor đặc biệt nguy hiểm: khớp tốt hơn copy constructor với lvalue không const, và chiếm lời gọi copy/move constructor của class cha từ class con.
Tự kiểm traVì sao `Person p("A"); Person q(p);` gọi constructor template chứ không gọi copy constructor?

p là lvalue không const. Template suy ra T = Person&, khớp chính xác; copy constructor cần thêm const. Khớp chính xác thắng.

Item 27 · Các cách thay thế cho overload trên universal reference Lướt tr. 184 · PDF 202

Item 26 cho thấy vấn đề. Item này đưa ra các cách giải quyết, từ đơn giản đến phức tạp.

1. Bỏ overload, dùng tên khác

log_and_add_name(...) và log_and_add_name_idx(...). Đơn giản, nhưng không áp dụng được cho constructor (tên cố định) và đôi khi làm interface kém tự nhiên.

2. Truyền const T&

Quay về C++98: tham số const std::string&. Mất hiệu quả (không move, tạo object tạm), nhưng đơn giản và dự đoán được.

3. Truyền theo giá trị

Một lựa chọn thường tốt bất ngờ: thay tham chiếu bằng giá trị, rồi move vào thành viên (Item 41 phân tích chi phí):

class Person {
public:
    explicit Person(std::string n) : name_(std::move(n)) {}
    explicit Person(int idx) : name_(name_from_idx(idx)) {}
};

Đối số kiểu số nguyên (int, short, std::size_t…) gọi bản int; đối số kiểu chuỗi gọi bản std::string. Không còn tham lam.

4. Tag dispatch

Giữ universal reference (vì hiệu quả) nhưng không overload nó. Hàm public duy nhất nhận universal reference, rồi chuyển sang hai hàm cài đặt khác nhau dựa trên một tag: một đối số mà giá trị không quan trọng, chỉ kiểu của nó quyết định overload nào được chọn.

template<typename T>
void log_and_add(T&& name) {
    log_and_add_impl(std::forward<T>(name),
                     std::is_integral<std::remove_reference_t<T>>());   // tag
}

template<typename T>
void log_and_add_impl(T&& name, std::false_type) {     // không phải số nguyên
    log(now(), "add");
    names.emplace(std::forward<T>(name));
}

void log_and_add_impl(int idx, std::true_type) {       // số nguyên
    log_and_add(name_from_idx(idx));
}

Điểm tinh tế:

  • std::is_integral<T> với T = int& cho kết quả false (tham chiếu tới int không phải kiểu số nguyên), nên phải remove_reference trước.
  • std::true_type và std::false_type là hai kiểu khác nhau; is_integral<...>() tạo một object thuộc một trong hai kiểu đó. Lựa chọn overload xảy ra hoàn toàn lúc compile; tham số tag không có tên và compiler loại bỏ nó hoàn toàn.

Bản log_and_add public giờ không bị overload, nên không còn vấn đề tham lam.

5. Ràng buộc template bằng std::enable_if

Tag dispatch không giải quyết được constructor (constructor do compiler sinh không đi qua hàm dispatch). Cần một cách bảo compiler: "chỉ xét template này khi điều kiện X thỏa". Đó là std::enable_if, dựa trên quy tắc SFINAE (Substitution Failure Is Not An Error): nếu thay T vào khai báo template mà ra kiểu không hợp lệ, template đó bị loại khỏi danh sách ứng viên thay vì gây lỗi.

Điều kiện mong muốn cho Person: chỉ dùng constructor template khi T không phải Person hoặc class con của Person, và không phải kiểu số nguyên:

class Person {
public:
    template<
        typename T,
        typename = std::enable_if_t<
            !std::is_base_of<Person, std::decay_t<T>>::value &&
            !std::is_integral<std::remove_reference_t<T>>::value
        >
    >
    explicit Person(T&& n) : name_(std::forward<T>(n)) {
        static_assert(std::is_constructible<std::string, T>::value,
                      "Không tạo được std::string từ đối số truyền vào");
    }
    explicit Person(int idx) : name_(name_from_idx(idx)) {}
};

Giải thích:

  • std::decay_t<T> bỏ tham chiếu và const/volatile (và biến mảng/hàm thành con trỏ): Person&, const Person&, Person&& đều thành Person.
  • std::is_base_of<Person, X> đúng khi X là Person hoặc class con. (Một class được coi là base của chính nó.)
  • static_assert cho thông báo lỗi dễ đọc khi người dùng truyền kiểu không tạo được chuỗi. Thông báo lỗi của template chuyển tiếp hoàn hảo thường dài hàng trăm dòng và chỉ vào chỗ sâu bên trong (nơi std::string được khởi tạo).
Ghi chúC++20: concepts

enable_if khó đọc. C++20 có concepts và mệnh đề requires làm cùng việc rõ ràng hơn nhiều, kèm thông báo lỗi tốt hơn:

template<typename T>
    requires (!std::derived_from<std::remove_cvref_t<T>, Person>)
          && std::constructible_from<std::string, T>
explicit Person(T&& n) : name_(std::forward<T>(n)) {}

Đánh đổi

Ba cách đầu (tên khác, const T&, giá trị) yêu cầu chỉ định kiểu cho tham số. Hai cách sau (tag dispatch, enable_if) giữ perfect forwarding. Perfect forwarding hiệu quả hơn (không tạo object tạm), nhưng có hai nhược điểm: một số kiểu đối số không forward được (Item 30), và thông báo lỗi khó hiểu khi truyền sai.

Ý chínhÝ chính của Item 27
  • Thay thế cho universal reference + overload: tên khác, const T&, truyền theo giá trị, tag dispatch.
  • std::enable_if (hoặc concepts trong C++20) giới hạn khi nào template được xét, cho phép kết hợp universal reference với overload.
  • Universal reference hiệu quả hơn nhưng khó dùng hơn (lỗi khó đọc, một số kiểu không forward được).
Tự kiểm traVì sao trong `enable_if` của `Person` phải dùng `std::decay_t` thay vì `T`?

Với lvalue, T là Person& hoặc const Person&; is_base_of<Person, Person&> là false (tham chiếu không phải class). decay_t bỏ tham chiếu và cv để so sánh đúng kiểu class.

Item 28 · Hiểu reference collapsing Lướt tr. 197 · PDF 215

Cơ chế bên dưới universal reference

Item 1 nói: với template<typename T> void f(T&& param);, lvalue cho T = Widget&, rvalue cho T = Widget. Vậy với lvalue, ParamType là Widget& &&: tham chiếu tới tham chiếu. Bạn không được viết thứ này:

int x;
auto& & rx = x;   // lỗi: không khai báo được tham chiếu tới tham chiếu

Nhưng compiler có thể tự tạo ra chúng trong một số ngữ cảnh, và khi đó áp dụng reference collapsing (gộp tham chiếu):

Nếu một trong hai tham chiếu là lvalue reference, kết quả là lvalue reference. Ngược lại (cả hai là rvalue reference), kết quả là rvalue reference.

Ghép Kết quả
T& & T&
T& && T&
T&& & T&
T&& && T&&

std::forward hoạt động thế nào

Một bản cài đặt đơn giản hóa (C++14):

template<typename T>
T&& forward(std::remove_reference_t<T>& param) {
    return static_cast<T&&>(param);
}

Xét f(T&& fParam) { someFunc(std::forward<T>(fParam)); }:

  • Đối số là lvalue Widget: T = Widget&. Thay vào: kiểu trả về Widget& && → Widget&; cast static_cast<Widget& &&> → static_cast<Widget&>. Trả về lvalue reference: đúng là lvalue. Không có gì thay đổi.
  • Đối số là rvalue Widget: T = Widget. Kiểu trả về Widget&&; cast static_cast<Widget&&>. Hàm trả về rvalue reference là rvalue (cụ thể là xvalue), nên kết quả là rvalue.

Chính reference collapsing làm std::forward "cast có điều kiện".

Bốn ngữ cảnh xảy ra reference collapsing

  1. Template instantiation: phổ biến nhất, như trên.
  2. auto: auto&& w1 = w; với w là lvalue → auto = Widget&, Widget& && w1 → Widget& w1.
  3. typedef và alias declaration:
template<typename T>
class Holder {
    using RvalueRefToT = T&&;
};
Holder<int&> h;   // RvalueRefToT là int& && → int&  (tên gọi "rvalue ref" giờ sai)
  1. decltype: khi phân tích một kiểu có dùng decltype mà sinh ra tham chiếu tới tham chiếu.

Universal reference chỉ là rvalue reference trong ngữ cảnh đặc biệt

Giờ có thể nói chính xác: universal reference là rvalue reference trong ngữ cảnh mà (1) suy luận kiểu phân biệt lvalue và rvalue (lvalue của T cho T&, rvalue cho T) và (2) reference collapsing xảy ra.

Ý chínhÝ chính của Item 28
  • Reference collapsing xảy ra trong bốn ngữ cảnh: template instantiation, auto, typedef/alias, decltype.
  • Có lvalue reference thì kết quả là lvalue reference; chỉ && && cho rvalue reference.
  • Universal reference là rvalue reference trong ngữ cảnh có suy luận kiểu phân biệt lvalue/rvalue và có reference collapsing.
Tự kiểm tra`template void f(T&& p);` gọi `f(cx)` với `const int cx`. Viết ra từng bước để có kiểu của `p`.

cx là lvalue const int → T = const int&. ParamType = const int& && → collapsing → const int&.

Item 29 · Giả định move không có sẵn, không rẻ, và không được dùng Đọc kỹ tr. 203 · PDF 221

Move không phải phép màu

Move semantics là tính năng nổi bật nhất của C++11, và người ta hay nghe "move rẻ hơn copy rất nhiều", "chỉ cần biên dịch lại bằng C++11 là code nhanh hơn". Đúng một phần. Có nhiều trường hợp move không có lợi gì.

Kiểu không hỗ trợ move

Code C++98 cũ, hoặc class mà điều kiện sinh move tự động không thỏa (khai báo copy operation hoặc destructor, Item 17), không có move operation. Yêu cầu move sẽ thành copy.

Move không nhanh hơn copy

Lợi ích của move đến từ việc dữ liệu nằm ngoài object (trên heap) và object chỉ giữ con trỏ tới nó. Move chỉ cần copy con trỏ rồi đặt con trỏ nguồn về null.

std::vector<int> (move: O(1))            std::array<int, N> (move: O(N))
┌──────────┐                             ┌─────────────────────────┐
│ begin ───┼──▶ [heap: dữ liệu]          │ dữ liệu nằm ngay trong  │
│ end      │                             │ object: phải move từng  │
│ cap      │                             │ phần tử một             │
└──────────┘                             └─────────────────────────┘
  • std::array: dữ liệu nằm ngay trong object. Move phải move từng phần tử. Nếu phần tử là kiểu move rẻ (như std::string) thì vẫn có lợi, nhưng với std::array<int, 1000> thì move và copy tốn ngang nhau: O(n).
  • std::string với SSO (small string optimization): nhiều cài đặt lưu chuỗi ngắn (thường ≤ 15 ký tự) ngay trong object thay vì trên heap, để tránh cấp phát. Move chuỗi ngắn không nhanh hơn copy.

Move không được dùng

Ngay cả khi kiểu có move rẻ, nhiều tình huống vẫn copy:

  • Object nguồn là lvalue (trừ vài ngoại lệ như return).
  • Move constructor không phải noexcept và ngữ cảnh cần strong exception guarantee (Item 14): container sẽ copy.

Kết luận

Trong code tổng quát (template), không biết kiểu cụ thể, phải giả định move không có, không rẻ, không được dùng: viết code đúng và đủ nhanh với copy. Khi biết chắc kiểu và biết nó hỗ trợ move rẻ, cứ dựa vào move.

Góc EmbeddedÁp dụng

Trong firmware, buffer thường là mảng cố định (std::array<uint8_t, 512>, etl::vector có dung lượng cố định, struct chứa mảng). Với những kiểu này, "move" cũng copy toàn bộ byte. Muốn chuyển quyền sở hữu buffer với chi phí O(1), hãy chuyển con trỏ, chỉ số vào memory pool, hoặc unique_ptr với deleter trả về pool (Item 18), chứ không move cả buffer.

Ý chínhÝ chính của Item 29
  • Giả định move operation không có, không rẻ, và không được dùng.
  • Trong code biết rõ kiểu, hoặc kiểu đã hỗ trợ move semantics, không cần giả định này.
Tự kiểm tra`std::array` move có lợi không? `std::array` thì sao?

array<string, 3>: có lợi, vì mỗi phần tử string được move (rẻ với chuỗi dài). array<int, 3>: move và copy như nhau (copy 3 int).

Item 30 · Các trường hợp perfect forwarding thất bại Lướt tr. 207 · PDF 225

Perfect forwarding là gì

"Forwarding" là một hàm truyền đối số của nó cho hàm khác. "Perfect" nghĩa là hàm đích nhận được đúng những gì hàm chuyển tiếp nhận được: cùng kiểu, cùng lvalue/rvalue, cùng const. Mô hình chuẩn:

template<typename... Ts>
void fwd(Ts&&... params) {
    f(std::forward<Ts>(params)...);
}

Perfect forwarding thất bại khi với cùng đối số, gọi f(expr) làm một việc mà fwd(expr) làm việc khác (hoặc không compile). Nguyên nhân luôn là: suy luận kiểu thất bại, hoặc suy ra kiểu sai.

1. Braced initializer

void f(const std::vector<int>& v);
f({1, 2, 3});       // OK: {1, 2, 3} chuyển ngầm thành vector
fwd({1, 2, 3});     // lỗi: không suy ra được kiểu từ {…} (Item 2)

Sửa bằng cách dùng auto (vốn suy ra initializer_list):

auto il = {1, 2, 3};
fwd(il);            // OK

2. 0 hoặc NULL làm con trỏ null

Bị suy ra là số nguyên (Item 8). Dùng nullptr.

3. Static const data member chỉ khai báo, không định nghĩa

class Config {
public:
    static const std::size_t kMaxRetries = 3;   // khai báo (có giá trị), chưa định nghĩa
};
f(Config::kMaxRetries);     // OK: compiler thay bằng 3
fwd(Config::kMaxRetries);   // có thể lỗi link

Compiler thường không cấp bộ nhớ cho kMaxRetries mà thay trực tiếp giá trị (constant propagation). Nhưng fwd nhận tham chiếu, và tham chiếu (thực chất là con trỏ) cần một địa chỉ. Không có định nghĩa thì không có địa chỉ: lỗi link. Sửa bằng định nghĩa trong file .cpp: const std::size_t Config::kMaxRetries;. Từ C++17, static constexpr member tự động là inline variable, có định nghĩa sẵn.

4. Tên hàm overload và tên template

int process_val(int);
int process_val(int, int);

void f(int (*pf)(int));
f(process_val);     // OK: kiểu tham số chọn được overload phù hợp
fwd(process_val);   // lỗi: process_val là bản nào? Không có kiểu để suy luận

Tương tự với template hàm. Sửa bằng cách chỉ định rõ:

using ProcessFn = int (*)(int);
ProcessFn p = process_val;   // chọn bản một tham số
fwd(p);
fwd(static_cast<ProcessFn>(process_val));

5. Bit field

struct IpHeader {
    std::uint32_t version : 4, ihl : 4, dscp : 6, ecn : 2, total_length : 16;
};
void f(std::size_t sz);
IpHeader h;
f(h.total_length);     // OK
fwd(h.total_length);   // lỗi

fwd nhận tham chiếu không const, mà C++ không cho phép tham chiếu không const tới bit field (không có địa chỉ cho một nhóm bit tùy ý; đơn vị nhỏ nhất có địa chỉ là byte). Tham chiếu const thì được, nhưng thực chất trỏ tới một bản sao. Sửa bằng cách copy ra biến thường:

auto length = static_cast<std::uint16_t>(h.total_length);
fwd(length);
Ý chínhÝ chính của Item 30
  • Perfect forwarding thất bại khi suy luận kiểu thất bại hoặc suy ra kiểu sai.
  • Các trường hợp: braced initializer, 0/NULL làm null pointer, static const data member chỉ khai báo, tên hàm overload hoặc template, bit field.
Tự kiểm traVì sao không forward được bit field nhưng gọi trực tiếp thì được?

Gọi trực tiếp với tham số theo giá trị chỉ cần đọc giá trị. Forward cần tham chiếu, mà không thể có tham chiếu không const tới bit field (không có địa chỉ cho từng bit).

Ý chínhTổng kết Chương 5

std::move và std::forward là cast. T&& có suy luận kiểu là universal reference. std::move cho rvalue reference, std::forward cho universal reference, ở lần dùng cuối, không bao giờ trên biến cục bộ được return. Universal reference rất tham lam: tránh overload, hoặc ràng buộc bằng enable_if/concepts. Reference collapsing là cơ chế bên dưới. Đừng tin move luôn rẻ, và biết các trường hợp perfect forwarding thất bại.

Lambda thay đổi cách viết C++

Về mặt khả năng, lambda không thêm gì mới: mọi thứ lambda làm được đều viết được bằng một class có operator(). Nhưng viết tay thì dài dòng đến mức người ta ngại làm. Lambda biến việc tạo một function object thành chuyện vài ký tự, và điều đó thay đổi hẳn cách dùng thư viện chuẩn (std::find_if, std::sort với tiêu chí tùy biến), cách viết callback, cách tạo thread.

auto it = std::find_if(sensors.begin(), sensors.end(),
                       [](const Sensor& s) { return s.temp() > 85.0f; });

Ba thuật ngữ

  • Lambda expression: đoạn mã trong source, ví dụ [](const Sensor& s) { return s.temp() > 85.0f; }.
  • Closure: object được tạo lúc chạy từ lambda expression. Tùy cách capture, closure giữ bản sao hoặc tham chiếu tới dữ liệu.
  • Closure class: class do compiler sinh ra cho mỗi lambda. Câu lệnh trong lambda trở thành thân operator() của class đó.

Mối quan hệ giống như class và instance: một lambda (một closure class) có thể tạo nhiều closure.

int threshold = 10;
auto c1 = [threshold](int v) { return v > threshold; };   // c1 là closure
auto c2 = c1;                                             // c2 là bản sao của closure

Lambda được dịch thành gì

Để hiểu các bẫy trong chương này, cần thấy compiler biến lambda thành gì. Lambda sau:

int limit = 100;
auto check = [limit](int v) { return v < limit; };

tương đương với:

class __ClosureCheck {
public:
    __ClosureCheck(int limit) : limit_(limit) {}
    bool operator()(int v) const { return v < limit_; }   // const theo mặc định
private:
    int limit_;                                            // bản sao của limit
};
auto check = __ClosureCheck(limit);

Capture theo giá trị trở thành thành viên dữ liệu copy giá trị lúc tạo closure; capture theo tham chiếu trở thành thành viên tham chiếu. operator() mặc định là const; thêm mutable để sửa được bản sao bên trong.

Lambda không capture gì chuyển ngầm được sang con trỏ hàm thường, rất hữu ích để truyền vào API C (HAL, thư viện C).

Item 31 · Tránh default capture mode Đọc kỹ tr. 216 · PDF 234

C++11 có hai default capture mode: [&] (capture mọi thứ dùng tới theo tham chiếu) và [=] (theo giá trị). Cả hai đều dẫn tới bug khó thấy.

[&] dễ gây tham chiếu treo

Capture theo tham chiếu tạo closure chứa tham chiếu tới biến cục bộ hoặc tham số. Nếu closure sống lâu hơn biến đó, tham chiếu treo.

Ví dụ: một hệ thống lọc giá trị đo, nơi các bộ lọc được đăng ký vào một container và dùng sau:

using FilterList = std::vector<std::function<bool(int)>>;
FilterList filters;

void add_divisor_filter() {
    auto calib = compute_calibration();
    auto divisor = compute_divisor(calib);
    filters.emplace_back(
        [&](int value) { return value % divisor == 0; }   // tham chiếu tới divisor
    );
}   // divisor bị hủy ở đây. filters vẫn giữ closure có tham chiếu treo

Lần gọi bộ lọc tiếp theo là undefined behavior. Capture tường minh [&divisor] vẫn sai y hệt, nhưng ít ra người đọc thấy rõ lambda phụ thuộc vào divisor và có thể tự hỏi "divisor có sống đủ lâu không?". [&] giấu mất điều đó.

Có người lập luận: "lambda này chỉ dùng ngay tại chỗ (truyền cho std::all_of chẳng hạn), không bị lưu lại, nên [&] an toàn". Đúng ở thời điểm viết. Nhưng code thay đổi: ai đó copy lambda sang chỗ khác nơi nó được lưu lại, và không có gì nhắc họ kiểm tra vòng đời.

Sửa ví dụ trên: capture theo giá trị [divisor] hoặc [=]. Nhưng [=] có vấn đề riêng.

[=] không an toàn như vẻ ngoài

Bẫy 1: con trỏ. Capture theo giá trị một con trỏ chỉ copy con trỏ. Nếu object mà nó trỏ tới bị hủy, closure vẫn treo. Ta "biết" con trỏ thô nguy hiểm, nhưng có một con trỏ ẩn mà ít ai nghĩ tới: this.

Bẫy 2: this. Trong member function:

class Monitor {
public:
    void add_filter() const {
        filters.emplace_back(
            [=](int value) { return value % divisor_ == 0; }   // divisor_ là thành viên
        );
    }
private:
    int divisor_;
};

Trông như [=] copy divisor_ vào closure. Không phải. Capture chỉ áp dụng cho biến cục bộ không static (gồm tham số) trong phạm vi tạo lambda. divisor_ là thành viên, không capture được. Code compile được là vì [=] ngầm capture con trỏ this, và divisor_ thực chất là this->divisor_. Viết [divisor_] hay bỏ trống [] sẽ báo lỗi compile.

Vậy closure phụ thuộc vào vòng đời của object Monitor:

void demo() {
    auto m = std::make_unique<Monitor>();
    m->add_filter();          // closure giữ this của *m
}                             // *m bị hủy → filters chứa closure có this treo

Cách sửa trong C++11: copy thành viên vào biến cục bộ, rồi capture biến đó:

void add_filter() const {
    auto d = divisor_;
    filters.emplace_back([d](int value) { return value % d == 0; });
}

C++14 có cách gọn hơn: init capture (Item 32):

filters.emplace_back([d = divisor_](int value) { return value % d == 0; });
Ghi chúThay đổi từ C++20

C++20 deprecated việc [=] ngầm capture this. Muốn capture this phải viết rõ [=, this]; muốn copy cả object thì [=, *this] (C++17).

Bẫy 3: biến static và toàn cục. Lambda dùng được biến có static storage duration (biến toàn cục, biến static trong namespace, class, hoặc hàm) mà không capture chúng. [=] không copy chúng, dù trông như có:

void add_filter_static() {
    static auto calib = compute_calibration();
    static auto divisor = compute_divisor(calib);
    filters.emplace_back([=](int value) { return value % divisor == 0; });  // không capture gì!
    ++divisor;   // closure đã tạo cũng thấy giá trị mới
}

Người đọc thấy [=] sẽ nghĩ closure "tự chứa" với một bản sao divisor. Thực tế nó dùng biến static chung, và mỗi lần gọi hàm divisor thay đổi thì mọi closure đã tạo đều bị ảnh hưởng. Không có default capture mode, ý nghĩa này rõ ràng hơn.

MCU / bare-metalLambda làm callback trên MCU

Callback đăng ký vào timer, bộ dispatch ngắt, event queue hay HAL gần như luôn sống lâu hơn scope tạo ra nó. Quy tắc thực tế: - Capture tường minh, theo giá trị, dữ liệu nhỏ. - Không capture this của object có thể bị hủy trước callback. - Lambda không capture chuyển được sang con trỏ hàm C: hal_timer_register(TIM2, [](void* ctx) { static_cast<Led*>(ctx)->toggle(); }, &led); với API C dạng void (*cb)(void*) và con trỏ ngữ cảnh.

Ý chínhÝ chính của Item 31
  • [&] có thể gây tham chiếu treo.
  • [=] dễ gây treo qua con trỏ (đặc biệt là this), và gây hiểu lầm rằng closure tự chứa.
Tự kiểm traTrong member function, `[=]{ return count_; }` capture gì?

Con trỏ this, không phải bản sao của count_. Closure sẽ treo nếu sống lâu hơn object.

Tự kiểm traVì sao `[divisor_]` (với `divisor_` là thành viên) báo lỗi compile?

Chỉ biến cục bộ không static (và tham số) mới capture được. Thành viên được truy cập qua this. Dùng init capture [d = divisor_] (C++14) hoặc copy ra biến cục bộ trước.

Item 32 · Dùng init capture để move object vào closure Lướt tr. 224 · PDF 242

Vấn đề của C++11

C++11 chỉ capture được theo giá trị (copy) hoặc theo tham chiếu. Muốn đưa một object chỉ-move (std::unique_ptr, std::future) hoặc object đắt khi copy nhưng rẻ khi move (container lớn) vào closure, không có cách nào trực tiếp.

Init capture (C++14)

C++14 có init capture, còn gọi là generalized lambda capture. Bạn chỉ định:

  1. Tên của thành viên dữ liệu trong closure class.
  2. Biểu thức để khởi tạo thành viên đó.
auto frame = std::make_unique<Frame>(read_dma());

auto task = [f = std::move(frame)] {       // f: thành viên của closure, move từ frame
    return f->is_valid() && f->crc_ok();
};
  • Phía trái dấu = thuộc phạm vi của closure class: f là thành viên.
  • Phía phải thuộc phạm vi nơi tạo lambda: frame là biến cục bộ.

Init capture còn khởi tạo được từ biểu thức bất kỳ, không cần biến có sẵn:

auto task = [f = std::make_unique<Frame>(read_dma())] { return f->is_valid(); };
auto log = [prefix = std::string("uart1: ")](const std::string& msg) { write(prefix + msg); };

Init capture cũng tạo được thành viên tham chiếu với tên mới: [&r = some_var].

Giả lập trong C++11

Lambda chỉ là cách tạo class nhanh. Vậy viết class tay:

class IsValidAndCrcOk {
public:
    explicit IsValidAndCrcOk(std::unique_ptr<Frame>&& f) : f_(std::move(f)) {}
    bool operator()() const { return f_->is_valid() && f_->crc_ok(); }
private:
    std::unique_ptr<Frame> f_;
};
auto task = IsValidAndCrcOk(std::move(frame));

Hoặc dùng std::bind để giữ một bản move bên trong bind object, rồi truyền nó vào lambda qua tham chiếu:

auto task = std::bind(
    [](const std::unique_ptr<Frame>& f) { return f->is_valid() && f->crc_ok(); },
    std::move(frame));      // bind object chứa unique_ptr được move vào

Bind object lưu bản copy (ở đây là move) của mọi đối số. Khi gọi task(), bản lưu trữ được truyền cho lambda như lvalue. Phần lớn code hiện đại không cần điều này nữa.

Ý chínhÝ chính của Item 32
  • Dùng init capture của C++14 để move object vào closure.
  • Trong C++11, giả lập bằng class viết tay hoặc std::bind.
Tự kiểm tra`[buf = std::move(buf)]`: hai chữ `buf` là gì?

buf bên trái là tên thành viên của closure. buf bên phải là biến trong scope tạo lambda, được move vào thành viên đó.

Item 33 · Dùng decltype trên tham số auto&& để std::forward Bỏ qua tr. 229 · PDF 247

Generic lambda

C++14 cho phép tham số lambda là auto. Closure class khi đó có operator() là template:

auto f = [](auto x) { return normalize(x); };
// closure class: template<typename T> auto operator()(T x) const { return normalize(x); }

Vấn đề với perfect forwarding

Nếu normalize xử lý lvalue và rvalue khác nhau, lambda trên luôn truyền lvalue (vì x là tham số). Muốn chuyển tiếp hoàn hảo, ta cần universal reference và std::forward:

auto f = [](auto&& x) { return normalize(std::forward<???>(x)); };

Nhưng không có tên kiểu T để viết vào std::forward<T>. Nó chỉ tồn tại bên trong template do compiler sinh.

Giải pháp: decltype(x)

decltype(x) cho kiểu của x:

  • x gắn với lvalue: decltype(x) là lvalue reference Widget&. Quy ước của std::forward cũng dùng T = Widget& cho lvalue. Khớp.
  • x gắn với rvalue: decltype(x) là rvalue reference Widget&&. Quy ước của std::forward dùng T = Widget (không tham chiếu). Không khớp, nhưng thay vào cài đặt của std::forward (Item 28): kiểu trả về Widget&& && → Widget&& qua reference collapsing. Kết quả giống hệt với T = Widget.

Vậy std::forward<decltype(x)>(x) luôn đúng:

auto f = [](auto&& x) { return normalize(std::forward<decltype(x)>(x)); };
auto g = [](auto&&... xs) { return normalize(std::forward<decltype(xs)>(xs)...); };  // variadic
Ghi chúC++20

Lambda có danh sách tham số template rõ ràng: []<typename T>(T&& x) { return normalize(std::forward<T>(x)); }.

Ý chínhÝ chính của Item 33
  • Dùng decltype trên tham số auto&& để std::forward chúng.

Item 34 · Ưu tiên lambda thay cho std::bind Lướt tr. 232 · PDF 250

std::bind (C++11, kế thừa từ std::tr1::bind) tạo một function object bằng cách "gắn" sẵn một số đối số cho một hàm. Bind object là object do std::bind trả về. Item này lập luận lambda hầu như luôn tốt hơn.

Lý do 1: dễ đọc hơn

Giả sử có hàm đặt báo thức và muốn một callback "bật báo thức 1 giờ kể từ lúc gọi, kéo dài 30 giây":

using Time = std::chrono::steady_clock::time_point;
enum class Sound { Beep, Siren, Whistle };
using Duration = std::chrono::steady_clock::duration;
void set_alarm(Time t, Sound s, Duration d);

auto set_sound_l = [](Sound s) {
    using namespace std::chrono;
    using namespace std::literals;
    set_alarm(steady_clock::now() + 1h, s, 30s);
};

Bản std::bind "tương đương":

using namespace std::placeholders;   // cho _1
auto set_sound_b = std::bind(set_alarm, steady_clock::now() + 1h, _1, 30s);

Không chỉ khó đọc (_1 nghĩa là "đối số đầu tiên của bind object", và bạn phải tra chữ ký set_alarm để biết kiểu của nó), mà còn sai.

Lý do 2: thời điểm tính đối số

Trong bản lambda, steady_clock::now() + 1h là đối số của set_alarm, được tính mỗi lần gọi lambda. Trong bản std::bind, nó là đối số của std::bind, được tính một lần khi tạo bind object. Báo thức sẽ đặt 1 giờ kể từ lúc gọi bind, không phải lúc gọi callback.

Sửa phải lồng bind:

auto set_sound_b = std::bind(set_alarm,
    std::bind(std::plus<>(), std::bind(steady_clock::now), 1h), _1, 30s);

So với lambda, khó chấp nhận.

Lý do 3: overload

Thêm một overload set_alarm có 4 tham số. Lambda vẫn hoạt động (gọi 3 đối số thì chọn bản 3 tham số). std::bind thì lỗi: chỉ có tên set_alarm, không biết chọn bản nào. Phải cast sang kiểu con trỏ hàm cụ thể:

using SetAlarm3 = void (*)(Time, Sound, Duration);
auto set_sound_b = std::bind(static_cast<SetAlarm3>(set_alarm), /* ... */);

Lý do 4: hiệu năng

Lambda gọi set_alarm theo cách thông thường, compiler dễ inline. Bind object lưu con trỏ hàm tới set_alarm và gọi qua con trỏ đó, compiler khó inline hơn. Lambda có thể nhanh hơn.

Lý do 5: cách lưu đối số không rõ ràng

Widget w;
auto c = std::bind(compress, w, _1);

w được lưu theo giá trị hay tham chiếu trong bind object? Theo giá trị (copy), nhưng chỉ biết được khi đã thuộc cách bind hoạt động. Muốn theo tham chiếu phải dùng std::ref(w). Ngược lại, đối số truyền khi gọi bind object (c(level)) được truyền theo tham chiếu (bind dùng perfect forwarding). Với lambda, mọi thứ đều hiện rõ trong code: [w](Level lev) { … } là giá trị, [&w] là tham chiếu, và tham số Level lev là theo giá trị.

Khi nào std::bind còn hợp lý (chỉ C++11)

  • Move capture: C++11 không có init capture (Item 32).
  • Polymorphic function object: bind object dùng perfect forwarding nên nhận được đối số mọi kiểu. Hữu ích khi bind một object có operator() template. C++14 có generic lambda làm được việc này.

Trong C++14 trở đi, không có lý do chính đáng nào để dùng std::bind.

Ý chínhÝ chính của Item 34
  • Lambda dễ đọc hơn, rõ nghĩa hơn, và có thể hiệu quả hơn std::bind.
  • Chỉ trong C++11, std::bind còn có ích cho move capture hoặc bind object với operator() template.
Tự kiểm tra`auto cb = std::bind(log_at, now(), _1);` gọi `cb(msg)` một giờ sau. Thời gian ghi log là lúc nào?

Lúc tạo cb, vì now() được tính khi gọi std::bind. Lambda [](auto msg) { log_at(now(), msg); } tính now() lúc gọi.

Ý chínhTổng kết Chương 6

Lambda là cách viết function object gọn. Tránh [&] và [=] mặc định: capture tường minh, cẩn thận với this và biến static. Init capture (C++14) để move vào closure. std::forward<decltype(x)>(x) trong generic lambda. Dùng lambda thay std::bind.

Item 35 · Ưu tiên task-based programming thay vì thread-based Lướt tr. 241 · PDF 259

Hai cách chạy một hàm bất đồng bộ

Muốn chạy do_async_work() song song, có hai lựa chọn:

int do_async_work();

std::thread t(do_async_work);                 // thread-based
auto fut = std::async(do_async_work);         // task-based

Với cách thứ hai, hàm truyền cho std::async được coi là một task.

Lợi ích 1: lấy được kết quả và exception

do_async_work trả về int. Với std::thread, không có cách trực tiếp nào lấy giá trị đó. Với std::async, fut.get() trả về nó. Nếu do_async_work ném exception, get() ném lại exception đó trong thread gọi. Với std::thread, exception thoát khỏi hàm thread làm chương trình chết (std::terminate).

Lợi ích 2: không phải tự quản lý thread

Ba nghĩa khác nhau của "thread" trong C++:

  • Hardware thread: luồng thực thi thật của CPU. Mỗi core có một hoặc nhiều (với hyper-threading).
  • Software thread (OS thread, system thread): luồng mà hệ điều hành lập lịch lên hardware thread. Thường có nhiều hơn hardware thread rất nhiều.
  • std::thread: object C++ đóng vai handle cho một software thread. Có thể ở trạng thái "null" (không gắn với thread nào): vừa default-construct, đã bị move đi, đã join, hoặc đã detach.

Software thread là tài nguyên có hạn. Khi bạn tạo nhiều hơn mức hệ thống cung cấp được, std::thread ném std::system_error, kể cả khi hàm thread là noexcept. Ngay cả khi chưa hết, quá nhiều software thread so với hardware thread gây oversubscription: scheduler liên tục chuyển đổi (context switch) giữa các thread, cache CPU bị xáo trộn, hiệu năng giảm.

Tránh oversubscription là việc khó, vì tỷ lệ tối ưu phụ thuộc vào máy, vào việc thread hay bị chặn vì I/O hay tính toán liên tục, và vào các chương trình khác cùng chạy. Với std::async, runtime chịu trách nhiệm này. Nó có thể chọn chạy task trên thread gọi get()/wait() thay vì tạo thread mới khi hệ thống đang quá tải (Item 36 bàn hậu quả của lựa chọn này).

Khi nào dùng std::thread trực tiếp

  • Cần truy cập API thread của nền tảng (pthreads, Windows) qua native_handle(): đặt priority, CPU affinity, scheduling policy (SCHED_FIFO). Rất phổ biến trong Embedded Linux realtime.
  • Cần tối ưu thread cho một ứng dụng có profile chạy biết trước (ví dụ server chạy độc quyền một máy).
  • Cần xây dựng công nghệ thread vượt ra ngoài API của C++ (thread pool tự viết).
std::thread rt_worker(control_loop);
sched_param sp{};
sp.sched_priority = 80;
pthread_setschedparam(rt_worker.native_handle(), SCHED_FIFO, &sp);   // Linux realtime
Ý chínhÝ chính của Item 35
  • std::thread không cho cách trực tiếp lấy kết quả của hàm bất đồng bộ, và exception trong đó làm chương trình kết thúc.
  • Thread-based programming phải tự xử lý hết thread, oversubscription, cân bằng tải.
  • Task-based programming với std::async để runtime lo các vấn đề đó.
Tự kiểm traMột ứng dụng Embedded Linux cần một thread điều khiển chạy với `SCHED_FIFO` priority 80. Nên dùng `std::async` hay `std::thread`?

std::thread, vì cần native_handle() để đặt scheduling policy và priority. std::async không cho kiểm soát thread nào chạy task.

Hai launch policy

Gọi std::async(f) không có nghĩa f chắc chắn chạy bất đồng bộ. Có hai launch policy:

  • std::launch::async: f phải chạy bất đồng bộ, trên thread khác.
  • std::launch::deferred: f chỉ chạy khi get() hoặc wait() được gọi trên future, và chạy đồng bộ trên thread gọi. Nếu không ai gọi get()/wait(), f không bao giờ chạy.

Policy mặc định là async | deferred: runtime được chọn một trong hai.

auto fut1 = std::async(f);                                          // mặc định
auto fut2 = std::async(std::launch::async | std::launch::deferred, f); // giống hệt fut1

Hệ quả của policy mặc định

Với auto fut = std::async(f); chạy trên thread t:

  • Không biết f có chạy đồng thời với t không: có thể bị deferred.
  • Không biết f chạy trên thread nào: thread mới, hoặc thread gọi get().
  • Có thể không biết f có chạy không: không ai gọi get()/wait() trên mọi đường thì không chạy.

Hệ quả cụ thể:

thread_local không dùng được an toàn: không biết f đọc ghi biến thread_local của thread nào.

Vòng chờ có timeout có thể lặp mãi. Đây là bẫy hay gặp nhất:

using namespace std::literals;
void f() { std::this_thread::sleep_for(1s); }

auto fut = std::async(f);
while (fut.wait_for(100ms) != std::future_status::ready) {   // có thể lặp vô hạn!
    update_progress();
}

Nếu f bị deferred, wait_for luôn trả về std::future_status::deferred, không bao giờ ready. Bug này dễ lọt qua test (hệ thống ít tải thì runtime thường chọn async), rồi xuất hiện khi hệ thống quá tải.

Sửa bằng cách kiểm tra deferred trước:

auto fut = std::async(f);
if (fut.wait_for(0s) == std::future_status::deferred) {
    fut.get();                        // bị deferred: gọi get để chạy đồng bộ
} else {
    while (fut.wait_for(100ms) != std::future_status::ready) { update_progress(); }
}

Khi nào policy mặc định ổn

Khi đáp ứng tất cả:

  • Task không cần chạy đồng thời với thread gọi get/wait.
  • Không quan trọng biến thread_local của thread nào được dùng.
  • Chắc chắn get/wait sẽ được gọi, hoặc chấp nhận task có thể không chạy.
  • Code dùng wait_for/wait_until đã xử lý trường hợp deferred.

Nếu không, chỉ định rõ std::launch::async. Có thể viết hàm tiện ích:

template<typename F, typename... Ts>
inline auto really_async(F&& f, Ts&&... params) {          // C++14
    return std::async(std::launch::async, std::forward<F>(f), std::forward<Ts>(params)...);
}
Ý chínhÝ chính của Item 36
  • Launch policy mặc định cho phép chạy bất đồng bộ hoặc đồng bộ.
  • Sự linh hoạt đó gây bất định khi dùng thread_local, cho thấy task có thể không bao giờ chạy, và ảnh hưởng tới logic chờ có timeout.
  • Chỉ định std::launch::async nếu bắt buộc phải chạy bất đồng bộ.
Tự kiểm tra`fut.wait_for(10ms)` trả về giá trị nào khi task bị deferred?

std::future_status::deferred, mỗi lần gọi, không bao giờ ready cho tới khi gọi get()/wait().

Joinable và unjoinable

Mỗi std::thread ở một trong hai trạng thái:

  • Joinable: đang gắn với một software thread đang chạy, đang chờ lập lịch, đang bị chặn, hoặc đã chạy xong nhưng chưa được join.
  • Unjoinable: không gắn với thread nào: default-constructed, đã bị move đi, đã join(), hoặc đã detach().

Hủy thread joinable thì chương trình chết

Đây là quy tắc quan trọng nhất: nếu destructor của một std::thread joinable được gọi, chương trình kết thúc bằng std::terminate.

Ví dụ: một hàm lọc dữ liệu cảm biến trên thread riêng, rồi xử lý nếu điều kiện thỏa:

constexpr auto kTenMillion = 10'000'000;

bool filter_and_process(std::function<bool(int)> filter, int max_val = kTenMillion) {
    std::vector<int> good;
    std::thread t([&filter, max_val, &good] {
        for (auto i = 0; i <= max_val; ++i)
            if (filter(i)) good.push_back(i);
    });
    set_priority(t.native_handle(), LowPriority);   // cần native handle → dùng std::thread

    if (conditions_satisfied()) {
        t.join();
        perform_computation(good);
        return true;
    }
    return false;                                   // t vẫn joinable → terminate!
}

Nếu conditions_satisfied() trả false (hoặc ném exception), t bị hủy khi vẫn joinable, và chương trình chết.

Vì sao chuẩn không tự join hay tự detach?

Hai lựa chọn kia đều tệ hơn:

  • Tự join ngầm trong destructor: hàm filter_and_process sẽ chờ thread lọc chạy xong 10 triệu giá trị, kể cả khi conditions_satisfied() đã nói không cần. Hiệu năng bất thường, khó debug.
  • Tự detach ngầm: thread lọc tiếp tục chạy, ghi vào good qua tham chiếu, trong khi good (biến cục bộ) đã bị hủy và stack frame của filter_and_process đã bị hàm khác dùng lại. Hỏng bộ nhớ ngẫu nhiên, gần như không thể debug.

Ủy ban chuẩn chọn biến lỗi này thành lỗi ngay lập tức và rõ ràng (terminate), buộc lập trình viên quyết định.

Giải pháp: RAII

"Làm việc X trên mọi đường thoát khỏi scope" là bài toán mà RAII giải quyết: đặt việc X vào destructor của một object cục bộ. Thư viện chuẩn C++11 không có lớp RAII cho thread, nhưng viết rất dễ:

class ThreadRAII {
public:
    enum class DtorAction { join, detach };

    ThreadRAII(std::thread&& t, DtorAction a) : action_(a), t_(std::move(t)) {}
    ~ThreadRAII() {
        if (t_.joinable()) {
            if (action_ == DtorAction::join) t_.join();
            else t_.detach();
        }
    }
    ThreadRAII(ThreadRAII&&) = default;            // khai báo destructor làm mất move (Item 17)
    ThreadRAII& operator=(ThreadRAII&&) = default;
    std::thread& get() { return t_; }
private:
    DtorAction action_;
    std::thread t_;
};

Ghi chú thiết kế:

  • Constructor chỉ nhận rvalue std::thread vì std::thread không copy được.
  • Thứ tự thành viên: t_ khai báo cuối cùng. Thành viên được khởi tạo theo thứ tự khai báo; thread bắt đầu chạy ngay khi được khởi tạo, nên nó nên được khởi tạo sau khi mọi thành viên khác đã sẵn sàng (thread có thể dùng chúng).
  • Kiểm tra joinable() trước khi join/detach vì gọi chúng trên thread unjoinable là UB.
  • Có một race lý thuyết: giữa joinable() và join(), thread khác có thể làm t_ thành unjoinable. Nhưng một std::thread chỉ đổi trạng thái qua lời gọi member function (join, detach, move), mà destructor đang chạy thì không ai được gọi member function khác trên object. Nếu có, đó là lỗi của người dùng.

Áp dụng:

bool filter_and_process(std::function<bool(int)> filter, int max_val = kTenMillion) {
    std::vector<int> good;
    ThreadRAII t(std::thread([&filter, max_val, &good] { /* ... */ }),
                 ThreadRAII::DtorAction::join);
    set_priority(t.get().native_handle(), LowPriority);
    if (conditions_satisfied()) {
        t.get().join();
        perform_computation(good);
        return true;
    }
    return false;   // destructor join: không còn terminate
}

Chọn join vì detach gây UB (thread truy cập good đã chết). Vấn đề còn lại của join: hàm vẫn phải chờ thread lọc chạy hết. Cách đúng là báo cho thread dừng sớm (interruptible thread). C++11 không có cơ chế chuẩn cho điều này.

Ghi chúC++20: `std::jthread`

C++20 có std::jthread: tự động join trong destructor, và hỗ trợ dừng hợp tác qua std::stop_token. Hàm thread nhận một stop_token, định kỳ kiểm tra stop_requested(); destructor của jthread gọi request_stop() rồi join(). Đây chính là giải pháp hoàn chỉnh cho ví dụ trên.

std::jthread t([&](std::stop_token st) {
    for (int i = 0; i <= max_val && !st.stop_requested(); ++i) if (filter(i)) good.push_back(i);
});
Ý chínhÝ chính của Item 37
  • Làm std::thread unjoinable trên mọi đường đi.
  • Join trong destructor có thể gây vấn đề hiệu năng khó debug; detach trong destructor có thể gây UB khó debug.
  • Khai báo object std::thread cuối cùng trong danh sách thành viên.
Tự kiểm traVì sao `ThreadRAII` cần khai báo move operation `= default`?

Vì nó khai báo destructor, nên compiler không sinh move (Item 17). Không có move thì không trả ThreadRAII từ hàm hay đặt vào container được.

Tự kiểm traVì sao thành viên `std::thread` nên được khai báo cuối cùng trong class?

Thành viên khởi tạo theo thứ tự khai báo, và thread chạy ngay khi khởi tạo. Đặt cuối để mọi thành viên mà thread có thể dùng đã được khởi tạo xong.

Item 38 · Hiểu hành vi destructor khác nhau của thread handle Lướt tr. 258 · PDF 276

Future cũng là một handle

std::thread joinable và future đều là handle tới một thread hệ thống. Nhưng destructor của chúng hành xử khác nhau: hủy std::thread joinable thì terminate, còn hủy future thì đôi khi giống join ngầm, đôi khi giống detach ngầm, và không bao giờ terminate.

Shared state

Future là đầu nhận của một kênh, đầu gửi là callee (thường chạy bất đồng bộ). Callee tính ra kết quả và ghi vào đâu? Không thể là std::promise của callee (promise là object cục bộ của callee, có thể bị hủy trước khi caller gọi get). Cũng không thể là future của caller (future có thể được dùng để tạo std::shared_future, rồi bị copy nhiều lần sau khi future gốc đã bị hủy; mà kết quả có thể chỉ-move, không copy được).

Vì vậy kết quả được lưu ở một nơi thứ ba: shared state, thường là một object trên heap.

 Caller                    Shared state                 Callee
 ┌────────┐             ┌──────────────────┐          ┌───────────────┐
 │ future │ ──────────▶ │ kết quả của      │ ◀─────── │ std::promise  │
 └────────┘             │ callee           │          │ (thường)      │
                        └──────────────────┘          └───────────────┘

Quy tắc destructor của future

  • Thông thường: destructor của future chỉ hủy object future. Nó không join, không detach, không làm gì với thread bên dưới. Nó giảm bộ đếm tham chiếu tới shared state.
  • Ngoại lệ: destructor của future cuối cùng tham chiếu tới shared state của một task không deferred được tạo bởi std::async sẽ chặn cho tới khi task chạy xong. Về bản chất là join ngầm.

Cả ba điều kiện phải thỏa: shared state được tạo bởi std::async; launch policy là async (do chỉ định, hoặc runtime chọn); và đây là future cuối cùng tham chiếu tới shared state đó.

Lý do của ngoại lệ: ủy ban chuẩn lo ngại hậu quả của detach ngầm (giống Item 37), nhưng cũng không muốn terminate. Join ngầm là thỏa hiệp. Lựa chọn này gây tranh cãi.

Hệ quả

API của future không cho biết nó có tham chiếu tới shared state do std::async tạo hay không. Nên không thể biết destructor của một future bất kỳ có chặn hay không:

std::vector<std::future<void>> futs;   // destructor của vector có thể chặn!

class Pipeline {
    std::shared_future<double> fut_;    // destructor của Pipeline có thể chặn
};

Nếu future tới từ std::packaged_task thì không có ngoại lệ:

int calc_value();
std::packaged_task<int()> pt(calc_value);   // bọc calc_value để chạy bất đồng bộ
auto fut = pt.get_future();
std::thread t(std::move(pt));               // packaged_task không copy được
// ...
// fut bị hủy: không chặn. Nhưng t phải được join/detach trước khi bị hủy (Item 37)
Ý chínhÝ chính của Item 38
  • Destructor của future thường chỉ hủy các thành viên dữ liệu của future.
  • Future cuối cùng tham chiếu tới shared state của task không deferred tạo bằng std::async sẽ chặn cho tới khi task hoàn thành.
Tự kiểm traHàm tạo `auto f = std::async(std::launch::async, heavy);` rồi return mà không gọi `f.get()`. Hàm có trả về ngay không?

Không: khi f bị hủy (là future cuối cùng tới shared state của task async), destructor chặn cho tới khi heavy chạy xong.

Item 39 · Cân nhắc void future cho giao tiếp sự kiện một lần Lướt tr. 262 · PDF 280

Bài toán

Một thread (detecting task) cần báo cho thread khác (reacting task) rằng một sự kiện đã xảy ra: dữ liệu đã khởi tạo xong, một chế độ đã được cấu hình, cảm biến đã sẵn sàng. Có mấy cách:

Cách 1: condition variable

std::condition_variable cv;
std::mutex m;

// detecting task
cv.notify_one();

// reacting task
{
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk);
    // phản ứng với sự kiện
}

Ba vấn đề:

  • Code smell: phải có mutex dù không có dữ liệu chia sẻ nào cần bảo vệ.
  • Lost wakeup: nếu detecting task gọi notify_one trước khi reacting task kịp wait, thông báo bị mất, reacting task chờ mãi.
  • Spurious wakeup: wait có thể trả về dù không ai notify. Phải kiểm tra điều kiện, mà ở đây không có điều kiện nào để kiểm tra (đó chính là thứ ta đang cố báo hiệu).

Cách 2: cờ atomic

std::atomic<bool> flag(false);
// detecting: flag = true;
// reacting:  while (!flag);

Không cần mutex, không lost/spurious wakeup. Nhưng reacting task polling liên tục, đốt CPU, chiếm hardware thread của task khác, tốn context switch.

Cách 3: kết hợp cờ và condition variable

std::condition_variable cv;
std::mutex m;
bool flag(false);              // không cần atomic, đã có mutex bảo vệ

// detecting task
{
    std::lock_guard<std::mutex> g(m);
    flag = true;
}
cv.notify_one();

// reacting task
{
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk, [] { return flag; });   // kiểm tra cờ: chống spurious & lost wakeup
}

Đúng, không polling. Nhưng rườm rà: detecting task phải vừa set cờ vừa notify, hai cơ chế cho một thông điệp.

Cách 4: std::promise<void>

Reacting task chờ một future; detecting task đặt giá trị cho promise. Vì không có dữ liệu cần truyền, dùng kiểu void:

std::promise<void> p;

// detecting task
p.set_value();

// reacting task
p.get_future().wait();

Không cần mutex, không lost wakeup (nếu set_value trước wait thì wait trả về ngay), không spurious wakeup, và reacting task thật sự ngủ khi chờ.

Hai nhược điểm:

  • Shared state được cấp phát động (heap).
  • Promise chỉ đặt giá trị một lần: dùng cho sự kiện một lần, không dùng cho sự kiện lặp lại.

Ứng dụng: tạo thread ở trạng thái tạm dừng

Muốn tạo thread nhưng chưa cho nó chạy, để kịp cấu hình trước (priority, affinity), rồi mới thả nó chạy:

std::promise<void> start;

void react();
void detect() {
    std::thread t([] {
        start.get_future().wait();    // tạm dừng cho tới khi được thả
        react();
    });
    configure_thread(t.native_handle());   // đặt priority, affinity...
    start.set_value();                      // thả cho chạy
    // ...
    t.join();
}

Lưu ý: nếu configure_thread ném exception, set_value không được gọi, lambda chờ mãi, t không bao giờ join được. Phải xử lý cẩn thận (dùng RAII như Item 37, và đảm bảo set_value trên mọi đường).

Muốn thả nhiều thread cùng lúc, dùng std::shared_future: mỗi thread giữ một bản sao.

auto sf = start.get_future().share();
std::vector<std::thread> workers;
for (int i = 0; i < n; ++i)
    workers.emplace_back([sf] { sf.wait(); react(); });   // mỗi thread một bản sao sf
start.set_value();                                        // thả tất cả
MCU / bare-metalTrên RTOS

FreeRTOS không có std::promise, nhưng mẫu "báo sự kiện một lần" rất phổ biến: dùng binary semaphore, task notification (xTaskNotifyGive / ulTaskNotifyTake) hoặc event group. Task notification là nhẹ nhất và gửi được từ ISR (vTaskNotifyGiveFromISR). Ý tưởng giống hệt: thread chờ ngủ thật sự, không lost wakeup (notification được "nhớ" nếu gửi trước khi chờ).

Ý chínhÝ chính của Item 39
  • Với sự kiện đơn giản, thiết kế dùng condition variable cần mutex thừa, giới hạn thứ tự giữa detecting và reacting task, và reacting task phải tự kiểm tra sự kiện đã xảy ra chưa.
  • Dùng cờ tránh được các vấn đề đó nhưng phải polling.
  • Condition variable kết hợp cờ thì đúng nhưng rườm rà.
  • std::promise và future tránh được tất cả, nhưng dùng bộ nhớ heap cho shared state và chỉ dùng một lần.
Tự kiểm traVì sao condition variable thuần (không có cờ) có thể khiến reacting task chờ mãi?

Item này giải quyết một nhầm lẫn rất phổ biến, đặc biệt với người đến từ C và Embedded: volatile và std::atomic khác nhau thế nào. Câu trả lời ngắn: chúng giải quyết hai vấn đề hoàn toàn khác nhau.

std::atomic: thao tác không bị chia nhỏ

Object std::atomic<T> đảm bảo các thao tác trên nó là atomic khi nhìn từ các thread khác: như thể được bảo vệ bởi mutex, nhưng thường được cài đặt bằng lệnh CPU đặc biệt nên nhanh hơn nhiều.

std::atomic<int> ai(0);   // khởi tạo
ai = 10;                  // ghi atomic
std::cout << ai;          // đọc atomic
++ai;                     // read-modify-write atomic: tăng thành 11
--ai;                     // read-modify-write atomic: giảm thành 10

Lưu ý: trong std::cout << ai, chỉ việc đọc ai là atomic. Thread khác có thể sửa ai giữa lúc đọc và lúc operator<< in ra. Điều này không ảnh hưởng giá trị in ra (đã đọc xong), nhưng cho thấy "atomic" chỉ áp dụng cho từng thao tác riêng lẻ.

++ai và --ai là read-modify-write (RMW): đọc, sửa, ghi trong một thao tác không thể chia cắt. Thread khác chỉ thấy giá trị trước hoặc sau, không bao giờ thấy trạng thái giữa chừng.

volatile: không đảm bảo gì về concurrency

Cùng đoạn code với volatile:

volatile int vi(0);
vi = 10;
std::cout << vi;
++vi;
--vi;

Nếu thread khác đọc vi trong lúc đó, nó có thể thấy bất kỳ giá trị nào, kể cả 12 hay −12. Đó là data race, và data race là undefined behavior.

Ví dụ rõ hơn: hai thread cùng tăng một bộ đếm:

std::atomic<int> ac(0);   // "atomic counter"
volatile int vc(0);       // "volatile counter"

// Thread 1          // Thread 2
++ac;                ++ac;
++vc;                ++vc;

Sau khi cả hai chạy xong, ac chắc chắn là 2. vc thì không: ++vc gồm đọc, tăng, ghi. Nếu hai thread đọc cùng lúc (cùng thấy 0), cùng tăng thành 1, cùng ghi 1, kết quả là 1. Thực ra đây là data race nên kết quả là UB, nhưng mô tả trên là điều thường xảy ra trong thực tế.

Vấn đề thứ hai: thứ tự

Một thread tính một giá trị quan trọng, rồi báo cho thread khác bằng một cờ:

std::atomic<bool> value_available(false);
auto imptValue = compute_important_value();
value_available = true;                       // báo cho thread khác

Thread kia thấy value_available là true thì phải thấy imptValue đã được tính xong. Nhưng compiler (và phần cứng) thường được phép sắp xếp lại các lệnh ghi không liên quan với nhau. Với:

a = b;
x = y;

compiler được đổi thành x = y; a = b; nếu a, b, x, y độc lập. Nếu điều đó xảy ra với imptValue và value_available, thread kia có thể thấy cờ true trước khi giá trị được ghi.

std::atomic (với memory order mặc định, sequential consistency) ngăn điều này: không lệnh đọc ghi nào đứng trước lần ghi value_available trong code được phép xảy ra sau nó. Đây là cái cho phép dùng atomic để đồng bộ dữ liệu không atomic.

volatile không ngăn việc đổi thứ tự này:

volatile bool value_available(false);
auto imptValue = compute_important_value();
value_available = true;                       // thread khác có thể thấy cờ trước giá trị!

Vậy volatile để làm gì?

volatile báo cho compiler: đây là bộ nhớ đặc biệt, không hành xử như bộ nhớ thường. Bộ nhớ "thường" có đặc tính: ghi một giá trị rồi không ai ghi đè thì giá trị đó còn nguyên. Nhờ vậy compiler được tối ưu:

auto y = x;        // đọc x
y = x;             // đọc x lần nữa → compiler bỏ, vì x chưa đổi

x = 10;            // ghi x
x = 20;            // ghi x lần nữa → compiler bỏ lần ghi đầu (dead store)

Trong memory-mapped I/O, những tối ưu đó là sai:

// Thanh ghi data của UART: mỗi lần ghi là một byte được gửi ra dây
volatile uint32_t& TXDR = *reinterpret_cast<volatile uint32_t*>(0x40004428);
TXDR = 'O';
TXDR = 'K';        // không được bỏ lần ghi 'O': phải gửi cả hai byte

// Thanh ghi data nhận: mỗi lần đọc là lấy một byte mới từ FIFO
volatile uint32_t& RXDR = *reinterpret_cast<volatile uint32_t*>(0x40004424);
auto b1 = RXDR;
auto b2 = RXDR;    // không được gộp: hai lần đọc là hai byte khác nhau

volatile đảm bảo compiler không bỏ, không gộp các lần truy cập. Đó là tất cả những gì nó làm.

std::atomic thì được tối ưu như bộ nhớ thường

Điều thú vị: compiler được phép loại bỏ các thao tác thừa trên std::atomic:

std::atomic<int> x;
x = 10;
x = 20;            // compiler có thể bỏ lần ghi 10

(Trên thực tế compiler hiện nay hiếm khi làm, nhưng chuẩn cho phép.) Một số thao tác trên atomic còn không viết được như với biến thường:

std::atomic<int> x;
auto y = x;              // lỗi: atomic không copy được
y = x;                   // lỗi
std::atomic<int> y(x.load());   // đúng
y.store(x.load());              // đúng

Copy construct y từ x cần đọc x và ghi y trong một thao tác atomic. Phần cứng thường không hỗ trợ thao tác atomic trên hai vùng nhớ, nên copy bị xóa (= delete). Viết rõ load() và store() làm lộ ra rằng đây là hai thao tác riêng.

Kết hợp: volatile std::atomic

Hai thứ này trực giao, kết hợp được:

Item 41 · Cân nhắc truyền theo giá trị cho tham số copy được, move rẻ, và luôn được copy Lướt tr. 281 · PDF 299

Bài toán: hàm lưu lại đối số

Một số hàm nhận đối số và lưu một bản sao của nó (setter, hàm thêm vào container, constructor). Ví dụ một class giữ danh sách tên topic MQTT:

Cách 1: hai overload

class Subscriber {
public:
    void add_topic(const std::string& t) { topics_.push_back(t); }             // lvalue: copy
    void add_topic(std::string&& t)      { topics_.push_back(std::move(t)); }  // rvalue: move
private:
    std::vector<std::string> topics_;
};

Hiệu quả, nhưng phải viết và bảo trì hai hàm gần giống nhau. Hai hàm, hai bản object code (nếu không inline).

Cách 2: universal reference

template<typename T>
void add_topic(T&& t) { topics_.push_back(std::forward<T>(t)); }

Một hàm trong source, nhưng là template nên phải nằm ở header, có thể sinh nhiều bản instantiation (cho std::string, const char*, const char[N] với mọi N…), và có các nhược điểm của universal reference (Item 26, 30: lỗi khó đọc, một số kiểu không forward được).

Cách 3: truyền theo giá trị

void add_topic(std::string t) { topics_.push_back(std::move(t)); }

Chỉ một hàm, không template. Nghe có vẻ trái với mọi lời khuyên C++98 ("không truyền object lớn theo giá trị"). Nhưng trong C++11, phân tích kỹ:

  • t được khởi tạo từ đối số: với lvalue là copy construct, với rvalue là move construct.
  • Sau đó t được move vào vector (t là bản sao riêng của hàm, không ai khác dùng, nên move an toàn).

So sánh chi phí

Cách Đối số lvalue Đối số rvalue
Hai overload 1 copy 1 move
Universal reference 1 copy 1 move
Truyền theo giá trị 1 copy + 1 move 2 move

Truyền theo giá trị tốn thêm một lần move mỗi trường hợp. Nếu move rẻ (như std::string dài, std::vector, std::unique_ptr), đó là cái giá nhỏ cho sự đơn giản.

Bốn điều kiện trong tiêu đề, và vì sao mỗi điều quan trọng

Tiêu đề là "cân nhắc truyền theo giá trị cho tham số copy được, move rẻ, và luôn được copy".

  1. "Cân nhắc": đây không phải luật. Thêm một lần move có thể không chấp nhận được trong code nóng.
  2. "Copy được": kiểu chỉ-move (như std::unique_ptr) chỉ cần một overload nhận T&&; không có gì để copy nên không cần bản const T&. Truyền theo giá trị cho kiểu chỉ-move tốn thêm một move so với overload T&& mà không được lợi gì.
class Holder {
public:
    void set(std::unique_ptr<Frame>&& p) { p_ = std::move(p); }   // 1 move
    // void set(std::unique_ptr<Frame> p) { p_ = std::move(p); } // 2 move
private:
    std::unique_ptr<Frame> p_;
};
  1. "Move rẻ": với kiểu mà move đắt (như std::array lớn, std::string ngắn có SSO, Item 29), lần move thêm có thể tốn như một lần copy.
  2. "Luôn được copy": nếu hàm chỉ copy trong một số nhánh, truyền theo giá trị luôn tốn chi phí tạo t, kể cả nhánh không dùng:
void add_topic(std::string t) {
    if (t.size() > kMinLen && t.size() < kMaxLen) topics_.push_back(std::move(t));
    // nhánh không thỏa: vẫn tốn chi phí tạo và hủy t
}

Copy bằng phép gán có thể đắt hơn nhiều

Phân tích trên giả định đối số được lưu bằng construct (như push_back). Nếu lưu bằng phép gán vào một thành viên đã có, chuyện khác hẳn:

class Password {
public:
    explicit Password(std::string pwd) : text_(std::move(pwd)) {}
    void change_to(std::string new_pwd) { text_ = std::move(new_pwd); }   // gán
private:
    std::string text_;
};

Password p("Supercalifragilisticexpialidocious");   // text_ chứa chuỗi dài
std::string new_password = "Beware the Jabberwock";
p.change_to(new_password);

Với truyền theo giá trị: copy new_password vào new_pwd (cấp phát bộ nhớ mới), move vào text_ (giải phóng bộ nhớ cũ của text_). Một lần cấp phát và một lần giải phóng.

Với overload const std::string&: text_ = new_pwd; gán trực tiếp. Vì text_ đã có đủ dung lượng (chuỗi cũ dài hơn), std::string::operator= tái sử dụng bộ nhớ có sẵn, không cấp phát gì cả. Truyền theo giá trị có thể đắt hơn nhiều trong trường hợp này. Điều này áp dụng cho mọi kiểu giữ dữ liệu trên heap (std::string, std::vector).

Slicing

Truyền theo giá trị một kiểu class cha sẽ cắt (slice) mất phần của class con:

class Widget { /* ... */ };
class SpecialWidget : public Widget { /* ... */ };
void process(Widget w);   // truyền theo giá trị

process(sw);              // w chỉ là phần Widget; mọi thứ của SpecialWidget bị cắt

Không nên truyền theo giá trị kiểu có thể là class cha trong hệ phân cấp.

  • Với tham số copy được, move rẻ, luôn được copy, truyền theo giá trị gần hiệu quả bằng truyền tham chiếu, dễ cài đặt hơn, và sinh ít object code hơn.
  • Copy bằng phép gán có thể đắt hơn nhiều so với copy bằng construct.

Item 42 · Cân nhắc emplacement thay vì insertion Lướt tr. 292 · PDF 310

Chi phí ẩn của push_back

std::vector<std::string> names;
names.push_back("xyzzy");

Container chứa std::string, nhưng đối số là chuỗi literal const char[6]. push_back có hai overload, nhận const std::string& và std::string&&, nên compiler phải tạo object tạm:

  1. Tạo std::string tạm từ "xyzzy" (có thể cấp phát).
  2. Gọi push_back(std::string&&): move construct phần tử mới trong vector từ object tạm.
  3. Hủy object tạm.

Một lần tạo và một lần hủy thừa.

emplace_back: tạo trực tiếp tại chỗ

emplace_back dùng perfect forwarding: nhận đối số bất kỳ và chuyển thẳng cho constructor của phần tử, tạo phần tử ngay trong vùng nhớ của vector:

names.emplace_back("xyzzy");                  // tạo string trực tiếp từ const char*
names.emplace_back(50, 'x');                  // tạo string 50 ký tự 'x', không có object tạm

Mọi container chuẩn có hàm emplace tương ứng với hàm chèn: push_back → emplace_back, push_front → emplace_front, insert → emplace (và emplace_hint cho container có thứ tự).

Emplacement làm được mọi thứ insertion làm được (truyền một object cùng kiểu thì nó gọi copy hoặc move constructor). Vậy có nên luôn dùng emplacement không?

Khi nào emplacement nhanh hơn

Trên lý thuyết emplacement không bao giờ chậm hơn. Trên thực tế, tùy cài đặt, kiểu đối số, kiểu container, vị trí chèn… có trường hợp insertion nhanh hơn. Cách chắc chắn duy nhất là đo. Nhưng có heuristic: emplacement gần như chắc chắn nhanh hơn khi đủ ba điều kiện:

  1. Giá trị được construct vào container, không phải gán. emplace_back ở cuối vector thì construct vào vùng nhớ mới. Nhưng v.emplace(v.begin(), "xyzzy") chèn vào đầu: phần tử đầu tiên đã tồn tại, nên giá trị mới được move assign vào vị trí đó, và move assign cần một object nguồn, tức vẫn phải tạo object tạm. Container dạng node (std::list, std::map, std::set) hầu như luôn construct node mới, nên điều kiện này thường thỏa.
  2. Kiểu đối số khác kiểu phần tử. Nếu truyền một std::string vào container std::string, không có object tạm nào để tránh: cả hai cách đều copy/move một lần.
  3. Container không có khả năng từ chối giá trị vì trùng lặp. Với std::set hay std::map, để kiểm tra trùng, emplacement thường phải tạo node với giá trị mới trước, rồi so sánh; nếu trùng thì hủy node. Chi phí tạo và hủy node có thể lớn hơn chi phí insertion tiết kiệm được.

Bẫy 1: rò rỉ tài nguyên

std::list<std::shared_ptr<Frame>> frames;
void release_frame(Frame* f);   // custom deleter

frames.push_back(std::shared_ptr<Frame>(new Frame, release_frame));
frames.emplace_back(new Frame, release_frame);   // nguy hiểm

Với push_back:

  1. Object tạm shared_ptr được tạo từ new Frame: con trỏ đã được quản lý.
  2. push_back cấp phát node cho list. Nếu thất bại (hết bộ nhớ), ném exception; object tạm shared_ptr bị hủy và giải phóng Frame. Không rò rỉ.

Với emplace_back:

  1. new Frame tạo con trỏ thô, được chuyển tiếp vào bên trong emplace_back.
  2. emplace_back cấp phát node. Nếu thất bại, ném exception. Con trỏ thô chưa được ai quản lý (shared_ptr chỉ được tạo trong node, mà node chưa cấp phát được): rò rỉ.

Vấn đề không nằm ở emplace mà ở việc truyền new trực tiếp (Item 21 đã cảnh báo). Cách đúng là tạo smart pointer trong một câu lệnh riêng:

std::shared_ptr<Frame> f(new Frame, release_frame);
frames.push_back(std::move(f));      // hoặc emplace_back(std::move(f)), như nhau

Bẫy 2: explicit constructor

std::vector<std::regex> regexes;
regexes.emplace_back(nullptr);   // compile được!
regexes.push_back(nullptr);      // lỗi compile

std::regex có constructor nhận const char*, khai báo explicit (để tránh chuyển ngầm tốn kém). nullptr chuyển ngầm được sang const char*.

  • push_back(nullptr) cần copy initialization một std::regex từ nullptr (giống std::regex r = nullptr;), mà copy initialization không dùng được constructor explicit. Lỗi compile: tốt.
  • emplace_back(nullptr) dùng direct initialization (giống std::regex r(nullptr);), dùng được constructor explicit. Compile được, và lúc chạy, tạo regex từ con trỏ null là undefined behavior.

Khi dùng emplacement, phải chắc chắn đang truyền đúng đối số, vì compiler sẽ cố tìm mọi cách để chấp nhận, kể cả qua constructor explicit.

Góc EmbeddedÁp dụng

Với container trong firmware (thường là etl::vector, etl::queue có dung lượng cố định, không cấp phát heap), emplace_back vẫn có lợi: construct trực tiếp, tránh copy object lớn qua stack. Điều kiện "construct chứ không gán" thường thỏa vì chủ yếu chèn vào cuối.

Ý chínhÝ chính của Item 42
  • Về nguyên tắc, emplacement đôi khi hiệu quả hơn insertion và không bao giờ kém hơn.
  • Trên thực tế, emplacement nhiều khả năng nhanh hơn khi: giá trị được construct (không gán) vào container, kiểu đối số khác kiểu phần tử, và container không từ chối giá trị trùng.
  • Emplacement có thể gọi các chuyển đổi kiểu mà insertion từ chối (constructor explicit).

Gần như không: đối số cùng kiểu phần tử (điều kiện 2 không thỏa), và set có thể từ chối trùng lặp (điều kiện 3 không thỏa), nên emplace có thể còn tạo rồi hủy một node thừa.

Tự kiểm traVì sao `v.emplace_back(nullptr)` compile được với `std::vector` còn `push_back(nullptr)` thì không?

emplace_back dùng direct initialization nên gọi được constructor explicit std::regex(const char*). push_back cần copy initialization, không dùng constructor explicit.
