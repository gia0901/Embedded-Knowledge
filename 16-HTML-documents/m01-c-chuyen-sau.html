C chuyên sâu cho Embedded

Những phần của ngôn ngữ C quyết định chương trình chạy đúng hay sai trên phần cứng thật: bộ nhớ nằm ở đâu, compiler được phép làm gì, và những chỗ chuẩn C cố tình để mở.

Module này đi theo thứ tự từ "dữ liệu nằm ở đâu" (memory layout, storage, linkage) đến "compiler hiểu code ra sao" (const, volatile, aliasing, UB), rồi tới các kỹ thuật thao tác dữ liệu ở mức bit và byte. Mỗi phần có ghi chú riêng cho MCU và Embedded Linux khi hai bên khác nhau.

Memory layout của chương trình C

Một chương trình C sau khi link được chia thành các section. Biết biến của mình nằm ở section nào giúp trả lời ba câu hỏi hay gặp: tốn Flash hay RAM, được khởi tạo khi nào, và sống bao lâu.

Section Chứa gì MCU: nằm ở Linux: nằm ở
.text Mã máy, hằng số literal nhỏ Flash Trang read-only + exec
.rodata Biến const toàn cục, chuỗi literal Flash Trang read-only
.data Biến toàn cục/static có giá trị khởi tạo khác 0 Giá trị ban đầu ở Flash (LMA), chạy ở RAM (VMA) Trang read-write, nạp từ file ELF
.bss Biến toàn cục/static khởi tạo bằng 0 hoặc không khởi tạo RAM, startup code ghi 0 Trang ẩn danh, kernel cấp sẵn toàn 0
heap malloc RAM, giữa .bss và stack (nếu có) Vùng brk + mmap
stack Biến cục bộ, địa chỉ trả về, tham số RAM, thường ở đỉnh RAM, mọc xuống Mỗi thread một stack, có guard page 
#include <stdint.h>

const uint32_t lut[4] = {1, 2, 4, 8};   // .rodata  -> Flash
uint32_t boot_count = 5;                // .data    -> RAM, giá trị 5 lưu ở Flash
uint32_t rx_bytes;                      // .bss     -> RAM, = 0 khi vào main()
static uint8_t buf[256];                // .bss     (static chỉ đổi linkage)

void task(void) {
    static uint32_t calls = 0;          // .bss  (static cục bộ sống suốt chương trình)
    uint8_t tmp[32];                    // stack (mất khi hàm trả về)
    const char *msg = "hello";          // con trỏ trên stack, "hello" ở .rodata
    (void)tmp; (void)msg; calls++;
}

LMA và VMA: vì sao .data tốn cả Flash lẫn RAM

Trên MCU, RAM mất dữ liệu khi tắt nguồn. Giá trị ban đầu của .data phải lưu ở Flash (Load Memory Address), còn biến thực sự được đọc ghi ở RAM (Virtual/Run Memory Address). Startup code (chạy trước main) làm hai việc:

  1. Copy khối .data từ Flash sang RAM.
  2. Ghi 0 toàn bộ .bss.

Vì thế một mảng uint8_t table[1024] = {1, 2, 3}; tốn 1 KB Flash và 1 KB RAM, trong khi static const cùng nội dung chỉ tốn Flash.

MCU / bare-metalĐọc kết quả lệnh size

arm-none-eabi-size firmware.elf in ra text data bss. Flash dùng = text + data. RAM tĩnh dùng = data + bss. Phần RAM còn lại chia cho heap và stack.

Embedded LinuxKhông có bước copy thủ công

Trên Linux, loader của kernel map các segment của file ELF vào không gian địa chỉ ảo. Trang .data được map copy-on-write, trang .bss là trang ẩn danh đã zero sẵn. Xem /proc/<pid>/maps để thấy layout thật của process.

Stack overflow

Trên MCU không có MMU, stack tràn sẽ âm thầm ghi đè lên .bss hoặc heap. Lỗi xuất hiện xa chỗ gây ra, rất khó debug. Các cách phát hiện:

  • Stack painting: tô stack bằng một mẫu (ví dụ 0xDEADBEEF) lúc khởi động, định kỳ quét xem mẫu còn lại bao nhiêu để biết high-water mark.
  • MPU guard region: đặt một vùng nhỏ không cho phép ghi ở đáy stack, tràn sẽ gây MemManage fault ngay tại chỗ.
  • -fstack-usage của GCC sinh file .su cho biết mỗi hàm dùng bao nhiêu stack; kết hợp call graph để ước lượng worst case.
  • FreeRTOS: uxTaskGetStackHighWaterMark() và configCHECK_FOR_STACK_OVERFLOW.

Trên Linux, mỗi stack có guard page, tràn sẽ gây SIGSEGV. Stack thread chính mặc định 8 MB (ulimit -s), stack thread tạo bằng pthread mặc định cũng thường 8 MB và chỉnh bằng pthread_attr_setstacksize.

Phỏng vấn hay hỏiCâu hỏi kinh điển

"Biến static trong hàm nằm ở đâu và được khởi tạo khi nào?" Nằm ở .data hoặc .bss, không phải stack. Trong C nó được khởi tạo một lần trước khi chương trình chạy (giá trị khởi tạo phải là hằng số lúc compile). Khác với C++, nơi static cục bộ được khởi tạo ở lần đầu đi qua khai báo.

Storage duration, scope và linkage

Ba khái niệm hay bị trộn lẫn:

  • Storage duration (thời gian sống): automatic (stack), static (toàn chương trình), allocated (malloc), thread (_Thread_local).
  • Scope (phạm vi nhìn thấy tên): block, file, function prototype.
  • Linkage (tên có được chia sẻ giữa các file không): external, internal, none.

Từ khóa static mang hai nghĩa khác nhau tùy vị trí:

Vị trí Tác dụng của static
Biến trong hàm Đổi storage duration thành static (giữ giá trị giữa các lần gọi)
Biến/hàm ở mức file Đổi linkage thành internal (chỉ thấy trong file .c đó) 
// uart.c
static uint8_t rx_ring[128];      // không file nào khác truy cập trực tiếp được
static void uart_isr_body(void);  // compiler được phép inline, loại bỏ nếu không dùng
int uart_errors;                  // external linkage: định nghĩa

// uart.h
extern int uart_errors;           // khai báo, không cấp phát bộ nhớ
Cẩn thậnTentative definition và -fno-common

Viết int counter; (không extern, không khởi tạo) trong hai file .c từng được linker gộp làm một (common symbol). Từ GCC 10, mặc định là -fno-common nên sẽ báo lỗi multiple definition. Quy tắc an toàn: định nghĩa đúng một lần trong file .c, header chỉ chứa extern.

Dùng static cho mọi hàm và biến không cần lộ ra ngoài là thói quen tốt: tránh trùng tên giữa các module, và cho compiler thêm thông tin để tối ưu (inline, bỏ code chết).

const: hợp đồng chỉ-đọc

const là lời hứa ở mức ngôn ngữ rằng code này không sửa đối tượng qua tên hoặc con trỏ đó. Nó không có nghĩa đối tượng không bao giờ thay đổi.

Đọc khai báo con trỏ

Đọc từ phải sang trái, const áp dụng cho thứ đứng ngay bên trái nó (hoặc bên phải nếu nó đứng đầu):

const uint8_t *p;          // con trỏ tới uint8_t hằng: *p = 1 lỗi, p++ được
uint8_t const *p;          // y hệt dòng trên
uint8_t *const p = buf;    // con trỏ hằng: p++ lỗi, *p = 1 được
const uint8_t *const p = buf; // cả hai đều không đổi được

const trong Embedded

  • Đặt dữ liệu vào Flash: bảng tra, font, chuỗi menu nên khai báo static const để không tốn RAM.
  • API rõ ràng: int crc16(const uint8_t *data, size_t len) cho người gọi biết hàm không sửa buffer.
  • Thanh ghi chỉ đọc: const volatile uint32_t *status nghĩa là code không được ghi, nhưng phần cứng có thể đổi giá trị bất kỳ lúc nào. CMSIS định nghĩa __I là volatile const cho đúng mục đích này.
Ghi chúconst trong C khác C++

Trong C, biến const int N = 10; không phải constant expression, nên không dùng làm kích thước mảng toàn cục hay nhãn case được. Dùng enum { N = 10 }; hoặc #define. Trong C++, const int khởi tạo bằng hằng là constant expression và mặc định có internal linkage.

Ép bỏ const (cast) rồi ghi vào một đối tượng được định nghĩa là const là undefined behavior. Trên MCU, đối tượng đó thường nằm trong Flash nên lệnh ghi sẽ bị bỏ qua hoặc gây BusFault.

volatile: nói với compiler rằng có người khác đang chạm vào

volatile báo cho compiler rằng giá trị của đối tượng có thể thay đổi, hoặc việc đọc ghi có tác dụng phụ, theo cách mà compiler không nhìn thấy. Hệ quả: mỗi lần đọc/ghi trong source phải sinh ra đúng một lần truy cập bộ nhớ, theo đúng thứ tự giữa các truy cập volatile với nhau.

Ba trường hợp cần volatile

  1. Thanh ghi ngoại vi (MMIO): đọc thanh ghi status có thể xóa cờ, ghi thanh ghi data có thể đẩy một byte ra UART.
  2. Biến dùng chung giữa ISR và code chính (hoặc giữa task và ISR).
  3. Biến cục bộ bị sửa giữa setjmp và longjmp.
volatile bool data_ready = false;     // thiếu volatile: vòng while dưới có thể thành vòng lặp vô hạn

void USART1_IRQHandler(void) {
    rx = USART1->DR;
    data_ready = true;
}

int main(void) {
    for (;;) {
        while (!data_ready) { }        // với -O2, không có volatile compiler có thể đọc 1 lần rồi lặp mãi
        data_ready = false;
        process(rx);
    }
}

Những gì volatile KHÔNG làm

  • Không atomic. counter++ trên biến volatile uint32_t vẫn là đọc, cộng, ghi. ISR chen vào giữa thì mất một lần đếm.
  • Không tạo memory barrier phần cứng. CPU vẫn có thể sắp xếp lại hoặc buffer việc ghi (write buffer trên Cortex-M, out-of-order trên Cortex-A).
  • Không ngăn compiler đổi thứ tự giữa truy cập volatile và truy cập không volatile.
// Sai: compiler được phép ghi buf[] SAU khi ghi ready = 1
uint8_t buf[64];            // không volatile
volatile int ready;

void producer(void) {
    fill(buf);
    ready = 1;              // consumer có thể thấy ready = 1 khi buf chưa đầy đủ
}

Cách sửa: dùng C11 atomic_store_explicit(&ready, 1, memory_order_release) ở bên ghi và memory_order_acquire ở bên đọc, hoặc tắt ngắt quanh đoạn dùng chung trên MCU.

MCU / bare-metalCritical section quanh dữ liệu dùng chung với ISR

Với dữ liệu nhiều byte hoặc thao tác read-modify-write, volatile chưa đủ. Trên Cortex-M, cách phổ biến là lưu trạng thái PRIMASK, gọi __disable_irq(), làm việc, rồi khôi phục PRIMASK. Cortex-M3/M4/M7 có LDREX/STREX nên dùng được <stdatomic.h> cho biến 32-bit. Cortex-M0/M0+ không có, chỉ còn cách tắt ngắt.

static inline uint32_t irq_save(void) {
    uint32_t primask = __get_PRIMASK();
    __disable_irq();
    return primask;
}
static inline void irq_restore(uint32_t primask) { __set_PRIMASK(primask); }

void stats_add(uint32_t n) {
    uint32_t s = irq_save();
    total_bytes += n;           // biến 64-bit dùng chung với ISR
    irq_restore(s);
}
Embedded Linuxvolatile không dùng để đồng bộ thread

Trong userspace, dùng std::atomic / _Atomic hoặc mutex. Trong kernel, tài liệu volatile considered harmful khuyên không khai báo biến volatile; thay vào đó dùng READ_ONCE()/WRITE_ONCE(), các API MMIO như readl()/writel() (đã có barrier phù hợp), và các primitive đồng bộ (spinlock, mutex).

Bẫy read-modify-write trên thanh ghi

  • Thanh ghi kiểu write-1-to-clear (W1C): viết REG |= FLAG_A; sẽ đọc ra các cờ khác đang bằng 1 rồi ghi lại 1, vô tình xóa luôn chúng. Phải ghi trực tiếp REG = FLAG_A;.
  • GPIO trên STM32 có thanh ghi BSRR để set/reset từng chân trong một lần ghi, tránh việc ISR và main cùng sửa ODR bằng read-modify-write.

Pointer và array

Array không phải pointer

Tên mảng decay (tự chuyển) thành con trỏ tới phần tử đầu trong hầu hết biểu thức, trừ khi đi với sizeof, &, hoặc là chuỗi literal khởi tạo mảng.

uint8_t frame[16];
size_t a = sizeof frame;            // 16
uint8_t *p = frame;                 // decay
size_t b = sizeof p;                // 4 trên Cortex-M, 8 trên Linux 64-bit

void send(uint8_t buf[16]) {        // tham số mảng thực chất là uint8_t *buf
    size_t c = sizeof buf;          // kích thước con trỏ, không phải 16. GCC cảnh báo -Wsizeof-array-argument
}

#define ARRAY_SIZE(a) (sizeof(a) / sizeof((a)[0]))   // chỉ đúng với mảng thật

&frame có kiểu uint8_t (*)[16]: cùng địa chỉ với frame nhưng &frame + 1 nhảy 16 byte, còn frame + 1 nhảy 1 byte.

Pointer arithmetic

p + n tiến n * sizeof(*p) byte. Chỉ được trỏ trong phạm vi mảng hoặc một phần tử sau cuối; tạo con trỏ ra ngoài phạm vi đó (kể cả không dereference) đã là UB. Trừ hai con trỏ chỉ hợp lệ khi cùng một mảng, kết quả kiểu ptrdiff_t.

Truy cập thanh ghi bằng con trỏ

#define GPIOA_BASE   0x40020000UL
#define GPIOA_ODR    (*(volatile uint32_t *)(GPIOA_BASE + 0x14))

GPIOA_ODR |= (1u << 5);             // bật PA5

// Kiểu CMSIS: struct ánh xạ đúng offset thanh ghi
typedef struct {
    volatile uint32_t MODER;    // 0x00
    volatile uint32_t OTYPER;   // 0x04
    volatile uint32_t OSPEEDR;  // 0x08
    volatile uint32_t PUPDR;    // 0x0C
    volatile const uint32_t IDR;// 0x10 chỉ đọc
    volatile uint32_t ODR;      // 0x14
    volatile uint32_t BSRR;     // 0x18
} gpio_regs_t;
#define GPIOA ((gpio_regs_t *)GPIOA_BASE)

GPIOA->BSRR = (1u << 5);            // set PA5, atomic, không cần đọc trước
GPIOA->BSRR = (1u << (5 + 16));     // reset PA5

Dùng struct cho thanh ghi hoạt động được vì các thành viên uint32_t liên tiếp không có padding. Nên thêm _Static_assert(offsetof(gpio_regs_t, BSRR) == 0x18, "layout"); để chắc chắn.

Function pointer

typedef void (*handler_t)(const uint8_t *payload, size_t len);

static void on_ping(const uint8_t *p, size_t n);
static void on_read(const uint8_t *p, size_t n);

static const handler_t handlers[] = {   // bảng dispatch đặt trong Flash
    [0x01] = on_ping,
    [0x02] = on_read,
};

void dispatch(uint8_t cmd, const uint8_t *p, size_t n) {
    if (cmd < ARRAY_SIZE(handlers) && handlers[cmd]) handlers[cmd](p, n);
}

Function pointer là nền tảng của callback, bảng vector ngắt, driver interface (struct chứa các con trỏ hàm như struct file_operations trong Linux) và state machine dạng bảng.

MCU / bare-metalNULL không gây lỗi trên Cortex-M

Địa chỉ 0 trên Cortex-M thường là đầu Flash (bảng vector). Đọc *(uint32_t *)0 trả về giá trị stack pointer ban đầu thay vì crash. Lỗi dereference NULL vì thế có thể chạy "bình thường" và gây hậu quả ở chỗ khác. Có thể cấu hình MPU chặn vùng 0x0 để bắt lỗi này khi debug.

void* và generic code

void * chuyển ngầm định sang mọi con trỏ đối tượng trong C (C++ thì không). Không làm arithmetic trên void * (GCC cho phép như extension, coi kích thước là 1). Callback thường nhận thêm một void *ctx để truyền ngữ cảnh mà không cần biến toàn cục.

Struct: alignment, padding, packing

Mỗi kiểu có alignment: địa chỉ của nó phải chia hết cho một số (thường bằng kích thước với kiểu cơ bản). Compiler chèn padding để thỏa mãn alignment của từng thành viên và của cả struct (để mảng struct cũng thẳng hàng).

struct a { uint8_t x; uint32_t y; uint8_t z; };   // 1 + 3 pad + 4 + 1 + 3 pad = 12
struct b { uint32_t y; uint8_t x; uint8_t z; };   // 4 + 1 + 1 + 2 pad = 8

Quy tắc: sắp xếp thành viên từ alignment lớn đến nhỏ để giảm padding. Kiểm tra bằng sizeof và offsetof, khóa layout bằng _Static_assert.

packed

__attribute__((packed)) bỏ padding. Dùng khi struct phải khớp từng byte với một định dạng ngoài (frame giao thức, header file). Cái giá:

  • Truy cập thành viên lệch alignment chậm hơn: compiler sinh nhiều lệnh đọc byte rồi ghép.
  • Cortex-M0/M0+ không hỗ trợ unaligned access: nếu lấy địa chỉ thành viên packed rồi truy cập qua con trỏ uint32_t * sẽ HardFault. Cortex-M3/M4 cho phép unaligned với LDR/STR đơn nhưng vẫn fault với LDRD/LDM.
  • GCC cảnh báo -Waddress-of-packed-member khi lấy địa chỉ như vậy.
MẹoCách an toàn để parse frame

Thay vì ép (struct hdr *)rx_buf, hãy đọc từng trường bằng hàm có dịch bit (xem phần Endianness) hoặc memcpy vào struct thường. Vừa tránh unaligned access, vừa tránh vi phạm strict aliasing, vừa độc lập với endianness.

Flexible array member và container_of

struct msg {
    uint16_t len;
    uint8_t  type;
    uint8_t  data[];            // C99: phải là thành viên cuối, sizeof(struct msg) không tính nó
};
struct msg *m = malloc(sizeof *m + n);

#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

container_of lấy con trỏ struct cha từ con trỏ tới một thành viên. Đây là nền tảng của intrusive linked list trong Linux kernel (struct list_head nằm bên trong struct dữ liệu) và được dùng nhiều trong driver.

Thao tác bit và bit field

#define BIT(n)            (1u << (n))
#define SET_BIT(r, m)     ((r) |=  (m))
#define CLR_BIT(r, m)     ((r) &= ~(m))
#define TGL_BIT(r, m)     ((r) ^=  (m))
#define TST_BIT(r, m)     (((r) & (m)) != 0u)

// Ghi một trường nhiều bit: xóa trường cũ rồi OR giá trị mới
#define FIELD_SET(r, mask, shift, v) \
    ((r) = ((r) & ~(mask)) | (((uint32_t)(v) << (shift)) & (mask)))

FIELD_SET(GPIOA->MODER, 0x3u << 10, 10, 0x1u);   // PA5 output mode

Luôn dùng hằng unsigned (1u, 0x3u) khi dịch bit. 1 << 31 với int 32-bit là undefined behavior vì kết quả không biểu diễn được trong int.

Một số mẹo hay hỏi:

Mục đích Biểu thức
Kiểm tra lũy thừa của 2 x && !(x & (x - 1))
Xóa bit 1 thấp nhất x & (x - 1)
Lấy bit 1 thấp nhất x & -x (với unsigned)
Đếm bit 1 __builtin_popcount(x) hoặc vòng x &= x - 1
Làm tròn lên bội số của 2^k (x + (A - 1)) & ~(A - 1)

Vì sao không dùng bit field cho thanh ghi và giao thức

struct ctrl { uint32_t en : 1; uint32_t mode : 3; uint32_t div : 4; };

Chuẩn C để implementation-defined: thứ tự cấp phát bit trong một đơn vị (từ LSB hay MSB), việc bit field có được vắt qua hai đơn vị không, kiểu int trơn là có dấu hay không. Ngoài ra ghi một bit field luôn là read-modify-write cả word, có thể không đúng với thanh ghi W1C. Vì vậy driver và giao thức dùng mask + shift. Bit field vẫn ổn cho cờ trạng thái nội bộ cần tiết kiệm RAM.

Endianness

Little-endian lưu byte thấp ở địa chỉ thấp (x86, hầu hết ARM Cortex-M, RISC-V). Big-endian lưu byte cao trước (network byte order, nhiều giao thức công nghiệp, một số PowerPC).

static inline uint32_t rd_be32(const uint8_t *p) {
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) |
           ((uint32_t)p[2] << 8)  |  (uint32_t)p[3];
}
static inline void wr_le16(uint8_t *p, uint16_t v) {
    p[0] = (uint8_t)v;
    p[1] = (uint8_t)(v >> 8);
}

Đọc ghi bằng dịch bit như trên đúng trên mọi CPU, không cần biết CPU là endian gì, không có unaligned access. Compiler hiện đại nhận ra mẫu này và sinh một lệnh load + REV khi có thể.

Embedded LinuxHàm có sẵn

Userspace: htonl/ntohl, htobe32/le32toh trong <endian.h>. Kernel: cpu_to_be32(), le16_to_cpu(), kiểu __be32 để công cụ sparse bắt lỗi quên chuyển đổi.

Cast (uint32_t *)buf rồi đọc vừa phụ thuộc endianness, vừa có thể unaligned, vừa có thể vi phạm strict aliasing: ba lỗi trong một dòng.

Kiểu số nguyên và integer promotion

Kiểu có độ rộng cố định

Dùng <stdint.h>: uint8_t, int16_t, uint32_t... cho dữ liệu phần cứng và giao thức. int có thể là 16-bit trên MSP430/AVR. size_t cho kích thước, uintptr_t khi cần lưu địa chỉ dưới dạng số. In bằng macro PRIu32 trong <inttypes.h>.

Cẩn thậnchar có dấu hay không là tùy nền tảng

GCC trên ARM mặc định char là unsigned, trên x86 là signed. Code char c = 0xFF; if (c == -1) cho kết quả khác nhau. Với byte dữ liệu luôn dùng uint8_t, với chữ dùng char.

Integer promotion

Trước khi tính toán, mọi toán hạng có kiểu nhỏ hơn int (char, short, uint8_t, uint16_t, bit field) được promote lên int (nếu int chứa được mọi giá trị của kiểu gốc), ngược lại lên unsigned int.

uint8_t a = 0xFF;
if (~a == 0x00) { }          // không bao giờ đúng: a -> int 0x000000FF, ~a = 0xFFFFFF00
if ((uint8_t)~a == 0) { }    // đúng ý

uint16_t x = 0xFFFF;
uint32_t y = x * x;          // x promote lên int (signed 32-bit): 65535*65535 tràn int -> UB!
uint32_t z = (uint32_t)x * x;// đúng

uint8_t len = 200;
if (len + 100 > 255) { }     // đúng: phép cộng làm ở kiểu int, không bị cắt

Usual arithmetic conversions

Khi hai toán hạng khác kiểu, kiểu "lớn hơn" thắng; nếu cùng hạng thì unsigned thắng signed:

int i = -1;
unsigned int u = 1;
if (i < u) { }               // sai: -1 bị đổi thành UINT_MAX
size_t n = strlen(s);
for (int k = n - 1; k >= 0; k--) { }   // ổn; nhưng viết size_t k thì k >= 0 luôn đúng -> lặp vô hạn

Bật -Wall -Wextra -Wconversion -Wsign-compare để compiler chỉ ra các chỗ này.

Tràn số

  • Unsigned tràn là định nghĩa rõ: quay vòng modulo 2^N. Dùng được cho timestamp: (uint32_t)(now - start) >= timeout vẫn đúng khi tick counter quay vòng.
  • Signed tràn là undefined behavior. Compiler được giả định nó không xảy ra, nên if (x + 1 < x) có thể bị xóa luôn.
  • Dịch bit: dịch số âm sang trái, hoặc dịch với số bit ≥ độ rộng kiểu đều là UB. Dịch phải số âm là implementation-defined.

Undefined, unspecified và implementation-defined behavior

Loại Ý nghĩa Ví dụ
Implementation-defined Compiler chọn và phải ghi tài liệu Kích thước int, char có dấu không, dịch phải số âm, layout bit field
Unspecified Có vài khả năng hợp lệ, không cần ghi tài liệu, có thể khác nhau mỗi lần Thứ tự tính các đối số f(a(), b())
Undefined (UB) Chuẩn không đặt ra yêu cầu nào; compiler giả định không xảy ra Tràn signed, dereference NULL, truy cập ngoài mảng, vi phạm strict aliasing, dùng biến chưa khởi tạo, sửa một biến hai lần không có sequence point

UB nguy hiểm vì compiler tối ưu dựa trên giả định UB không xảy ra. Ví dụ kinh điển:

int read_reg(struct dev *d) {
    int v = d->status;       // dereference trước
    if (d == NULL) return -1;// compiler suy ra d != NULL ở dòng trên, xóa luôn phép kiểm tra này
    return v;
}

Các ví dụ khác: i = i++ + 1; (sửa i hai lần không có thứ tự), a[i] = i++;, vòng lặp đọc a[N] vượt mảng khiến compiler biến vòng lặp thành vô hạn.

MẹoCông cụ bắt UB

Trên host: -fsanitize=undefined,address (UBSan, ASan). Static analysis: cppcheck, clang-tidy, PC-lint, các bộ kiểm tra MISRA. Đây là lý do nên chạy unit test của firmware trên máy tính (xem Module 13).

Strict aliasing và type punning

Quy tắc strict aliasing: một đối tượng chỉ được truy cập qua lvalue có kiểu tương thích với nó (cộng thêm phiên bản signed/unsigned, có qualifier, và kiểu ký tự char/unsigned char được đọc mọi thứ). Compiler dựa vào quy tắc này để giả định float * và int * không trỏ cùng chỗ.

float f = 1.0f;
uint32_t bits1 = *(uint32_t *)&f;     // vi phạm strict aliasing -> UB
uint32_t bits2;
memcpy(&bits2, &f, sizeof bits2);     // đúng, compiler tối ưu thành một lệnh mov
union { float f; uint32_t u; } pun = { .f = 1.0f };
uint32_t bits3 = pun.u;               // hợp lệ trong C (C99 TC3 trở đi), là UB trong C++

Nhiều dự án Embedded (và Linux kernel) build với -fno-strict-aliasing để an toàn với code cũ, đổi lại mất một số tối ưu.

restrict

restrict (C99) là lời hứa của lập trình viên: trong phạm vi con trỏ đó, vùng nhớ nó trỏ tới chỉ được truy cập qua nó. Compiler nhờ đó có thể vector hóa và giữ giá trị trong thanh ghi. Đó là khác biệt giữa memcpy(void *restrict, const void *restrict, size_t) (hai vùng không được chồng nhau) và memmove (cho phép chồng nhau). Hứa sai là UB.

Preprocessor và macro

#define SQUARE(x)  ((x) * (x))           // ngoặc quanh tham số VÀ cả biểu thức
int r = SQUARE(i++);                      // i tăng hai lần, UB: dùng static inline thay thế

#define LOG_ERR(fmt, ...)  do { \
        log_write(LVL_ERR, __FILE__, __LINE__, fmt, ##__VA_ARGS__); \
    } while (0)                           // do-while(0) để macro dùng an toàn sau if không có ngoặc

#define STR(x)   #x                       // stringify
#define CAT(a,b) a##b                     // token pasting
  • Ưu tiên static inline thay cho macro dạng hàm: có kiểm tra kiểu, tham số chỉ tính một lần, debug được. Macro chỉ cần khi phải dùng #, ##, __FILE__/__LINE__, hoặc hằng số cho preprocessor (#if).
  • _Static_assert(cond, "msg") (C11) kiểm tra lúc compile: kích thước struct, offset thanh ghi, kích thước buffer là lũy thừa 2.
  • Include guard #ifndef UART_H / #define UART_H / #endif hoặc #pragma once.

X-macro

Kỹ thuật giữ nhiều bảng đồng bộ từ một nguồn duy nhất:

#define ERR_LIST(X)            \
    X(ERR_OK,       "ok")      \
    X(ERR_TIMEOUT,  "timeout") \
    X(ERR_CRC,      "crc")

#define AS_ENUM(id, s)  id,
#define AS_STR(id, s)   s,
typedef enum { ERR_LIST(AS_ENUM) ERR_COUNT } err_t;
static const char *const err_str[] = { ERR_LIST(AS_STR) };
_Static_assert(ARRAY_SIZE(err_str) == ERR_COUNT, "err table");

Memory layout và storage

01Các section .text, .rodata, .data, .bss chứa gì? Trên MCU mỗi section nằm ở Flash hay RAM?Hay hỏi
  • .text: code → Flash. .rodata: hằng và chuỗi literal → Flash.
  • .data: biến toàn cục/static có giá trị khởi tạo khác 0 → chạy ở RAM, nhưng giá trị ban đầu lưu ở Flash. Startup code copy từ Flash sang RAM.
  • .bss: biến toàn cục/static bằng 0 hoặc không khởi tạo → RAM, startup code ghi 0. Không tốn Flash.

Ý ghi điểm: nói được khái niệm LMA/VMA và vì sao static const tiết kiệm RAM.

02Biến static trong hàm khác biến cục bộ thường ở điểm nào?Hay hỏi

Biến cục bộ thường nằm trên stack, mất khi hàm trả về. Biến static cục bộ nằm ở .data/.bss, sống suốt chương trình, giữ giá trị giữa các lần gọi, được khởi tạo một lần trước khi chương trình chạy. Phạm vi nhìn thấy vẫn chỉ trong hàm. Lưu ý: hàm dùng static cục bộ không reentrant và không an toàn khi gọi từ nhiều task/ISR.

03static ở mức file có tác dụng gì?

Đổi linkage thành internal: tên chỉ dùng được trong file .c đó. Lợi ích: đóng gói module, tránh trùng tên khi link, compiler biết hết mọi chỗ gọi nên dễ inline và loại bỏ code không dùng.

04Stack overflow trên MCU biểu hiện thế nào và phát hiện ra sao?Hay hỏi

Không có MMU nên tràn stack ghi đè âm thầm lên .bss/heap; triệu chứng là biến toàn cục đổi giá trị vô cớ hoặc HardFault ở chỗ không liên quan. Phát hiện: stack painting + đo high-water mark, MPU guard region ở đáy stack, -fstack-usage + phân tích call graph, cơ chế kiểm tra của RTOS (configCHECK_FOR_STACK_OVERFLOW). Phòng ngừa: tránh đệ quy, tránh mảng lớn trên stack, đặt buffer lớn thành static.

05extern dùng để làm gì? Định nghĩa và khai báo khác nhau ra sao?

Khai báo (declaration) giới thiệu tên và kiểu; định nghĩa (definition) cấp phát bộ nhớ. extern int x; trong header là khai báo; int x = 0; trong đúng một file .c là định nghĩa. Từ GCC 10 (-fno-common), định nghĩa trùng ở hai file sẽ báo lỗi link.

const và volatile

06volatile làm gì? Khi nào cần dùng?Hay hỏi

Báo compiler rằng giá trị có thể đổi ngoài tầm nhìn của nó, nên mỗi lần đọc/ghi trong source phải thực hiện đúng một truy cập bộ nhớ, không được cache trong thanh ghi hay bỏ đi. Dùng cho: thanh ghi ngoại vi, biến dùng chung giữa ISR và main, biến cục bộ sửa giữa setjmp/longjmp.

07volatile có làm biến thành atomic không? Có thay được mutex không?Hay hỏi

Không. volatile không đảm bảo atomic (x++ vẫn là đọc-sửa-ghi), không tạo memory barrier phần cứng, không ngăn compiler đổi thứ tự với truy cập không volatile. Trên MCU cần critical section (tắt ngắt) hoặc atomic (LDREX/STREX trên M3+). Trên Linux dùng _Atomic/std::atomic hoặc mutex.

08Một biến có thể vừa const vừa volatile không? Ví dụ?

Có. const volatile nghĩa là code không được ghi, nhưng phần cứng có thể thay đổi giá trị. Ví dụ thanh ghi status hay input data register chỉ đọc. CMSIS định nghĩa #define __I volatile const.

09Phân biệt const int *p, int const *p, int *const p.

Hai cái đầu giống nhau: con trỏ tới int hằng, không sửa được *p nhưng đổi được p. int *const p: con trỏ hằng, không đổi được p nhưng sửa được *p. Mẹo: đọc từ phải sang trái.

10Vì sao REG |= FLAG có thể gây bug với thanh ghi write-1-to-clear?

|= đọc giá trị hiện tại (các cờ khác đang bằng 1), OR thêm, rồi ghi lại. Với thanh ghi W1C, ghi 1 vào các cờ kia sẽ xóa chúng ngoài ý muốn. Phải ghi trực tiếp REG = FLAG;. Cùng nhóm vấn đề: read-modify-write trên ODR có thể bị ISR chen giữa, nên dùng thanh ghi set/reset riêng như BSRR.

Pointer, array, struct

11Kết quả sizeof của mảng truyền vào hàm là gì? Vì sao?Hay hỏi

Là kích thước con trỏ (4 trên Cortex-M, 8 trên Linux 64-bit), vì tham số kiểu mảng được điều chỉnh thành con trỏ. Muốn biết độ dài phải truyền thêm tham số len. Macro ARRAY_SIZE chỉ đúng với mảng thật trong cùng scope.

12Viết macro truy cập thanh ghi tại địa chỉ 0x40020014.

#define REG (*(volatile uint32_t *)0x40020014u). Phải có volatile để compiler không bỏ qua hoặc gộp truy cập. Trong code thực tế nên dùng struct kiểu CMSIS ánh xạ cả khối thanh ghi.

13Tính sizeof(struct { char a; int b; char c; }) trên máy 32-bit. Làm sao giảm?

12 byte: a (1) + 3 padding + b (4) + c (1) + 3 padding cuối để mảng struct vẫn thẳng hàng. Sắp lại {int b; char a; char c;} còn 8. Hoặc dùng packed nếu cần layout byte-chính xác, chấp nhận truy cập chậm và rủi ro unaligned.

14__attribute__((packed)) có rủi ro gì trên Cortex-M0?Hay hỏi

Cortex-M0/M0+ không hỗ trợ truy cập không thẳng hàng. Truy cập trực tiếp qua tên thành viên thì compiler tự sinh các lệnh đọc byte nên vẫn đúng (chỉ chậm), nhưng nếu lấy địa chỉ thành viên rồi dùng qua con trỏ uint32_t * thì lệnh LDR không thẳng hàng sẽ gây HardFault. M3/M4 hỗ trợ LDR/STR không thẳng hàng nhưng LDRD/LDM vẫn fault.

15container_of hoạt động thế nào?

Lấy địa chỉ thành viên trừ đi offsetof(type, member) để ra địa chỉ đầu struct chứa nó. Dùng trong intrusive list (list_head), driver Linux lấy struct thiết bị riêng từ struct con nhúng bên trong.

16Dereference NULL trên Cortex-M có crash không?

Thường không: địa chỉ 0 là đầu Flash/bảng vector, đọc vẫn ra dữ liệu. Ghi có thể bị bỏ qua hoặc gây BusFault tùy chip. Vì vậy lỗi NULL dễ bị che giấu; có thể dùng MPU chặn vùng địa chỉ thấp khi debug.

Bit, endianness, integer

17Viết các thao tác set, clear, toggle, test bit n.

Set r |= (1u << n), clear r &= ~(1u << n), toggle r ^= (1u << n), test (r >> n) & 1u. Dùng hằng unsigned để tránh UB khi n = 31.

18Kiểm tra số có phải lũy thừa của 2?

x != 0 && (x & (x - 1)) == 0. x & (x - 1) xóa bit 1 thấp nhất; nếu chỉ có một bit 1 thì kết quả bằng 0.

19Vì sao không nên dùng bit field để mô tả thanh ghi hoặc frame giao thức?Hay hỏi

Thứ tự bit, việc vắt qua đơn vị lưu trữ và dấu của bit field int đều là implementation-defined, nên code không portable giữa compiler. Ghi bit field là read-modify-write cả word, nguy hiểm với thanh ghi W1C. Dùng mask và shift thay thế.

20Little-endian và big-endian là gì? Viết hàm kiểm tra và hàm đọc số big-endian từ buffer.Hay hỏi

Little-endian để byte thấp ở địa chỉ thấp. Kiểm tra: uint16_t x = 1; return *(uint8_t *)&x == 1;. Đọc big-endian an toàn: ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) | ((uint32_t)p[2] << 8) | p[3] — chạy đúng trên mọi CPU, không phụ thuộc alignment.

21uint8_t a = 0xFF; if (~a == 0) cho kết quả gì?Hay hỏi

Sai (false). a được promote lên int có giá trị 255, ~a là 0xFFFFFF00 (= -256), khác 0. Phải ép kiểu: (uint8_t)~a == 0.

22So sánh -1 < 1u cho kết quả gì?

False. Theo usual arithmetic conversions, int -1 đổi thành unsigned int bằng UINT_MAX. Bật -Wsign-compare để bắt.

23Tràn số signed và unsigned khác nhau thế nào? Ứng dụng?

Unsigned tràn được định nghĩa, quay vòng modulo 2^N. Signed tràn là UB. Ứng dụng: tính thời gian trôi qua với tick counter 32-bit (uint32_t)(now - start) vẫn đúng khi counter quay vòng, miễn là khoảng thời gian nhỏ hơn 2^32 tick.

24char trên ARM là signed hay unsigned?

GCC cho ARM mặc định char là unsigned (x86 là signed). Code phụ thuộc dấu của char có thể chạy khác khi port. Dữ liệu byte nên dùng uint8_t/int8_t rõ ràng.

UB, aliasing, macro

25Undefined, unspecified và implementation-defined behavior khác nhau thế nào? Cho ví dụ.

Implementation-defined: compiler chọn và ghi tài liệu (kích thước int, dịch phải số âm). Unspecified: một trong vài kết quả hợp lệ, không cần ghi tài liệu (thứ tự tính đối số hàm). Undefined: không có yêu cầu nào, compiler tối ưu như thể nó không xảy ra (tràn signed, truy cập ngoài mảng, vi phạm strict aliasing).

26Strict aliasing là gì? Cách type-punning float sang uint32_t đúng chuẩn?Hay hỏi

Quy tắc cho phép compiler giả định con trỏ khác kiểu không trỏ cùng vùng nhớ (trừ kiểu ký tự). Ép *(uint32_t *)&f vi phạm quy tắc. Cách đúng: memcpy(&u, &f, 4) (compiler tối ưu thành 1 lệnh), hoặc union (hợp lệ trong C, không hợp lệ trong C++). C++20 có std::bit_cast.

27restrict là gì? Liên hệ memcpy và memmove.

Lời hứa vùng nhớ chỉ được truy cập qua con trỏ đó trong phạm vi của nó, giúp compiler tối ưu mạnh hơn. memcpy có tham số restrict nên hai vùng không được chồng nhau; memmove xử lý được vùng chồng nhau, đổi lại có thể chậm hơn.

28Vì sao macro nhiều câu lệnh nên bọc trong do { ... } while (0)?

Để macro hoạt động như một câu lệnh duy nhất và đòi dấu ; phía sau. Không có nó, if (x) MACRO(); else ... sẽ lỗi cú pháp hoặc chỉ câu lệnh đầu thuộc nhánh if.

29Macro #define SQUARE(x) x*x có vấn đề gì?Hay hỏi

SQUARE(a + 1) thành a + 1*a + 1. Sửa thành ((x) * (x)) nhưng vẫn còn lỗi tính hai lần: SQUARE(i++) tăng i hai lần (UB). Giải pháp tốt nhất là static inline function.

30malloc có nên dùng trong firmware MCU không?

Thường tránh: phân mảnh heap làm hệ thống chạy lâu rồi hỏng, thời gian cấp phát không tất định, lỗi hết bộ nhớ khó xử lý, MISRA cấm. Thực hành: cấp phát tĩnh, chỉ cấp phát lúc khởi động, hoặc memory pool kích thước cố định. Trên Embedded Linux dùng được nhưng tránh trong đường xử lý realtime.

    volatile: checklist

    Thao tác bit

    r |=  (1u << n);          // set
r &= ~(1u << n);          // clear
r ^=  (1u << n);          // toggle
(r >> n) & 1u;            // test
r = (r & ~M) | ((v << S) & M); // ghi trường
x && !(x & (x - 1));      // lũy thừa 2
x & (x - 1);              // xóa bit 1 thấp nhất
(x + A - 1) & ~(A - 1);   // làm tròn lên bội 2^k

    Integer promotion

    • Kiểu < int → int trước khi tính
    • signed vs unsigned cùng hạng → unsigned thắng
    • ~u8, u16 * u16 là bẫy kinh điển
    • Signed tràn = UB · Unsigned tràn = quay vòng
    • 1 << 31 là UB → dùng 1u << 31
    • char trên ARM GCC là unsigned
    • Cờ: -Wall -Wextra -Wconversion -Wsign-compare

    Struct layout

    • Sắp thành viên từ alignment lớn → nhỏ
    • sizeof gồm cả padding cuối
    • Khóa layout: _Static_assert(offsetof(T, f) == 0x18, "")
    • packed: chậm, M0 fault nếu truy cập qua con trỏ lệch
    • Parse frame: dịch bit hoặc memcpy, không cast con trỏ
