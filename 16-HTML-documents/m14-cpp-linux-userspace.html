Bài 0 · Bức tranh một chương trình C++ trên Linux

Hình dạng điển hình

Dù là daemon trên gateway Embedded Linux hay service trên server, phần lớn chương trình C++ chạy lâu dài trên Linux có cùng một hình dạng:

                       systemd (khởi động, restart, giới hạn tài nguyên)
                                     │
 ┌───────────────────────────────── process ────────────────────────────────┐
 │  main(): đọc cấu hình → tạo các thành phần → nối chúng lại → chạy         │
 │                                                                           │
 │   Event loop thread(s)                     Worker pool                    │
 │   ┌───────────────────────┐   giao việc    ┌──────────────────────┐       │
 │   │ epoll: socket, timer,  │ ─────────────▶ │ việc nặng / chặn:    │       │
 │   │ signalfd, eventfd,     │ ◀───────────── │ nén, mã hóa, DB, I/O │       │
 │   │ fd thiết bị            │   trả kết quả  │ file lớn             │       │
 │   └───────────────────────┘                └──────────────────────┘       │
 │            │                                                              │
 │            ▼                                                              │
 │   Logic nghiệp vụ (không biết socket, không biết thread)                  │
 │            │                                                              │
 │   Adapter ra ngoài: socket, file, /dev/*, D-Bus, process khác             │
 └───────────────────────────────────────────────────────────────────────────┘

Các bài trong module đi qua từng phần của hình này: cách viết API của từng thành phần (Bài 1), quy ước lỗi (Bài 2), cách đóng gói thành thư viện và plugin (Bài 3), cách giữ tài nguyên hệ thống (Bài 4), cách các thành phần gọi lại nhau an toàn (Bài 5), event loop (Bài 6), mô hình đồng thời (Bài 7), nhiều process (Bài 8), và test (Bài 9). Bài 10–11 là các đề low-level design hay gặp khi phỏng vấn.

Năm nguyên tắc xuyên suốt

  1. Sở hữu và vòng đời phải rõ ràng. Với mỗi đối tượng, trả lời được: ai tạo, ai hủy, ai chỉ mượn. Phần lớn crash trong service C++ là dùng đối tượng đã bị hủy (callback gọi vào đối tượng đã chết, thread còn chạy khi đối tượng đã bị xóa).
  2. Mô hình đồng thời phải rõ ràng. Với mỗi dữ liệu, trả lời được: thread nào được chạm vào. Tốt nhất là "chỉ một thread" (thread confinement), dữ liệu đi giữa các thread bằng message. Mutex là lựa chọn thứ hai.
  3. Lõi thuần, vỏ I/O. Logic nghiệp vụ không gọi read, send, time() trực tiếp mà nhận dữ liệu và trả quyết định; phần I/O nằm ở rìa. Lõi khi đó test được nhanh, tất định (Bài 9). Ý tưởng này được gọi là functional core, imperative shell, là bản Linux của dependency inversion ở M08.
  4. Chính sách lỗi theo tầng. Tầng thấp báo lỗi chi tiết, tầng cao quyết định xử lý; lỗi mang theo ngữ cảnh (Bài 2).
  5. Đo trước khi tối ưu. Thread pool, lock-free, zero-copy đều có giá về độ phức tạp. Bắt đầu đơn giản, đo bằng perf, chỉ phức tạp hóa ở chỗ nóng.

Bài 1 · Thiết kế API: sở hữu, tham số và kiểu

Chữ ký hàm nói lên quyền sở hữu

Người đọc chữ ký phải biết hàm có giữ lại đối tượng không, có nhận quyền sở hữu không, có chấp nhận null không. C++ hiện đại diễn đạt được tất cả bằng kiểu:

Chữ ký Nghĩa
void use(const Widget& w) Mượn để đọc trong lúc gọi, không giữ lại, không null
void modify(Widget& w) Mượn để sửa, không giữ lại
void maybe(const Widget* w) Như trên nhưng có thể null
void take(std::unique_ptr<Widget> w) Nhận quyền sở hữu; người gọi phải std::move
void share(std::shared_ptr<Widget> w) Giữ lại một bản đồng sở hữu
std::unique_ptr<Widget> make() Trả quyền sở hữu cho người gọi (factory)
Widget make() Trả giá trị; copy elision làm nó rẻ

Hai quy tắc từ C++ Core Guidelines hay được hỏi:

  • Chỉ nhận shared_ptr khi hàm thực sự giữ lại hoặc chia sẻ quyền sở hữu. Hàm chỉ dùng đối tượng thì nhận Widget&; truyền shared_ptr theo giá trị tốn hai thao tác atomic (tăng, giảm refcount) mỗi lần gọi và ép người gọi phải dùng shared_ptr.
  • Con trỏ thô và tham chiếu không bao giờ mang quyền sở hữu. Gặp T* thì hiểu là "mượn".

Tham số "chìm" (sink): nhận theo giá trị rồi move

Khi hàm (thường là constructor hoặc setter) sẽ lưu tham số lại:

class Endpoint {
public:
    explicit Endpoint(std::string host, std::uint16_t port)   // nhận theo giá trị
        : host_(std::move(host)), port_(port) {}               // rồi move vào thành viên
private:
    std::string host_;
    std::uint16_t port_;
};

Endpoint a("gateway.local", 8883);        // chuỗi tạm: move, không copy
std::string h = load_host();
Endpoint b(h, 8883);                      // lvalue: đúng một lần copy
Endpoint c(std::move(h), 8883);           // không copy

Một hàm duy nhất phục vụ tốt cả lvalue và rvalue, thay vì viết hai overload const std::string& và std::string&&.

View: std::string_view và std::span

Cho tham số chỉ đọc không cần sở hữu, dùng view: một con trỏ cộng độ dài, nhận được từ nhiều kiểu nguồn mà không copy.

std::uint32_t crc32(std::span<const std::byte> data);    // vector, array, mảng C, buffer mmap
bool starts_with_cmd(std::string_view line);             // std::string, literal, char* + len

Bẫy duy nhất nhưng nghiêm trọng: view không giữ dữ liệu sống.

std::string_view name() const { return prefix_ + id_; }  // SAI: view vào chuỗi tạm đã chết

struct Request { std::string_view path; };  // nguy hiểm: path trỏ vào buffer nào? còn sống tới bao giờ?

Quy tắc: dùng view cho tham số; tránh dùng cho giá trị trả về và thành viên trừ khi vòng đời của dữ liệu gốc được đảm bảo rõ ràng (ví dụ view vào chuỗi literal, hoặc vào buffer mà chính đối tượng sở hữu).

const và thread-safety

Thư viện chuẩn đặt ra một quy ước mà code của bạn nên theo: gọi đồng thời các hàm const trên cùng một đối tượng phải an toàn. Nếu hàm const có sửa trạng thái bên trong (cache, bộ đếm thống kê), phần đó phải được đồng bộ:

class RouteTable {
public:
    Route lookup(std::string_view dst) const {
        std::lock_guard g(mtx_);          // mutable mutex: khóa trong hàm const
        ++lookups_;
        return find(dst);
    }
private:
    mutable std::mutex mtx_;
    mutable std::uint64_t lookups_ = 0;
    /* ... */
};

Kiểu mạnh thay cho số trần

void connect(std::string host, int port, int timeout, int retries);   // dễ đảo tham số
connect("broker", 1883, 3, 5000);                                       // biên dịch được, sai

void connect(const ConnectOptions& opt);                                // tốt hơn
connect({.host = "broker", .port = 1883,
         .timeout = std::chrono::seconds(5), .retries = 3});            // C++20 designated init
  • Thời gian luôn dùng std::chrono: std::chrono::milliseconds không thể bị nhầm với giây; phép chuyển đổi là tự động và an toàn.
  • Struct tùy chọn với designated initializer thay cho hàm có nhiều tham số cùng kiểu, có giá trị mặc định từng trường.
  • Kiểu riêng cho giá trị dễ nhầm: struct DeviceId { std::uint32_t v; }; không thể truyền nhầm vào chỗ cần PortNumber.

Khó dùng sai

  • [[nodiscard]] trên hàm trả lỗi hoặc trả tài nguyên: bỏ qua giá trị trả về sinh cảnh báo.
  • Constructor một tham số luôn explicit (trừ khi chuyển đổi ngầm thực sự là ý muốn).
  • Đối tượng giữ tài nguyên duy nhất (fd, thread, kết nối): xóa copy, cho phép move (Bài 4).
  • Rule of Zero: nếu mọi thành viên tự quản lý tài nguyên (std::string, std::vector, unique_ptr, unique_fd), class không cần viết destructor, copy hay move nào. Chỉ class bọc trực tiếp một tài nguyên thô mới cần viết các hàm đặc biệt (Rule of Five).
#include <chrono>
#include <cstdint>
#include <string>

struct ConnectOptions {
    std::string host;
    std::uint16_t port = 1883;
    std::chrono::milliseconds timeout{3000};
    int retries = 3;
    bool tls = false;
};

class Client {
public:
    explicit Client(ConnectOptions opt) : opt_(std::move(opt)) {}
    [[nodiscard]] bool connect();                // bỏ qua kết quả: compiler cảnh báo
    const ConnectOptions& options() const noexcept { return opt_; }
private:
    ConnectOptions opt_;
};

inline bool Client::connect() { return !opt_.host.empty(); }

Bài 2 · Xử lý lỗi

Ba loại "lỗi" khác nhau

Trước khi chọn cơ chế, phân loại:

  1. Lỗi lập trình (bug): vi phạm tiền điều kiện, trạng thái không thể xảy ra. Ví dụ truyền con trỏ null vào hàm cấm null, index vượt biên. Không xử lý được ở runtime một cách có nghĩa: dùng assert, ghi log rồi abort() để có core dump. Cố "phục hồi" chỉ che giấu lỗi.
  2. Lỗi môi trường có thể xảy ra: file không tồn tại, mạng timeout, thiết bị chưa sẵn sàng, dữ liệu đầu vào sai định dạng. Đây là phần của luồng chương trình bình thường, phải được báo về và xử lý.
  3. Cạn tài nguyên: hết bộ nhớ, hết fd. Thường không phục hồi được tại chỗ; trên Linux với overcommit, new hiếm khi ném bad_alloc mà OOM killer ra tay trước.

Cơ chế dưới đây là cho loại 2.

Không có lựa chọn đúng tuyệt đối; điều quan trọng là nhất quán theo tầng và trả lời được vì sao. Hướng phổ biến trong code C++ hiện đại cho Linux:

  • Tầng hệ thống (bọc system call, parser, driver userspace): trả std::expected hoặc std::error_code. Lỗi ở đây là chuyện thường ngày và người gọi gần như luôn muốn xử lý ngay.
  • Tầng nghiệp vụ: tùy codebase. Nếu dùng exception, ném ở chỗ không thể tiếp tục và bắt ở ranh giới đơn vị công việc (một request, một message, một lần xử lý file).
  • Biên: nơi exception không được phép đi qua: callback trong event loop (một handler lỗi không được giết cả loop), thân hàm thread (thoát ra là std::terminate), hàm extern "C" và callback truyền cho thư viện C, destructor. Tại đó bắt hết (catch (...)), ghi log, chuyển thành mã lỗi.

std::expected trong thực tế

#include <charconv>
#include <expected>
#include <string>
#include <string_view>
#include <system_error>

enum class ParseError { empty, not_a_number, out_of_range };

std::expected<int, ParseError> parse_port(std::string_view s) {
    if (s.empty()) return std::unexpected(ParseError::empty);
    int v = 0;
    auto [p, ec] = std::from_chars(s.data(), s.data() + s.size(), v);
    if (ec != std::errc{} || p != s.data() + s.size())
        return std::unexpected(ParseError::not_a_number);
    if (v < 1 || v > 65535) return std::unexpected(ParseError::out_of_range);
    return v;
}

// Kết hợp các bước, lỗi tự lan ra mà không cần if lồng nhau
std::expected<std::string, ParseError> make_url(std::string_view host, std::string_view port) {
    return parse_port(port).transform([&](int p) {

}

errno và std::error_code

System call báo lỗi bằng -1 và errno. Chuyển ngay sang std::error_code để không mất errno (bất kỳ lời gọi thư viện nào sau đó cũng có thể ghi đè nó) và để mang được qua các tầng:

std::error_code last_error() { return {errno, std::generic_category()}; }

int fd = ::open(path, O_RDONLY | O_CLOEXEC);
if (fd < 0) {
    auto ec = last_error();                  // chụp lại NGAY
    log("open {}: {}", path, ec.message());  // "open /etc/app.conf: No such file or directory"
    return std::unexpected(ec);
}
// muốn ném: throw std::system_error(ec, "open /etc/app.conf");

std::error_code gồm một số nguyên cộng một category (generic_category cho giá trị errno, hoặc category riêng của thư viện). So sánh được với điều kiện chung: if (ec == std::errc::no_such_file_or_directory). Thư viện có enum lỗi riêng có thể đăng ký một category để enum của mình chuyển ngầm thành error_code (Boost.Asio làm vậy).

Lỗi phải mang ngữ cảnh

"No such file or directory" một mình gần như vô dụng khi đọc log. Mỗi tầng khi chuyển lỗi lên nên thêm ngữ cảnh của mình: file nào, thao tác gì, request id nào. Với exception: bắt, rồi ném lỗi mới kèm std::throw_with_nested; với expected: kiểu lỗi chứa thêm chuỗi mô tả hoặc danh sách ngữ cảnh.

noexcept

  • Đánh dấu noexcept cho move constructor và move assignment: std::vector chỉ dùng move khi phát triển nếu move là noexcept, nếu không nó copy để giữ đảm bảo strong exception safety.
  • Destructor mặc định đã là noexcept. Ném exception ra khỏi destructor là std::terminate.
  • Hàm noexcept mà vẫn ném: std::terminate, không unwind. Chỉ đánh dấu khi chắc chắn, không phải "cho nhanh".
  • Hàm swap, hàm giải phóng tài nguyên, hàm dùng trong destructor: nên noexcept.

Tự kiểm traMột callback được đăng ký với thư viện C (ví dụ `libmosquitto` gọi `on_message`). Bên trong callback, code C++ có thể ném exception. Rủi ro là gì và xử lý thế nào?

ABI là gì và cái gì làm vỡ nó

API là hợp đồng ở mức mã nguồn (code biên dịch được không). ABI là hợp đồng ở mức nhị phân: một chương trình đã biên dịch với phiên bản cũ của thư viện có chạy đúng với file .so mới không. ABI của C++ gồm: cách gọi hàm, cách mã hóa tên (name mangling), bố cục đối tượng (kích thước, vị trí từng thành viên), bố cục vtable, cách ném exception, và bố cục của chính các kiểu thư viện chuẩn.

pImpl: tách hoàn toàn phần riêng tư khỏi header

Ý tưởng: header chỉ khai báo một con trỏ tới struct cài đặt; mọi thành viên dữ liệu nằm trong file .cpp. Kích thước class public không bao giờ đổi, thêm trường thoải mái mà không vỡ ABI.

// ===== mqtt_client.h (public) =====
#include <memory>
#include <string>

class MqttClient {
public:
    explicit MqttClient(std::string broker);
    ~MqttClient();                                   // KHAI BÁO ở đây
    MqttClient(MqttClient&&) noexcept;
    MqttClient& operator=(MqttClient&&) noexcept;

    bool publish(const std::string& topic, const std::string& payload);
    std::size_t published() const;
private:
    struct Impl;                                     // chỉ khai báo trước
    std::unique_ptr<Impl> impl_;
};

// ===== mqtt_client.cpp (riêng tư) =====
// #include <mosquitto.h> chỉ xuất hiện ở đây, người dùng header không cần nó
struct MqttClient::Impl {
    std::string broker;
    std::size_t count = 0;
    // mosquitto* handle; std::mutex m; ... thêm bớt tùy ý mà không vỡ ABI
};

MqttClient::MqttClient(std::string broker)
    : impl_(std::make_unique<Impl>(Impl{std::move(broker)})) {}
MqttClient::~MqttClient() = default;                 // ĐỊNH NGHĨA ở đây, nơi Impl đầy đủ
MqttClient::MqttClient(MqttClient&&) noexcept = default;
MqttClient& MqttClient::operator=(MqttClient&&) noexcept = default;

bool MqttClient::publish(const std::string&, const std::string&) { ++impl_->count; return true; }
std::size_t MqttClient::published() const { return impl_->count; }

Bẫy hay được hỏi: nếu để compiler tự sinh destructor trong header (không khai báo ~MqttClient()), nó sinh code gọi delete trên Impl tại chỗ Impl chưa đầy đủ và lỗi biên dịch "invalid application of sizeof to incomplete type". Phải khai báo destructor (và move) trong header, định nghĩa = default trong .cpp.

Lợi ích ngoài ABI: tường lửa biên dịch. Header không kéo theo <mosquitto.h>, <openssl/...>, nên đổi cài đặt không bắt mọi file include phải biên dịch lại, và người dùng thư viện không phụ thuộc header bên thứ ba. Giá phải trả: một lần cấp phát heap, một lần gián tiếp con trỏ, không inline được hàm truy cập. Không dùng cho class nhỏ ở đường nóng.

Kiểm soát symbol xuất ra

Mặc định trên Linux, mọi symbol không static trong .so đều được xuất. Nên làm ngược lại: ẩn tất cả, chỉ xuất API công khai.

// export.h
#define MYLIB_API __attribute__((visibility("default")))

class MYLIB_API MqttClient { /* ... */ };     // chỉ class này được xuất

Biên dịch với -fvisibility=hidden -fvisibility-inlines-hidden. Lợi ích: bảng symbol động nhỏ (nạp nhanh hơn), compiler tối ưu được các hàm nội bộ, và bề mặt ABI chỉ là những gì bạn chủ ý công bố.

SONAME và đánh số phiên bản

Liên kết với -Wl,-soname,libmqttc.so.2. Chương trình ghi lại SONAME (readelf -d app | grep NEEDED). Quy tắc: vỡ ABI thì tăng số major (.so.3), để chương trình cũ vẫn nạp .so.2 cũ. Công cụ kiểm tra: abidiff (libabigail) so sánh ABI hai phiên bản .so trong CI.

Ranh giới C: ABI ổn định nhất

Khi thư viện cần dùng từ ngôn ngữ khác (Python ctypes, Rust, Go) hoặc từ binary biên dịch bằng compiler khác, xuất API C bọc quanh phần C++:

extern "C" {
typedef struct mqttc mqttc_t;                    // opaque handle

MYLIB_API mqttc_t* mqttc_create(const char* broker);
MYLIB_API int      mqttc_publish(mqttc_t*, const char* topic, const void* data, size_t len);
MYLIB_API void     mqttc_destroy(mqttc_t*);      // giải phóng trong CÙNG thư viện đã cấp phát
}

Quy tắc: chỉ kiểu C qua ranh giới (không std::string, không exception), handle mờ, hàm create/destroy đi cặp, mỗi hàm extern "C" bắt mọi exception bên trong và đổi thành mã lỗi.

Plugin với dlopen

Plugin cho phép thêm tính năng (một driver thiết bị, một codec, một giao thức) mà không build lại chương trình chính. Mẫu chuẩn:

  1. Chương trình chính định nghĩa interface (class trừu tượng) và một số phiên bản API.
  2. Mỗi plugin là một .so xuất hai hàm extern "C" (tên không bị mangle nên dlsym tìm được): tạo và hủy đối tượng.
  3. Chương trình chính dlopen, dlsym, kiểm tra phiên bản, gói đối tượng vào unique_ptr với deleter gọi hàm hủy của plugin.
// ===== codec_plugin.h: dùng chung giữa host và plugin =====
#include <cstdint>
#include <string>
#include <vector>

inline constexpr int kCodecApiVersion = 1;

class Codec {
public:
    virtual ~Codec() = default;
    virtual std::string name() const = 0;
    virtual std::vector<std::uint8_t> encode(const std::vector<std::uint8_t>& in) = 0;
};

extern "C" {
using CreateCodecFn  = Codec* (*)(int api_version);  // trả nullptr nếu không hỗ trợ version
using DestroyCodecFn = void (*)(Codec*);
}

// ===== xor_codec.cpp → libxor_codec.so =====
#include "codec_plugin.h"

namespace {
class XorCodec final : public Codec {
public:
    std::string name() const override { return "xor"; }
    std::vector<std::uint8_t> encode(const std::vector<std::uint8_t>& in) override {
        std::vector<std::uint8_t> out(in);
        for (auto& b : out) b ^= 0x5A;
        return out;
    }
};
}  // namespace

extern "C" __attribute__((visibility("default")))
Codec* create_codec(int api_version) {
    if (api_version != kCodecApiVersion) return nullptr;
    try { return new XorCodec; } catch (...) { return nullptr; }   // không để exception thoát ra
}

extern "C" __attribute__((visibility("default")))
void destroy_codec(Codec* c) { delete c; }                         // xóa trong cùng .so

// ===== host =====
#include <dlfcn.h>
#include <memory>
#include <stdexcept>
#include <string>
#include "codec_plugin.h"

class LoadedCodec {
public:
    explicit LoadedCodec(const std::string& path) {
        lib_.reset(dlopen(path.c_str(), RTLD_NOW | RTLD_LOCAL));
        if (!lib_) throw std::runtime_error(dlerror());
        auto create  = reinterpret_cast<CreateCodecFn>(dlsym(lib_.get(), "create_codec"));
        auto destroy = reinterpret_cast<DestroyCodecFn>(dlsym(lib_.get(), "destroy_codec"));
        if (!create || !destroy) throw std::runtime_error("plugin thiếu symbol");
        codec_ = {create(kCodecApiVersion), destroy};
        if (!codec_) throw std::runtime_error("plugin không hỗ trợ API version");
    }
    Codec& operator*() const { return *codec_; }
    Codec* operator->() const { return codec_.get(); }
private:
    struct DlClose { void operator()(void* h) const noexcept { dlclose(h); } };
    // THỨ TỰ QUAN TRỌNG: lib_ khai báo trước nên bị hủy SAU codec_.
    // Đối tượng phải chết trước khi code của nó bị gỡ khỏi bộ nhớ.
    std::unique_ptr<void, DlClose> lib_;
    std::unique_ptr<Codec, DestroyCodecFn> codec_{nullptr, nullptr};
};

// LoadedCodec c("./libxor_codec.so");  auto out = c->encode({1, 2, 3});

Biên dịch plugin: g++ -std=c++20 -fPIC -shared -fvisibility=hidden xor_codec.cpp -o libxor_codec.so.

Những điều cần nói khi bàn về plugin:

  • Vòng đời: mọi đối tượng (và mọi callback, mọi std::function trỏ vào code) đến từ plugin phải bị hủy trước dlclose. Nếu không, lời gọi hàm virtual sau đó nhảy vào vùng nhớ đã bị gỡ.
  • Interface C++ qua plugin yêu cầu host và plugin dùng cùng compiler, cùng thư viện chuẩn, cùng cờ ABI. Nếu plugin do bên thứ ba build độc lập, dùng ranh giới C (vtable tự làm bằng struct con trỏ hàm, như M08).
  • Phiên bản API: luôn có, để từ chối plugin cũ thay vì crash.
  • RTLD_NOW báo lỗi symbol thiếu ngay lúc nạp (thay vì khi gọi); RTLD_LOCAL không để symbol của plugin này ảnh hưởng plugin khác.
Tự kiểm traĐồng nghiệp thêm một trường `int retries_` vào giữa class public `MqttClient` (không dùng pImpl) trong `libmqttc.so.2`, build lại thư viện và cập nhật lên thiết bị, nhưng không build lại ứng dụng. Điều gì có thể xảy ra?

Ứng dụng cũ được biên dịch với sizeof(MqttClient) và offset thành viên cũ: nó cấp phát thiếu bộ nhớ cho đối tượng (trên stack hoặc heap), và code inline trong ứng dụng đọc/ghi các trường ở offset cũ, lệch so với thư viện mới. Kết quả là hỏng bộ nhớ ngẫu nhiên, khó debug, vì nạp thư viện vẫn thành công (tên symbol không đổi). Đúng quy trình: đây là thay đổi vỡ ABI, phải tăng SONAME lên .so.3; hoặc dùng pImpl để thêm trường không bao giờ vỡ ABI; và chạy abidiff trong CI để bắt lỗi kiểu này.

Bài 4 · RAII cho tài nguyên hệ thống

Tài nguyên nào cần bọc

Mọi thứ "mở" thì phải "đóng": file descriptor (file, socket, pipe, epoll, timerfd, eventfd, inotify…), vùng mmap, FILE*, DIR*, handle dlopen, kết quả getaddrinfo, process con (phải waitpid để không thành zombie), thread, file tạm, signal mask, thư mục làm việc đã đổi. Một service chạy hàng tháng chỉ cần rò một fd mỗi lần lỗi là cuối cùng chạm giới hạn (ulimit -n, thường 1024) và mọi accept/open thất bại với EMFILE.

RAII (Resource Acquisition Is Initialization): tài nguyên được lấy trong constructor và trả trong destructor của một đối tượng có vòng đời rõ ràng. Destructor chạy trên mọi đường thoát: return sớm, exception, break.

unique_fd: viết một lần, dùng khắp nơi

#include <unistd.h>
#include <utility>

class unique_fd {
public:
    unique_fd() noexcept = default;
    explicit unique_fd(int fd) noexcept : fd_(fd) {}
    ~unique_fd() { reset(); }

    unique_fd(const unique_fd&) = delete;                 // một fd, một chủ
    unique_fd& operator=(const unique_fd&) = delete;
    unique_fd(unique_fd&& o) noexcept : fd_(o.release()) {}
    unique_fd& operator=(unique_fd&& o) noexcept {
        if (this != &o) reset(o.release());
        return *this;
    }

    int get() const noexcept { return fd_; }
    explicit operator bool() const noexcept { return fd_ >= 0; }
    int release() noexcept { return std::exchange(fd_, -1); }   // trao quyền sở hữu ra ngoài
    void reset(int fd = -1) noexcept {
        if (fd_ >= 0) ::close(fd_);       // KHÔNG thử lại khi EINTR (xem dưới)
        fd_ = fd;
    }
private:
    int fd_ = -1;
};
  • Move-only: sao chép một fd thì hai đối tượng cùng close một số, lần thứ hai có thể đóng nhầm fd mới được cấp cùng số. Đó là lỗi thật, rất khó tìm.
  • release() khi cần trao fd cho API khác tự quản lý (ví dụ fdopen).
  • Về close(): trên Linux, fd luôn được giải phóng kể cả khi close trả EINTR, nên không được gọi lại (lần gọi thứ hai có thể đóng fd vừa được thread khác mở). Nếu quan tâm lỗi ghi bị trì hoãn (NFS, đĩa đầy), gọi fsync trước close và kiểm tra kết quả fsync.

Bọc handle C bằng unique_ptr và deleter

struct FileCloser { void operator()(FILE* f) const noexcept { std::fclose(f); } };
using FilePtr = std::unique_ptr<FILE, FileCloser>;

struct DirCloser { void operator()(DIR* d) const noexcept { ::closedir(d); } };
using DirPtr = std::unique_ptr<DIR, DirCloser>;

struct AddrInfoFree { void operator()(addrinfo* a) const noexcept { ::freeaddrinfo(a); } };
using AddrInfoPtr = std::unique_ptr<addrinfo, AddrInfoFree>;

FilePtr f(std::fopen("/proc/meminfo", "re"));       // "e" = O_CLOEXEC
if (!f) { /* lỗi */ }

Deleter dạng struct không trạng thái không làm tăng kích thước unique_ptr (vẫn bằng một con trỏ), còn unique_ptr<FILE, decltype(&fclose)> phải lưu thêm con trỏ hàm. fclose có thể trả lỗi ghi; với file quan trọng, gọi fflush + kiểm tra trước khi để destructor đóng.

Scope guard: dọn dẹp tùy ý và giao dịch

Không phải dọn dẹp nào cũng xứng đáng có một class. Scope guard chạy một lambda khi ra khỏi scope, trừ khi được hủy kích hoạt:

#include <utility>

template <class F>
class [[nodiscard]] ScopeGuard {
public:
    explicit ScopeGuard(F f) noexcept : f_(std::move(f)) {}
    ~ScopeGuard() { if (active_) f_(); }
    void dismiss() noexcept { active_ = false; }      // "commit": không chạy dọn dẹp nữa
    ScopeGuard(const ScopeGuard&) = delete;
    ScopeGuard& operator=(const ScopeGuard&) = delete;
private:
    F f_;
    bool active_ = true;
};

Mẫu quan trọng trên Embedded Linux, nơi mất điện có thể xảy ra bất kỳ lúc nào: ghi file nguyên tử. Không bao giờ ghi đè trực tiếp file cấu hình; ghi ra file tạm, fsync, rồi rename (thao tác nguyên tử trên cùng filesystem), rồi fsync thư mục để chính việc đổi tên được ghi xuống đĩa.

#include <fcntl.h>
#include <string>
#include <string_view>
#include <system_error>
#include <unistd.h>

std::error_code write_file_atomic(const std::string& dir, const std::string& name,
                                  std::string_view data) {
    auto err = [] { return std::error_code(errno, std::generic_category()); };
    const std::string path = dir + "/" + name;
    const std::string tmp  = path + ".tmp";

    unique_fd fd(::open(tmp.c_str(), O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644));
    if (!fd) return err();
    ScopeGuard remove_tmp([&] { ::unlink(tmp.c_str()); });   // lỗi ở đâu cũng xóa file tạm

    for (std::size_t off = 0; off < data.size();) {           // write có thể ghi thiếu
        ssize_t n = ::write(fd.get(), data.data() + off, data.size() - off);
        if (n < 0) { if (errno == EINTR) continue; return err(); }
        off += static_cast<std::size_t>(n);
    }
    if (::fsync(fd.get()) != 0) return err();                // dữ liệu xuống đĩa
    fd.reset();
    if (::rename(tmp.c_str(), path.c_str()) != 0) return err();
    remove_tmp.dismiss();                                    // commit: file tạm đã thành file thật

    unique_fd d(::open(dir.c_str(), O_RDONLY | O_DIRECTORY | O_CLOEXEC));
    if (d) ::fsync(d.get());                                 // ghi entry thư mục
    return {};
}

Sau khi mất điện, file chỉ có thể là bản cũ đầy đủ hoặc bản mới đầy đủ, không bao giờ là bản ghi dở. C++26 dự kiến có std::scope_exit; hiện nay có trong Library Fundamentals TS và các thư viện như GSL (gsl::finally), Abseil (absl::Cleanup).

Thứ tự hủy thành viên: thread khai báo cuối cùng

Thành viên được hủy theo thứ tự ngược với thứ tự khai báo. Với class sở hữu một thread dùng các thành viên khác, thứ tự này quyết định đúng sai:

class Uploader {
    // SAI: worker_ khai báo đầu nên bị hủy (join) CUỐI CÙNG.
    // Khi ~Uploader chạy, queue_ và client_ đã bị hủy trong lúc worker_ vẫn đang dùng chúng.
    std::jthread worker_;
    BoundedQueue<Job> queue_{100};
    HttpClient client_;
};

class Uploader {
    BoundedQueue<Job> queue_{100};
    HttpClient client_;
    std::jthread worker_;      // ĐÚNG: khai báo cuối → bị hủy (dừng và join) ĐẦU TIÊN
public:
    Uploader() : worker_([this](std::stop_token st) { run(st); }) {}
    ~Uploader() { queue_.close(); }    // thân destructor chạy TRƯỚC khi hủy thành viên:
};                                      // đánh thức worker để nó thấy stop và thoát

Trình tự khi hủy Uploader: thân destructor (queue_.close()) → hủy worker_ (request_stop rồi join) → hủy client_ → hủy queue_. Lưu ý thêm: khởi động thread trong danh sách khởi tạo của thành viên cuối cùng, để các thành viên nó dùng đã được dựng xong; không khởi động thread trong thân constructor nếu sau đó constructor còn có thể ném (thread đang chạy với đối tượng dựng dở).

Tự kiểm traĐoạn code: `int fd = socket(...); if (setsockopt(fd, ...) < 0) throw std::system_error(...); return fd;`. Có vấn đề gì và sửa thế nào?

Khi setsockopt lỗi, exception được ném mà fd chưa được đóng: rò fd. Service chạy lâu với lỗi lặp lại sẽ cạn fd. Sửa: bọc ngay sau khi tạo, unique_fd fd(::socket(AF_INET, SOCK_STREAM | SOCK_CLOEXEC, 0));, mọi đường thoát tự đóng, và trả về unique_fd (move) thay vì int để người gọi cũng nhận quyền sở hữu rõ ràng. Thêm SOCK_CLOEXEC để fd không rò sang process con.

Type erasure: giá trị nhưng đa hình

Khi muốn API nhận "bất kỳ đối tượng nào có write(string_view)" mà không bắt chúng kế thừa một base class và không biến API thành template:

#include <memory>
#include <string_view>
#include <utility>

class AnyWriter {
public:
    template <class W>                                   // nhận bất kỳ kiểu nào có write()
    AnyWriter(W w) : self_(std::make_unique<Model<W>>(std::move(w))) {}

    AnyWriter(const AnyWriter& o) : self_(o.self_->clone()) {}
    AnyWriter& operator=(const AnyWriter& o) { self_ = o.self_->clone(); return *this; }
    AnyWriter(AnyWriter&&) noexcept = default;
    AnyWriter& operator=(AnyWriter&&) noexcept = default;

    void write(std::string_view s) { self_->write(s); }

private:
    struct Concept {                                     // interface nội bộ
        virtual ~Concept() = default;
        virtual void write(std::string_view) = 0;
        virtual std::unique_ptr<Concept> clone() const = 0;
    };
    template <class W>
    struct Model final : Concept {                       // bọc kiểu cụ thể
        explicit Model(W w) : w_(std::move(w)) {}
        void write(std::string_view s) override { w_.write(s); }
        std::unique_ptr<Concept> clone() const override { return std::make_unique<Model>(*this); }
        W w_;
    };
    std::unique_ptr<Concept> self_;
};

Đây chính là cách std::function hoạt động. Kiểu người dùng (ConsoleWriter, FileWriter, một writer giả trong test) không cần biết AnyWriter tồn tại. Thư viện thật thêm small buffer optimization: đối tượng nhỏ được đặt ngay trong AnyWriter thay vì heap.

Callback: std::function và các lựa chọn

  • std::function<R(Args...)>: sở hữu, copy được, có thể cấp phát heap khi lambda bắt nhiều dữ liệu (libstdc++ chỉ để gọn trong đối tượng những callable nhỏ, cỡ hai con trỏ). Yêu cầu callable copy được, nên không chứa được lambda bắt unique_ptr.
  • std::move_only_function (C++23): như trên nhưng chấp nhận callable chỉ move được. Hợp cho task trong queue.
  • Tham số kiểu template F&& f: không chi phí, dùng khi gọi ngay trong hàm và không lưu lại.
  • std::function_ref (C++26): tham chiếu không sở hữu tới callable, cho tham số callback gọi ngay.

Vấn đề lớn nhất: callback gọi vào đối tượng đã chết

class Session {
public:
    void start() {
        loop_.run_after(5s, [this] { on_timeout(); });   // bắt this thô
    }
    void on_timeout();
};
// Session bị xóa sau 2 giây. 3 giây sau timer kích hoạt, gọi on_timeout() trên vùng nhớ đã giải phóng.

Đây là lỗi crash phổ biến nhất trong code bất đồng bộ C++. Bốn cách giải quyết:

  1. Hủy đăng ký trong destructor. run_after trả về một handle RAII; Session giữ handle làm thành viên, destructor của handle hủy timer. Đơn giản và rõ ràng, với điều kiện mọi thứ chạy trên cùng một thread (event loop): nếu timer có thể đang chạy trên thread khác đúng lúc hủy, việc hủy phải chờ callback đó chạy xong.
  2. Bắt weak_ptr. Đối tượng được quản lý bằng shared_ptr và kế thừa enable_shared_from_this: cpp loop_.run_after(5s, [weak = weak_from_this()] { if (auto self = weak.lock()) self->on_timeout(); // chết rồi thì bỏ qua });
  3. Bắt shared_ptr để giữ đối tượng sống tới khi thao tác bất đồng bộ xong ([self = shared_from_this()]). Kiểu Boost.Asio: một kết nối sống chừng nào còn thao tác đang chờ. Cẩn thận chu trình: đối tượng giữ callback, callback giữ đối tượng, không bao giờ được giải phóng.
  4. Đối tượng kết nối (signal/slot). Đăng ký trả về một Connection; hủy Connection là ngắt kết nối. Người nghe giữ Connection làm thành viên.

Signal/slot thread-safe với Connection RAII

#include <algorithm>
#include <atomic>
#include <functional>
#include <memory>
#include <mutex>
#include <vector>

template <class... Args>
class Signal {
    struct Slot {
        std::function<void(Args...)> fn;
        std::atomic<bool> connected{true};
    };
public:
    class Connection {                                  // hủy = ngắt kết nối
    public:
        Connection() = default;
        explicit Connection(std::weak_ptr<Slot> s) : slot_(std::move(s)) {}
        Connection(Connection&&) noexcept = default;
        Connection& operator=(Connection&& o) noexcept {
            disconnect();
            slot_ = std::move(o.slot_);
            return *this;
        }
        ~Connection() { disconnect(); }
        void disconnect() {
            if (auto s = slot_.lock()) s->connected = false;
            slot_.reset();
        }
    private:
        std::weak_ptr<Slot> slot_;
    };

    [[nodiscard]] Connection connect(std::function<void(Args...)> fn) {
        auto s = std::make_shared<Slot>();
        s->fn = std::move(fn);
        std::lock_guard g(m_);
        slots_.push_back(s);
        return Connection(s);
    }

    void emit(Args... args) {
        std::vector<std::shared_ptr<Slot>> snapshot;
        {
            std::lock_guard g(m_);
            std::erase_if(slots_, [](const auto& s) { return !s->connected; });
            snapshot = slots_;                          // chép danh sách rồi nhả khóa
        }
        for (auto& s : snapshot)                        // gọi NGOÀI khóa
            if (s->connected) s->fn(args...);
    }
private:
    std::mutex m_;
    std::vector<std::shared_ptr<Slot>> slots_;
};

Các quyết định thiết kế:

  • Gọi slot ngoài khóa: slot có thể connect/disconnect hoặc emit tiếp mà không tự deadlock; và không giữ khóa trong khi chạy code lạ (M05 Bài 7).
  • Snapshot bằng shared_ptr: slot đang được gọi không bị giải phóng giữa chừng dù ai đó ngắt kết nối.
  • [[nodiscard]] trên connect: bỏ qua Connection nghĩa là ngắt kết nối ngay lập tức, gần như chắc chắn là lỗi.
  • Giới hạn còn lại: nếu thread A disconnect trong lúc thread B đang chạy đúng slot đó, slot vẫn chạy nốt lần này sau khi disconnect trả về. Nếu người nghe bị hủy ngay sau đó, vẫn có rủi ro. Muốn đảm bảo tuyệt đối thì disconnect phải chờ lần gọi đang chạy kết thúc (thêm khóa riêng cho mỗi slot), hoặc đơn giản hơn: giam signal vào một thread (event loop), nơi không có hai việc chạy cùng lúc. Đây là lý do nhiều framework (Qt, GLib) gắn đối tượng với thread của nó.
Tự kiểm traVì sao `Signal::emit` chép danh sách slot ra rồi mới gọi, thay vì giữ mutex trong suốt vòng lặp gọi?

Nếu giữ mutex khi gọi: một slot gọi connect, disconnect (qua Connection bị hủy) hoặc emit lại trên cùng signal sẽ tự deadlock vì mutex không đệ quy; slot chạy lâu chặn mọi thread khác muốn connect/emit; và giữ khóa khi gọi code lạ là nguồn deadlock kinh điển khi slot lấy khóa khác. Chép danh sách shared_ptr ra thì nhả khóa sớm, slot vẫn được giữ sống trong lúc gọi.

  • Virtual cho interface mở, variant cho tập đóng (message), template/concept cho đường nóng, type erasure cho giá trị đa hình.
  • Type erasure = interface nội bộ + model template; đó là cách std::function hoạt động.
  • Callback bắt this thô là nguồn crash số một: hủy đăng ký RAII, weak_ptr, shared_ptr giữ sống, hoặc Connection.

Bài 6 · Event loop trên Linux

Vì sao cần event loop

Cách đơn giản nhất để phục vụ nhiều kết nối là một thread cho mỗi kết nối, mỗi thread gọi read chặn. Dễ viết, nhưng mỗi thread tốn stack và lịch trình; vài nghìn kết nối phần lớn thời gian chỉ ngồi chờ là đã lãng phí, và mọi dữ liệu dùng chung giữa chúng đều cần khóa.

Event loop đảo ngược: một thread hỏi kernel "trong tất cả các fd này, fd nào đang sẵn sàng?", rồi xử lý lần lượt từng fd sẵn sàng bằng thao tác không chặn. Một thread phục vụ hàng chục nghìn kết nối, và vì mọi xử lý chạy trên cùng thread nên trạng thái của các kết nối không cần khóa.

Level-triggered và edge-triggered

Đây là câu hỏi epoll phổ biến nhất.

  • Level-triggered (mặc định): epoll_wait báo fd chừng nào điều kiện còn đúng. Socket còn 100 byte chưa đọc thì lần nào cũng báo. Đọc thiếu cũng không sao, lần sau được báo lại. Đơn giản, ít lỗi.
  • Edge-triggered (EPOLLET): chỉ báo khi trạng thái thay đổi (có dữ liệu mới tới). Nếu bạn chỉ đọc một phần rồi quay lại epoll_wait, phần còn lại không bao giờ được báo nữa cho tới khi dữ liệu mới đến, và kết nối có vẻ "treo". Bắt buộc: fd non-blocking và đọc/ghi tới khi gặp EAGAIN. Lợi: ít lần epoll_wait trả về hơn khi tải cao.

Các cờ khác đáng biết: EPOLLONESHOT (báo một lần rồi tự tắt, phải EPOLL_CTL_MOD để bật lại; dùng khi nhiều thread cùng chờ một epoll để đảm bảo mỗi fd chỉ một thread xử lý), EPOLLRDHUP (đầu kia đóng chiều ghi), EPOLLEXCLUSIVE (tránh thundering herd khi nhiều epoll instance cùng theo dõi một socket lắng nghe).

Cẩn thậnFile thường không dùng được với epoll

epoll_ctl trên fd của file thường trả EPERM: với kernel, file thường luôn "sẵn sàng", đọc có thể chặn vì đĩa nhưng không có cơ chế báo trước. I/O file bất đồng bộ thật sự cần io_uring, hoặc đẩy sang worker thread (Bài 7).

I/O không chặn và bộ đệm ghi

Mọi fd trong event loop phải non-blocking (O_NONBLOCK, SOCK_NONBLOCK): một lời gọi chặn làm đứng tất cả các kết nối khác.

Phía đọc: đọc vào bộ đệm của kết nối, tách message (độ dài đứng trước, hoặc ký tự phân cách) và chỉ xử lý message đầy đủ. Phía ghi phức tạp hơn và hay bị làm sai:

  • write trên socket non-blocking có thể ghi thiếu (buffer gửi của kernel đầy) hoặc trả EAGAIN.
  • Phần chưa ghi phải được giữ trong bộ đệm ghi của kết nối, và đăng ký EPOLLOUT để được báo khi ghi tiếp được.
  • Chỉ bật EPOLLOUT khi bộ đệm ghi không rỗng. Socket gần như lúc nào cũng ghi được, nên bật EPOLLOUT thường trực làm epoll_wait trả về liên tục và loop quay 100% CPU.
  • Bộ đệm ghi phải có giới hạn: client đọc chậm làm nó phình mãi. Vượt giới hạn thì ngừng đọc request mới từ client đó (backpressure) hoặc đóng kết nối.

Xây một event loop nhỏ

Event loop dưới đây gồm đủ các phần của một reactor thật: theo dõi fd, timer (dùng một timerfd cho mọi timer, sắp theo thời điểm hết hạn), và post() để thread khác gửi việc vào loop (dùng eventfd đánh thức). Dùng unique_fd của Bài 4.

#include <sys/epoll.h>
#include <sys/eventfd.h>
#include <sys/timerfd.h>
#include <atomic>
#include <chrono>
#include <cstdint>
#include <functional>
#include <map>
#include <mutex>
#include <stdexcept>
#include <system_error>
#include <unordered_map>
#include <vector>

class EventLoop {
public:
    using Clock      = std::chrono::steady_clock;     // = CLOCK_MONOTONIC trên Linux
    using Callback   = std::function<void()>;
    using IoCallback = std::function<void(std::uint32_t events)>;
    using TimerId    = std::uint64_t;

    EventLoop()
        : ep_(::epoll_create1(EPOLL_CLOEXEC)),
          wake_(::eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC)),
          tfd_(::timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC)) {
        if (!ep_ || !wake_ || !tfd_) throw_errno("EventLoop");
        watch(wake_.get(), EPOLLIN);
        watch(tfd_.get(), EPOLLIN);
    }

    // ---- chỉ gọi từ thread của loop ----
    void add_fd(int fd, std::uint32_t events, IoCallback cb) {
        handlers_[fd] = std::move(cb);
        watch(fd, events);
    }
    void remove_fd(int fd) {
        ::epoll_ctl(ep_.get(), EPOLL_CTL_DEL, fd, nullptr);
        handlers_.erase(fd);
    }
    TimerId run_after(std::chrono::milliseconds delay, Callback cb) {
        const TimerId id = ++next_id_;
        const auto when = Clock::now() + delay;
        timers_.emplace(std::pair{when, id}, std::move(cb));
        deadline_[id] = when;
        arm_timerfd();
        return id;
    }
    void cancel(TimerId id) {
        if (auto it = deadline_.find(id); it != deadline_.end()) {
            timers_.erase({it->second, id});
            deadline_.erase(it);
            arm_timerfd();
        }
    }

    // ---- gọi được từ MỌI thread ----
    void post(Callback cb) {
        { std::lock_guard g(pending_mtx_); pending_.push_back(std::move(cb)); }
        wakeup();
    }
    void stop() { running_ = false; wakeup(); }

    void run() {
        running_ = true;
        epoll_event evs[64];
        while (running_) {
            int n = ::epoll_wait(ep_.get(), evs, 64, -1);
            if (n < 0) { if (errno == EINTR) continue; throw_errno("epoll_wait"); }
            for (int i = 0; i < n; ++i) {
                const int fd = evs[i].data.fd;
                if (fd == wake_.get())     run_pending();
                else if (fd == tfd_.get()) run_timers();
                else if (auto it = handlers_.find(fd); it != handlers_.end()) {
                    auto cb = it->second;          // chép: callback có thể tự remove_fd
                    cb(evs[i].events);
                }                                  // không tìm thấy: đã bị remove trong lượt này
            }
        }
    }

private:
    [[noreturn]] static void throw_errno(const char* what) {
        throw std::system_error(errno, std::generic_category(), what);
    }
    void watch(int fd, std::uint32_t events) {
        epoll_event ev{};
        ev.events = events;
        ev.data.fd = fd;
        if (::epoll_ctl(ep_.get(), EPOLL_CTL_ADD, fd, &ev) != 0) throw_errno("epoll_ctl");
    }
    void wakeup() {
        std::uint64_t one = 1;
        [[maybe_unused]] auto r = ::write(wake_.get(), &one, sizeof one);
    }
    void run_pending() {
        std::uint64_t cnt;
        [[maybe_unused]] auto r = ::read(wake_.get(), &cnt, sizeof cnt);   // reset bộ đếm eventfd
        std::vector<Callback> batch;
        { std::lock_guard g(pending_mtx_); batch.swap(pending_); }        // lấy hết, nhả khóa
        for (auto& cb : batch) cb();                                       // chạy ngoài khóa
    }
    void run_timers() {
        std::uint64_t expirations;
        [[maybe_unused]] auto r = ::read(tfd_.get(), &expirations, sizeof expirations);
        const auto now = Clock::now();
        while (!timers_.empty() && timers_.begin()->first.first <= now) {
            auto node = timers_.extract(timers_.begin());
            deadline_.erase(node.key().second);
            node.mapped()();                  // callback có thể run_after / cancel timer khác
        }
        arm_timerfd();
    }
    void arm_timerfd() {
        itimerspec its{};                     // toàn 0 = tắt timer
        if (!timers_.empty()) {
            auto ns = std::chrono::duration_cast<std::chrono::nanoseconds>(
                          timers_.begin()->first.first.time_since_epoch()).count();
            its.it_value.tv_sec  = ns / 1'000'000'000;
            its.it_value.tv_nsec = ns % 1'000'000'000;
        }
        ::timerfd_settime(tfd_.get(), TFD_TIMER_ABSTIME, &its, nullptr);
    }

    unique_fd ep_, wake_, tfd_;
    std::unordered_map<int, IoCallback> handlers_;
    std::map<std::pair<Clock::time_point, TimerId>, Callback> timers_;   // sắp theo hạn
    std::unordered_map<TimerId, Clock::time_point> deadline_;            // để cancel theo id
    TimerId next_id_ = 0;
    std::mutex pending_mtx_;
    std::vector<Callback> pending_;
    std::atomic<bool> running_{false};
};

Những điểm thiết kế đáng nói khi phỏng vấn:

  • Phân chia thread rõ ràng: chỉ post và stop an toàn từ thread khác; mọi thứ khác chỉ gọi trên thread của loop. Muốn thêm fd từ thread khác thì post([=]{ loop.add_fd(...); }).
  • Một timerfd cho mọi timer: timer được giữ trong cây sắp theo thời điểm hết hạn; timerfd luôn được đặt tới hạn sớm nhất. Thời điểm tuyệt đối (TFD_TIMER_ABSTIME) trên CLOCK_MONOTONIC không bị ảnh hưởng khi đồng hồ hệ thống bị chỉnh (NTP, người dùng đổi giờ). Với hàng trăm nghìn timer có thể thay bằng timer wheel (M07 Bài 5).
  • eventfd để đánh thức: thread khác ghi vào eventfd, epoll_wait trả về, loop chạy các việc đang chờ. Trước khi có eventfd, người ta dùng "self-pipe trick" (pipe ghi một byte).
  • Callback có thể sửa chính loop (thêm, xóa fd, đặt timer): vì vậy chép callback trước khi gọi, kiểm tra lại fd còn đăng ký không, lấy timer ra khỏi cây trước khi gọi.
  • Exception từ callback ở đây sẽ thoát khỏi run(). Loop thực tế bọc mỗi lần gọi callback trong try/catch và ghi log (Bài 2).

Reactor, proactor và io_uring

  • Reactor (epoll, đoạn code trên): kernel báo "fd sẵn sàng", ứng dụng tự thực hiện read/write.
  • Proactor: ứng dụng nộp thao tác ("đọc vào buffer này"), kernel báo khi thao tác hoàn tất. Windows IOCP là proactor; trên Linux là io_uring (kernel 5.1+): hai vòng đệm chia sẻ giữa userspace và kernel (submission và completion), nộp nhiều thao tác bằng một system call hoặc không cần system call nào; hỗ trợ cả file thường. Phù hợp cho I/O cường độ rất cao. Một số hệ thống tắt io_uring vì lý do bảo mật (bề mặt tấn công kernel), nên kiểm tra môi trường đích trước khi phụ thuộc vào nó.

Quy tắc chọn ngắn gọn: bắt đầu từ một event loop + worker pool; chỉ chuyển sang N loop khi đo thấy một nhân không đủ.

Thread pool

#include <condition_variable>
#include <deque>
#include <functional>
#include <future>
#include <memory>
#include <mutex>
#include <thread>
#include <type_traits>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(unsigned n = std::thread::hardware_concurrency()) {
        if (n == 0) n = 1;
        for (unsigned i = 0; i < n; ++i)
            workers_.emplace_back([this] { worker_loop(); });
    }
    ~ThreadPool() { shutdown(); }

    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    // Việc không cần kết quả
    void execute(std::function<void()> task) {
        {
            std::lock_guard g(m_);
            if (stopping_) throw std::runtime_error("pool đã dừng");
            tasks_.push_back(std::move(task));
        }
        cv_.notify_one();
    }

    // Việc có kết quả (hoặc exception) trả qua future
    template <class F, class... A>
    auto submit(F&& f, A&&... args) -> std::future<std::invoke_result_t<F, A...>> {
        using R = std::invoke_result_t<F, A...>;
        auto task = std::make_shared<std::packaged_task<R()>>(
            [fn = std::forward<F>(f), ... as = std::forward<A>(args)]() mutable {
                return std::invoke(std::move(fn), std::move(as)...);
            });
        auto fut = task->get_future();
        execute([task] { (*task)(); });   // shared_ptr vì std::function cần copy được
        return fut;
    }

    // Dừng nhận việc mới, chạy NỐT các việc đã nhận, rồi join
    void shutdown() {
        {
            std::lock_guard g(m_);
            if (stopping_) return;
            stopping_ = true;
        }
        cv_.notify_all();
        for (auto& t : workers_) if (t.joinable()) t.join();
    }

private:
    void worker_loop() {
        for (;;) {
            std::function<void()> task;
            {
                std::unique_lock lk(m_);
                cv_.wait(lk, [&] { return stopping_ || !tasks_.empty(); });
                if (tasks_.empty()) return;       // đang dừng và đã hết việc
                task = std::move(tasks_.front());
                tasks_.pop_front();
            }
            task();                               // chạy ngoài khóa
        }
    }

    std::mutex m_;
    std::condition_variable cv_;
    std::deque<std::function<void()>> tasks_;
    bool stopping_ = false;
    std::vector<std::thread> workers_;            // khai báo cuối (Bài 4)
};

Những câu hỏi tiếp theo thường gặp:

  • Exception trong task? packaged_task bắt và lưu vào future; fut.get() ném lại ở thread người gọi. Với execute, task tự bắt lỗi của mình (nếu không, exception thoát khỏi worker là std::terminate).
  • Bao nhiêu thread? Việc thuần CPU: bằng số nhân. Việc chặn I/O: nhiều hơn, nhưng tốt hơn là tách pool: một pool CPU nhỏ và một pool cho thao tác chặn, để việc chặn không chiếm hết worker của việc tính toán.
  • Deadlock do pool: task A trong pool chờ future của task B cũng nằm trong pool. Khi mọi worker đều đang chạy những task kiểu A, không còn worker nào chạy B. Quy tắc: task trong pool không chặn chờ task khác của cùng pool.
  • Queue không giới hạn ở đây; production nên có giới hạn và chính sách khi đầy: chặn người gửi, từ chối (trả lỗi "quá tải"), hoặc để chính người gửi chạy task (caller-runs, tự tạo backpressure).
  • Work stealing: mỗi worker một deque riêng, worker rảnh "ăn trộm" việc từ đuôi deque của worker khác; giảm tranh chấp trên một queue chung khi task rất nhỏ (B02 chương 9).

Event loop + worker pool: giữ kỷ luật thread

Đối tượng kết nối thuộc về thread của loop. Worker không bao giờ chạm vào chúng; worker nhận bản sao dữ liệu, trả kết quả về loop bằng post:

// chạy trên thread của loop, khi nhận đủ một request
void Session::on_request(Request req) {
    pool_.execute([req = std::move(req), loop = &loop_, weak = weak_from_this()] {
        Response resp = process(req);                // việc nặng, trên worker
        loop->post([weak, resp = std::move(resp)] {  // quay về thread của loop
            if (auto self = weak.lock())             // Session có thể đã đóng
                self->send(resp);
        });
    });
}

Không có mutex nào trong logic: Session chỉ bị chạm trên thread của loop, req và resp được chuyển (move) giữa các thread chứ không chia sẻ. Đây là thread confinement cộng message passing.

Strand: tuần tự hóa mà không cần thread riêng

Đôi khi một nhóm dữ liệu cần được xử lý tuần tự (như actor) nhưng không đáng một thread riêng. Strand là hàng đợi chạy trên pool chung, đảm bảo các việc của cùng strand không bao giờ chạy đồng thời, và chạy theo thứ tự gửi:

#include <deque>
#include <functional>
#include <mutex>

class Strand {
public:
    explicit Strand(ThreadPool& pool) : pool_(pool) {}

    void post(std::function<void()> fn) {
        bool need_schedule = false;
        {
            std::lock_guard g(m_);
            q_.push_back(std::move(fn));
            if (!running_) { running_ = true; need_schedule = true; }
        }
        if (need_schedule) pool_.execute([this] { drain(); });
    }

private:
    void drain() {
        for (int budget = 64; budget > 0; --budget) {     // không chiếm worker quá lâu
            std::function<void()> fn;
            {
                std::lock_guard g(m_);
                if (q_.empty()) { running_ = false; return; }
                fn = std::move(q_.front());
                q_.pop_front();
            }
            fn();                                          // chỉ một drain() chạy tại một thời điểm
        }
        pool_.execute([this] { drain(); });               // hết lượt: xếp hàng lại, nhường việc khác
    }

    ThreadPool& pool_;
    std::mutex m_;
    std::deque<std::function<void()>> q_;
    bool running_ = false;
};

Cờ running_ đảm bảo tại mọi thời điểm chỉ có một drain() được lên lịch, nên các việc của strand chạy tuần tự (dù có thể trên các worker khác nhau) và mọi ghi của việc trước được nhìn thấy bởi việc sau (qua mutex). Một actor chính là trạng thái riêng cộng một strand: mọi phương thức public chỉ post vào strand. Lưu ý vòng đời: Strand phải sống lâu hơn mọi drain() đã lên lịch (hủy pool trước, hoặc chờ strand rỗng).

Tắt service gọn gàng

systemd dừng service bằng SIGTERM, chờ TimeoutStopSec (mặc định 90 giây) rồi SIGKILL. Trình tự tắt đúng:

int main() {
    block_signals({SIGTERM, SIGINT});          // M05 Bài 6: trước khi tạo thread
    EventLoop loop;
    ThreadPool pool(4);
    Server server(loop, pool, cfg);            // listen socket, session...
    SignalWatcher sig(loop, [&] {              // signalfd trong loop
        server.stop_accepting();               // 1. ngừng nhận việc mới
        server.close_idle_sessions();          // 2. đóng phiên rảnh, báo phiên đang bận
        loop.run_after(5s, [&] { loop.stop(); });   // 3. hạn chót cho việc đang làm dở
        server.on_all_closed([&] { loop.stop(); }); //    hoặc dừng sớm khi xong hết
    });
    loop.run();
    pool.shutdown();                           // 4. chạy nốt / hủy việc trong pool, join
    flush_logs();                              // 5. ghi log còn trong buffer
}                                              // 6. destructor theo thứ tự ngược khai báo

Nguyên tắc: ngừng nhận trước, xử lý nốt có hạn chót, join theo thứ tự ngược phụ thuộc (người dùng tài nguyên dừng trước tài nguyên), và không bao giờ để destructor của static chạy khi thread còn sống (M05 Bài 6).

Tự kiểm traService dùng một `ThreadPool` 8 thread. Một task tính báo cáo chia việc thành 16 task con, `submit` vào cùng pool rồi `get()` từng future. Khi có 8 yêu cầu báo cáo đồng thời, service treo. Giải thích và đề xuất sửa.

Tám task báo cáo chiếm cả 8 worker, mỗi task chặn ở get() chờ task con; task con nằm trong queue nhưng không còn worker nào rảnh để chạy: deadlock do pool. Sửa: không chặn chờ trong task của pool. Cách làm: tách pool (task cha chạy ở pool khác với task con); hoặc task cha không chờ mà đăng ký phần tổng hợp chạy khi task con cuối cùng xong (đếm bằng atomic, task con cuối gọi bước tổng hợp); hoặc dùng framework có fork/join với work stealing, nơi thread đang chờ tự chạy task con.

Ý chínhÝ chính của Bài 7
  • Mặc định: một event loop + worker pool; nhiều loop khi đo thấy cần.
  • Thread pool: queue + worker + shutdown chạy nốt; future mang exception; tách pool CPU và pool chặn; task không chờ task cùng pool.
  • Dữ liệu thuộc một thread; giữa các thread chỉ chuyển message (move), kết quả post về chủ.
  • Strand/actor: tuần tự hóa trên pool chung, không mutex trong logic.
  • Queue có giới hạn + chính sách khi đầy; tắt service: ngừng nhận, làm nốt có hạn chót, join ngược phụ thuộc.

Bài 8 · Nhiều process và IPC

Khi nào tách thành nhiều process

Một process nhiều thread là cách rẻ nhất để chạy song song. Tách thành nhiều process có giá (IPC, serialization, xử lý khi bên kia chết), nên cần lý do rõ ràng:

  • Cô lập lỗi: parser dữ liệu từ mạng crash không kéo theo phần điều khiển thiết bị.
  • Tách quyền (privilege separation): chỉ một process nhỏ chạy với quyền cao (mở /dev/*, cấu hình mạng); phần xử lý dữ liệu không tin cậy chạy với user thường, bị giới hạn bằng seccomp.
  • Vòng đời độc lập: cập nhật, restart từng thành phần; systemd giám sát từng service.
  • Giới hạn tài nguyên riêng: cgroup cho bộ nhớ, CPU của từng service (rò bộ nhớ ở một service không làm chết cả hệ).
  • Khác ngôn ngữ: phần AI bằng Python, phần thời gian thực bằng C++.

Đổi lại, hệ thống giờ có các vấn đề của hệ phân tán thu nhỏ: bên kia có thể chưa khởi động, đang restart, trả lời chậm. Mọi lời gọi qua IPC cần timeout, kết nối lại có backoff, và yêu cầu nên idempotent (gửi lại không gây tác dụng kép).

Unix socket và đóng khung message

SOCK_STREAM là dòng byte: một lần send 100 byte có thể đến bên kia thành hai lần recv 60 + 40 byte, hoặc hai message dính vào một lần recv. Phải tự đóng khung (framing). Cách phổ biến nhất: 4 byte độ dài (big-endian) rồi tới nội dung.

#include <arpa/inet.h>
#include <sys/socket.h>
#include <cerrno>
#include <cstdint>
#include <optional>
#include <string>
#include <system_error>

inline constexpr std::uint32_t kMaxMessage = 1 << 20;   // chặn message giả mạo cực lớn

// Gửi đủ n byte (send có thể gửi thiếu)
std::error_code send_all(int fd, const void* buf, std::size_t n) {
    auto* p = static_cast<const char*>(buf);
    while (n > 0) {
        ssize_t k = ::send(fd, p, n, MSG_NOSIGNAL);      // không nhận SIGPIPE khi bên kia đóng
        if (k < 0) {
            if (errno == EINTR) continue;
            return {errno, std::generic_category()};
        }
        p += k;
        n -= static_cast<std::size_t>(k);
    }
    return {};
}

// Nhận đủ n byte; eof = true nếu bên kia đóng kết nối trước khi đủ
std::error_code recv_exact(int fd, void* buf, std::size_t n, bool& eof) {
    auto* p = static_cast<char*>(buf);
    eof = false;
    while (n > 0) {
        ssize_t k = ::recv(fd, p, n, 0);
        if (k == 0) { eof = true; return {}; }
        if (k < 0) {
            if (errno == EINTR) continue;
            return {errno, std::generic_category()};
        }
        p += k;
        n -= static_cast<std::size_t>(k);
    }
    return {};
}

std::error_code send_msg(int fd, const std::string& payload) {
    if (payload.size() > kMaxMessage) return std::make_error_code(std::errc::message_size);
    std::uint32_t len = htonl(static_cast<std::uint32_t>(payload.size()));
    if (auto ec = send_all(fd, &len, sizeof len)) return ec;
    return send_all(fd, payload.data(), payload.size());
}

// nullopt khi bên kia đóng gọn gàng; ec khi lỗi
std::optional<std::string> recv_msg(int fd, std::error_code& ec) {
    bool eof = false;
    std::uint32_t len = 0;
    if ((ec = recv_exact(fd, &len, sizeof len, eof)) || eof) return std::nullopt;
    len = ntohl(len);
    if (len > kMaxMessage) { ec = std::make_error_code(std::errc::message_size); return std::nullopt; }
    std::string payload(len, '\0');
    if ((ec = recv_exact(fd, payload.data(), len, eof))) return std::nullopt;
    if (eof) { ec = std::make_error_code(std::errc::connection_reset); return std::nullopt; }
    return payload;
}

Code trên dùng socket chặn (hợp cho client đơn giản hoặc thread riêng). Trong event loop, cùng logic được viết thành máy trạng thái: đọc được bao nhiêu thì nạp vào bộ đệm, đủ 4 byte thì biết độ dài, đủ độ dài thì có một message (Bài 6).

Vài điểm nhỏ nhưng quan trọng: giới hạn kích thước để một byte độ dài hỏng không làm cấp phát 4 GiB; MSG_NOSIGNAL (hoặc bỏ qua SIGPIPE toàn process) để ghi vào socket đã đóng trả lỗi EPIPE thay vì giết process; SOCK_SEQPACKET của Unix socket giữ ranh giới message sẵn, có thể bỏ được phần đóng khung.

Truyền file descriptor giữa các process

Unix socket có một khả năng đặc biệt: gửi fd sang process khác (SCM_RIGHTS). Process nhận có một fd mới trỏ tới cùng file/socket/vùng nhớ.

#include <sys/socket.h>
#include <cstring>

bool send_fd(int sock, int fd_to_send) {
    char dummy = 'F';                                   // phải gửi ít nhất 1 byte dữ liệu
    iovec iov{&dummy, 1};
    alignas(cmsghdr) char ctrl[CMSG_SPACE(sizeof(int))] = {};
    msghdr msg{};
    msg.msg_iov = &iov;
    msg.msg_iovlen = 1;
    msg.msg_control = ctrl;
    msg.msg_controllen = sizeof ctrl;
    cmsghdr* c = CMSG_FIRSTHDR(&msg);
    c->cmsg_level = SOL_SOCKET;
    c->cmsg_type = SCM_RIGHTS;
    c->cmsg_len = CMSG_LEN(sizeof(int));
    std::memcpy(CMSG_DATA(c), &fd_to_send, sizeof(int));
    return ::sendmsg(sock, &msg, MSG_NOSIGNAL) == 1;
}

int recv_fd(int sock) {                                 // -1 nếu lỗi
    char dummy;
    iovec iov{&dummy, 1};
    alignas(cmsghdr) char ctrl[CMSG_SPACE(sizeof(int))] = {};
    msghdr msg{};
    msg.msg_iov = &iov;
    msg.msg_iovlen = 1;
    msg.msg_control = ctrl;
    msg.msg_controllen = sizeof ctrl;
    if (::recvmsg(sock, &msg, MSG_CMSG_CLOEXEC) != 1) return -1;
    cmsghdr* c = CMSG_FIRSTHDR(&msg);
    if (!c || c->cmsg_type != SCM_RIGHTS) return -1;
    int fd;
    std::memcpy(&fd, CMSG_DATA(c), sizeof(int));
    return fd;
}

Ứng dụng thực tế:

  • Tách quyền: process quyền cao mở /dev/ttyS1 hoặc socket cổng 80, gửi fd cho process quyền thấp; process quyền thấp dùng được mà không bao giờ có quyền mở.
  • Zero-copy: producer tạo vùng nhớ bằng memfd_create, ghi khung hình vào, gửi fd; consumer mmap cùng vùng nhớ. Trên SoC có GPU/VPU, cùng ý tưởng với buffer dmabuf.
  • systemd socket activation: systemd mở sẵn socket lắng nghe và truyền cho service khi khởi động (qua sd_listen_fds), cho phép restart service mà không mất kết nối đang chờ.

Kèm theo đó, getsockopt(fd, SOL_SOCKET, SO_PEERCRED, ...) cho biết pid, uid, gid của process ở đầu kia, đủ để kiểm tra quyền mà không cần mật khẩu.

Shared memory: những điều phải tự lo

  • Không có con trỏ trong vùng nhớ chung: mỗi process mmap vùng nhớ ở địa chỉ khác nhau. Dùng offset tính từ đầu vùng.
  • Đồng bộ: atomic đặt trong vùng nhớ chung phải lock-free (static_assert(std::atomic<std::uint64_t>::is_always_lock_free)), vì bản không lock-free dùng khóa nằm trong process. Ring buffer SPSC (M06 Bài 1) với chỉ số atomic là lựa chọn kinh điển. Nếu cần mutex: pthread_mutex với thuộc tính PTHREAD_PROCESS_SHARED và PTHREAD_MUTEX_ROBUST (M05 Bài 3), để process chết khi giữ khóa không làm treo cả hệ.
  • Báo hiệu: shared memory không tự đánh thức ai. Kèm theo một cơ chế báo (futex trên địa chỉ chung, eventfd được truyền qua socket, hoặc một message nhỏ qua socket).
  • Phiên bản bố cục: đặt header có magic number và version ở đầu vùng nhớ.

Quy tắc tương thích kiểu protobuf, áp dụng cho mọi định dạng: chỉ thêm trường mới, trường mới có giá trị mặc định hợp lý, không bao giờ dùng lại số hiệu/tên trường đã xóa, bên nhận bỏ qua trường không biết. Mọi message có trường loại và phiên bản trong header. Trên thiết bị nhúng, các process được cập nhật không đồng thời (cập nhật dở, rollback) nên tương thích hai chiều là bắt buộc.

Tự kiểm traProcess giám sát camera (quyền root) và process phân tích ảnh (user thường, có seccomp) cần trao đổi khung hình 1080p ở 30 fps. Thiết kế IPC?

Mỗi khung khoảng 3 MB (NV12) × 30 fps ≈ 90 MB/s: không nên copy qua socket. Process camera cấp phát một vài buffer bằng memfd_create (hoặc dmabuf từ driver), truyền fd một lần qua Unix socket (SCM_RIGHTS) lúc thiết lập; process phân tích mmap chỉ đọc. Sau đó mỗi khung chỉ gửi message nhỏ qua socket: chỉ số buffer, timestamp, sequence. Process phân tích trả lại "đã xong buffer i" để buffer được tái sử dụng (vòng buffer có giới hạn, khi phân tích chậm thì bỏ khung cũ). Kiểm tra quyền người kết nối bằng SO_PEERCRED. Thêm version vào message thiết lập để hai bên được cập nhật độc lập.

  • Unix socket là mặc định; stream cần đóng khung có giới hạn kích thước; MSG_NOSIGNAL.

Bài 9 · Testing và chất lượng

Thiết kế để test được

Bài 0 nói về lõi thuần, vỏ I/O. Đây là lúc nó trả lãi: phần lõi (tính toán, quyết định, máy trạng thái) nhận dữ liệu và trả kết quả, test bằng unit test chạy trong vài mili giây. Phần vỏ (socket, file, thiết bị) mỏng, được test bằng integration test ít hơn.

GoogleTest và GoogleMock

Ví dụ: bộ điều khiển sưởi bật lò khi nhiệt độ dưới ngưỡng, tắt khi trên ngưỡng (có trễ), và báo lỗi nếu cảm biến không phản hồi quá 30 giây.

#include <gmock/gmock.h>
#include <gtest/gtest.h>
#include <chrono>
#include <optional>

using namespace std::chrono_literals;

// ---- interface theo ngôn ngữ bài toán ----
struct TemperatureSensor {
    virtual ~TemperatureSensor() = default;
    virtual std::optional<double> read_celsius() = 0;     // nullopt: không đọc được
};
struct Heater {
    virtual ~Heater() = default;
    virtual void set(bool on) = 0;
};
struct Clock {
    virtual ~Clock() = default;
    virtual std::chrono::steady_clock::time_point now() const = 0;
};

// ---- lõi: không biết I2C, GPIO hay thời gian thật ----
class Thermostat {
public:
    Thermostat(TemperatureSensor& s, Heater& h, const Clock& c, double target)
        : sensor_(s), heater_(h), clock_(c), target_(target), last_ok_(c.now()) {}

    enum class Status { ok, sensor_fault };

    Status tick() {
        if (auto t = sensor_.read_celsius()) {
            last_ok_ = clock_.now();
            if (*t < target_ - 0.5 && !on_) { heater_.set(true);  on_ = true; }
            if (*t > target_ + 0.5 &&  on_) { heater_.set(false); on_ = false; }
            return Status::ok;
        }
        if (clock_.now() - last_ok_ > 30s) {          // mất cảm biến quá lâu: an toàn trước
            if (on_) { heater_.set(false); on_ = false; }
            return Status::sensor_fault;
        }
        return Status::ok;
    }
private:
    TemperatureSensor& sensor_;
    Heater& heater_;
    const Clock& clock_;
    double target_;
    bool on_ = false;
    std::chrono::steady_clock::time_point last_ok_;
};

// ---- test doubles ----
struct MockSensor : TemperatureSensor { MOCK_METHOD(std::optional<double>, read_celsius, (), (override)); };
struct MockHeater : Heater            { MOCK_METHOD(void, set, (bool), (override)); };
struct FakeClock : Clock {                              // fake: có hành vi thật, tua được
    std::chrono::steady_clock::time_point t{};
    std::chrono::steady_clock::time_point now() const override { return t; }
    void advance(std::chrono::seconds d) { t += d; }
};

using ::testing::Return;
using ::testing::StrictMock;

class ThermostatTest : public ::testing::Test {
protected:
    MockSensor sensor;
    StrictMock<MockHeater> heater;                      // gọi không được khai báo = test fail
    FakeClock clock;
    Thermostat th{sensor, heater, clock, 21.0};
};

TEST_F(ThermostatTest, TurnsHeaterOnBelowHysteresisBand) {
    EXPECT_CALL(sensor, read_celsius()).WillOnce(Return(20.0));
    EXPECT_CALL(heater, set(true)).Times(1);

Bài 10 · Đề low-level design (1): LRU cache và logger bất đồng bộ

Đề low-level design (LLD) trong phỏng vấn C++ thường kéo dài 45–60 phút và được chấm theo trình tự: làm rõ yêu cầu → thiết kế interface → chọn cấu trúc dữ liệu → xử lý đồng thời → code → thảo luận mở rộng. Đừng lao vào code ngay; năm phút đầu hỏi yêu cầu cho thấy bạn thiết kế cho bài toán thật chứ không phải bài đã thuộc. Code dưới đây đều đã biên dịch và chạy kiểm tra (kèm TSan).

Đề 1 · LRU cache thread-safe

Làm rõ yêu cầu. Những câu nên hỏi:

  • Giới hạn theo số phần tử hay theo dung lượng byte? (Bắt đầu với số phần tử.)
  • Bao nhiêu thread truy cập, tỉ lệ đọc/ghi? Value lớn hay nhỏ?
  • Cần TTL (hết hạn theo thời gian) không? Cần thống kê hit/miss?
  • Khi miss, ai nạp dữ liệu: người gọi tự nạp rồi put, hay cache tự gọi loader?

Cấu trúc dữ liệu. get và put đều phải O(1):

 items_ (list):   [a:1] ⇄ [c:3] ⇄ [b:2]
                    ▲                 ▲
                    đầu: vừa dùng     cuối: lâu nhất chưa dùng, bỏ đi khi đầy
 index_ (map):    "a" → iterator tới [a:1]
                  "b" → iterator tới [b:2]
                  "c" → iterator tới [c:3]
  • Map tìm node trong O(1); list giữ thứ tự sử dụng.
  • get: tìm qua map, chuyển node lên đầu bằng list::splice (O(1), không cấp phát, iterator trong map vẫn hợp lệ).
  • put khi đầy: xóa node cuối list và entry tương ứng trong map.
#include <algorithm>
#include <array>
#include <cstddef>
#include <cstdint>
#include <functional>
#include <list>
#include <memory>
#include <mutex>
#include <optional>
#include <unordered_map>
#include <utility>

template <class K, class V, class Hash = std::hash<K>>
class LruCache {
public:
    explicit LruCache(std::size_t capacity) : cap_(std::max<std::size_t>(capacity, 1)) {}

    std::optional<V> get(const K& key) {
        std::lock_guard g(m_);
        auto it = index_.find(key);
        if (it == index_.end()) { ++misses_; return std::nullopt; }
        items_.splice(items_.begin(), items_, it->second);   // đưa lên đầu, O(1)
        ++hits_;
        return it->second->second;
    }

    void put(const K& key, V value) {
        std::lock_guard g(m_);
        if (auto it = index_.find(key); it != index_.end()) {
            it->second->second = std::move(value);
            items_.splice(items_.begin(), items_, it->second);
            return;
        }
        if (items_.size() == cap_) {                          // đầy: bỏ phần tử ít dùng nhất
            index_.erase(items_.back().first);
            items_.pop_back();
        }
        items_.emplace_front(key, std::move(value));
        index_.emplace(key, items_.begin());
    }

    bool erase(const K& key) {
        std::lock_guard g(m_);
        auto it = index_.find(key);
        if (it == index_.end()) return false;
        items_.erase(it->second);
        index_.erase(it);
        return true;
    }

    std::size_t size() const { std::lock_guard g(m_); return items_.size(); }
    std::pair<std::uint64_t, std::uint64_t> stats() const {
        std::lock_guard g(m_);
        return {hits_, misses_};
    }

private:
    using List = std::list<std::pair<K, V>>;
    mutable std::mutex m_;
    List items_;
    std::unordered_map<K, typename List::iterator, Hash> index_;
    const std::size_t cap_;
    std::uint64_t hits_ = 0, misses_ = 0;
};

// Chia nhỏ khóa: N cache độc lập, chọn theo hash của key
template <class K, class V, std::size_t Shards = 16, class Hash = std::hash<K>>
class ShardedLruCache {
public:
    explicit ShardedLruCache(std::size_t total_capacity) {
        for (auto& s : shards_)
            s = std::make_unique<LruCache<K, V, Hash>>(std::max<std::size_t>(1, total_capacity / Shards));
    }
    std::optional<V> get(const K& k) { return shard(k).get(k); }
    void put(const K& k, V v)        { shard(k).put(k, std::move(v)); }
private:
    LruCache<K, V, Hash>& shard(const K& k) {
        std::size_t h = Hash{}(k);
        h ^= h >> 17; h *= 0x9E3779B97F4A7C15ull;      // trộn bit: std::hash<int> là hàm đồng nhất
        return *shards_[(h >> 32) % Shards];
    }
    std::array<std::unique_ptr<LruCache<K, V, Hash>>, Shards> shards_;
};

Thảo luận đồng thời (phần ăn điểm):

  • Vì sao không dùng shared_mutex cho get? Vì get sửa thứ tự list (splice). Trong LRU, đọc cũng là ghi; mọi thao tác cần khóa độc quyền. Đây là câu hỏi bẫy hay gặp.
  • Contention: một mutex cho cả cache thành nút thắt khi nhiều thread. Sharding chia thành N cache độc lập; đổi lại thứ tự LRU chỉ đúng trong từng shard (LRU xấp xỉ toàn cục), thường chấp nhận được. Chọn shard bằng hash đã được trộn bit, vì std::hash<int> trên libstdc++ trả lại chính số đó.
  • Value lớn: get trả bản sao trong khi giữ khóa. Lưu std::shared_ptr<const V> để chỉ copy con trỏ; người đọc giữ value sống kể cả khi cache đã bỏ nó.
  • Giảm tranh chấp hơn nữa: thay LRU chính xác bằng CLOCK (mỗi phần tử một bit "vừa dùng", get chỉ đặt bit bằng atomic, không cần khóa sửa list) hoặc chỉ cập nhật thứ tự với xác suất / theo lô. Các cache hiệu năng cao (Caffeine, cachelib) dùng biến thể của những ý tưởng này.

Mở rộng hay được hỏi:

  • TTL: lưu thêm thời điểm hết hạn; get gặp phần tử hết hạn thì xóa và trả miss (xóa lười); kèm quét định kỳ nếu cần giải phóng bộ nhớ chủ động.
  • Giới hạn theo byte: mỗi phần tử có cost, tổng cost vượt giới hạn thì bỏ từ cuối tới khi đủ.
  • Cache stampede: 100 thread cùng miss một key và cùng gọi database. Giải pháp single-flight: cache giữ thêm map key → shared_future của lần nạp đang chạy; thread miss sau chỉ chờ future đó thay vì nạp lại.

Đề 2 · Logger bất đồng bộ

Làm rõ yêu cầu.

  • Thread gọi log() không được chờ I/O (ghi đĩa, gửi mạng); chi phí phải nhỏ và ổn định.
  • Thứ tự log của cùng một thread phải được giữ.
  • Bộ nhớ có giới hạn. Khi đĩa chậm và buffer đầy: chặn người gọi hay bỏ log (và đếm số dòng bị bỏ)? Thường chọn bỏ, vì logger không được làm chậm chức năng chính.
  • Khi tắt bình thường: không mất log. Cần flush() đồng bộ (ví dụ trước khi ghi log lỗi nghiêm trọng rồi abort).

Thiết kế: double buffering. Thread gọi chỉ nối chuỗi vào buffer hiện tại trong một vùng khóa rất ngắn. Một thread nền định kỳ (hoặc khi buffer đầy) tráo toàn bộ buffer ra khỏi khóa rồi ghi ra sink ngoài khóa. Mutex chỉ bảo vệ vài thao tác nối chuỗi và tráo con trỏ, không bao giờ bị giữ trong lúc I/O.

 thread A ─┐  log()                       thread nền
 thread B ─┼──▶ [current_ 64 KiB] ──đầy──▶ [full_ ...] ──tráo (O(1))──▶ ghi ra sink (ngoài khóa)
 thread C ─┘    (khóa ngắn)                                             file / journald / UART

#include <chrono>
#include <condition_variable>
#include <cstdint>
#include <functional>
#include <mutex>
#include <string>
#include <string_view>
#include <thread>
#include <vector>

class AsyncLogger {
public:
    using Sink = std::function<void(std::string_view)>;   // chỉ được gọi từ thread nền
    struct Options {
        std::size_t max_pending_bytes = 4 << 20;           // giới hạn bộ nhớ chờ ghi
        std::size_t buffer_bytes = 64 << 10;               // kích thước một buffer
        std::chrono::milliseconds flush_interval{200};
    };

    AsyncLogger(Sink sink, Options opt)
        : sink_(std::move(sink)), opt_(opt), worker_([this] { run(); }) {}

    ~AsyncLogger() {
        { std::lock_guard g(m_); stop_ = true; }
        cv_.notify_one();
        worker_.join();                                     // thread nền ghi nốt rồi mới thoát
    }

    void log(std::string_view line) {                       // gọi từ mọi thread
        std::unique_lock lk(m_);
        if (pending_bytes_ + line.size() + 1 > opt_.max_pending_bytes) { ++dropped_; return; }
        current_.append(line);
        current_.push_back('\n');
        pending_bytes_ += line.size() + 1;
        if (current_.size() >= opt_.buffer_bytes) {
            full_.push_back(std::move(current_));
            current_ = std::string();
            current_.reserve(opt_.buffer_bytes);
            lk.unlock();
            cv_.notify_one();                               // có buffer đầy: đánh thức sớm
        }
    }

    // Chờ tới khi mọi dòng log() TRƯỚC lời gọi này đã được ghi ra sink
    void flush() {
        std::unique_lock lk(m_);
        const std::uint64_t ticket = ++flush_requested_;
        cv_.notify_one();
        done_cv_.wait(lk, [&] { return flush_completed_ >= ticket; });
    }

    std::uint64_t dropped() const { std::lock_guard g(m_); return dropped_; }

private:
    void run() {
        std::vector<std::string> batch;
        for (;;) {
            std::uint64_t ticket;
            bool stopping;
            {
                std::unique_lock lk(m_);
                cv_.wait_for(lk, opt_.flush_interval, [&] {
                    return stop_ || !full_.empty() || flush_requested_ > flush_completed_;
                });
                if (!current_.empty()) { full_.push_back(std::move(current_)); current_ = std::string(); }
                batch.swap(full_);                          // lấy hết, O(1)
                pending_bytes_ = 0;
                ticket = flush_requested_;                  // mọi flush tới thời điểm này được phục vụ
                stopping = stop_;
            }
            for (const auto& b : batch) sink_(b);           // I/O ngoài khóa
            batch.clear();
            {
                std::lock_guard g(m_);
                flush_completed_ = ticket;
            }
            done_cv_.notify_all();
            if (stopping) return;   // stop_ đã được thấy TRƯỚC khi lấy batch: không còn gì sót
        }
    }

    Sink sink_;
    const Options opt_;
    mutable std::mutex m_;
    std::condition_variable cv_, done_cv_;
    std::string current_;
    std::vector<std::string> full_;
    std::size_t pending_bytes_ = 0;
    std::uint64_t dropped_ = 0;
    std::uint64_t flush_requested_ = 0, flush_completed_ = 0;
    bool stop_ = false;
    std::thread worker_;                                    // khai báo cuối (Bài 4)
};

Các quyết định cần giải thích:

  • Vì sao flush() dùng số vé? Thread gọi flush lấy vé k trong khóa, sau khi các dòng log trước đó của nó đã vào buffer (cũng trong khóa). Thread nền đọc flush_requested_ trong cùng lần giữ khóa mà nó lấy buffer, nên mọi dòng thuộc các vé ≤ giá trị đó chắc chắn nằm trong batch vừa lấy. Ghi xong mới báo hoàn tất.
  • Thoát an toàn: thread nền chỉ thoát khi nó đã thấy stop_ == true trước lần lấy buffer cuối, nên không dòng nào được log trước khi destructor chạy bị bỏ sót.
  • Giới hạn bộ nhớ: max_pending_bytes áp cho phần đang chờ; cộng thêm một batch đang được ghi. Khi vượt, bỏ dòng mới và đếm; định kỳ ghi một dòng "đã bỏ N dòng log" để người đọc log biết có khoảng trống.
  • Thứ tự: một mutex nên thứ tự trong cùng thread được giữ; giữa các thread là thứ tự lấy được khóa.

Mở rộng hay được hỏi:

  • Giảm chi phí ở người gọi hơn nữa: mỗi thread một ring buffer SPSC riêng (không tranh chấp), thread nền gom lại theo timestamp. Hoặc trì hoãn định dạng: thread gọi chỉ chép tham số nhị phân và con trỏ tới chuỗi định dạng hằng, thread nền mới định dạng (NanoLog, các hệ "binary logging"; trên MCU là tokenized logging ở M09).
  • Crash: khi process sắp chết vì SIGSEGV, không được gọi logger (khóa, cấp phát). Giữ buffer ở vùng nhớ đã cấp sẵn và để signal handler write() thẳng ra fd, hoặc dựa vào core dump để đọc buffer.
  • Log rotation, journald: trên systemd, ghi ra stdout/stderr là đủ, journald lo thời gian, rotation, giới hạn dung lượng; logger chỉ cần không chặn.
  • Mức log và lọc: kiểm tra mức trước khi định dạng chuỗi (macro hoặc hàm template nhận lambda), để log debug bị tắt gần như không tốn gì.

  • LLD: làm rõ yêu cầu → interface → cấu trúc dữ liệu → đồng thời → code → mở rộng.
  • LRU: map + list, splice O(1); get cũng ghi nên không dùng shared lock; sharding; shared_ptr<const V>; single-flight chống stampede.

Đề 3 · Rate limiter

Làm rõ yêu cầu.

  • Giới hạn theo khóa nào: theo client, theo địa chỉ IP, theo API key? Bao nhiêu khóa (có thể hàng triệu)?
  • Giới hạn dạng gì: "100 request mỗi phút", có cho phép dồn cục (burst) không?
  • Bị từ chối thì trả gì: lỗi ngay, hay cho biết bao lâu nữa thử lại (Retry-After)?
  • Một máy hay nhiều máy? (Nhiều máy cần trạng thái dùng chung, thuộc M16; ở đây một process.)

Token bucket là lựa chọn phổ biến nhất (dùng trong traffic shaping của Linux tc, API gateway). Không cần thread nạp token: tính lười số token lúc có request, từ thời gian trôi qua kể từ lần trước.

#include <algorithm>
#include <array>
#include <chrono>
#include <cstdint>
#include <functional>
#include <mutex>
#include <string>
#include <string_view>

class TokenBucket {
public:
    using Clock = std::chrono::steady_clock;

    TokenBucket(double rate_per_sec, double burst, Clock::time_point now)
        : rate_(rate_per_sec), cap_(burst), tokens_(burst), last_(now) {}

    bool try_acquire(Clock::time_point now, double cost = 1.0) {
        refill(now);
        if (tokens_ < cost) return false;
        tokens_ -= cost;
        return true;
    }
    // Bao lâu nữa thì đủ token (để trả Retry-After)
    Clock::duration wait_time(Clock::time_point now, double cost = 1.0) {
        refill(now);
        if (tokens_ >= cost) return Clock::duration::zero();
        return std::chrono::duration_cast<Clock::duration>(
            std::chrono::duration<double>((cost - tokens_) / rate_));
    }
    Clock::time_point last_update() const { return last_; }

private:
    void refill(Clock::time_point now) {
        if (now <= last_) return;                      // đồng hồ đơn điệu, nhưng vẫn phòng thủ
        const std::chrono::duration<double> dt = now - last_;
        tokens_ = std::min(cap_, tokens_ + dt.count() * rate_);
        last_ = now;
    }
    double rate_, cap_, tokens_;
    Clock::time_point last_;
};

class KeyedRateLimiter {
public:
    using Clock = TokenBucket::Clock;

    KeyedRateLimiter(double rate, double burst, std::chrono::seconds idle_ttl)
        : rate_(rate), burst_(burst), idle_ttl_(idle_ttl) {}

    bool allow(std::string_view key, Clock::time_point now = Clock::now()) {
        Shard& sh = shard_for(key);
        std::lock_guard g(sh.m);
        auto it = sh.buckets.find(key);               // tra bằng string_view, không cấp phát
        if (it == sh.buckets.end())
            it = sh.buckets.try_emplace(std::string(key), rate_, burst_, now).first;
        const bool ok = it->second.try_acquire(now);
        if (++sh.ops % 1024 == 0) sweep(sh, now);     // dọn khóa nhàn rỗi theo lô
        return ok;
    }

    std::size_t tracked_keys() {
        std::size_t n = 0;
        for (auto& sh : shards_) { std::lock_guard g(sh.m); n += sh.buckets.size(); }
        return n;
    }

private:
    struct SvHash {                                   // cho phép find(string_view)
        using is_transparent = void;
        std::size_t operator()(std::string_view s) const noexcept { return std::hash<std::string_view>{}(s); }
    };
    struct Shard {
        std::mutex m;
        std::unordered_map<std::string, TokenBucket, SvHash, std::equal_to<>> buckets;
        std::uint64_t ops = 0;
    };

    Shard& shard_for(std::string_view key) { return shards_[SvHash{}(key) % shards_.size()]; }

    void sweep(Shard& sh, Clock::time_point now) {
        std::erase_if(sh.buckets, [&](const auto& kv) { return now - kv.second.last_update() > idle_ttl_; });
    }

    const double rate_, burst_;
    const std::chrono::seconds idle_ttl_;
    std::array<Shard, 16> shards_;
};

Những điểm cần nói:

  • Thời gian là tham số (now truyền vào, mặc định Clock::now()): test được tất định, không cần sleep. Luôn dùng steady_clock: đồng hồ hệ thống nhảy lùi (NTP) sẽ phá token bucket.
  • Bộ nhớ có giới hạn: hàng triệu IP mỗi cái một bucket là rò bộ nhớ nếu không dọn. Bucket không dùng lâu hơn thời gian nạp đầy (burst / rate) thì đã đầy trở lại, xóa nó và tạo lại khi cần cho kết quả y hệt. Chọn idle_ttl ≥ burst / rate thì việc dọn không đổi hành vi.
  • Tra cứu không cấp phát: hash "trong suốt" (is_transparent) cho phép find(string_view) mà không tạo std::string tạm ở mỗi request (C++20).
  • Sharding giảm tranh chấp như LRU. Muốn không khóa hẳn: gói (số token cố định điểm, timestamp) vào một atomic<uint64_t> và cập nhật bằng CAS.
  • Nhiều máy: mỗi máy giới hạn N/số máy (đơn giản, kém chính xác khi tải lệch), hoặc giữ bucket ở Redis với script nguyên tử; thảo luận ở M16.

Đề 4 · Timer scheduler

Làm rõ yêu cầu.

  • API: schedule_after(delay, cb) → id, schedule_every(period, cb) → id, cancel(id).
  • Callback chạy ở đâu: một thread riêng của scheduler, hay đẩy sang thread pool? Callback có thể chạy lâu không?
  • Độ chính xác cần thiết (mili giây?), số timer đồng thời (hàng chục hay hàng triệu)?
  • Ngữ nghĩa cancel khi callback đang chạy: trả về ngay, hay chờ callback xong?

Thiết kế. Một min-heap theo thời điểm hết hạn; một thread điều phối ngủ bằng condition_variable::wait_until tới hạn sớm nhất. Thêm timer mới sớm hơn thì đánh thức nó để tính lại. cancel dùng xóa lười: chỉ xóa khỏi bảng id → callback; phần tử trong heap bị bỏ qua khi tới lượt (xóa giữa heap tốn O(n)).

#include <chrono>
#include <condition_variable>
#include <cstdint>
#include <functional>
#include <mutex>
#include <queue>
#include <thread>
#include <tuple>
#include <unordered_map>
#include <vector>

class TimerScheduler {
public:
    using Clock    = std::chrono::steady_clock;
    using Callback = std::function<void()>;
    using TimerId  = std::uint64_t;

    TimerScheduler() : worker_([this] { run(); }) {}
    ~TimerScheduler() {
        { std::lock_guard g(m_); stop_ = true; }
        cv_.notify_one();
        worker_.join();
    }

    TimerId schedule_after(Clock::duration delay, Callback cb) {
        return add(Clock::now() + delay, Clock::duration::zero(), std::move(cb));
    }
    TimerId schedule_every(Clock::duration period, Callback cb) {
        return add(Clock::now() + period, period, std::move(cb));
    }
    // true: đã hủy trước khi chạy (lần kế tiếp với timer lặp). false: không tồn tại / đã chạy xong
    bool cancel(TimerId id) {
        std::lock_guard g(m_);
        return entries_.erase(id) > 0;
    }

private:
    struct Entry { Callback cb; Clock::duration period; };
    struct Item {
        Clock::time_point when;
        TimerId id;
        bool operator>(const Item& o) const { return std::tie(when, id) > std::tie(o.when, o.id); }
    };

    TimerId add(Clock::time_point when, Clock::duration period, Callback cb) {
        TimerId id;
        {
            std::lock_guard g(m_);
            id = ++next_id_;
            entries_.emplace(id, Entry{std::move(cb), period});
            heap_.push({when, id});
        }
        cv_.notify_one();                    // có thể là hạn sớm nhất mới
        return id;
    }

    void run() {
        std::unique_lock lk(m_);
        while (!stop_) {
            if (heap_.empty()) {
                cv_.wait(lk, [&] { return stop_ || !heap_.empty(); });
                continue;
            }
            const Item top = heap_.top();
            auto it = entries_.find(top.id);
            if (it == entries_.end()) { heap_.pop(); continue; }       // đã bị hủy: bỏ qua
            if (Clock::now() < top.when) {
                cv_.wait_until(lk, top.when);   // thức khi tới hạn, có timer sớm hơn, hoặc stop
                continue;                       // luôn đánh giá lại từ đầu
            }
            heap_.pop();
            Callback cb;
            if (it->second.period > Clock::duration::zero()) {
                cb = it->second.cb;                                     // giữ bản gốc cho lần sau
                heap_.push({top.when + it->second.period, top.id});     // tính từ hạn cũ: không trôi
            } else {
                cb = std::move(it->second.cb);
                entries_.erase(it);
            }
            lk.unlock();
            cb();                               // ngoài khóa: callback được schedule/cancel
            lk.lock();
        }
    }

    std::mutex m_;
    std::condition_variable cv_;
    std::priority_queue<Item, std::vector<Item>, std::greater<>> heap_;
    std::unordered_map<TimerId, Entry> entries_;
    TimerId next_id_ = 0;
    bool stop_ = false;
    std::thread worker_;                        // khai báo cuối
};

Những điểm cần nói:

  • steady_clock cho mọi timer: system_clock nhảy khi chỉnh giờ.
  • Không trôi (drift): timer lặp tính lần sau từ hạn trước (when + period), không phải từ now() + period; nếu tính từ now(), độ trễ của mỗi lần cộng dồn. Ngược lại, nếu callback chạy lâu hơn chu kỳ, các lần bị lỡ sẽ chạy dồn liền nhau; chính sách khác là bỏ các lần đã lỡ (while (next <= now) next += period).
  • Callback chạy ngoài khóa trên thread điều phối: callback chậm làm trễ mọi timer khác. Nếu callback có thể lâu, thread điều phối chỉ đẩy callback sang thread pool.
  • Ngữ nghĩa cancel: trả false nghĩa là timer đã chạy hoặc đang chạy. Nếu người gọi sắp hủy đối tượng mà callback dùng, cần thêm "cancel và chờ" (đánh dấu id đang chạy, cancel chờ trên cv tới khi lần chạy đó xong; cẩn thận deadlock nếu callback tự gọi cancel chính nó) hoặc dùng các kỹ thuật vòng đời ở Bài 5.
  • Xóa lười làm heap phình khi hủy nhiều (ví dụ timeout của request thường bị hủy vì request xong sớm): theo dõi số phần tử chết, vượt một nửa thì dựng lại heap.
  • Quy mô lớn: hàng triệu timeout (mỗi kết nối một timer) thì heap O(log n) và một khóa trở thành nút thắt. Dùng timer wheel (O(1), độ phân giải thô, M07 Bài 5), hoặc gắn timer vào event loop của thread sở hữu kết nối (Bài 6) để không cần khóa.
Tự kiểm traTrong `TimerScheduler::run`, vì sao sau `wait_until` lại `continue` để đánh giá lại từ đầu thay vì chạy luôn callback của `top`?

Vì thread có thể thức dậy vì nhiều lý do: tới hạn, có timer sớm hơn vừa được thêm (lúc đó top không còn là phần tử đầu), timer top vừa bị hủy, stop_ được đặt, hoặc spurious wakeup. Mọi trạng thái đã có thể thay đổi trong lúc ngủ (mutex được nhả khi chờ), nên phải đọc lại đầu heap và kiểm tra lại hạn. Đây cũng là lý do Item top được chép ra thay vì giữ tham chiếu vào heap.

  • Nhiều khóa: shard + mutex, tra không cấp phát, dọn bucket nhàn rỗi sau burst/rate.
  • Timer scheduler: min-heap + wait_until + xóa lười; đánh giá lại sau mỗi lần thức.

API và lỗi

01Khi nào hàm nên nhận std::shared_ptr<T> làm tham số?Hay hỏi

Chỉ khi hàm giữ lại hoặc chia sẻ quyền sở hữu (lưu vào thành viên, đưa sang thread khác). Hàm chỉ dùng đối tượng thì nhận T& hoặc const T& (hoặc T* nếu có thể null): không tốn hai thao tác atomic refcount và không ép người gọi dùng shared_ptr. Nhận quyền sở hữu độc quyền: std::unique_ptr<T> theo giá trị.

02std::string_view có rủi ro gì?Hay hỏi

Không giữ dữ liệu sống: trả về view tới chuỗi tạm, hoặc lưu view làm thành viên trỏ vào buffer đã bị giải phóng là dangling. Dùng cho tham số chỉ đọc; tránh cho giá trị trả về và thành viên trừ khi vòng đời dữ liệu gốc được đảm bảo.

03Vì sao hàm const nên an toàn khi gọi đồng thời?

Thư viện chuẩn giả định gọi đồng thời các hàm const trên cùng đối tượng là an toàn; container của bạn được dùng chung theo giả định đó. Nếu hàm const sửa trạng thái bên trong (cache, bộ đếm), phần đó phải được đồng bộ bằng mutable mutex hoặc atomic.

04Exception, error code hay std::expected: chọn thế nào?Hay hỏi

Theo tầng và nhất quán. Tầng hệ thống (system call, parser) trả expected/error_code vì lỗi là chuyện thường và người gọi xử lý ngay. Exception (nếu codebase dùng) ném khi không thể tiếp tục và bắt ở ranh giới đơn vị công việc. Không để exception đi qua: callback event loop, thân thread, hàm extern "C"/callback của thư viện C, destructor. Bug lập trình: assert/abort lấy core dump.

05Vì sao move constructor nên noexcept?

std::vector khi phát triển chỉ move phần tử nếu move là noexcept (hoặc không copy được); nếu không, nó copy để giữ strong exception guarantee. Thiếu noexcept làm mất lợi ích hiệu năng của move.

06Làm gì với errno khi system call thất bại?

Chụp ngay vào std::error_code(errno, std::generic_category()) trước khi gọi bất kỳ hàm nào khác (chúng có thể ghi đè errno), thêm ngữ cảnh (file nào, thao tác gì) rồi trả lên hoặc ném std::system_error.

Thư viện và tài nguyên

07Những thay đổi nào làm vỡ ABI của thư viện C++?Hay hỏi

Thêm/xóa/đổi thứ tự thành viên dữ liệu của class public (sizeof, offset), thêm hàm virtual (vtable), đổi chữ ký hàm (mangling), sửa code inline/template trong header, đổi giá trị enum. An toàn: thêm hàm không virtual, hàm tự do, class mới, sửa thân hàm trong .cpp. Vỡ ABI thì tăng SONAME major; kiểm tra bằng abidiff.

08pImpl là gì, lợi và hại?Hay hỏi

Class public chỉ chứa unique_ptr<Impl>, mọi dữ liệu ở .cpp. Lợi: ABI ổn định (sizeof không đổi), tường lửa biên dịch (header không kéo theo thư viện bên thứ ba, đổi cài đặt không biên dịch lại người dùng). Hại: một cấp phát heap, một gián tiếp, không inline. Destructor và move phải khai báo trong header, định nghĩa = default trong .cpp nơi Impl đầy đủ.

09Thiết kế plugin bằng dlopen thế nào?

Interface (class trừu tượng) + số phiên bản API dùng chung; plugin xuất hàm extern "C" create/destroy (không mangle, kiểm tra version, không để exception thoát); host dlopen(RTLD_NOW | RTLD_LOCAL), dlsym, bọc đối tượng trong unique_ptr với deleter gọi destroy; đối tượng phải bị hủy trước dlclose. Interface C++ yêu cầu cùng compiler/stdlib; khác thì dùng ranh giới C.

10Vì sao unique_fd phải move-only? Có gọi lại close khi EINTR không?Hay hỏi

Copy fd thì hai đối tượng cùng đóng một số, lần đóng thứ hai có thể đóng nhầm fd mới được cấp cùng số. Trên Linux fd luôn được giải phóng kể cả khi close trả EINTR, nên không gọi lại (có thể đóng fd của thread khác vừa mở).

11Ghi file cấu hình an toàn khi mất điện thế nào?Hay hỏi

Ghi ra file tạm cùng thư mục, fsync file, rename đè lên file thật (nguyên tử trên cùng filesystem), fsync thư mục. Lỗi ở bước nào thì xóa file tạm (scope guard). Sau mất điện chỉ có bản cũ đầy đủ hoặc bản mới đầy đủ.

12Class có thành viên std::jthread dùng các thành viên khác: khai báo ở đâu?Hay hỏi

Cuối cùng. Thành viên bị hủy theo thứ tự ngược khai báo, nên thread khai báo cuối bị dừng/join đầu tiên khi các thành viên nó dùng vẫn còn sống. Khởi động thread trong danh sách khởi tạo của thành viên cuối để mọi thứ nó dùng đã dựng xong.

Callback và đa hình

13Callback bắt this thô có vấn đề gì? Cách sửa?Hay hỏi

Đối tượng có thể bị hủy trước khi callback (timer, I/O bất đồng bộ) chạy: use-after-free. Sửa: handle RAII hủy đăng ký trong destructor (khi cùng một thread); bắt weak_ptr (weak_from_this(), lock rồi mới gọi); bắt shared_ptr để giữ sống tới khi xong (cẩn thận chu trình); đối tượng Connection của signal/slot.

14Type erasure là gì? Ví dụ trong thư viện chuẩn?

Bọc bất kỳ kiểu nào thỏa một "giao diện ngầm" vào một kiểu giá trị chung: interface nội bộ (Concept với hàm virtual) + template Model<T> cài đặt nó + unique_ptr<Concept>. Người dùng không cần kế thừa. Ví dụ: std::function, std::any, deleter của shared_ptr.

15Khi nào dùng std::variant thay cho kế thừa?

Khi tập kiểu đóng và biết trước (message, sự kiện, trạng thái): ngữ nghĩa giá trị, không cấp phát heap, std::visit với overload bắt buộc xử lý mọi kiểu lúc biên dịch. Kế thừa khi tập kiểu mở (plugin, test double).

16Vì sao gọi slot/callback ngoài khóa?

Callback có thể đăng ký/hủy đăng ký hoặc phát sự kiện lại (tự deadlock với mutex không đệ quy), có thể chạy lâu (chặn thread khác), có thể lấy khóa khác (deadlock thứ tự khóa). Chép danh sách (shared_ptr) trong khóa, gọi ngoài khóa.

Event loop và đồng thời

17epoll level-triggered và edge-triggered khác nhau thế nào?Hay hỏi

Level-triggered báo chừng nào điều kiện còn đúng (còn dữ liệu chưa đọc). Edge-triggered chỉ báo khi trạng thái thay đổi (dữ liệu mới tới): phải dùng fd non-blocking và đọc/ghi tới EAGAIN, nếu không phần còn lại không bao giờ được báo và kết nối có vẻ treo.

18Vì sao không bật EPOLLOUT thường trực?

Socket gần như lúc nào cũng ghi được, nên epoll_wait trả về liên tục và loop quay 100% CPU. Chỉ bật khi bộ đệm ghi của kết nối còn dữ liệu chờ, tắt khi đã ghi hết.

19Trên Linux có những loại fd nào để đưa mọi sự kiện vào một event loop?

Socket, timerfd (timer), eventfd (đánh thức từ thread khác), signalfd (signal), pidfd (process con kết thúc), inotify (file thay đổi), netlink (mạng, hotplug), fd thiết bị (serial, input, GPIO qua libgpiod). File thường không dùng được với epoll (EPERM).

20Reactor và proactor khác nhau thế nào?

Reactor: kernel báo fd sẵn sàng, ứng dụng tự đọc/ghi (epoll). Proactor: ứng dụng nộp thao tác, được báo khi hoàn tất (io_uring, IOCP). Asio cung cấp API kiểu proactor, trên Linux hiện thực bằng epoll hoặc io_uring.

21Thiết kế thread pool cần những gì?Hay hỏi

Queue việc (mutex + cv), N worker, submit trả future (packaged_task mang cả exception), shutdown: ngừng nhận, chạy nốt, join. Thảo luận: số thread (CPU-bound = số nhân; tách pool cho việc chặn), queue có giới hạn + chính sách khi đầy, deadlock khi task chờ task cùng pool, work stealing khi task nhỏ.

22Strand là gì?

Hàng đợi tuần tự hóa chạy trên pool chung: các việc của cùng strand không bao giờ chạy đồng thời và chạy theo thứ tự gửi, nên dữ liệu của strand không cần mutex. Actor = trạng thái riêng + strand (hoặc thread riêng) + hộp thư.

23Tắt một service gọn gàng thế nào?Hay hỏi

Nhận SIGTERM đồng bộ (signalfd/sigwait), ngừng nhận việc mới, đóng kết nối rảnh, cho việc đang làm một hạn chót, dừng event loop, shutdown pool (chạy nốt/hủy), flush log, join theo thứ tự ngược phụ thuộc; không để destructor static chạy khi thread còn sống. systemd chờ TimeoutStopSec rồi SIGKILL.

IPC và test

24Chọn cơ chế IPC giữa hai daemon trên cùng thiết bị?Hay hỏi

Mặc định Unix domain socket (hai chiều, xác thực bằng SO_PEERCRED, truyền được fd) với message đóng khung có giới hạn kích thước. Dữ liệu lớn: shared memory (memfd/dmabuf) với fd truyền qua socket, socket chỉ mang thông báo nhỏ. Tích hợp dịch vụ hệ thống: D-Bus. Ra ngoài thiết bị: TCP/MQTT/gRPC.

25Truyền file descriptor giữa process để làm gì? Bằng cách nào?

sendmsg với control message SCM_RIGHTS qua Unix socket. Dùng để tách quyền (process root mở thiết bị/cổng rồi trao fd cho process quyền thấp), zero-copy (memfd/dmabuf), socket activation của systemd. Bên nhận có fd mới trỏ tới cùng đối tượng; nhận với MSG_CMSG_CLOEXEC.

26Đóng khung message trên stream socket cần lưu ý gì?

Stream không giữ ranh giới: một send có thể thành nhiều recv và ngược lại. Dùng độ dài đứng trước (big-endian), vòng lặp send/recv đủ byte, giới hạn kích thước tối đa, MSG_NOSIGNAL để không chết vì SIGPIPE. Hoặc SOCK_SEQPACKET để kernel giữ ranh giới.

27Làm sao test code phụ thuộc thời gian mà không sleep?Hay hỏi

Coi đồng hồ là phụ thuộc: tiêm interface Clock (hoặc truyền now làm tham số), test dùng đồng hồ giả tua được. Với code dùng thread: tiêm executor, test chạy task tất định. Chờ tín hiệu cụ thể có timeout thay vì sleep cố định.

28Mock, fake khác nhau và khi nào dùng StrictMock?

Mock được lập trình kỳ vọng về lời gọi và tự kiểm tra; fake là cài đặt đơn giản có hành vi thật (đồng hồ giả, filesystem trong RAM). Ưu tiên fake để test kiểm tra kết quả, ít phụ thuộc thứ tự gọi. StrictMock cho tương tác quan trọng (bật/tắt thiết bị), tránh mock quá chặt mọi thứ vì test vỡ khi refactor.

29Bộ sanitizer tối thiểu trong CI?

Một bản ASan + UBSan (tràn buffer, use-after-free, rò bộ nhớ, UB), một bản TSan (race, lock order; không chung với ASan), bản Release với -Wall -Wextra -Werror, clang-tidy; fuzz mọi parser bằng libFuzzer + ASan.

Low-level design

30LRU cache thread-safe: cấu trúc và vì sao không dùng shared lock cho get?Hay hỏi

unordered_map<Key, list::iterator> + list<pair<Key, Value>>; get đưa node lên đầu bằng splice O(1), put khi đầy bỏ node cuối. get sửa thứ tự list nên cũng là ghi: cần khóa độc quyền. Giảm tranh chấp: sharding (LRU xấp xỉ), CLOCK; value lớn lưu shared_ptr<const V>; single-flight chống stampede.

31Logger bất đồng bộ thiết kế thế nào?Hay hỏi

Thread gọi chỉ nối vào buffer hiện tại trong khóa ngắn; thread nền tráo buffer ra và ghi ngoài khóa (double buffering). Giới hạn bộ nhớ, đầy thì bỏ và đếm; flush đồng bộ bằng số vé; thoát không sót. Mở rộng: ring buffer mỗi thread, trì hoãn định dạng, an toàn khi crash.

32Token bucket hoạt động thế nào? Rate limiter theo khóa cần gì thêm?Hay hỏi

Bình tối đa b token, nạp r/giây tính lười theo thời gian trôi, mỗi request lấy một token; cho burst tới b. Theo khóa: map khóa → bucket chia shard có mutex, tra không cấp phát, dọn bucket nhàn rỗi sau burst/rate (lúc đó đã đầy nên xóa không đổi hành vi); thời gian là tham số, dùng steady_clock.

33Timer scheduler: cấu trúc và các chi tiết khó?Hay hỏi

Min-heap (hạn, id) + bảng id → callback; thread điều phối wait_until hạn sớm nhất, thêm timer sớm hơn thì notify; cancel bằng xóa lười. Sau mỗi lần thức đánh giá lại từ đầu; callback chạy ngoài khóa (chậm thì đẩy sang pool); timer lặp tính từ hạn trước để không trôi; nói rõ cancel khi callback đang chạy; quy mô lớn dùng timer wheel.
