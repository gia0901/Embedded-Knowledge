Bài 0 · Vì sao firmware cần design pattern

Ghi chúPhạm vi module

Module này tập trung vào firmware MCU bare-metal và RTOS. Thiết kế C++ cho ứng dụng chạy trên Linux (API, ABI, event loop epoll, thread pool, IPC, test với gMock) nằm ở M14 · C++ design cho Linux userspace. Các ý tổng quát ở đây (phân lớp, interface, state machine, active object, DI) vẫn áp dụng cho cả hai.

Firmware sống lâu hơn bạn nghĩ

Một sản phẩm Embedded thường được bán và bảo trì 5 đến 15 năm. Trong thời gian đó: MCU bị ngừng sản xuất và phải thay chip khác, cảm biến đổi model, giao thức thêm tính năng, đội phát triển thay người. Firmware viết theo kiểu "một file main.c 5000 dòng, đọc thanh ghi ở khắp nơi" chạy được ở phiên bản đầu, nhưng mỗi thay đổi về sau đều đau đớn và rủi ro.

Design pattern là những cách tổ chức code đã được kiểm chứng để giải quyết các vấn đề lặp đi lặp lại. Trong Embedded, chúng nhắm tới mấy mục tiêu cụ thể:

  • Port được: thay MCU hay cảm biến mà không viết lại logic ứng dụng.
  • Test được trên máy tính: chạy phần lớn code trên PC với unit test, không cần board (nhanh hơn hàng trăm lần, chạy được trong CI).
  • Hiểu được: hành vi phức tạp (giao thức, chế độ hoạt động) được mô tả rõ ràng, không rải rác trong các cờ if.
  • Đúng khi đồng thời: dữ liệu chia sẻ giữa ISR, task, DMA được xử lý theo mẫu an toàn.

Hai nguyên tắc nền tảng

1. Coupling thấp, cohesion cao. Mỗi module làm một việc rõ ràng (cohesion cao) và biết càng ít về module khác càng tốt (coupling thấp). Một driver cảm biến không nên biết về giao diện người dùng; logic điều khiển không nên biết địa chỉ thanh ghi.

2. Dependency inversion (đảo ngược phụ thuộc). Module cấp cao (logic ứng dụng) không phụ thuộc vào module cấp thấp (driver phần cứng); cả hai cùng phụ thuộc vào một interface (trừu tượng). Đây là chìa khóa cho cả tính port được lẫn tính test được.

 Phụ thuộc trực tiếp (khó port, khó test):
   [Điều khiển nhiệt độ] ──▶ [Driver BME280] ──▶ [HAL I2C STM32]

 Đảo ngược phụ thuộc:
   [Điều khiển nhiệt độ] ──▶ «interface» TempSensor ◀── [Driver BME280]
                                                    ◀── [Fake sensor (test)]

Logic điều khiển chỉ biết TempSensor. Khi test trên PC, ta đưa vào một sensor giả trả về giá trị tùy ý. Khi đổi cảm biến, chỉ cần một driver mới cài đặt cùng interface.

Pattern không phải là mục tiêu

Mỗi lớp trừu tượng có giá: thêm code, thêm gián tiếp (function pointer, virtual call), khó theo dõi hơn khi đọc. Với một firmware nhỏ 2000 dòng cho một sản phẩm không bao giờ đổi phần cứng, nhiều lớp là thừa. Hãy thêm trừu tượng ở ranh giới có khả năng thay đổi (phần cứng, giao thức bên ngoài) và ở chỗ cần test, không thêm khắp nơi.

  • Coupling thấp, cohesion cao; dependency inversion qua interface.
  • Trừu tượng có giá: đặt ở ranh giới có khả năng thay đổi và chỗ cần test.

Bài 1 · Kiến trúc phân lớp và interface

Các lớp điển hình của firmware

 ┌──────────────────────────────────────────────────────┐
 │ Application      logic sản phẩm, chế độ, state machine │
 ├──────────────────────────────────────────────────────┤
 │ Services /       giao thức (Modbus, MQTT), file system, │
 │ Middleware       logging, cấu hình, OTA                │
 ├──────────────────────────────────────────────────────┤
 │ Device drivers   cảm biến, màn hình, flash ngoài: dùng  │
 │                  bus trừu tượng (I2C, SPI)              │
 ├──────────────────────────────────────────────────────┤
 │ HAL              trừu tượng ngoại vi của MCU: GPIO,     │
 │                  UART, I2C, SPI, timer, ADC             │
 ├──────────────────────────────────────────────────────┤
 │ BSP / CMSIS      chân nào nối gì, clock, startup,       │
 │                  định nghĩa thanh ghi                   │
 ├──────────────────────────────────────────────────────┤
 │ Phần cứng                                               │
 └──────────────────────────────────────────────────────┘
        (OS/RTOS là một lớp ngang, nhiều lớp dùng chung)
  • BSP (Board Support Package): mọi thứ đặc thù của board: chân nào nối LED, cảm biến ở bus I2C nào, tần số thạch anh, khởi tạo clock. Đổi board (cùng MCU) chỉ đổi BSP.
  • HAL (Hardware Abstraction Layer): API thống nhất cho ngoại vi của MCU, giấu chi tiết thanh ghi. Đổi MCU thì viết lại HAL (hoặc dùng HAL của hãng / Zephyr).
  • Device driver: điều khiển một linh kiện bên ngoài (cảm biến BME280, flash W25Q, màn hình SSD1306) thông qua HAL. Driver tốt không biết MCU nào đang chạy, chỉ biết "có một bus I2C".
  • Middleware: thành phần dùng lại được, độc lập phần cứng.
  • Application: logic của sản phẩm.

Quy tắc phụ thuộc: mỗi lớp chỉ gọi xuống lớp ngay dưới (hoặc qua interface); lớp dưới không bao giờ gọi lên lớp trên trực tiếp. Lớp dưới cần báo lên (dữ liệu đã nhận, sự kiện) thì dùng callback hoặc event (Bài 5), mà lớp trên đăng ký.

Interface trong C: struct các con trỏ hàm

C không có class, nhưng struct chứa con trỏ hàm chính là cách cài đặt interface (và là cách Linux kernel làm với struct file_operations, struct i2c_algorithm…). Ví dụ interface bus I2C:

/* i2c_bus.h: interface, không phụ thuộc MCU */
typedef struct i2c_bus i2c_bus_t;
struct i2c_bus {
    int (*write)(i2c_bus_t *bus, uint8_t addr, const uint8_t *data, size_t len);
    int (*write_read)(i2c_bus_t *bus, uint8_t addr, const uint8_t *tx, size_t tx_len,
                      uint8_t *rx, size_t rx_len);
    void *ctx;                                          /* dữ liệu riêng của cài đặt */
};

Driver cảm biến chỉ dùng interface:

/* tmp117.h / tmp117.c: driver cảm biến nhiệt, không biết MCU */
typedef struct { i2c_bus_t *bus; uint8_t addr; } tmp117_t;

int tmp117_read_centi(tmp117_t *dev, int32_t *centi_c) {
    uint8_t reg = 0x00, raw[2];
    int rc = dev->bus->write_read(dev->bus, dev->addr, &reg, 1, raw, 2);
    if (rc != 0) return rc;
    int16_t v = (int16_t)((raw[0] << 8) | raw[1]);      /* 1 LSB = 7,8125 m°C */
    *centi_c = ((int32_t)v * 78125) / 100000;           /* đổi sang 0,01 °C */
    return 0;
}

Cài đặt cho STM32 (trong lớp HAL/port):

/* i2c_stm32.c */
static int stm32_write_read(i2c_bus_t *bus, uint8_t addr, const uint8_t *tx, size_t tx_len,
                            uint8_t *rx, size_t rx_len) {
    I2C_HandleTypeDef *h = bus->ctx;
    if (HAL_I2C_Master_Transmit(h, addr << 1, (uint8_t *)tx, tx_len, 10) != HAL_OK) return -1;
    return HAL_I2C_Master_Receive(h, addr << 1, rx, rx_len, 10) == HAL_OK ? 0 : -1;
}
i2c_bus_t g_i2c1 = { .write = stm32_write, .write_read = stm32_write_read, .ctx = &hi2c1 };

Và cài đặt giả cho unit test trên PC (Bài 7) dùng cùng interface. Driver tmp117.c không đổi một dòng nào.

Opaque handle. Một biến thể khác: header chỉ khai báo typedef struct uart uart_t; (kiểu chưa hoàn chỉnh), người dùng chỉ cầm con trỏ, chi tiết struct nằm trong file .c. Đây là cách đóng gói trong C: người dùng không thể chạm vào thành viên bên trong.

Interface trong C++: virtual hay template

Dynamic polymorphism (virtual):

class I2cBus {
public:
    virtual ~I2cBus() = default;
    virtual int write_read(uint8_t addr, std::span<const uint8_t> tx, std::span<uint8_t> rx) = 0;
};
class Tmp117 {
public:
    explicit Tmp117(I2cBus& bus, uint8_t addr = 0x48) : bus_(bus), addr_(addr) {}
    std::optional<int32_t> read_centi();
private:
    I2cBus& bus_;
    uint8_t addr_;
};

Chi phí: mỗi object có vptr (một con trỏ), mỗi class có vtable trong Flash, mỗi lời gọi là gọi gián tiếp (thường không inline được). Trên Cortex-M, chi phí này nhỏ (vài chu kỳ), thường chấp nhận được. Không cần RTTI hay exception.

Static polymorphism (template, có thể kết hợp concepts của C++20):

template<typename Bus>
class Tmp117T {
public:
    explicit Tmp117T(Bus& bus) : bus_(bus) {}
    std::optional<int32_t> read_centi() {
        uint8_t reg = 0, raw[2];
        if (bus_.write_read(0x48, {&reg, 1}, raw) != 0) return std::nullopt;
        const auto v = static_cast<int16_t>((raw[0] << 8) | raw[1]);
        return int32_t{v} * 78125 / 100000;
    }
private:
    Bus& bus_;
};

Không có virtual call, compiler inline được toàn bộ: zero-cost abstraction. Đổi lại: code nằm trong header, mỗi kiểu Bus sinh một bản code (code bloat), thông báo lỗi khó đọc hơn (concepts giúp nhiều), và không thể chọn cài đặt lúc chạy.

Quy tắc chọn: cài đặt chọn lúc compile và không đổi (một board một loại bus) → template hợp lý; cần chọn lúc chạy (phát hiện loại cảm biến khi khởi động, nhiều cài đặt cùng tồn tại) → virtual hoặc function pointer. CRTP (Bài 6) là một cách khác cho static polymorphism.

Embedded LinuxInterface trong Linux driver model

Kernel dùng đúng mẫu struct con trỏ hàm ở mọi nơi: struct file_operations (open/read/write/ioctl cho character device), struct i2c_driver (probe/remove), struct platform_driver. Device tree mô tả phần cứng (tương tự BSP), driver chỉ làm việc qua API của subsystem (regmap, i2c, spi), nên cùng một driver chạy trên mọi SoC.

Tự kiểm traMột driver cảm biến gọi trực tiếp `HAL_I2C_Master_Transmit` của STM32. Có vấn đề gì khi đổi sang MCU nRF52?

Driver phải sửa vì phụ thuộc HAL của STM32. Nếu driver chỉ dùng interface bus I2C trừu tượng, chỉ cần viết cài đặt interface cho nRF52; driver giữ nguyên.

Khi cài đặt được chọn lúc compile và không đổi, và muốn compiler inline (zero-cost). Dùng virtual khi cần chọn cài đặt lúc chạy hoặc giữ code ngoài header.

Bài 2 · Mô hình thực thi: super-loop, scheduler và RTOS

Trước khi chọn các pattern khác, phải quyết định code chạy như thế nào theo thời gian. Đây là quyết định kiến trúc lớn nhất của firmware.

Super-loop

int main(void) {
    board_init();
    for (;;) {
        read_sensors();
        update_control();
        handle_uart();
        update_display();
    }
}

Đơn giản nhất, không cần OS, dễ hiểu. Nhược điểm:

  • Thời gian phản ứng của mỗi việc phụ thuộc thời gian chạy của tất cả việc khác. Nếu update_display() mất 30 ms, UART phải chờ 30 ms.
  • Mọi hàm phải không chặn (non-blocking): không được delay, không được chờ phần cứng vô hạn. Việc dài phải chia thành các bước nhỏ (thường bằng state machine).
  • Chu kỳ không đều: khó làm việc định kỳ chính xác.

Super-loop + ngắt (foreground/background)

Phần cấp bách chạy trong ISR (foreground): nhận byte UART vào ring buffer, đọc ADC, cập nhật bộ đếm tick. Phần còn lại chạy trong vòng lặp chính (background), xử lý dữ liệu ISR để lại. Đây là kiến trúc phổ biến nhất của firmware nhỏ.

volatile uint32_t g_ticks;                    /* SysTick tăng mỗi 1 ms */
void SysTick_Handler(void) { g_ticks++; }

int main(void) {
    board_init();
    uint32_t last_ctrl = 0, last_disp = 0;
    for (;;) {
        uart_process_rx();                                  /* lấy từ ring buffer ISR đổ vào */
        uint32_t now = g_ticks;
        if ((uint32_t)(now - last_ctrl) >= 10u) { last_ctrl += 10u; control_step(); }   /* 100 Hz */
        if ((uint32_t)(now - last_disp) >= 100u) { last_disp = now; display_step(); }   /* 10 Hz */
        __WFI();                                            /* ngủ tới ngắt tiếp theo: tiết kiệm điện */
    }
}

(last_ctrl += 10 thay vì = now để giữ chu kỳ trung bình đúng 10 ms, không bị trôi.)

Cooperative scheduler (time-triggered)

Mở rộng tự nhiên: một bảng task với chu kỳ, scheduler gọi task khi tới hạn. Mỗi task chạy tới khi xong rồi trả quyền (cooperative), không có task nào bị ngắt giữa chừng bởi task khác (chỉ bị ISR ngắt).

typedef struct { void (*fn)(void); uint32_t period_ms; uint32_t next; } task_t;

static task_t k_tasks[] = {
    { control_step, 10,  0 },
    { comm_step,    20,  5 },                                /* lệch pha để tránh dồn cùng tick */
    { display_step, 100, 7 },
};

void scheduler_run(void) {
    for (;;) {
        uint32_t now = g_ticks;
        for (size_t i = 0; i < sizeof k_tasks / sizeof k_tasks[0]; ++i) {
            if ((int32_t)(now - k_tasks[i].next) >= 0) {
                k_tasks[i].next += k_tasks[i].period_ms;
                k_tasks[i].fn();
            }
        }
        __WFI();
    }
}

Ưu điểm: tất định cao, dễ phân tích thời gian (mỗi task có WCET, tổng phải vừa chu kỳ), không có race giữa các task (chỉ một task chạy tại một thời điểm, không bị chen ngang bởi task khác), không cần mutex. Được dùng nhiều trong hệ thống an toàn (kiến trúc time-triggered của Michael Pont). Nhược điểm: một task chạy lâu làm trễ mọi task khác; việc dài phải tự chia nhỏ.

RTOS preemptive

Mỗi task là một luồng riêng có stack riêng và priority. Scheduler chen ngang (preempt) task ưu tiên thấp ngay khi task ưu tiên cao sẵn sàng. Task được phép chặn (chờ queue, semaphore, delay) mà không ảnh hưởng task khác.

void comm_task(void *arg) {
    for (;;) {
        frame_t f;
        xQueueReceive(rx_queue, &f, portMAX_DELAY);      /* chặn tới khi có frame */
        handle_frame(&f);                                /* code tuần tự, dễ đọc */
    }
}

Ưu điểm: code mỗi task viết tuần tự, tự nhiên (chờ ở đâu cứ chờ ở đó); task ưu tiên cao phản ứng nhanh bất kể task thấp đang làm gì; thư viện bên thứ ba (TCP/IP, USB, file system) thường cần RTOS. Nhược điểm: mỗi task tốn stack (khó ước lượng), có race condition giữa các task (cần mutex, queue), có rủi ro deadlock và priority inversion, khó phân tích thời gian hơn, tốn thêm Flash/RAM cho kernel.

Bài 3 · State machine

Vấn đề: logic điều khiển bằng cờ

Rất nhiều firmware mô tả hành vi bằng một đống biến cờ:

if (connected && !busy && retry_count < 3 && !waiting_ack && rx_ready) { ... }

Khi số cờ tăng, số tổ hợp tăng theo cấp số mũ; nhiều tổ hợp vô nghĩa nhưng vẫn có thể xảy ra, và không ai chắc code xử lý đúng mọi tổ hợp. Đó là nguồn bug kinh điển.

State machine (máy trạng thái hữu hạn, FSM) thay đống cờ bằng một biến trạng thái với tập giá trị rõ ràng, và các chuyển trạng thái (transition) xảy ra khi có sự kiện (event). Hệ thống luôn ở đúng một trạng thái; hành vi phụ thuộc vào trạng thái hiện tại và sự kiện vừa đến.

Ví dụ: bộ quản lý kết nối của module 4G/LTE:

                 power_on
     ┌──────┐ ─────────────▶ ┌──────────┐  modem_ready   ┌────────────┐
     │ OFF  │                │ BOOTING  │ ──────────────▶│ REGISTERING│
     └──────┘ ◀───────────── └──────────┘                └────────────┘
         ▲      power_off         │ timeout (×3)            │ registered
         │                        ▼                         ▼
         │                   ┌──────────┐  link_lost   ┌────────────┐
         └────────────────── │  ERROR   │ ◀─────────── │ CONNECTED  │
              reset          └──────────┘              └────────────┘

Các khái niệm:

  • State: trạng thái (OFF, BOOTING…).
  • Event: sự kiện kích hoạt (power_on, timeout, modem_ready).
  • Transition: chuyển từ trạng thái này sang trạng thái khác khi có sự kiện.
  • Action: hành động thực hiện khi chuyển (gửi lệnh AT, bật timer).
  • Guard: điều kiện phụ cho phép chuyển (timeout [retry < 3]).
  • Entry/exit action: hành động khi vào/ra một trạng thái (vào BOOTING thì bật nguồn modem và khởi động timer 10 s; ra khỏi thì dừng timer).

Cách 1: switch-case lồng nhau

Cách phổ biến và dễ đọc nhất với state machine nhỏ: switch theo trạng thái, bên trong xử lý theo sự kiện.

typedef enum { ST_OFF, ST_BOOTING, ST_REGISTERING, ST_CONNECTED, ST_ERROR } conn_state_t;
typedef enum { EV_POWER_ON, EV_POWER_OFF, EV_MODEM_READY, EV_REGISTERED,
               EV_LINK_LOST, EV_TIMEOUT, EV_RESET } conn_event_t;

typedef struct { conn_state_t state; uint8_t retries; } conn_t;

static void enter(conn_t *c, conn_state_t s) {           /* entry action tập trung một chỗ */
    c->state = s;
    switch (s) {
    case ST_BOOTING:     modem_power(true); timer_start(TMR_CONN, 10000); break;
    case ST_REGISTERING: modem_send("AT+CREG?"); timer_start(TMR_CONN, 30000); break;
    case ST_CONNECTED:   timer_stop(TMR_CONN); led_set(LED_NET, true); break;
    case ST_ERROR:       modem_power(false); led_blink(LED_NET); break;
    case ST_OFF:         modem_power(false); timer_stop(TMR_CONN); break;
    }
}

void conn_dispatch(conn_t *c, conn_event_t ev) {
    switch (c->state) {
    case ST_OFF:
        if (ev == EV_POWER_ON) { c->retries = 0; enter(c, ST_BOOTING); }
        break;
    case ST_BOOTING:
        if (ev == EV_MODEM_READY) enter(c, ST_REGISTERING);
        else if (ev == EV_TIMEOUT) {
            if (++c->retries < 3) enter(c, ST_BOOTING);  /* guard: thử lại */
            else enter(c, ST_ERROR);
        }
        else if (ev == EV_POWER_OFF) enter(c, ST_OFF);
        break;
    case ST_REGISTERING:
        if (ev == EV_REGISTERED) enter(c, ST_CONNECTED);
        else if (ev == EV_TIMEOUT) enter(c, ST_ERROR);
        else if (ev == EV_POWER_OFF) enter(c, ST_OFF);
        break;
    case ST_CONNECTED:
        if (ev == EV_LINK_LOST) enter(c, ST_ERROR);
        else if (ev == EV_POWER_OFF) enter(c, ST_OFF);
        break;
    case ST_ERROR:
        if (ev == EV_RESET) enter(c, ST_OFF);
        break;
    }
}

Ưu điểm: dễ đọc, dễ debug, compiler cảnh báo khi thiếu case cho enum (-Wswitch). Nhược điểm: với nhiều trạng thái và sự kiện, hàm dài; xử lý chung (ví dụ POWER_OFF ở mọi trạng thái) bị lặp lại.

Nguyên tắc quan trọng: state machine không chặn. dispatch xử lý một sự kiện rồi trả về ngay. Việc chờ (chờ modem trả lời) được biểu diễn bằng ở yên trong một trạng thái cho tới khi sự kiện tương ứng đến (EV_MODEM_READY hoặc EV_TIMEOUT). Đó là lý do state machine kết hợp tốt với super-loop và event queue.

Cách 2: bảng chuyển trạng thái

Biểu diễn transition bằng dữ liệu: bảng [trạng thái][sự kiện] → (trạng thái mới, hành động). Code chỉ còn tra bảng (table-driven, Module 6 Bài 7).

typedef void (*action_t)(conn_t *c);
typedef struct { conn_state_t next; action_t action; } transition_t;

/* giả sử hai enum có thêm phần tử cuối ST_COUNT và EV_COUNT; ô không khai báo = {0, NULL}: bỏ qua sự kiện */
static const transition_t k_table[ST_COUNT][EV_COUNT] = {
    /*             POWER_ON              POWER_OFF          MODEM_READY            ... */
    [ST_OFF]     = { [EV_POWER_ON] = { ST_BOOTING, act_boot } },
    [ST_BOOTING] = { [EV_MODEM_READY] = { ST_REGISTERING, act_query_reg },
                     [EV_POWER_OFF]   = { ST_OFF, act_power_down },
                     [EV_TIMEOUT]     = { ST_BOOTING, act_retry_or_fail } },
    /* ... */
};

void conn_dispatch_table(conn_t *c, conn_event_t ev) {
    const transition_t *t = &k_table[c->state][ev];
    if (t->action == NULL) return;                       /* sự kiện bị bỏ qua ở trạng thái này */
    c->state = t->next;
    t->action(c);                                        /* action có thể đổi state (guard) */
}

Ưu điểm: toàn bộ hành vi hiện rõ trong một bảng, dễ đối chiếu với sơ đồ, dễ sinh tự động từ công cụ, bảng const nằm trong Flash. Nhược điểm: guard và logic phức tạp phải đẩy vào action; bảng thưa (nhiều ô trống) tốn bộ nhớ (S × E ô).

Cách 3: con trỏ hàm trạng thái

Mỗi trạng thái là một hàm xử lý sự kiện; biến trạng thái là con trỏ tới hàm đó. Chuyển trạng thái là đổi con trỏ.

typedef struct conn conn_fp_t;
typedef void (*state_fn)(conn_fp_t *c, conn_event_t ev);
struct conn { state_fn state; uint8_t retries; };

static void st_off(conn_fp_t *c, conn_event_t ev);
static void st_booting(conn_fp_t *c, conn_event_t ev);

static void st_off(conn_fp_t *c, conn_event_t ev) {
    if (ev == EV_POWER_ON) { c->retries = 0; modem_power(true); c->state = st_booting; }
}
static void st_booting(conn_fp_t *c, conn_event_t ev) {
    switch (ev) {
    case EV_MODEM_READY: /* ... */ break;
    case EV_POWER_OFF:   modem_power(false); c->state = st_off; break;
    default: break;
    }
}
static inline void conn_fp_dispatch(conn_fp_t *c, conn_event_t ev) { c->state(c, ev); }

Mỗi trạng thái được đóng gói gọn trong một hàm, dễ thêm trạng thái mới. Đây là cách trạng thái được cài đặt trong framework QP và trong ví dụ máy ATM của C++ Concurrency in Action (Chương 4).

State pattern trong C++

Mẫu State (GoF): mỗi trạng thái là một class cài đặt cùng interface; context giữ con trỏ tới object trạng thái hiện tại. Với C++17, cách gọn hơn là dùng std::variant các struct trạng thái và std::visit, cho phép mỗi trạng thái mang dữ liệu riêng (ví dụ trạng thái BOOTING mang số lần thử, CONNECTED mang địa chỉ IP) mà không cần cấp phát.

struct Off {}; struct Booting { int retries; }; struct Connected { uint32_t ip; };
using State = std::variant<Off, Booting, Connected>;

State on_event(const State& s, Event ev) {
    return std::visit([&](const auto& st) -> State {
        using S = std::decay_t<decltype(st)>;
        if constexpr (std::is_same_v<S, Off>)      { if (ev == Event::PowerOn) return Booting{0}; }
        if constexpr (std::is_same_v<S, Booting>)  { if (ev == Event::Timeout) return st.retries < 2 ? State{Booting{st.retries + 1}} : State{Off{}}; }
        if constexpr (std::is_same_v<S, Connected>){ if (ev == Event::LinkLost) return Off{}; }
        return st;                                         /* không đổi */
    }, s);
}

Hierarchical state machine (HSM, statechart)

FSM phẳng có hai vấn đề khi lớn lên: bùng nổ trạng thái và xử lý lặp lại. Ví dụ: sự kiện POWER_OFF phải được xử lý giống nhau ở BOOTING, REGISTERING, CONNECTED; sự kiện BATTERY_LOW cũng vậy.

Hierarchical state machine (statechart của David Harel, chuẩn hóa trong UML) cho phép trạng thái lồng nhau: trạng thái con kế thừa hành vi của trạng thái cha. Sự kiện mà trạng thái con không xử lý sẽ được chuyển lên cha.

 ┌───────────────────── ON ─────────────────────────┐   POWER_OFF (xử lý một lần ở ON)
 │  ┌─────────┐   ┌────────────┐   ┌───────────┐   │ ─────────────────────▶ [OFF]
 │  │ BOOTING │──▶│ REGISTERING│──▶│ CONNECTED │   │
 │  └─────────┘   └────────────┘   └───────────┘   │
 └──────────────────────────────────────────────────┘

Khái niệm then chốt của UML statechart:

  • Entry/exit action: chuyển từ CONNECTED (con của ON) sang OFF: chạy exit của CONNECTED, exit của ON, rồi entry của OFF. Tài nguyên được dọn đúng thứ tự.
  • Initial transition: vào ON thì tự động đi vào trạng thái con mặc định (BOOTING).
  • Run-to-completion (RTC): mỗi sự kiện được xử lý xong hoàn toàn (kể cả mọi transition và action) trước khi sự kiện tiếp theo được xử lý. Không có sự kiện nào xen vào giữa. Đây là tính chất giúp state machine không có race bên trong.
  • History state: quay lại trạng thái con lần cuối khi vào lại trạng thái cha.

Cài đặt HSM thủ công khá phức tạp (tính đường đi exit/entry giữa hai trạng thái lồng nhau). Thường dùng framework: QP/C, QP/C++ (Quantum Leaps, có công cụ vẽ QM sinh code), Boost.SML / Boost.MSM (C++), SMC, hoặc các công cụ sinh code từ sơ đồ UML.

Phỏng vấn thường yêu cầu vẽ state machine cho một trong các bài toán này.

Bài 4 · Event-driven architecture và active object

Từ state machine tới active object

State machine cần ai đó gửi sự kiện cho nó. Trong hệ thống event-driven, sự kiện đến từ nhiều nguồn: ISR (byte nhận được, nút bấm, ADC xong), timer (hết hạn), các module khác (lệnh từ giao thức). Nếu nhiều nguồn gọi dispatch() trực tiếp từ nhiều ngữ cảnh (ISR, task khác), state machine sẽ bị xử lý đồng thời, vi phạm run-to-completion.

Giải pháp: mỗi state machine có một hàng đợi sự kiện riêng và một luồng thực thi riêng. Ai muốn gửi sự kiện chỉ việc đẩy vào queue (an toàn từ ISR và task khác); luồng của state machine lấy từng sự kiện ra và dispatch, tuần tự. Mẫu này gọi là active object (hay actor).

   ISR UART ──┐
   Timer   ───┼──▶ [ event queue ] ──▶ [ thread của AO ] ──▶ state machine (dữ liệu riêng)
   AO khác ───┘        (thread-safe)        lấy từng event,        chỉ AO này chạm vào
                                            dispatch tới khi xong

Ba thành phần của active object:

  1. Dữ liệu riêng (private): chỉ AO đó truy cập, không chia sẻ với ai.
  2. Event queue: cách duy nhất để giao tiếp với AO.
  3. Luồng thực thi: một task RTOS (hoặc một vòng lặp trong cooperative scheduler) chạy vòng lấy-dispatch.

Kết quả: mỗi AO là một "hòn đảo" đơn luồng. Không có dữ liệu chia sẻ nên không cần mutex trong logic nghiệp vụ; các AO giao tiếp với nhau chỉ bằng sự kiện (message passing, như CSP ở C++ Concurrency in Action, Chương 4).

Cài đặt với FreeRTOS

typedef struct { uint16_t sig; uint16_t len; uint8_t payload[28]; } event_t;   /* kích thước cố định */

typedef struct active active_t;
typedef void (*dispatch_fn)(active_t *me, const event_t *e);
struct active {
    QueueHandle_t queue;
    TaskHandle_t  task;
    dispatch_fn   dispatch;
};

static void active_loop(void *arg) {
    active_t *me = arg;
    event_t e;
    for (;;) {
        xQueueReceive(me->queue, &e, portMAX_DELAY);      /* điểm chặn DUY NHẤT */
        me->dispatch(me, &e);                             /* run-to-completion, không chặn */
    }
}

void active_start(active_t *me, const char *name, UBaseType_t prio, size_t qlen, uint16_t stack) {
    me->queue = xQueueCreate(qlen, sizeof(event_t));
    xTaskCreate(active_loop, name, stack, me, prio, &me->task);
}

bool active_post(active_t *me, const event_t *e) {                  /* từ task khác */
    return xQueueSend(me->queue, e, 0) == pdPASS;
}
bool active_post_from_isr(active_t *me, const event_t *e, BaseType_t *woken) {   /* từ ISR */
    return xQueueSendFromISR(me->queue, e, woken) == pdPASS;
}

Quy tắc quan trọng: trong dispatch, không bao giờ chặn (không vTaskDelay, không chờ semaphore). Muốn "chờ 100 ms" thì khởi động một timer, khi hết hạn timer gửi sự kiện TIMEOUT vào queue của chính AO. Điểm chặn duy nhất là xQueueReceive ở đầu vòng lặp.

Kiểu sự kiện

  • Kích thước cố định, copy vào queue (như trên): đơn giản, an toàn, nhưng copy tốn thời gian với payload lớn và giới hạn kích thước.
  • Con trỏ tới sự kiện cấp phát từ pool (Module 6, Bài 4): queue chỉ chứa con trỏ; sự kiện được trả về pool khi xử lý xong (QP dùng cơ chế này, kèm đếm tham chiếu để một sự kiện được gửi cho nhiều AO).

Publish-subscribe

Thay vì AO gửi trực tiếp cho AO khác (phải biết nó), AO publish sự kiện lên một "bảng tin" theo loại sự kiện; các AO quan tâm subscribe loại đó. Bên phát không biết bên nhận là ai: coupling thấp hơn nữa.

#define MAX_SIG 32
static uint32_t g_subscribers[MAX_SIG];                  /* bitmap: bit i = AO thứ i đăng ký */
static active_t *g_aos[32];

void subscribe(uint8_t ao_id, uint16_t sig) { g_subscribers[sig] |= 1u << ao_id; }

void publish(const event_t *e) {
    uint32_t mask = g_subscribers[e->sig];
    while (mask) {
        uint8_t id = (uint8_t)__builtin_ctz(mask);       /* duyệt từng bit 1 */
        active_post(g_aos[id], e);
        mask &= mask - 1u;
    }
}

Ví dụ: AO cảm biến publish TEMP_UPDATED; AO điều khiển quạt, AO ghi log, AO hiển thị đều subscribe. Thêm một AO mới (gửi dữ liệu lên cloud) không cần sửa AO cảm biến.

Ưu nhược điểm

Ưu điểm: không có race trong logic nghiệp vụ; mỗi AO test độc lập được (đưa sự kiện vào, kiểm tra sự kiện ra); kiến trúc rõ ràng, dễ trace (log mọi sự kiện là thấy toàn bộ luồng hoạt động); dùng ít task hơn kiểu "mỗi việc một task".

Nhược điểm: phải tư duy theo sự kiện (không viết tuần tự kiểu "gửi lệnh, chờ trả lời"); queue có thể đầy (phải chọn kích thước và xử lý lỗi post); độ trễ do xếp hàng.

Góc EmbeddedFramework thực tế
  • QP/C, QP/C++ (Quantum Leaps): framework active object + HSM hoàn chỉnh, có kernel riêng (QV cooperative, QK preemptive) hoặc chạy trên FreeRTOS/Zephyr; dùng trong thiết bị y tế, hàng không.
  • Zephyr: k_work, k_msgq, và State Machine Framework (SMF) hỗ trợ HSM.
  • ESP-IDF: esp_event (event loop + publish-subscribe).
  • Linux userspace: event loop (epoll, libuv, Boost.Asio, sd-event) theo cùng tư tưởng.
Ý chínhÝ chính của Bài 4
  • Active object = dữ liệu riêng + event queue + một luồng; giao tiếp chỉ bằng sự kiện.
  • Vòng lặp: chặn duy nhất ở lấy sự kiện; dispatch run-to-completion, không chặn; "chờ" bằng timer gửi sự kiện.
  • Sự kiện copy cố định hoặc con trỏ từ pool. Publish-subscribe giảm coupling.
  • Không cần mutex trong logic, dễ test, dễ trace; phải chọn kích thước queue và xử lý post thất bại.
Tự kiểm traVì sao không được gọi `vTaskDelay()` bên trong hàm dispatch của active object?

Nó chặn luồng của AO: mọi sự kiện khác trong queue phải chờ, AO không phản ứng được, và queue có thể tràn. Muốn chờ thì đặt timer và xử lý sự kiện timeout.

Tự kiểm traHai active object cần dùng chung dữ liệu cấu hình. Làm thế nào theo tinh thần active object?

Một AO sở hữu dữ liệu; AO khác yêu cầu bằng sự kiện và nhận bản copy qua sự kiện trả lời, hoặc AO sở hữu publish sự kiện CONFIG_CHANGED kèm dữ liệu mới. (Dữ liệu chỉ đọc, bất biến sau khởi động thì có thể chia sẻ trực tiếp.)

Bài 5 · Observer, callback, producer-consumer và command

Callback: lớp dưới báo lên lớp trên

Bài 1 nói lớp dưới không được gọi trực tiếp lớp trên. Nhưng driver UART cần báo "đã nhận một dòng", driver nút cần báo "nút được nhấn". Giải pháp: lớp trên đăng ký một hàm (callback) với lớp dưới; lớp dưới gọi hàm đó khi có sự kiện. Lớp dưới chỉ biết chữ ký của hàm, không biết ai đăng ký.

typedef void (*uart_rx_cb_t)(void *ctx, const uint8_t *line, size_t len);

typedef struct {
    uart_rx_cb_t cb;
    void        *ctx;                                    /* ngữ cảnh trả lại cho người đăng ký */
} uart_listener_t;

static uart_listener_t g_listener;
void uart_set_rx_callback(uart_rx_cb_t cb, void *ctx) { g_listener.cb = cb; g_listener.ctx = ctx; }

/* trong driver, khi có một dòng hoàn chỉnh: */
if (g_listener.cb) g_listener.cb(g_listener.ctx, line, len);

Tham số void *ctx là chi tiết bắt buộc của callback C tốt: nó cho phép đăng ký cùng một hàm cho nhiều object khác nhau (ví dụ hai instance của một parser), và tránh biến toàn cục. Trong C++, dùng lambda (lambda không capture chuyển được sang con trỏ hàm C), std::function (nếu chấp nhận khả năng cấp phát), hoặc etl::delegate.

Cẩn thậnCallback được gọi trong ngữ cảnh nào?

Đây là câu hỏi số một khi dùng callback trong firmware. Nếu driver gọi callback từ ISR, thì callback chạy trong ISR: phải ngắn, không chặn, không dùng API không an toàn với ISR (không printf, không xQueueSend mà phải dùng ...FromISR). Luôn ghi rõ trong tài liệu API: "callback được gọi từ ngữ cảnh ngắt". Cách an toàn hơn: driver chỉ đẩy sự kiện vào queue, để task xử lý (Bài 4, Bài 8).

Observer: nhiều người nghe

Observer mở rộng callback cho nhiều người đăng ký: subject giữ một danh sách observer và thông báo cho tất cả khi trạng thái đổi. Trong firmware không heap, danh sách là mảng cố định hoặc intrusive list (observer tự chứa node link, Module 6 Bài 3):

typedef struct observer {
    void (*notify)(struct observer *self, int32_t value);
    struct observer *next;                               /* intrusive: không cấp phát */
} observer_t;

typedef struct { observer_t *head; int32_t value; } subject_t;

void subject_attach(subject_t *s, observer_t *o) { o->next = s->head; s->head = o; }

void subject_set(subject_t *s, int32_t v) {
    s->value = v;
    for (observer_t *o = s->head; o; o = o->next) o->notify(o, v);
}

/* Một observer cụ thể nhúng observer_t và dùng container_of để lấy lại object */
typedef struct { observer_t base; int32_t threshold; bool alarm; } alarm_obs_t;
static void alarm_notify(observer_t *self, int32_t v) {
    alarm_obs_t *a = container_of(self, alarm_obs_t, base);
    a->alarm = v > a->threshold;
}

Cẩn thận: observer bị hủy mà quên detach thì subject gọi vào vùng nhớ chết (trong C++, cân nhắc weak_ptr như Effective Modern C++ Item 20, hoặc RAII để tự detach trong destructor). Observer gọi lại subject trong notify (sửa danh sách khi đang duyệt) cũng là nguồn bug.

Publish-subscribe (Bài 4) là phiên bản bất đồng bộ và tách rời hơn của observer: bên phát không giữ danh sách, thông báo đi qua queue.

Producer-consumer

Một bên sinh dữ liệu, một bên tiêu thụ, tốc độ có thể khác nhau tạm thời. Đặt một buffer ở giữa để hấp thụ chênh lệch: ring buffer (Module 6), queue của RTOS, hoặc double buffer.

Double buffering (ping-pong). Hai buffer: trong khi producer (thường là DMA) ghi vào buffer A, consumer xử lý buffer B; xong thì đổi vai. Dùng cho thu mẫu ADC/audio liên tục, cập nhật màn hình không nhấp nháy (vẽ vào buffer ẩn rồi đổi).

 thời gian →
 DMA ghi:     [ A ][ B ][ A ][ B ]
 CPU xử lý:        [ A ][ B ][ A ]
                ↑ ngắt half/full transfer báo buffer nào vừa đầy

Điều kiện đúng: consumer phải xử lý xong một buffer trước khi producer quay lại ghi vào nó, tức thời gian xử lý < thời gian lấp đầy một buffer. Nên kiểm tra và đếm lỗi overrun.

Command pattern

Đóng gói một yêu cầu thành một object (dữ liệu): loại lệnh + tham số. Lệnh có thể được xếp hàng, ghi log, gửi qua mạng, thực hiện sau, hoặc hoàn tác. Trong firmware:

  • Hàng đợi lệnh cho một task sở hữu tài nguyên (task flash nhận lệnh WRITE/ERASE từ nhiều nơi).
  • Lệnh từ giao thức (Modbus, CLI) được phân tích thành struct lệnh rồi mới thực thi.
  • Ghi lại macro, kịch bản test.
typedef enum { CMD_LED, CMD_MOTOR_SPEED, CMD_RESET_STATS } cmd_type_t;
typedef struct {
    cmd_type_t type;
    union { struct { uint8_t id; bool on; } led; struct { int16_t rpm; } motor; } arg;
} command_t;

void execute(const command_t *c) {
    switch (c->type) {
    case CMD_LED:         led_set(c->arg.led.id, c->arg.led.on); break;
    case CMD_MOTOR_SPEED: motor_set_rpm(c->arg.motor.rpm); break;
    case CMD_RESET_STATS: stats_reset(); break;
    }
}

Tagged union (enum + union) là cách tự nhiên trong C; C++17 dùng std::variant.

Ý chínhÝ chính của Bài 5
  • Callback (con trỏ hàm + void *ctx) cho lớp dưới báo lên; luôn ghi rõ ngữ cảnh gọi (ISR hay task).
  • Observer: nhiều người nghe, danh sách intrusive; cẩn thận observer bị hủy và sửa danh sách khi đang notify.
  • Producer-consumer: buffer ở giữa; double buffering cho DMA, điều kiện xử lý nhanh hơn lấp đầy.
  • Command: yêu cầu thành dữ liệu (tagged union / variant), xếp hàng được, ghi log được.
Tự kiểm traVì sao callback C nên có tham số `void *ctx`?

Để cùng một hàm phục vụ được nhiều instance (truyền con trỏ object qua ctx), tránh phải dùng biến toàn cục để biết callback thuộc object nào.

Tự kiểm traDriver gọi callback từ ISR, người dùng gọi `printf` trong callback. Vấn đề?

printf chậm, có thể dùng khóa hoặc cấp phát, không an toàn trong ISR; làm ISR dài, trễ các ngắt khác, có thể deadlock. Callback từ ISR phải ngắn; xử lý nặng chuyển sang task.

Bài 6 · Các mẫu hướng đối tượng áp dụng cho Embedded

Các mẫu kinh điển của "Gang of Four" vẫn có ích trong firmware, nhưng cần điều chỉnh cho môi trường không heap, ít bộ nhớ, và thường viết bằng C.

Singleton: tiện nhưng nguy hiểm

Singleton đảm bảo một class chỉ có một instance và cung cấp điểm truy cập toàn cục. Trong firmware nó xuất hiện tự nhiên: chỉ có một UART1, một bộ điều khiển nguồn, một logger.

class Logger {
public:
    static Logger& instance() {
        static Logger inst;              // C++11: khởi tạo thread-safe ở lần gọi đầu (magic statics)
        return inst;
    }
    void log(const char* msg);
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
private:
    Logger() = default;
};

Vấn đề:

  • Phụ thuộc ẩn: hàm nào cũng có thể gọi Logger::instance(), nhìn vào chữ ký hàm không biết nó phụ thuộc gì. Đây chính là biến toàn cục khoác áo đẹp.
  • Khó test: không thay được bằng bản giả; trạng thái tồn tại xuyên suốt các test.
  • Thứ tự khởi tạo: singleton dùng singleton khác trong constructor có thể gặp vòng phụ thuộc. Trên MCU, magic statics cần hỗ trợ khóa (__cxa_guard_acquire), thường bị tắt bằng -fno-threadsafe-statics.

Cách tốt hơn: tạo các object duy nhất một lần ở main (hoặc một hàm "composition root"), rồi truyền tham chiếu vào những ai cần (dependency injection, Bài 7). Vẫn chỉ có một instance, nhưng phụ thuộc hiện rõ và thay được khi test.

Factory

Factory tạo object mà người gọi không cần biết kiểu cụ thể. Trong firmware, thường gặp khi phát hiện phần cứng lúc chạy: đọc ID cảm biến hoặc biến thể board từ EEPROM/GPIO strap, rồi tạo driver tương ứng. Không có heap thì factory trả về object tĩnh đã cấp sẵn hoặc lấy từ pool:

static tmp117_t g_tmp117;
static sht31_t  g_sht31;

temp_sensor_t *temp_sensor_create(i2c_bus_t *bus) {
    if (probe_i2c(bus, 0x48)) { tmp117_init(&g_tmp117, bus); return &g_tmp117.iface; }
    if (probe_i2c(bus, 0x44)) { sht31_init(&g_sht31, bus);  return &g_sht31.iface;  }
    return NULL;                                         /* không phát hiện cảm biến nào */
}

Trong C++, factory trả về std::unique_ptr (Effective Modern C++, Item 18) nếu có heap, hoặc tham chiếu tới object tĩnh, hoặc std::variant các driver.

Adapter và Facade

Adapter chuyển interface của một thành phần sang interface mà code của bạn mong đợi. Ví dụ: thư viện bên thứ ba (một driver cảm biến của hãng) yêu cầu hai hàm platform_read(reg, buf, len) và platform_write(...); ta viết adapter nối chúng vào interface i2c_bus_t của mình. Adapter là cách chuẩn để tích hợp code bên ngoài mà không để nó lan khắp codebase.

Facade cung cấp một interface đơn giản cho một hệ thống con phức tạp. Ví dụ: module "power manager" với power_enter_sleep() che đi hàng chục bước (tắt ngoại vi, chuyển clock, cấu hình nguồn đánh thức, lưu ngữ cảnh). Ứng dụng chỉ gọi một hàm.

Strategy và policy-based design

Strategy: đóng gói một thuật toán thay đổi được sau một interface. Ví dụ: bộ lọc có thể là EMA, median hay Kalman tùy cảm biến; thuật toán điều khiển PID hay bang-bang. Trong C là con trỏ hàm (hoặc struct interface); trong C++ là virtual hoặc template.

Policy-based design (C++): strategy được chọn lúc compile qua tham số template, nên không có chi phí gọi gián tiếp. Mỗi "policy" là một class nhỏ cung cấp một khía cạnh hành vi:

struct NoLock      { void lock() {} void unlock() {} };            // dùng trong một luồng
struct IrqLock     { uint32_t s; void lock() { s = irq_save(); } void unlock() { irq_restore(s); } };

struct DropNewest  { template<class Q, class T> static bool on_full(Q&, const T&) { return false; } };
struct Overwrite   { template<class Q, class T> static bool on_full(Q& q, const T& v) { q.drop_oldest(); return q.push_unchecked(v); } };

template<typename T, std::size_t N, typename LockPolicy = NoLock, typename FullPolicy = DropNewest>
class Fifo {
public:
    bool push(const T& v) {
        lock_.lock();
        const bool ok = full() ? FullPolicy::on_full(*this, v) : push_unchecked(v);
        lock_.unlock();
        return ok;
    }
    // ...
private:
    LockPolicy lock_;
};

Fifo<Sample, 64, IrqLock, Overwrite> adc_fifo;     // chia sẻ với ISR, giữ mẫu mới nhất
Fifo<Cmd, 16> cmd_fifo;                            // một luồng, từ chối khi đầy

Cùng một code Fifo sinh ra các biến thể tối ưu cho từng ngữ cảnh. Thư viện ETL và nhiều HAL C++ (như modm, Kvasir) dựa trên kỹ thuật này.

CRTP: static polymorphism

CRTP (Curiously Recurring Template Pattern): class cơ sở là template nhận chính class con làm tham số. Class cơ sở gọi hàm của class con qua static_cast<Derived*>(this), không cần virtual:

template<typename Derived>
class SensorBase {
public:
    int32_t read_filtered() {                                    // thuật toán chung
        const int32_t raw = static_cast<Derived*>(this)->read_raw();   // "virtual" lúc compile
        acc_ += raw - (acc_ >> 3);                                      // EMA α = 1/8 (Module 7)
        return acc_ >> 3;
    }
private:
    int32_t acc_ = 0;                                                   // trạng thái có 3 bit thập phân
};

class Ntc : public SensorBase<Ntc> {
public:
    int32_t read_raw() { return adc_read(ADC_CH_NTC); }
};

Ntc ntc;
int32_t t = ntc.read_filtered();     // gọi trực tiếp, inline được, không vtable

Dùng khi muốn chia sẻ code chung (template method) mà không trả chi phí virtual và không cần chọn kiểu lúc chạy. std::enable_shared_from_this cũng là CRTP.

Proxy: truy cập thanh ghi an toàn kiểu

Proxy đứng thay cho một object khác. Trong firmware C++, các thư viện thanh ghi kiểu mới dùng proxy để truy cập thanh ghi an toàn kiểu: không thể ghi giá trị sai vào trường, không thể ghi vào thanh ghi chỉ đọc (lỗi compile). Ví dụ đơn giản:

template<uintptr_t Addr, unsigned Pos, unsigned Width>
struct Field {
    static constexpr uint32_t mask = ((1u << Width) - 1u) << Pos;
    static void write(uint32_t v) {
        auto& r = *reinterpret_cast<volatile uint32_t*>(Addr);
        r = (r & ~mask) | ((v << Pos) & mask);
    }
    static uint32_t read() { return (*reinterpret_cast<volatile uint32_t*>(Addr) & mask) >> Pos; }
};
using Gpioa_Moder5 = Field<0x40020000, 10, 2>;
Gpioa_Moder5::write(1);              // PA5 output: compiler sinh 3–4 lệnh, như viết tay

RAII guard

RAII (Effective Modern C++, Chương 4) là mẫu quan trọng nhất của C++ cho firmware: tài nguyên gắn với vòng đời object, được trả trên mọi đường thoát. Ví dụ critical section, chip select SPI, khóa mutex, bật/tắt nguồn ngoại vi:

class CriticalSection {
public:
    CriticalSection() : primask_(__get_PRIMASK()) { __disable_irq(); }
    ~CriticalSection() { __set_PRIMASK(primask_); }
    CriticalSection(const CriticalSection&) = delete;
    CriticalSection& operator=(const CriticalSection&) = delete;
private:
    uint32_t primask_;
};

class SpiSelect {                                  // CS kéo thấp trong suốt phạm vi
public:
    explicit SpiSelect(Gpio& cs) : cs_(cs) { cs_.low(); }
    ~SpiSelect() { cs_.high(); }
private:
    Gpio& cs_;
};

int flash_read_id(Spi& spi, Gpio& cs) {
    SpiSelect sel(cs);
    spi.transfer(0x9F);
    if (!spi.ok()) return -1;                      // return sớm: CS vẫn được kéo lên
    return spi.read24();
}

Trong C không có destructor, nên dùng quy ước "một điểm thoát" (goto cleanup) hoặc macro dạng for một vòng để mô phỏng phạm vi.

Ý chínhÝ chính của Bài 6
  • Singleton tiện nhưng là biến toàn cục ẩn; ưu tiên tạo một lần ở main và truyền tham chiếu.
  • Factory trả object tĩnh/pool khi phát hiện phần cứng lúc chạy.
  • Adapter tích hợp code bên ngoài; Facade đơn giản hóa hệ thống con.
  • Strategy (lúc chạy) và policy-based design (lúc compile, zero-cost); CRTP cho static polymorphism.
  • Proxy cho truy cập thanh ghi an toàn kiểu; RAII guard cho critical section, chip select, khóa.
Tự kiểm traVì sao singleton làm firmware khó unit test?

Code gọi X::instance() trực tiếp nên không thay được bằng bản giả; trạng thái của singleton tồn tại qua các test và phụ thuộc thứ tự chạy test.

Tự kiểm traCRTP khác virtual ở điểm nào?

CRTP giải quyết lời gọi lúc compile (không vptr, không vtable, inline được) nhưng không chọn được kiểu lúc chạy và không có con trỏ class cơ sở chung cho mọi class con.

Bài 7 · Dependency injection và test trên máy tính

Vì sao test firmware trên PC

Test trên board thật chậm (nạp firmware, chạy, quan sát), khó tự động, khó tạo các tình huống lỗi (cảm biến hỏng, bus lỗi, timeout). Nếu phần lớn code (logic, giao thức, state machine, thuật toán) chạy được trên PC với unit test, ta có thể chạy hàng nghìn test trong vài giây, trong CI, với AddressSanitizer/UBSan/ThreadSanitizer.

Điều kiện: code cần test phải tách khỏi phần cứng qua các điểm có thể thay thế. James Grenning gọi chúng là seam (đường nối): chỗ có thể thay hành vi mà không sửa code đang test. Dependency injection (DI) là cách tạo seam: module nhận những thứ nó phụ thuộc từ bên ngoài, thay vì tự tạo hay tự gọi toàn cục.

Các loại seam trong C/C++

1. Link-time seam (thay lúc link). Header khai báo hàm uint32_t hal_adc_read(int ch);. Bản firmware link với hal_adc_stm32.c; bản test link với hal_adc_fake.c có cùng chữ ký. Không sửa code nào, chỉ đổi file trong build. Đơn giản nhất, không tốn chi phí lúc chạy, nhưng chỉ một cài đặt cho mỗi bản build.

2. Function pointer seam. Module gọi qua con trỏ hàm (hoặc struct interface) mà test có thể đổi:

/* heater.h */
typedef struct {
    int32_t (*read_temp_centi)(void *ctx);
    void    (*set_heater)(void *ctx, bool on);
    void     *ctx;
} heater_io_t;

typedef struct { heater_io_t io; int32_t setpoint; bool on; } heater_ctrl_t;

void heater_step(heater_ctrl_t *h) {                       /* logic thuần, không chạm phần cứng */
    int32_t t = h->io.read_temp_centi(h->io.ctx);
    if (!h->on && t < h->setpoint - 50) h->on = true;      /* hysteresis ±0,5 °C */
    else if (h->on && t > h->setpoint + 50) h->on = false;
    h->io.set_heater(h->io.ctx, h->on);
}

Bài 8 · Các mẫu xử lý đồng thời trong firmware

Module 5 và C++ Concurrency in Action trình bày nền tảng. Bài này gom lại những mẫu cụ thể được dùng nhiều nhất trong firmware.

Critical section

Tắt ngắt (hoặc khóa scheduler) trong một đoạn rất ngắn để thao tác trên dữ liệu chung không bị chen ngang. Quy tắc:

  • Ngắn nhất có thể: vài chục lệnh. Thời gian critical section cộng vào độ trễ ngắt của mọi ngắt.
  • Lưu và khôi phục trạng thái ngắt (PRIMASK), không bật ngắt vô điều kiện, để lồng nhau an toàn.
  • Trên Cortex-M3+, có thể chỉ chặn các ngắt có priority thấp hơn một ngưỡng bằng BASEPRI, để ngắt rất khẩn cấp (ví dụ bảo vệ quá dòng) vẫn chạy được. FreeRTOS dùng BASEPRI với configMAX_SYSCALL_INTERRUPT_PRIORITY: ngắt có priority cao hơn ngưỡng này không bị critical section của kernel chặn, nhưng cũng không được gọi API FreeRTOS.
  • Không dùng critical section cho thao tác dài (copy buffer lớn, ghi flash); dùng mutex hoặc task sở hữu tài nguyên.

Guarded resource: mutex hoặc gatekeeper task

Tài nguyên dùng chung giữa các task (bus I2C, UART debug, flash ngoài) cần được truy cập tuần tự. Hai mẫu:

Mutex: mỗi task khóa trước khi dùng. Đơn giản, nhưng có rủi ro priority inversion (dùng mutex có priority inheritance), deadlock (thứ tự khóa), và mọi task phải tự giữ kỷ luật.

Gatekeeper task: chỉ một task được phép truy cập tài nguyên; task khác gửi yêu cầu cho nó qua queue (command pattern, Bài 5), nhận kết quả qua queue trả lời hoặc task notification. Không cần mutex, không priority inversion (gatekeeper có priority cố định), dễ thêm hàng đợi ưu tiên. Đây là active object (Bài 4) áp dụng cho một tài nguyên. Ví dụ quen thuộc: một task duy nhất in log ra UART; các task khác chỉ đẩy chuỗi vào queue.

Deferred interrupt processing (top half / bottom half)

ISR phải ngắn. Phần việc nặng được hoãn sang ngữ cảnh task:

 Ngắt UART ──▶ [ISR: đọc byte → ring buffer → báo task] ──▶ [Task: phân tích gói, xử lý]
               top half: vài µs, không chặn              bottom half: có thể chặn, dài

Cơ chế báo task trên FreeRTOS: task notification (nhẹ nhất), semaphore, hoặc queue; nhớ dùng phiên bản ...FromISR và yêu cầu context switch ngay nếu task được đánh thức có priority cao hơn (portYIELD_FROM_ISR(woken)), để task xử lý chạy ngay khi ISR kết thúc thay vì chờ tick tiếp theo:

static TaskHandle_t g_rx_task;

void USART2_IRQHandler(void) {
    BaseType_t woken = pdFALSE;
    while (USART2->ISR & USART_ISR_RXNE) rb_put(&g_rx_rb, (uint8_t)USART2->RDR);
    vTaskNotifyGiveFromISR(g_rx_task, &woken);
    portYIELD_FROM_ISR(woken);               /* chuyển sang task ngay nếu nó ưu tiên cao hơn */
}

void rx_task(void *arg) {
    for (;;) {
        ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(100));   /* chờ thông báo, tối đa 100 ms */
        uint8_t b;
        while (rb_get(&g_rx_rb, &b)) parser_feed(&g_parser, b);
    }
}

Linux kernel có cùng tư tưởng: top half (interrupt handler) và bottom half (softirq, tasklet, workqueue, threaded IRQ). Threaded IRQ (request_threaded_irq) là cách hiện đại: handler chính chỉ xác nhận ngắt, phần xử lý chạy trong một kernel thread có thể ngủ.

Lock-free SPSC

Giữa một producer và một consumer (ISR và task, hai nhân), ring buffer lock-free (Module 6 Bài 1, Module 5) tránh hoàn toàn critical section. Là mẫu mặc định cho luồng dữ liệu ISR → task.

Double buffering và sequence lock

Double buffering (Bài 5) cho dữ liệu khối liên tục từ DMA.

Sequence lock (seqlock) cho dữ liệu nhiều word do một bên ghi thường xuyên, nhiều bên đọc (ví dụ ISR cập nhật một struct trạng thái gồm vị trí, vận tốc, thời gian; task đọc nó). Bên ghi tăng một bộ đếm trước và sau khi ghi (số lẻ = đang ghi); bên đọc đọc bộ đếm, copy dữ liệu, đọc lại bộ đếm, và đọc lại từ đầu nếu bộ đếm lẻ hoặc đã đổi:

typedef struct { volatile uint32_t seq; int32_t pos, vel; uint32_t ts; } motion_t;
static motion_t g_motion;

void motion_write(int32_t p, int32_t v, uint32_t t) {     /* chỉ ISR gọi */
    g_motion.seq++; __DMB();                               /* lẻ: đang ghi */
    g_motion.pos = p; g_motion.vel = v; g_motion.ts = t;
    __DMB(); g_motion.seq++;                               /* chẵn: ghi xong */
}

void motion_read(int32_t *p, int32_t *v, uint32_t *t) {   /* task gọi */
    uint32_t s1, s2;
    do {
        s1 = g_motion.seq; __DMB();
        *p = g_motion.pos; *v = g_motion.vel; *t = g_motion.ts;
        __DMB(); s2 = g_motion.seq;
    } while ((s1 & 1u) || s1 != s2);                        /* đang ghi hoặc bị ghi chen: đọc lại */
}

Bên ghi không bao giờ chặn; bên đọc có thể phải thử lại (nhưng ISR ngắn nên hiếm). Linux kernel dùng seqlock cho thời gian hệ thống (jiffies_64, timekeeping). Lưu ý: về lý thuyết chuẩn C/C++, việc đọc dữ liệu thường trong lúc bị ghi là data race; cài đặt nghiêm ngặt dùng các thao tác atomic relaxed cho từng trường.

Tự kiểm traVì sao cần `portYIELD_FROM_ISR(woken)` cuối ISR?

Nếu ISR đánh thức một task có priority cao hơn task đang chạy, yêu cầu context switch ngay khi ISR kết thúc; không có nó, task chỉ chạy ở lần scheduler tiếp theo (tick), làm tăng độ trễ.

Tự kiểm traGatekeeper task có ưu điểm gì so với mutex?

Chỉ một task chạm tài nguyên nên không cần mutex, không có priority inversion hay deadlock do thứ tự khóa, dễ áp đặt thứ tự/ưu tiên các yêu cầu; đổi lại có thêm độ trễ xếp hàng và một task.

Firmware dễ bảo trì nhờ: phân lớp và interface (port được, test được), chọn đúng mô hình thực thi, state machine thay cho đống cờ, active object + event để loại race khỏi logic nghiệp vụ, callback/observer/command để giảm coupling, các mẫu OOP được điều chỉnh (DI thay singleton, policy/CRTP thay virtual khi cần zero-cost, RAII guard), seam để test trên PC, và một bộ mẫu đồng thời phù hợp với từng loại dữ liệu chia sẻ.

Kiến trúc

01Mô tả kiến trúc phân lớp của firmware bạn từng làm.Hay hỏi

BSP (chân, clock, startup) → HAL (ngoại vi MCU) → device driver (linh kiện ngoài, chỉ dùng interface bus) → middleware (giao thức, logging, file system) → application. Lớp dưới không gọi lên trực tiếp, báo lên bằng callback/event. Nêu điểm port được: đổi MCU chỉ viết lại HAL/BSP; logic test được trên PC qua interface.

02Cài đặt interface trong C thế nào?Hay hỏi

Struct chứa con trỏ hàm và void *ctx (như struct file_operations của Linux). Driver nhận con trỏ tới struct interface; mỗi nền tảng (hoặc test) cung cấp một cài đặt. Kết hợp opaque handle (khai báo struct trong header, định nghĩa trong .c) để đóng gói.

03Virtual function trên MCU có tốn kém không? So với template?

Mỗi object thêm một vptr, mỗi class một vtable trong Flash, lời gọi gián tiếp vài chu kỳ và thường không inline được: chấp nhận được trong đa số trường hợp, không cần RTTI/exception. Template/CRTP không chi phí lúc chạy, inline được, nhưng code nằm trong header, sinh nhiều bản và không chọn kiểu lúc chạy được.

04Super-loop, cooperative scheduler hay RTOS: chọn thế nào?Hay hỏi

Super-loop + ngắt cho thiết bị đơn giản, mọi việc ngắn và non-blocking. Cooperative time-triggered khi cần tất định cao và dễ phân tích (an toàn), không race giữa task. RTOS khi có nhiều hoạt động độc lập với yêu cầu thời gian khác nhau, cần code chặn được, hoặc dùng stack mạng/USB; trả giá bằng stack mỗi task, race, deadlock, priority inversion.

State machine và event

05Vì sao dùng state machine thay vì các biến cờ?Hay hỏi

Cờ tạo ra số tổ hợp tăng theo cấp số mũ, nhiều tổ hợp vô nghĩa nhưng vẫn xảy ra. State machine có một biến trạng thái với tập giá trị rõ ràng, transition theo sự kiện, hành vi ở mỗi trạng thái được định nghĩa đầy đủ; dễ đọc, dễ test, dễ đối chiếu với sơ đồ.

06Các cách cài đặt state machine trong C?

Switch-case theo trạng thái rồi sự kiện (dễ đọc); bảng [state][event] → (next, action) (table-driven, Flash); con trỏ hàm trạng thái (mỗi trạng thái một hàm). C++: State pattern hoặc std::variant + std::visit. Với HSM dùng framework (QP, Boost.SML, Zephyr SMF).

07Hierarchical state machine giải quyết vấn đề gì?

Bùng nổ trạng thái và xử lý lặp lại: trạng thái con kế thừa xử lý sự kiện của trạng thái cha (ví dụ POWER_OFF xử lý một lần ở trạng thái cha ON). Có entry/exit action theo thứ tự lồng nhau, initial transition, history.

08Active object là gì? Ưu điểm?Hay hỏi

Dữ liệu riêng + event queue + một luồng thực thi; mọi giao tiếp qua sự kiện; dispatch run-to-completion, chỉ chặn khi chờ sự kiện. Không có dữ liệu chia sẻ nên không cần mutex trong logic, dễ test (sự kiện vào → sự kiện ra), dễ trace. Framework: QP; ESP-IDF esp_event; Zephyr.

09Trong active object, muốn "chờ 100 ms" thì làm sao?

Không delay trong dispatch. Khởi động một timer (one-shot); khi hết hạn timer gửi sự kiện TIMEOUT vào queue của chính AO; xử lý tiếp trong trạng thái tương ứng.

10Run-to-completion nghĩa là gì?

Mỗi sự kiện được xử lý xong hoàn toàn (mọi transition và action) trước khi xử lý sự kiện kế tiếp, không xen kẽ; state machine không bao giờ bị thấy ở trạng thái dở dang.

Mẫu thiết kế và test

11Callback trong firmware cần lưu ý gì?Hay hỏi

Có tham số void *ctx; ghi rõ ngữ cảnh gọi (ISR hay task) vì callback từ ISR phải ngắn, không chặn, chỉ dùng API FromISR; đảm bảo người đăng ký còn sống khi được gọi; tránh để callback gọi ngược làm thay đổi cấu trúc đang duyệt.

12Singleton có vấn đề gì? Thay bằng gì?

Phụ thuộc ẩn (gọi instance() ở bất kỳ đâu), khó thay bằng bản giả khi test, trạng thái tồn tại xuyên test, thứ tự khởi tạo. Thay bằng tạo object một lần ở composition root (main) và truyền tham chiếu (dependency injection).

13Policy-based design là gì? Ví dụ trong firmware.

Chọn các khía cạnh hành vi qua tham số template, không chi phí lúc chạy. Ví dụ FIFO có LockPolicy (NoLock / IrqLock) và FullPolicy (DropNewest / Overwrite): một code, nhiều biến thể tối ưu cho từng ngữ cảnh.

14RAII dùng thế nào trong firmware C++?

Object cục bộ lấy tài nguyên trong constructor, trả trong destructor, đảm bảo trả trên mọi đường thoát: critical section (lưu/khôi phục PRIMASK), chip select SPI, khóa mutex, bật nguồn ngoại vi, buffer từ pool (unique_ptr + deleter).

15Làm sao unit test firmware trên PC?Hay hỏi

Tách logic khỏi phần cứng qua seam: link-time (đổi file .c khi build test), struct con trỏ hàm / virtual interface, template. Dùng test double (stub, fake, spy, mock) cho HAL; coi thời gian là phụ thuộc; chỉ composition root biết cài đặt cụ thể. Framework: Unity/CMock/Ceedling, CppUTest, FFF, GoogleTest. Chạy kèm ASan/UBSan.

17Top half / bottom half (deferred interrupt) là gì?Hay hỏi

ISR (top half) chỉ làm phần tối thiểu: đọc phần cứng, đẩy dữ liệu vào buffer, xóa cờ, báo task. Phần xử lý nặng (bottom half) chạy trong task (FreeRTOS: task notification + portYIELD_FROM_ISR) hoặc trong Linux là softirq/tasklet/workqueue/threaded IRQ.

18Gatekeeper task là gì?

Task duy nhất được truy cập một tài nguyên (UART log, bus I2C, flash); task khác gửi yêu cầu qua queue và nhận kết quả. Không cần mutex, không priority inversion, dễ kiểm soát thứ tự.

19BASEPRI khác PRIMASK thế nào?

PRIMASK chặn mọi ngắt có priority cấu hình được. BASEPRI (Cortex-M3+) chỉ chặn ngắt có priority thấp hơn (giá trị số lớn hơn hoặc bằng) ngưỡng, để ngắt khẩn cấp vẫn chạy. FreeRTOS dùng BASEPRI cho critical section; ngắt trên ngưỡng không được gọi API FreeRTOS.

20Chia sẻ một struct nhiều word giữa ISR (ghi) và task (đọc) thế nào?

Critical section khi task đọc (ngắn); hoặc seqlock (ISR tăng bộ đếm trước/sau khi ghi, task đọc lại nếu bộ đếm lẻ hoặc thay đổi); hoặc double buffer + chỉ số buffer hợp lệ cập nhật atomic.
