Ba việc của một hệ điều hành

Không có hệ điều hành, mỗi chương trình phải tự điều khiển phần cứng: tự đọc thanh ghi card mạng, tự quản lý RAM, và chỉ một chương trình chạy được tại một thời điểm. Hệ điều hành (operating system, OS) là lớp phần mềm nằm giữa ứng dụng và phần cứng, làm ba việc lớn (cách chia của giáo trình OSTEP):

Việc Ý nghĩa Ví dụ cụ thể
Ảo hóa (virtualization) Biến một tài nguyên vật lý thành nhiều tài nguyên "ảo", mỗi chương trình tưởng mình độc chiếm Một CPU → nhiều process chạy "cùng lúc"; một RAM → mỗi process một không gian địa chỉ riêng
Đồng thời (concurrency) Cho nhiều luồng việc chạy xen kẽ hoặc song song mà không phá nhau Thread, khóa, hàng đợi, xử lý ngắt
Bền vững (persistence) Giữ dữ liệu qua lần tắt máy, mất điện File system, journaling, fsync

Thêm hai việc phụ nhưng quan trọng: bảo vệ (chương trình này không phá chương trình khác hay kernel) và trừu tượng hóa (cung cấp API thống nhất: một file trên ổ SSD, trên USB hay trên mạng đều được đọc bằng read()).

Kernel, user space và system call

Phần cốt lõi của OS là kernel (nhân). Kernel chạy ở chế độ đặc quyền của CPU (F01 Bài 1: ring 0, EL1), được làm mọi thứ. Ứng dụng chạy ở user space (ring 3, EL0): không được chạm phần cứng trực tiếp, không được đọc bộ nhớ của process khác.

Khi ứng dụng cần kernel làm gì đó (mở file, gửi gói, cấp bộ nhớ, tạo thread), nó gọi system call (lời gọi hệ thống). Trong C/C++ bạn gọi hàm thư viện như read(), write(), socket(); hàm đó (trong glibc) đặt số hiệu system call vào thanh ghi rồi chạy lệnh syscall:

  ứng dụng           glibc                        kernel
  read(fd,buf,n) ──► đặt rax=0 (SYS_read),  ──► entry_SYSCALL_64
                     rdi=fd, rsi=buf, rdx=n      → sys_read() → VFS → driver
                     lệnh `syscall`         ◄──  trả kết quả trong rax
                     nếu rax < 0: errno = -rax, trả -1

Linux có khoảng 450 system call. Các nhóm chính: process (fork, execve, exit, wait4, clone), file (open, read, write, close, lseek, fsync), bộ nhớ (mmap, munmap, brk, mprotect), mạng (socket, bind, connect, sendmsg, recvmsg), sự kiện (epoll_wait, poll), thời gian (clock_nanosleep), tín hiệu (kill, rt_sigaction).

Lệnh strace cho bạn xem mọi system call của một chương trình, công cụ gỡ lỗi quan trọng nhất trên Linux:

$ strace -f -e trace=network,read,write ./client
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP) = 3
connect(3, {sa_family=AF_INET, sin_port=htons(8080), sin_addr=inet_addr("10.0.0.5")}, 16) = 0
write(3, "GET / HTTP/1.1\r\n...", 78) = 78
read(3, "HTTP/1.1 200 OK\r\n...", 4096) = 512

System call tốn bao nhiêu

Chương trình sau so sánh một lời gọi hàm thường với system call rẻ nhất có thể (getppid, chỉ đọc một trường trong kernel):

// So sánh chi phí: gọi một hàm bình thường và gọi một system call rẻ nhất có thể.
#include <chrono>
#include <cstdio>
#include <sys/syscall.h>
#include <unistd.h>

__attribute__((noinline)) long plain_function(long x) { return x + 1; }

int main() {
    const int N = 2'000'000;
    long sink = 0;
    auto t0 = std::chrono::steady_clock::now();
    for (int i = 0; i < N; ++i) sink += plain_function(i);
    auto t1 = std::chrono::steady_clock::now();
    for (int i = 0; i < N; ++i) sink += syscall(SYS_getppid);   // luôn vào kernel, không cache ở libc
    auto t2 = std::chrono::steady_clock::now();
    auto ns = [&](auto a, auto b) { return std::chrono::duration<double, std::nano>(b - a).count() / N; };
    std::printf("goi ham thuong : %6.1f ns/lan\n", ns(t0, t1));
    std::printf("system call    : %6.1f ns/lan   (sink=%ld)\n", ns(t1, t2), sink % 7);
}

goi ham thuong :    1.2 ns/lan
system call    :  107.0 ns/lan       ← gần 100 lần

107 ns là cho system call không làm gì. read() từ socket, sendmsg() qua stack TCP/IP thực tế tốn từ vài trăm ns tới vài µs. Đây là con số then chốt cho mọi thiết kế networking: nếu mỗi gói tốn một system call, một nhân chỉ xử lý được vài trăm nghìn tới một hai triệu gói mỗi giây.

Một số "system call" rất nhanh vì không thật sự vào kernel: clock_gettime() và gettimeofday() dùng vDSO, một trang code kernel ánh xạ sẵn vào mọi process, đọc đồng hồ ngay trong user space (khoảng 20 ns).

Khởi động một hệ thống Linux

Tóm tắt quá trình từ lúc bật nguồn (chi tiết cho nhúng ở M15 và B08):

  1. Firmware (BIOS/UEFI trên PC; ROM code của SoC trên thiết bị nhúng) khởi tạo phần cứng tối thiểu, nạp bootloader.
  2. Bootloader (GRUB, systemd-boot; U-Boot trên nhúng) nạp kernel và initramfs vào RAM, truyền tham số dòng lệnh kernel (và device tree trên ARM).
  3. Kernel khởi tạo CPU, bộ nhớ, driver, mount root file system, chạy process đầu tiên PID 1.
  4. init (thường là systemd) khởi động các service theo phụ thuộc.

Tham số dòng lệnh kernel (/proc/cmdline) là nơi cấu hình nhiều thứ quan trọng cho hệ thống hiệu năng cao: isolcpus=, nohz_full=, hugepages=, intel_iommu=on (Bài 3, Bài 9).

Liên hệ EmbeddedBare metal, RTOS và Embedded Linux: ba mức "có hệ điều hành"
  • Bare metal / super-loop: không OS. main() là vòng lặp vô hạn, sự kiện đến từ ngắt. Bạn tự làm mọi việc của bài này: tự chia thời gian, tự đồng bộ giữa ISR và vòng lặp.
  • RTOS (FreeRTOS, Zephyr, ThreadX, RTX): kernel nhỏ cung cấp task, scheduler ưu tiên, queue, semaphore, mutex, timer. Thường không có user/kernel tách biệt, không có bộ nhớ ảo (MPU tùy chọn), không có file system mặc định. "System call" chỉ là gọi hàm (FreeRTOS-MPU dùng lệnh svc để chuyển đặc quyền).
  • Embedded Linux: đầy đủ mọi khái niệm của bài này, trên SoC Cortex-A. Khác server ở chỗ tài nguyên ít, rootfs thường chỉ đọc, khởi động phải nhanh, và hay có yêu cầu thời gian thực (PREEMPT_RT).

Kiến thức OS chung là nền cho cả ba: một người hiểu scheduling, đồng bộ, bộ nhớ ảo sẽ học FreeRTOS hay Linux driver nhanh hơn nhiều.

Liên hệ công việc · Networking/5GOS trong phần mềm mạng và 5G

Phần mềm 5G Core chạy trên Linux, thường trong container trên Kubernetes (Bài 9). Bạn sẽ chạm tới OS ở mọi tầng:

  • Control plane (AMF, SMF, NRF, AUSF... trong Open5GS, free5GC): service bình thường, dùng socket, epoll/thread pool, SCTP cho giao diện N2 với trạm gốc, HTTP/2 cho giao diện SBI giữa các function. Hiểu system call, thread, I/O multiplexing là đủ.
  • User plane (UPF): xử lý gói tốc độ cao; nghẽn chính là system call và chuyển ngữ cảnh, nên dùng kernel bypass (DPDK, AF_XDP) hoặc module kernel (Open5GS và free5GC có chế độ dùng module kernel gtp5g để đóng/mở gói GTP-U trong kernel).
  • Công cụ hằng ngày: strace (system call), perf (CPU), ss (socket), ip / ethtool (mạng), /proc và /sys (trạng thái kernel), journalctl (log của systemd), top/htop/pidstat (CPU theo process/thread).
Tự kiểm traMột service gọi write() để gửi mỗi message 100 byte, 500.000 message mỗi giây. perf top cho thấy phần lớn thời gian CPU nằm trong kernel. Giải thích và đề xuất.

Mỗi message là một system call: chi phí chuyển mức đặc quyền (cỡ 100 ns trở lên) cộng với đường đi qua stack TCP/IP trong kernel (vài trăm ns tới µs). 500.000 lần mỗi giây nghĩa là hàng trăm ms CPU mỗi giây chỉ cho phần "vào kernel". Đề xuất: gom nhiều message vào một buffer rồi ghi một lần (write lớn hơn hoặc writev với nhiều buffer), dùng sendmmsg() cho UDP (nhiều datagram một system call), hoặc io_uring để nộp nhiều thao tác mà không cần một system call cho mỗi thao tác. Với tải rất cao thì cân nhắc kernel bypass.

Bài 1 · Process

Process là gì

Chương trình (program) là một file trên đĩa: code và dữ liệu khởi tạo, nằm im. Process (tiến trình) là một chương trình đang chạy: có không gian địa chỉ riêng, thanh ghi CPU, các file đang mở, trạng thái. Chạy cùng một chương trình hai lần cho ra hai process độc lập.

Kernel lưu thông tin mỗi process trong một cấu trúc gọi là PCB (process control block); trong Linux là struct task_struct, khoảng vài KB, chứa:

  • PID (process ID), PID của cha, user/group sở hữu.
  • Trạng thái (đang chạy, sẵn sàng, đang chờ...).
  • Thanh ghi đã lưu khi process không chạy (PC, SP, các thanh ghi khác).
  • Con trỏ tới không gian địa chỉ (bảng trang, danh sách vùng nhớ).
  • Bảng file descriptor: các file, socket, pipe đang mở.
  • Thông tin lập lịch (độ ưu tiên, thời gian CPU đã dùng), tín hiệu, giới hạn tài nguyên.

Không gian địa chỉ của một process

Mỗi process thấy bố cục bộ nhớ ảo như sau (Linux x86-64, đơn giản hóa):

địa chỉ cao  ┌────────────────────────┐ 0x7fff...
             │ stack (thread chính)    │ ↓ mọc xuống
             │ ...                     │
             │ thư viện chia sẻ, mmap  │ libc.so, vùng mmap, stack của thread khác
             │ ...                     │
             │ heap                    │ ↑ mọc lên (malloc, new)
             │ .bss  (biến toàn cục =0)│
             │ .data (biến toàn cục)   │
             │ .text (code), .rodata   │
địa chỉ thấp └────────────────────────┘ 0x400000 (hoặc ngẫu nhiên với PIE + ASLR)
             (nửa trên của không gian ảo thuộc về kernel, process không truy cập được)

Xem bố cục thật của một process: cat /proc/<pid>/maps. ASLR (address space layout randomization) xáo vị trí các vùng mỗi lần chạy để khó khai thác lỗi bộ nhớ.

Trạng thái của process

             tạo mới
                │
                ▼
   ┌──────► READY ──── scheduler chọn ────► RUNNING ─── kết thúc ───► ZOMBIE ── cha gọi wait ──► (xóa)
   │          ▲                               │  │
   │          └──── hết time slice / ─────────┘  │
   │                bị process ưu tiên cao chiếm │
   │                                             │ chờ I/O, khóa, sleep
   │                                             ▼
   └──────── sự kiện xảy ra ─────────────── BLOCKED (waiting)
  • Running: đang chạy trên một nhân CPU.
  • Ready (runnable): sẵn sàng chạy, chờ tới lượt.
  • Blocked (waiting, sleeping): chờ một sự kiện (dữ liệu từ socket, khóa, timer). Không tốn CPU.
  • Zombie: đã kết thúc nhưng cha chưa lấy mã thoát.

Lệnh ps hiển thị trạng thái bằng chữ: R (running/runnable), S (sleep có thể ngắt), D (sleep không thể ngắt, thường chờ I/O đĩa; không giết được bằng tín hiệu), Z (zombie), T (bị dừng).

Tạo process: fork, exec, wait

UNIX tách việc tạo process làm hai bước, một thiết kế lạ nhưng mạnh:

  • fork(): nhân bản process hiện tại. Con là bản sao của cha (bộ nhớ, file descriptor, thanh ghi); khác nhau duy nhất ở giá trị trả về: cha nhận PID của con, con nhận 0.
  • execve(path, argv, envp): thay toàn bộ chương trình của process hiện tại bằng chương trình khác. Không trả về nếu thành công.
  • waitpid(pid, &status, 0): cha chờ con kết thúc và lấy mã thoát.
pid_t pid = fork();
if (pid == 0) {                         // tiến trình con
    execlp("ls", "ls", "-l", nullptr);  // thay bằng chương trình ls
    _exit(127);                         // chỉ tới đây nếu exec thất bại
}
int status;
waitpid(pid, &status, 0);               // cha chờ con

Vì sao tách đôi? Giữa fork và exec, con có thể chỉnh môi trường của chính nó (đổi thư mục, chuyển hướng stdin/stdout bằng dup2, đóng file, đổi user) mà không cần API phức tạp. Shell dùng đúng cơ chế này để làm ls > out.txt và ls | grep x.

fork() không chép toàn bộ bộ nhớ ngay: nhờ copy-on-write (F01 Bài 5), cha và con dùng chung trang vật lý cho tới khi một bên ghi. Đo thật:

// Cấp phát lười và copy-on-write, đo bằng số minor page fault mà kernel báo (getrusage).
#include <cstdio>
#include <cstring>
#include <sys/mman.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <unistd.h>

static long minflt() { rusage r; getrusage(RUSAGE_SELF, &r); return r.ru_minflt; }

int main() {
    const size_t SZ = 64 << 20;                                    // 64 MB = 16384 trang 4 KB
    long f0 = minflt();
    char* p = static_cast<char*>(mmap(nullptr, SZ, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0));
    if (p == MAP_FAILED) return 1;
    long f1 = minflt();
    std::memset(p, 1, SZ);                                         // chạm mọi trang
    long f2 = minflt();
    std::printf("mmap 64 MB        : %ld page fault (chua cap trang nao)\n", f1 - f0);
    std::printf("ghi lan dau 64 MB : %ld page fault (~1 fault moi trang, it hon neu THP gop trang 2 MB)\n", f2 - f1);

    std::fflush(stdout);                    // xả buffer TRƯỚC fork, nếu không con sẽ in lại phần của cha
    pid_t pid = fork();
    if (pid == 0) {                                                // con: dùng chung trang với cha, chỉ đọc
        long c0 = minflt(); long s = 0;
        for (size_t i = 0; i < SZ; i += 4096) s += p[i];
        long c1 = minflt();
        for (size_t i = 0; i < SZ; i += 4096) p[i] = 2;             // ghi: mỗi trang bị sao chép (COW)
        long c2 = minflt();
        std::printf("[con] doc sau fork : %ld fault (dung chung, s=%ld)\n", c1 - c0, s / 4096);
        std::printf("[con] ghi sau fork : %ld fault (copy-on-write)\n", c2 - c1);
        std::fflush(stdout);                                       // _exit không xả buffer của stdio
        _exit(0);
    }
    int st; waitpid(pid, &st, 0);
    std::printf("[cha] p[0] van la  : %d (khong bi con sua)\n", p[0]);
    munmap(p, SZ);
}

Đọc kết quả: mmap 64 MB không tốn trang nào (cấp phát lười); lần ghi đầu tốn đúng một page fault cho mỗi trang 4 KB; sau fork, con đọc không tốn gì (dùng chung), ghi thì mỗi trang tốn một fault để sao chép; thay đổi của con không ảnh hưởng cha.

Khi viết chương trình này, lần chạy đầu in ra các dòng của cha hai lần. Lý do: khi stdout không phải terminal (chuyển sang file hay pipe), printf gom vào buffer trong bộ nhớ; fork sao chép cả buffer chưa xả đó sang con, và con xả nó ra lần nữa. Đó là lý do có hai dòng fflush(stdout) trong code. Đây là câu hỏi phỏng vấn kinh điển.

Linux còn có vfork() và posix_spawn() (tạo process mới chạy chương trình khác mà không sao chép bảng trang, nhanh hơn nhiều với process lớn) và clone() (system call tổng quát, cho chọn chia sẻ những gì; thread được tạo bằng clone với cờ chia sẻ bộ nhớ).

Zombie, orphan và tín hiệu

  • Zombie: con đã thoát nhưng cha chưa gọi wait. Kernel giữ lại một ít thông tin (PID, mã thoát). Một vài zombie vô hại; hàng nghìn zombie làm cạn bảng PID. Cách tránh: cha gọi waitpid, hoặc xử lý tín hiệu SIGCHLD, hoặc đặt SIGCHLD thành SIG_IGN.
  • Orphan (mồ côi): cha thoát trước con. Con được "nhận nuôi" bởi PID 1 (hoặc một subreaper), PID 1 sẽ wait cho nó.
  • Tín hiệu (signal): thông báo bất đồng bộ tới process: SIGINT (Ctrl+C), SIGTERM (yêu cầu kết thúc lịch sự), SIGKILL (giết ngay, không chặn được), SIGSEGV (truy cập bộ nhớ sai), SIGPIPE (ghi vào socket/pipe đã bị đóng phía bên kia), SIGCHLD (con thay đổi trạng thái). Handler tín hiệu chạy chen ngang bất kỳ đâu, nên chỉ được gọi hàm async-signal-safe; cách an toàn nhất trong chương trình nhiều thread là chặn tín hiệu và nhận chúng qua signalfd hoặc một thread riêng dùng sigwait.

Tự kiểm traMột chương trình in "start" bằng printf("start\n"), gọi fork(), rồi cả cha và con đều kết thúc bình thường. Chạy trên terminal thấy "start" một lần, nhưng ./prog > log.txt thì file có hai dòng "start". Vì sao?

Bài 2 · Thread và chuyển ngữ cảnh

Thread là gì

Một process có thể có nhiều thread (luồng). Các thread của cùng process dùng chung: không gian địa chỉ (heap, biến toàn cục, code), file descriptor, handler tín hiệu, thư mục làm việc. Mỗi thread có riêng: thanh ghi (PC, SP), stack, biến thread_local, độ ưu tiên, mặt nạ tín hiệu, errno.

Trong Linux, kernel không phân biệt mạnh process và thread: cả hai đều là task (task_struct), tạo bằng clone(); thread chỉ là task chia sẻ bộ nhớ và file với task khác. getpid() trả về ID nhóm thread (giống nhau cho mọi thread của process), gettid() trả về ID riêng của thread. top -H và ps -eLf hiển thị từng thread.

Mô hình thread

  • 1:1 (kernel thread): mỗi thread của ứng dụng là một thread kernel, kernel lập lịch trực tiếp. Linux NPTL (pthread), Windows, và std::thread dùng mô hình này.
  • N:1 (user thread, green thread): nhiều thread ứng dụng trên một thread kernel, thư viện tự chuyển đổi. Chuyển rất rẻ, nhưng một system call chặn làm cả nhóm dừng, không dùng được nhiều nhân.
  • M:N: M thread ứng dụng trên N thread kernel. Goroutine của Go, coroutine C++20 kết hợp thread pool, Seastar, fiber của Boost. Chuyển rẻ, dùng nhiều nhân, nhưng phức tạp.

Chuyển ngữ cảnh (context switch)

Khi kernel ngừng chạy thread A để chạy thread B trên cùng một nhân, nó chuyển ngữ cảnh:

  1. Vào kernel (do A gọi system call chặn, do ngắt timer báo hết lượt, hoặc do B có ưu tiên cao hơn vừa thức dậy).
  2. Lưu thanh ghi của A vào task_struct của A.
  3. Scheduler chọn B.
  4. Nếu B thuộc process khác: đổi bảng trang (CR3), có thể mất hiệu lực TLB.
  5. Khôi phục thanh ghi của B, quay về user space ở chỗ B đã dừng.

Chi phí trực tiếp khoảng 1–3 µs. Chi phí gián tiếp thường lớn hơn: B tìm thấy cache, TLB, bộ dự đoán rẽ nhánh đầy dữ liệu của A, phải nạp lại.

Đo thật: hai thread chuyền một byte qua lại bằng hai pipe. Mỗi vòng gồm hai lần ghi, hai lần đọc, hai lần một thread ngủ và thread kia thức dậy.

// Đo chi phí chuyển ngữ cảnh: hai thread chuyền một byte qua lại bằng hai pipe.
// Mỗi vòng = 2 lần write + 2 lần read + 2 lần ngủ/thức. Ghim cả hai thread vào CÙNG một nhân
// để buộc kernel chuyển ngữ cảnh mỗi lần; rồi so với hai nhân khác nhau.
#include <chrono>
#include <cstdio>
#include <pthread.h>
#include <sched.h>
#include <thread>
#include <unistd.h>

static void pin(int cpu) {
    cpu_set_t s; CPU_ZERO(&s); CPU_SET(cpu, &s);
    pthread_setaffinity_np(pthread_self(), sizeof s, &s);
}

static double pingpong(int cpu_a, int cpu_b) {
    int ab[2], ba[2];
    if (pipe(ab) || pipe(ba)) return -1;
    const int rounds = 100000;
    std::thread peer([&] {
        pin(cpu_b); char c;
        for (int i = 0; i < rounds; ++i) { if (read(ab[0], &c, 1) != 1 || write(ba[1], &c, 1) != 1) return; }
    });
    pin(cpu_a); char c = 'x';
    auto t0 = std::chrono::steady_clock::now();
    for (int i = 0; i < rounds; ++i) { if (write(ab[1], &c, 1) != 1 || read(ba[0], &c, 1) != 1) break; }
    auto t1 = std::chrono::steady_clock::now();
    peer.join();
    for (int fd : {ab[0], ab[1], ba[0], ba[1]}) close(fd);
    return std::chrono::duration<double, std::micro>(t1 - t0).count() / rounds;
}

int main() {
    std::printf("cung 1 nhan : %5.2f us moi vong (2 lan chuyen ngu canh)\n", pingpong(0, 0));
    std::printf("2 nhan khac : %5.2f us moi vong (danh thuc thread o nhan khac)\n", pingpong(0, 1));
}

cung 1 nhan :  2.35 us moi vong (2 lan chuyen ngu canh)
2 nhan khac : 23.15 us moi vong (danh thuc thread o nhan khac)

Cùng một nhân: khoảng 1,2 µs mỗi lần chuyển (bao gồm cả system call read/write). Hai nhân khác nhau lại chậm hơn 10 lần: mỗi lần thread bên kia ngủ, nhân của nó rảnh và đi vào trạng thái nghỉ; đánh thức nó cần một ngắt liên nhân (IPI, inter-processor interrupt) và thời gian thoát trạng thái nghỉ. Trên máy ảo (như máy đo ở đây), nhân ảo rảnh còn bị hypervisor cho "ngủ" thật, nên chi phí đánh thức lên tới hàng chục µs; trên máy vật lý con số nhỏ hơn nhưng cùng bản chất.

Bài học cho thiết kế độ trễ thấp: ngủ rồi được đánh thức là đắt. Đó là lý do các hệ thống mạng hiệu năng cao chọn busy-polling (thread không bao giờ ngủ, liên tục kiểm tra hàng đợi) và chấp nhận đốt trọn một nhân.

Bài 3 · Lập lịch CPU (scheduling)

Bài toán

Có nhiều thread sẵn sàng (ready) hơn số nhân CPU. Scheduler (bộ lập lịch) quyết định thread nào chạy, trên nhân nào, trong bao lâu. Không có lời giải tốt nhất cho mọi trường hợp, vì các mục tiêu mâu thuẫn nhau:

Chỉ số Nghĩa Ai quan tâm
Turnaround time Thời gian từ lúc việc đến tới lúc xong Batch job, build
Response time Thời gian từ lúc đến tới lần đầu được chạy Ứng dụng tương tác
Throughput Số việc xong mỗi đơn vị thời gian Server
Fairness Mỗi việc được phần CPU công bằng Hệ đa người dùng
Deadline / độ trễ tối đa Việc phải xong trước hạn Hệ thời gian thực
Overhead Chi phí của chính scheduler và chuyển ngữ cảnh Mọi hệ thống

Hai kiểu lập lịch cơ bản: non-preemptive (thread chạy tới khi tự nhường hoặc chặn) và preemptive (kernel có thể giành CPU giữa chừng, nhờ ngắt timer). Mọi OS hiện đại và RTOS đều preemptive.

Các thuật toán kinh điển

Ví dụ: ba việc A (cần 10 ms), B (2 ms), C (2 ms) đến cùng lúc, theo thứ tự A, B, C.

FIFO / FCFS (first come, first served): chạy theo thứ tự đến. A xong ở 10, B ở 12, C ở 14; turnaround trung bình (10 + 12 + 14) / 3 = 12 ms. Vấn đề convoy effect: việc ngắn kẹt sau việc dài.

SJF (shortest job first): việc ngắn trước. B 2, C 4, A 14; trung bình 6,7 ms. Tối ưu cho turnaround khi biết trước độ dài, nhưng thực tế không biết, và việc dài có thể đói (starvation). Bản preemptive là STCF/SRTF (shortest time to completion first).

Round Robin (RR): mỗi việc được một time slice (quantum, ví dụ 1 ms), hết lượt thì xếp cuối hàng. Response time tốt; turnaround kém hơn SJF. Slice quá nhỏ thì tốn chi phí chuyển ngữ cảnh; quá lớn thì thành FIFO.

Priority scheduling: luôn chạy việc ưu tiên cao nhất. Việc ưu tiên thấp có thể đói; chữa bằng aging (chờ lâu thì tăng ưu tiên).

MLFQ (multi-level feedback queue): nhiều hàng đợi theo ưu tiên. Việc mới vào hàng cao nhất; dùng hết slice thì bị hạ hàng (có vẻ là việc nặng CPU); nhường CPU sớm vì chờ I/O thì giữ hàng (có vẻ là việc tương tác). Định kỳ đẩy mọi việc lên hàng cao để chống đói. MLFQ học hành vi của việc mà không cần biết trước, là nền của scheduler trong Windows, macOS và các UNIX cổ điển.

Scheduler của Linux

Linux có nhiều scheduling class, xét theo thứ tự ưu tiên:

Class Chính sách Dùng cho
Stop (nội bộ kernel) Di chuyển task giữa nhân
Deadline SCHED_DEADLINE Việc định kỳ có hạn: khai báo runtime, period, deadline; kernel dùng EDF (earliest deadline first) và từ chối nếu không đủ CPU
Real-time SCHED_FIFO, SCHED_RR Ưu tiên tĩnh 1–99; FIFO chạy tới khi chặn hoặc bị ưu tiên cao hơn chiếm; RR thêm time slice giữa các task cùng ưu tiên
Fair SCHED_OTHER (mặc định), SCHED_BATCH, SCHED_IDLE Mọi process thường; chia CPU công bằng có trọng số theo nice (−20 tới 19)

Scheduler của class fair: từ 2007 tới 2023 là CFS (completely fair scheduler), từ kernel 6.6 được thay bằng EEVDF (earliest eligible virtual deadline first). Ý tưởng chung: mỗi task có thời gian chạy ảo (vruntime) tăng theo thời gian CPU đã dùng, chia cho trọng số (nice thấp thì trọng số cao, vruntime tăng chậm hơn). Scheduler luôn chọn task "bị thiệt" nhất. Task được sắp trong cây đỏ đen theo vruntime (hoặc deadline ảo với EEVDF) nên chọn task tiếp theo là O(log n). EEVDF thêm khái niệm deadline ảo để task cần độ trễ thấp (slice ngắn) được chạy sớm hơn.

Lệnh liên quan: nice -n 10 ./job, renice, chrt -f 50 ./rt_app (chạy SCHED_FIFO ưu tiên 50), chrt -p <pid> (xem chính sách).

Cảnh báo về real-time trên Linux: một thread SCHED_FIFO vòng lặp vô hạn sẽ chiếm trọn nhân đó, các thread thường không bao giờ được chạy ở nhân này. Linux có RT throttling mặc định (/proc/sys/kernel/sched_rt_runtime_us = 950000 trên sched_rt_period_us = 1000000: task RT chỉ được 95% mỗi giây) để chống treo máy.

Lập lịch đa nhân

Với nhiều nhân, scheduler còn quyết định chạy ở nhân nào: - Mỗi nhân một runqueue riêng (tránh khóa chung), định kỳ cân bằng tải (load balancing) bằng cách chuyển task từ nhân bận sang nhân rảnh. - Cache affinity: task chạy lại trên nhân cũ thì cache còn nóng; chuyển nhân là mất cache. Scheduler cân nhắc giữa cân bằng tải và giữ affinity. - NUMA-aware: Linux có thể di chuyển task về gần bộ nhớ của nó (automatic NUMA balancing).

Người dùng điều khiển bằng: - CPU affinity: taskset, sched_setaffinity, pthread_setaffinity_np, cgroup cpuset. - isolcpus=2-7 (tham số kernel): loại nhân 2–7 khỏi cân bằng tải; chỉ task được ghim tường minh mới chạy ở đó. - nohz_full=2-7: tắt ngắt timer định kỳ (tick) trên các nhân đó khi chỉ có một task chạy, để task không bị ngắt mỗi 1–4 ms. - rcu_nocbs=2-7: dời việc callback RCU của kernel sang nhân khác. - IRQ affinity: đẩy ngắt thiết bị sang nhân khác (/proc/irq/*/smp_affinity_list, dịch vụ irqbalance).

Hệ thời gian thực và RTOS

Real-time không có nghĩa là "nhanh" mà là đúng hạn, dự đoán được. Hệ hard real-time: trễ hạn là lỗi hệ thống (phanh ABS, điều khiển động cơ). Soft real-time: trễ hạn làm giảm chất lượng (video giật, gói thoại trễ). Chỉ số quan trọng là độ trễ tối đa (worst case), không phải trung bình.

RTOS dùng lập lịch ưu tiên preemptive cố định: luôn chạy task sẵn sàng có ưu tiên cao nhất, ngay lập tức. Lý thuyết đi kèm: - Rate Monotonic Scheduling (RMS): với các task định kỳ, gán ưu tiên cao hơn cho task có chu kỳ ngắn hơn. Đủ điều kiện lập lịch được (Liu & Layland 1973) nếu tổng tải U = Σ Cᵢ/Tᵢ ≤ n(2^(1/n) − 1), tiến tới khoảng 69% khi n lớn (điều kiện đủ, không cần). - EDF (earliest deadline first): ưu tiên động theo hạn gần nhất; lập lịch được tới U ≤ 100% (với deadline bằng chu kỳ). Linux SCHED_DEADLINE dùng EDF.

Priority inversion

Hiện tượng kinh điển của lập lịch ưu tiên kết hợp với khóa. Ba task ưu tiên H (cao), M (trung bình), L (thấp):

thời gian ─────────────────────────────────────────────────────────►
L:  [chạy, khóa mutex X]·······(bị M chiếm)··········[chạy tiếp, nhả X]
H:        [thức dậy, cần X → chặn chờ L]·································[chạy]
M:              [thức dậy, ưu tiên > L → chiếm CPU, chạy rất lâu]

H chờ L nhả khóa, nhưng L không được chạy vì M (không liên quan gì tới khóa) có ưu tiên cao hơn L. Kết quả: H bị chặn bởi M, độ trễ của H không giới hạn. Sự cố nổi tiếng: tàu Mars Pathfinder (1997) liên tục khởi động lại vì watchdog phát hiện task ưu tiên cao bị trễ do priority inversion trên VxWorks; được sửa từ xa bằng cách bật priority inheritance.

Giải pháp: - Priority inheritance (kế thừa ưu tiên): khi H chờ khóa của L, L tạm được nâng lên ưu tiên của H cho tới khi nhả khóa, nên M không chen vào được. FreeRTOS mutex có sẵn; POSIX dùng pthread_mutexattr_setprotocol(&a, PTHREAD_PRIO_INHERIT); Linux PREEMPT_RT dùng rt_mutex có kế thừa. - Priority ceiling (trần ưu tiên): mỗi khóa có trần bằng ưu tiên cao nhất của các task dùng nó; ai giữ khóa thì chạy ở mức trần. Chặn được cả deadlock giữa các khóa có trần. - Thiết kế tránh chia sẻ khóa giữa task ưu tiên khác xa nhau (dùng hàng đợi message thay vì khóa).

Liên hệ EmbeddedLập lịch trong FreeRTOS và PREEMPT_RT

FreeRTOS: ưu tiên cố định 0 tới configMAX_PRIORITIES - 1, preemptive, các task cùng ưu tiên chia lượt theo tick (configUSE_TIME_SLICING). Tick thường 1 ms (configTICK_RATE_HZ); vTaskDelay tính bằng tick; tickless idle tắt tick khi rảnh để tiết kiệm điện. ISR luôn có ưu tiên cao hơn mọi task, nên ISR dài làm trễ mọi task; chỉ gọi API có hậu tố FromISR và dùng portYIELD_FROM_ISR để chuyển ngay sang task vừa được đánh thức. Phân tích lập lịch (RMS, WCET) là kỹ năng phỏng vấn firmware thực thụ. Trên Embedded Linux, bản vá PREEMPT_RT (đã vào mainline từ kernel 6.12) biến spinlock thành rt_mutex có kế thừa ưu tiên, đưa xử lý ngắt vào thread, cho độ trễ tối đa cỡ vài chục µs đo bằng cyclictest.

Liên hệ công việc · Networking/5GLập lịch cho data plane và 5G
  • Cô lập nhân cho data plane: cấu hình chuẩn của server UPF/DPDK là chia nhân thành nhóm "housekeeping" (OS, control plane, ngắt, systemd) và nhóm "data plane" với isolcpus, nohz_full, rcu_nocbs, IRQ affinity ra khỏi nhóm này. Trên Kubernetes, tương đương là CPU Manager static policy (pod Guaranteed nhận nhân độc quyền), cộng với profile tinh chỉnh (ví dụ Performance Profile của OpenShift hay tuned profile cpu-partitioning).
  • Thread poll-mode không được ngủ: nếu nhân data plane lỡ có thread khác cùng chạy, scheduler fair sẽ chia thời gian, gây khoảng mất gói cỡ mili giây. Kiểm tra bằng perf sched, /proc/<pid>/status (dòng nonvoluntary_ctxt_switches tăng là bị chiếm).
  • Real-time cho RAN: phần mềm trạm gốc (vRAN/O-RAN DU, ví dụ OpenAirInterface, srsRAN) có hạn chót theo slot vô tuyến (0,5 ms hoặc ngắn hơn với numerology cao), chạy trên kernel PREEMPT_RT với thread SCHED_FIFO. 5G Core ít khắt khe hơn nhưng UPF vẫn cần độ trễ tối đa ổn định.
  • Đừng dùng SCHED_FIFO bừa bãi: thread FIFO busy-poll trên nhân không cô lập có thể bỏ đói kernel worker của nhân đó (ví dụ ksoftirqd, kworker), gây treo khó hiểu.
Tự kiểm traBa task định kỳ: T1 chạy 1 ms mỗi 4 ms, T2 chạy 2 ms mỗi 8 ms, T3 chạy 2 ms mỗi 10 ms. Có lập lịch được bằng Rate Monotonic không theo điều kiện Liu–Layland? Bằng EDF?

U = 1/4 + 2/8 + 2/10 = 0,25 + 0,25 + 0,2 = 0,70. Giới hạn Liu–Layland với n = 3 là 3(2^(1/3) − 1) ≈ 0,780. Vì 0,70 ≤ 0,78 nên chắc chắn lập lịch được bằng RMS (ưu tiên T1 > T2 > T3 theo chu kỳ ngắn hơn). EDF lập lịch được mọi tập có U ≤ 1, nên cũng được. Nếu U vượt 0,78 nhưng dưới 1, RMS có thể vẫn được nhưng phải kiểm tra bằng phân tích thời gian đáp ứng (response time analysis).

  • Mục tiêu mâu thuẫn: turnaround, response, throughput, fairness, deadline, overhead.
  • FIFO (convoy), SJF/STCF (tối ưu turnaround, cần biết trước, có thể đói), RR (response tốt), priority (+aging), MLFQ (học hành vi).

Bài 4 · Đồng bộ (synchronization)

Race condition

Khi nhiều thread truy cập cùng dữ liệu và ít nhất một thread ghi, kết quả có thể phụ thuộc vào thứ tự xen kẽ ngẫu nhiên: đó là race condition. Ví dụ quen thuộc: counter++ thực chất là ba bước đọc – cộng – ghi. Hai thread cùng đọc giá trị 5, cùng cộng thành 6, cùng ghi 6: mất một lần tăng.

Thí nghiệm sau dùng std::atomic nhưng tách đọc và ghi thành hai thao tác riêng (mỗi thao tác nguyên tử, nhưng cặp thì không), nên không có undefined behavior mà vẫn thấy race:

// Race condition không cần UB: "đọc rồi ghi" là HAI thao tác atomic riêng, không phải một.
// Hai thread cùng tăng bộ đếm 1 triệu lần; kết quả đúng phải là 2 triệu.
#include <atomic>
#include <cstdio>
#include <mutex>
#include <thread>

int main() {
    const int N = 1'000'000;
    std::atomic<long> a{0};
    auto read_then_write = [&] { for (int i = 0; i < N; ++i) a.store(a.load() + 1); };   // SAI: không nguyên tử
    std::thread t1(read_then_write), t2(read_then_write); t1.join(); t2.join();
    std::printf("load + store   : %ld  (mat %ld lan cap nhat)\n", a.load(), 2L * N - a.load());

    std::atomic<long> b{0};
    auto rmw = [&] { for (int i = 0; i < N; ++i) b.fetch_add(1); };                     // ĐÚNG: một thao tác
    std::thread t3(rmw), t4(rmw); t3.join(); t4.join();
    std::printf("fetch_add      : %ld\n", b.load());

    long c = 0; std::mutex m;
    auto locked = [&] { for (int i = 0; i < N; ++i) { std::lock_guard g(m); ++c; } };   // ĐÚNG: vùng găng
    std::thread t5(locked), t6(locked); t5.join(); t6.join();
    std::printf("mutex          : %ld\n", c);
    return (b.load() == 2L * N && c == 2L * N) ? 0 : 1;
}

load + store   : 1465654  (mat 534346 lan cap nhat)
fetch_add      : 2000000
mutex          : 2000000

Hơn một phần tư số lần cập nhật bị mất. Với biến thường (long counter; counter++ từ hai thread) thì còn tệ hơn: đó là data race, undefined behavior trong C/C++, trình biên dịch được phép tối ưu theo giả định không có thread nào khác.

Thuật ngữ: - Critical section (vùng găng): đoạn code truy cập dữ liệu chung, chỉ được một thread vào tại một thời điểm. - Mutual exclusion (loại trừ lẫn nhau): tính chất đó. - Yêu cầu của một giải pháp đúng: loại trừ lẫn nhau, tiến triển (không ai trong vùng găng thì phải cho người chờ vào), chờ có giới hạn (không ai chờ mãi).

Phần cứng làm nền: lệnh nguyên tử

Mọi cơ chế đồng bộ dựng trên vài lệnh nguyên tử của CPU (F01 Bài 4): - Test-and-set / exchange: ghi giá trị mới, trả về giá trị cũ, nguyên tử (xchg trên x86). - Compare-and-swap (CAS): "nếu giá trị hiện tại bằng expected thì ghi desired", trả về thành công hay không (lock cmpxchg trên x86, cas trên ARMv8.1; C++ compare_exchange_weak/strong). - Load-linked / store-conditional (LL/SC): ldxr/stxr trên ARM, lr/sc trên RISC-V: ghi chỉ thành công nếu không ai chạm địa chỉ đó từ lúc đọc. - Fetch-and-add: lock xadd, ldadd.

Các công cụ đồng bộ

Spinlock: thread chờ bằng cách quay vòng kiểm tra (busy-wait) cho tới khi lấy được khóa.

class Spinlock {
    std::atomic<bool> locked{false};
public:
    void lock()   { while (locked.exchange(true, std::memory_order_acquire)) { while (locked.load(std::memory_order_relaxed)) { /* _mm_pause() */ } } }
    void unlock() { locked.store(false, std::memory_order_release); }
};

Hợp khi vùng găng rất ngắn và chủ khóa không bị ngủ (trong kernel: khi đã tắt preempt hoặc ngắt). Trong user space, spinlock nguy hiểm: nếu thread giữ khóa bị scheduler cho ngủ, các thread khác quay vòng phí cả time slice.

Mutex: nếu không lấy được khóa thì ngủ (nhường CPU), được đánh thức khi khóa được nhả. Có chủ sở hữu: chỉ thread đã khóa mới được mở. Trên Linux, pthread_mutex (và std::mutex) được xây trên futex (fast userspace mutex): trường hợp không tranh chấp chỉ là một lệnh CAS trong user space (khoảng 20 ns, không system call); chỉ khi phải chờ mới gọi system call futex(FUTEX_WAIT) để ngủ và futex(FUTEX_WAKE) để đánh thức. Nhiều cài đặt quay vòng một chút trước khi ngủ (adaptive mutex).

Semaphore (Dijkstra, 1965): một bộ đếm với hai thao tác: wait (P, down: giảm, nếu âm thì chờ) và post (V, up, signal: tăng, đánh thức một thread chờ). Semaphore đếm (giá trị khởi đầu N) giới hạn N thread cùng dùng một tài nguyên (pool N kết nối). Semaphore nhị phân (0/1) dùng để báo hiệu giữa thread (ISR báo cho task). Khác mutex: không có chủ sở hữu, thread này wait thread khác post được, và không có priority inheritance. C++20 có std::counting_semaphore, std::binary_semaphore.

Condition variable: cho thread chờ một điều kiện trên dữ liệu được bảo vệ bởi mutex. Luôn dùng với mutex và vòng lặp kiểm tra điều kiện (vì có thể thức dậy giả, spurious wakeup, và vì điều kiện có thể đã đổi):

std::mutex m; std::condition_variable cv; std::queue<Job> q;

void producer(Job j) {
    { std::lock_guard g(m); q.push(std::move(j)); }
    cv.notify_one();
}
Job consumer() {
    std::unique_lock lk(m);
    cv.wait(lk, [&] { return !q.empty(); });     // = while (q.empty()) cv.wait(lk);
    Job j = std::move(q.front()); q.pop();
    return j;
}

wait nhả mutex và ngủ một cách nguyên tử, rồi khóa lại mutex trước khi trả về.

Reader-writer lock: nhiều thread đọc cùng lúc, hoặc một thread ghi. C++17 std::shared_mutex. Chỉ có lợi khi đọc chiếm áp đảo và vùng găng đủ dài; với vùng ngắn, chi phí cập nhật bộ đếm người đọc (một cache line chung) làm nó chậm hơn mutex thường.

RCU (read-copy-update): kỹ thuật của kernel Linux cho dữ liệu đọc rất nhiều, ghi rất ít (bảng định tuyến, danh sách module). Người đọc không khóa gì cả; người ghi tạo bản sao mới, sửa, rồi đổi con trỏ một cách nguyên tử; bản cũ chỉ được giải phóng sau khi mọi người đọc đang dở đã xong (grace period). Trong user space có liburcu; C++ có thể mô phỏng bằng std::atomic<std::shared_ptr<T>> (C++20) với chi phí cao hơn.

Atomic và lock-free: dùng trực tiếp lệnh nguyên tử, không khóa. Lock-free đảm bảo hệ thống luôn tiến triển (một thread bị treo không chặn thread khác), nhưng không tự động nhanh hơn (F01 Bài 4) và rất khó viết đúng (vấn đề ABA, thu hồi bộ nhớ). Dùng cấu trúc đã được kiểm chứng (ring SPSC/MPMC, rte_ring, folly, Boost.Lockfree).

Bài 5 · Deadlock

Định nghĩa và bốn điều kiện

Deadlock (bế tắc): một nhóm thread chờ nhau vĩnh viễn, mỗi thread giữ tài nguyên mà thread khác cần. Ví dụ đơn giản nhất:

std::mutex a, b;
void t1() { std::lock_guard la(a); std::lock_guard lb(b); /*...*/ }   // khóa a rồi b
void t2() { std::lock_guard lb(b); std::lock_guard la(a); /*...*/ }   // khóa b rồi a
// t1 giữ a chờ b; t2 giữ b chờ a → treo mãi

Deadlock xảy ra khi và chỉ khi cả bốn điều kiện sau cùng đúng (điều kiện Coffman, 1971):

  1. Mutual exclusion: tài nguyên chỉ một thread giữ được tại một thời điểm.
  2. Hold and wait: thread đang giữ tài nguyên lại chờ thêm tài nguyên khác.
  3. No preemption: không thể giật tài nguyên khỏi thread đang giữ.
  4. Circular wait: có vòng tròn thread mỗi thread chờ tài nguyên của thread kế tiếp.

Phá một điều kiện bất kỳ là tránh được deadlock.

Bốn chiến lược

Chiến lược Cách làm Thực tế
Phòng ngừa (prevention) Thiết kế để một trong bốn điều kiện không bao giờ xảy ra Cách phổ biến nhất trong code thực tế
Tránh (avoidance) Trước mỗi lần cấp tài nguyên, kiểm tra hệ thống còn ở trạng thái an toàn không (thuật toán Banker của Dijkstra) Cần biết trước nhu cầu tối đa; hầu như chỉ có trong sách
Phát hiện và phục hồi (detection) Cho xảy ra, định kỳ tìm chu trình trong đồ thị chờ, rồi hủy/khởi động lại một bên Database (hủy một transaction), watchdog

Phòng ngừa trong thực tế

  • Phá circular wait bằng thứ tự khóa: quy định một thứ tự toàn cục cho mọi khóa (theo cấp: khóa module trước khóa đối tượng; hoặc theo địa chỉ), mọi chỗ trong code đều khóa theo thứ tự đó. Đây là kỹ thuật số một. Kernel Linux có công cụ lockdep kiểm tra thứ tự khóa lúc chạy và cảnh báo ngay cả khi deadlock chưa xảy ra.
  • Khóa nhiều mutex một lần: std::scoped_lock lk(a, b); (C++17) dùng thuật toán tránh deadlock bên trong (thử khóa, nhả nếu không được, thử lại theo thứ tự khác), không phụ thuộc thứ tự viết.
  • Phá hold and wait: lấy mọi khóa cần thiết cùng lúc, hoặc không giữ khóa khi chờ thứ khác. Quy tắc vàng: không gọi code không kiểm soát được (callback, hàm ảo của người dùng, I/O) khi đang giữ khóa.
  • Phá no preemption: try_lock / try_lock_for (chờ có thời hạn): không lấy được thì nhả những gì đang giữ và thử lại sau.
  • Tránh khóa: mỗi dữ liệu một chủ sở hữu duy nhất (một thread), thread khác gửi message cho nó (actor, active object, M08). Không có khóa thì không có deadlock khóa (nhưng vẫn có thể có deadlock chờ message vòng tròn).

Các dạng "kẹt" khác

  • Livelock: các thread không bị chặn nhưng liên tục phản ứng với nhau mà không tiến triển (hai người nhường đường nhau mãi trong hành lang). Ví dụ: hai thread cùng try_lock thất bại, cùng nhả, cùng thử lại đúng nhịp. Chữa bằng thời gian chờ ngẫu nhiên (backoff).
  • Starvation (đói): một thread không bao giờ được tài nguyên vì người khác luôn được ưu tiên (người ghi trong RW lock ưu tiên người đọc; task ưu tiên thấp).
  • Priority inversion (Bài 3): không phải deadlock nhưng có thể làm trễ vô hạn.
  • Tự deadlock: một thread khóa lại mutex nó đang giữ (std::mutex không đệ quy: UB, thường treo). Gặp khi hàm A khóa rồi gọi hàm B cũng khóa cùng mutex.

Bài 6 · Quản lý bộ nhớ

F01 Bài 5 đã giải thích phần cứng của bộ nhớ ảo (trang, bảng trang, MMU, TLB). Bài này nhìn từ phía hệ điều hành: kernel dùng phần cứng đó thế nào để chia RAM cho các process, và cấp phát bộ nhớ trong ứng dụng hoạt động ra sao.

Từ phân vùng tới phân trang

Lịch sử quản lý bộ nhớ đi qua ba bước, mỗi bước giải một vấn đề của bước trước:

  1. Phân vùng cố định / động: mỗi process một vùng RAM liền mạch, thanh ghi base và bound (giới hạn) kiểm tra mọi truy cập. Đơn giản, nhưng gây phân mảnh ngoài (external fragmentation): RAM trống bị chia thành nhiều mảnh nhỏ, không mảnh nào đủ cho process mới dù tổng đủ.
  2. Segmentation (phân đoạn): mỗi process có vài đoạn (code, heap, stack), mỗi đoạn một cặp base/bound riêng. Linh hoạt hơn nhưng vẫn phân mảnh ngoài. x86 32-bit còn dấu vết (thanh ghi segment), x86-64 gần như bỏ.
  3. Paging (phân trang): chia cả bộ nhớ ảo và vật lý thành trang cùng kích thước, ánh xạ trang nào vào khung nào cũng được. Hết phân mảnh ngoài; còn phân mảnh trong (internal fragmentation) nhỏ: trang cuối của một vùng dùng không hết. Mọi OS hiện đại dùng phân trang.

Demand paging và swap

Kernel chỉ đưa trang vào RAM khi cần (demand paging): page fault lần đầu chạm thì mới cấp khung (cho bộ nhớ ẩn danh) hoặc đọc từ file (cho code, thư viện, file mmap). Khi RAM đầy, kernel phải thu hồi (reclaim) trang: - Trang sạch có bản trên đĩa (code, thư viện, page cache của file chưa sửa): bỏ đi, cần thì đọc lại. - Trang bẩn của file: ghi về file rồi bỏ. - Trang ẩn danh (heap, stack): chỉ bỏ được nếu có swap (vùng trên đĩa); ghi trang ra swap, đánh dấu bảng trang là "không có mặt", lần truy cập sau gây major page fault để đọc lại.

Thuật toán thay trang

Chọn trang nào để đẩy ra? Tiêu chí: tối thiểu số page fault sau này.

Thuật toán Cách chọn Ghi chú

Working set và thrashing

Working set của một process là tập trang nó dùng trong một khoảng thời gian gần đây. Nếu tổng working set của mọi process vượt RAM, hệ thống liên tục đẩy trang ra rồi lại cần ngay: thrashing. CPU gần như rảnh, đĩa bận 100%, mọi thứ chậm hàng trăm lần. Chữa bằng cách giảm số process chạy đồng thời hoặc thêm RAM; trên server thường tắt hoặc giảm swap để thà báo lỗi sớm còn hơn chậm vô hạn.

Overcommit và OOM killer

Linux mặc định overcommit: cho phép tổng bộ nhớ ảo đã cấp vượt RAM + swap, vì phần lớn chương trình không dùng hết những gì xin (cấp phát lười). vm.overcommit_memory: 0 (heuristic, mặc định), 1 (luôn cho), 2 (không cho vượt giới hạn CommitLimit).

Hệ quả: malloc gần như không bao giờ trả NULL trên Linux, nhưng khi các process thật sự chạm vào quá nhiều trang, kernel hết RAM và gọi OOM killer: chọn một process (điểm oom_score cao nhất, chủ yếu theo lượng RAM dùng) và giết bằng SIGKILL. Điều chỉnh bằng /proc/<pid>/oom_score_adj (−1000 là không bao giờ giết). Trong container, giới hạn bộ nhớ của cgroup (memory.max) cũng kích hoạt OOM killer khi bị vượt, chỉ giết trong cgroup đó; Kubernetes báo trạng thái OOMKilled.

Cấp phát bộ nhớ trong kernel

  • Buddy allocator: quản lý khung vật lý theo khối lũy thừa 2 (1, 2, 4... 1024 trang). Xin 3 trang thì cấp khối 4; khi giải phóng, hai khối "bạn" (buddy) kề nhau cùng trống được gộp lại. Nhanh, chống phân mảnh ngoài ở mức chấp nhận được. /proc/buddyinfo hiển thị số khối trống mỗi cấp; số khối lớn ít là dấu hiệu phân mảnh, ảnh hưởng tới khả năng cấp hugepage lúc chạy.
  • Slab allocator (SLUB trong Linux hiện đại): trên các trang lấy từ buddy, chia thành cache theo loại đối tượng cùng kích thước (task_struct, sk_buff, inode). Cấp/giải phóng đối tượng cực nhanh, ít phân mảnh, giữ đối tượng "ấm" trong cache CPU. /proc/slabinfo, slabtop.

Cấp phát bộ nhớ trong user space

malloc/new không gọi kernel mỗi lần. Allocator (glibc ptmalloc, jemalloc, tcmalloc, mimalloc) xin từ kernel những vùng lớn (bằng brk để nới heap, hoặc mmap cho vùng lớn, mặc định từ 128 KB trở lên trong glibc), rồi tự chia nhỏ:

  • Chia theo lớp kích thước (size class), mỗi lớp một danh sách khối trống.
  • Cache theo thread (tcache của glibc, thread cache của tcmalloc) để cấp phát nhỏ không cần khóa.
  • Arena riêng để giảm tranh chấp giữa thread.

Các vấn đề hay gặp: phân mảnh (RSS cao hơn nhiều so với dữ liệu thật đang dùng, nhất là với chương trình chạy lâu cấp/giải phóng nhiều kích thước), tranh chấp khóa khi nhiều thread cấp phát, độ trễ không đoán được (đôi khi phải gọi mmap/munmap, page fault). Chương trình hiệu năng cao thường đổi sang jemalloc/tcmalloc/mimalloc (chỉ cần LD_PRELOAD hoặc link), và tránh cấp phát trên đường nóng bằng pool, arena, std::pmr (M14, M16).

Bài 7 · File system và độ bền dữ liệu

File, inode và thư mục

Với ứng dụng, file là một dãy byte có tên. Bên dưới, file system (ext4, XFS, Btrfs, F2FS...) lưu:

  • Inode (index node): cấu trúc mô tả một file: kích thước, chủ sở hữu, quyền, thời gian, số liên kết, và vị trí các khối dữ liệu trên đĩa. Inode không chứa tên file. Mỗi inode có số hiệu (ls -i).
  • Khối dữ liệu (data block): nội dung file, thường 4 KB mỗi khối. ext4 dùng extent (một dải khối liền nhau: bắt đầu + độ dài) thay vì liệt kê từng khối.
  • Thư mục: một file đặc biệt chứa bảng tên → số inode.

Vì tên nằm trong thư mục, một inode có thể có nhiều tên: - Hard link (ln a b): thêm một mục tên trỏ tới cùng inode. Xóa a chỉ xóa một tên; dữ liệu còn tới khi số liên kết về 0 và không còn process nào mở file. Không link được thư mục hay sang file system khác. - Symbolic link (ln -s a b): một file nhỏ chứa đường dẫn tới file khác. Có thể trỏ sang file system khác, có thể "treo" nếu đích bị xóa.

Hệ quả hay gặp: xóa một file log lớn đang được process ghi không giải phóng dung lượng (process vẫn giữ inode qua file descriptor); lsof +L1 liệt kê các file đã xóa nhưng còn mở.

VFS

VFS (virtual file system) là lớp trừu tượng trong kernel: ứng dụng gọi read(), VFS chuyển tới hàm read của file system cụ thể (ext4, NFS, procfs, sysfs, tmpfs...). Nhờ VFS mà /proc và /sys (không nằm trên đĩa, do kernel sinh ra lúc đọc) dùng được như file thường.

Page cache

Kernel giữ nội dung file vừa đọc/ghi trong RAM, gọi là page cache. read() lần hai từ cùng file thường không chạm đĩa. write() mặc định chỉ chép dữ liệu vào page cache, đánh dấu trang bẩn rồi trả về ngay; một luồng nền (writeback) ghi xuống đĩa sau (mặc định vài giây tới 30 giây). Lệnh free -h cho thấy RAM "buff/cache" chính là page cache; RAM rảnh được dùng làm cache là điều tốt, kernel thu hồi khi cần.

Hệ quả quan trọng: write() thành công không có nghĩa dữ liệu đã nằm trên đĩa. Mất điện ngay sau đó là mất dữ liệu.

Độ bền: fsync và những cái bẫy

Muốn dữ liệu chắc chắn bền: - fsync(fd): chờ tới khi dữ liệu và metadata của file đã xuống thiết bị lưu trữ (và yêu cầu thiết bị xả cache ghi của nó). - fdatasync(fd): chỉ dữ liệu và metadata cần thiết để đọc lại (bỏ qua thời gian sửa), nhanh hơn. - O_SYNC / O_DSYNC: mỗi write như kèm fsync/fdatasync. - O_DIRECT: bỏ qua page cache, đọc/ghi thẳng thiết bị (buffer phải căn lề); database dùng để tự quản lý cache.

Mẫu ghi file nguyên tử (cập nhật file cấu hình, trạng thái mà không bao giờ để lại file hỏng nửa chừng):

// 1. ghi vào file tạm cùng thư mục
int fd = open("state.json.tmp", O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
write_all(fd, data);
fsync(fd);                                   // 2. dữ liệu file tạm đã bền
close(fd);
rename("state.json.tmp", "state.json");      // 3. rename là nguyên tử trên cùng file system
int dfd = open(".", O_RDONLY | O_DIRECTORY);
fsync(dfd);                                  // 4. bền cả mục thư mục (tên mới)
close(dfd);

Bỏ bước 2 thì sau mất điện có thể thấy state.json mới nhưng rỗng (trên một số file system và chế độ mount). Bỏ bước 4 thì rename có thể chưa bền. Lỗi fsync (EIO) không được bỏ qua: sau một lần lỗi, trang bẩn có thể đã bị đánh dấu sạch, gọi fsync lại "thành công" mà dữ liệu đã mất (sự cố "fsyncgate" của PostgreSQL năm 2018); cách an toàn là coi lỗi fsync là nghiêm trọng.

Nhất quán sau sự cố: journaling

Một thao tác file system thường sửa nhiều chỗ trên đĩa (thêm khối dữ liệu, cập nhật inode, cập nhật bitmap khối trống, thêm mục thư mục). Mất điện giữa chừng để lại trạng thái mâu thuẫn. Hai cách cũ và mới: - fsck: khi khởi động lại, quét toàn bộ đĩa tìm và sửa mâu thuẫn. Rất chậm với đĩa lớn. - Journaling (ghi nhật ký, write-ahead logging): trước khi sửa cấu trúc thật, ghi mô tả các thay đổi vào vùng journal và đánh dấu "commit"; sau đó mới áp vào vị trí thật (checkpoint). Sau sự cố, chỉ cần đọc journal: giao dịch đã commit thì áp lại (replay), chưa commit thì bỏ. ext4 có ba chế độ: journal (ghi cả dữ liệu vào journal, chậm nhất), ordered (mặc định: chỉ journal metadata, nhưng ghi dữ liệu xuống trước khi commit metadata), writeback (nhanh nhất, có thể thấy dữ liệu cũ trong file sau sự cố).

Các hướng khác: copy-on-write file system (Btrfs, ZFS: không bao giờ ghi đè, ghi bản mới rồi đổi con trỏ gốc nguyên tử, có snapshot rẻ) và log-structured (F2FS cho flash: ghi tuần tự mọi thứ như một log, dọn rác định kỳ). Ý tưởng write-ahead log này xuất hiện lại ở database (F04) và ở hệ phân tán.

Lưu trữ flash

SSD và flash nhúng (eMMC, NAND, SD) khác đĩa từ: - Không ghi đè được tại chỗ: phải xóa cả khối lớn (erase block, hàng trăm KB tới vài MB) trước khi ghi lại các trang trong khối. - Mỗi khối chỉ chịu được số lần xóa giới hạn (vài nghìn tới vài trăm nghìn tùy loại). - FTL (flash translation layer) trong bộ điều khiển SSD/eMMC giả lập một thiết bị khối bình thường: ánh xạ địa chỉ logic sang vật lý, wear leveling (dàn đều số lần xóa), garbage collection. Hệ quả: write amplification (ghi 4 KB từ ứng dụng có thể thành ghi nhiều lần hơn trong flash), hiệu năng giảm khi đầy, và lệnh TRIM/discard báo cho FTL khối nào không còn dùng.

Khi đọc từ socket mà chưa có dữ liệu, chương trình có thể làm gì? Phân loại kinh điển (Stevens, UNIX Network Programming):

Mô hình Cách làm Thread bị chặn?

Phân biệt hai khái niệm hay bị nhầm: readiness (sẵn sàng: kernel báo "bây giờ đọc sẽ không chặn", bạn tự gọi read; epoll là mô hình này) và completion (hoàn tất: kernel báo "tôi đã đọc xong vào buffer của bạn"; io_uring, IOCP).

select, poll, epoll

  • select: truyền ba tập bit (đọc, ghi, lỗi) mỗi lần gọi; giới hạn FD_SETSIZE = 1024; kernel quét mọi fd mỗi lần: O(n).
  • poll: mảng struct pollfd, không giới hạn 1024, nhưng vẫn truyền toàn bộ danh sách và quét O(n) mỗi lần.
  • epoll (Linux): đăng ký fd một lần vào một đối tượng epoll (epoll_ctl), kernel giữ danh sách và tự thêm fd vào danh sách sẵn sàng khi có sự kiện; epoll_wait chỉ trả về các fd sẵn sàng: O(số fd sẵn sàng). Tương đương: kqueue trên BSD/macOS.

Đây là khung tối giản của một event loop: bốn pipe, một thread ghi xen kẽ vào chúng, thread chính dùng epoll để phục vụ cả bốn:

// Một thread theo dõi nhiều fd bằng epoll: 4 pipe, một thread khác ghi ngẫu nhiên vào chúng.
// Đây là khung của mọi event loop (nginx, Redis, libuv, Boost.Asio trên Linux).
#include <cstdio>
#include <fcntl.h>
#include <sys/epoll.h>
#include <thread>
#include <unistd.h>

int main() {
    const int K = 4, MSGS = 1000;
    int fds[K][2];
    int ep = epoll_create1(EPOLL_CLOEXEC);
    for (int i = 0; i < K; ++i) {
        if (pipe2(fds[i], O_NONBLOCK | O_CLOEXEC)) return 1;
        epoll_event ev{};
        ev.events = EPOLLIN;          // level-triggered: báo chừng nào còn dữ liệu
        ev.data.u32 = i;              // gắn "ngữ cảnh" vào sự kiện
        epoll_ctl(ep, EPOLL_CTL_ADD, fds[i][0], &ev);
    }
    std::thread producer([&] {
        for (int m = 0; m < MSGS; ++m) {
            char c = 'a' + m % 26;
            while (write(fds[m % K][1], &c, 1) != 1) {}          // pipe đầy thì thử lại
        }
        for (int i = 0; i < K; ++i) close(fds[i][1]);           // đóng đầu ghi → đầu đọc nhận EOF
    });
    int got[K] = {}, open_fds = K, wakeups = 0;
    epoll_event evs[16];
    while (open_fds > 0) {
        int n = epoll_wait(ep, evs, 16, 1000);                  // ngủ tới khi có fd sẵn sàng
        ++wakeups;
        for (int j = 0; j < n; ++j) {
            int i = evs[j].data.u32; char buf[256];
            ssize_t r = read(fds[i][0], buf, sizeof buf);       // đọc hết những gì đang có
            if (r > 0) got[i] += r;
            else if (r == 0) { epoll_ctl(ep, EPOLL_CTL_DEL, fds[i][0], nullptr); close(fds[i][0]); --open_fds; }
        }
    }
    producer.join();
    int total = 0;
    for (int i = 0; i < K; ++i) { std::printf("pipe %d: %d byte\n", i, got[i]); total += got[i]; }
    std::printf("tong %d byte sau %d lan epoll_wait\n", total, wakeups);
    close(ep);
    return total == MSGS ? 0 : 1;
}

1000 byte được nhận qua 88 lần epoll_wait (lần chạy khác: 36; con số phụ thuộc thời điểm hai thread xen nhau): mỗi lần thức dậy, loop xử lý mọi fd sẵn sàng và đọc tất cả dữ liệu đang có. Đây là hiệu ứng gom tự nhiên (natural batching) của event loop: tải càng cao, mỗi lần thức dậy càng làm được nhiều việc, chi phí cố định mỗi lần chia cho nhiều đơn vị.

Hai chế độ báo của epoll: - Level-triggered (mặc định): báo chừng nào fd còn sẵn sàng. Dễ dùng: đọc một phần cũng được, lần epoll_wait sau báo tiếp. - Edge-triggered (EPOLLET): báo khi trạng thái đổi (từ không có sang có dữ liệu). Phải đọc tới khi EAGAIN, nếu không sẽ không bao giờ được báo lại. Giảm số lần thức dậy, dùng trong server hiệu năng cao. EPOLLONESHOT: báo một lần rồi tắt, hữu ích khi nhiều thread dùng chung một epoll.

io_uring

io_uring (Linux 5.1+, 2019) là giao diện I/O bất đồng bộ dựa trên hai ring buffer chia sẻ giữa user space và kernel: - Submission queue (SQ): ứng dụng ghi các yêu cầu (đọc, ghi, accept, send, recv, fsync, timeout...) vào ring. - Completion queue (CQ): kernel ghi kết quả vào ring.

Một lời gọi io_uring_enter có thể nộp hàng trăm yêu cầu và lấy hàng trăm kết quả; với chế độ SQPOLL, một thread kernel liên tục đọc SQ nên ứng dụng không cần system call nào khi đang bận. Có thêm registered buffers/files (bỏ chi phí tra cứu mỗi lần), zero-copy send/receive (bản mới), multishot accept/recv. Thư viện liburing bọc giao diện thô. io_uring hợp nhất I/O file và mạng vào một mô hình completion, nhưng đã có nhiều lỗ hổng bảo mật nên một số môi trường (Android, một số cấu hình container và cloud) tắt nó.

Tín hiệu (signal) trong chương trình nhiều thread

Tín hiệu là cơ chế IPC cũ nhất và khó dùng đúng nhất: handler chạy chen ngang tại điểm bất kỳ, chỉ được gọi hàm async-signal-safe (không malloc, không printf, không khóa mutex). Với process nhiều thread, tín hiệu gửi cho process được giao cho một thread bất kỳ không chặn nó. Mẫu an toàn:

  1. Ở đầu main, trước khi tạo thread: chặn các tín hiệu cần xử lý (pthread_sigmask(SIG_BLOCK, ...)); thread con thừa hưởng mặt nạ.
  2. Nhận tín hiệu một cách đồng bộ: signalfd (đưa vào epoll như một fd bình thường) hoặc một thread riêng gọi sigwait.
  3. Bỏ qua SIGPIPE cho server mạng.

Zero-copy

Gửi một file qua socket theo cách thông thường: read() chép từ page cache vào buffer user, write() chép từ buffer user vào socket buffer của kernel: hai lần chép, hai system call. Các cách bỏ bớt: - sendfile(): kernel chuyển thẳng từ page cache sang socket (web server tĩnh, broker gửi log). - splice() / tee() / vmsplice(): di chuyển dữ liệu giữa fd qua pipe trong kernel. - MSG_ZEROCOPY: gửi từ buffer user mà không chép (kernel ghim trang, báo khi xong); có lợi với buffer lớn (từ khoảng 10 KB trở lên). - mmap file: đọc file như bộ nhớ, không chép qua read. - Kernel bypass (phía dưới): gói nằm trong buffer DMA mà ứng dụng truy cập trực tiếp.

Con đường của một gói qua kernel và cách đi tắt

Quá trình nhận một gói UDP qua kernel stack (rút gọn): NIC DMA vào RX ring → ngắt → NAPI poll trong softirq → tạo sk_buff → xử lý tầng IP (định tuyến, netfilter/iptables) → tầng UDP → tìm socket theo cổng → xếp vào hàng đợi nhận của socket → đánh thức thread đang chờ (epoll) → ứng dụng gọi recvmsg() → chép dữ liệu sang buffer user. Mỗi bước có chi phí; tổng cộng một nhân thường xử lý được khoảng 1–2 triệu gói nhỏ mỗi giây theo đường này.

Các cách giảm chi phí, từ nhẹ tới mạnh: 1. Gom theo lô: recvmmsg()/sendmmsg() (nhiều gói một system call), GRO/GSO (gộp/tách gói trong kernel). 2. Busy polling của socket (SO_BUSY_POLL, net.core.busy_poll): thread chờ quay vòng poll trực tiếp hàng đợi NIC thay vì ngủ chờ ngắt; giảm độ trễ, tốn CPU. 3. io_uring: bớt system call, có recv/send nhiều lần một lần nộp. 4. XDP / AF_XDP: chương trình eBPF xử lý gói ngay trong driver, trước khi tạo sk_buff; AF_XDP đưa gói vào vùng nhớ chung với ứng dụng, không chép. 5. Kernel bypass hoàn toàn (DPDK): driver user space điều khiển NIC qua VFIO, polling, không system call, không ngắt.

Liên hệ EmbeddedI/O và IPC trong firmware và Embedded Linux

Trên RTOS, "I/O multiplexing" tương đương là chờ nhiều nguồn sự kiện: FreeRTOS có queue set (xQueueAddToSet, xQueueSelectFromSet), event group (chờ nhiều bit), hoặc gộp mọi sự kiện vào một queue duy nhất của task (mẫu active object, M08). IPC giữa task là queue, stream buffer, message buffer, task notification. Trên Embedded Linux, các service giao tiếp qua Unix domain socket, D-Bus, hoặc MQTT nội bộ; driver thiết bị được truy cập qua fd (/dev/ttyS*, /dev/spidev*, /dev/i2c-*, GPIO qua /dev/gpiochip* với libgpiod), và có thể đưa tất cả vào một epoll loop cùng socket mạng và timerfd. Đây là kiến trúc điển hình của một gateway.

  • User plane: chọn giữa kernel module (gtp5g, đóng gói GTP-U trong kernel), XDP/AF_XDP, và DPDK/VPP. Hiểu con đường gói qua kernel ở trên là nền để hiểu vì sao từng lựa chọn nhanh hay chậm, và đánh đổi gì (công cụ debug, tính năng của kernel như netfilter, routing, mất đi khi bypass).
  • IPC giữa process trong cùng node: shared memory + ring lock-free (DPDK multi-process dùng hugepage chung giữa primary và secondary process), Unix socket cho kênh điều khiển, memif (shared memory packet interface của VPP/DPDK) để chuyển gói giữa container trên cùng máy mà không qua kernel.
Tự kiểm traMột event loop dùng epoll edge-triggered. Khi nhận EPOLLIN, code gọi read(fd, buf, 4096) đúng một lần. Thỉnh thoảng một kết nối "treo": client đã gửi request nhưng server không xử lý. Vì sao?

Với edge-triggered, epoll chỉ báo khi trạng thái chuyển từ không có dữ liệu sang có dữ liệu. Nếu socket nhận nhiều hơn 4096 byte (hoặc nhiều request liên tiếp) mà code chỉ đọc một lần, phần còn lại nằm trong buffer socket; vì trạng thái vẫn là "có dữ liệu", không có cạnh mới nên epoll không báo nữa cho tới khi client gửi thêm. Sửa: với EPOLLET, luôn đọc lặp tới khi read trả -1 với errno == EAGAIN (fd phải non-blocking), hoặc dùng level-triggered. Tương tự với ghi: chỉ đăng ký EPOLLOUT khi buffer gửi đầy và có dữ liệu chờ.

Máy ảo (VM)

Ảo hóa phần cứng cho nhiều hệ điều hành chạy trên một máy vật lý, mỗi OS tưởng mình có phần cứng riêng. Phần mềm quản lý là hypervisor: - Type 1 (bare-metal): chạy trực tiếp trên phần cứng: VMware ESXi, Xen, Hyper-V. KVM biến chính kernel Linux thành hypervisor (QEMU giả lập thiết bị, KVM chạy CPU). - Type 2 (hosted): chạy như ứng dụng trên OS khác: VirtualBox, VMware Workstation.

CPU hiện đại có hỗ trợ phần cứng (Intel VT-x, AMD-V, ARM EL2): code của máy ảo chạy trực tiếp trên CPU, chỉ các lệnh nhạy cảm mới "thoát" (VM exit) về hypervisor. Bộ nhớ dịch hai tầng (EPT/NPT, nested paging: địa chỉ ảo của khách → địa chỉ vật lý của khách → địa chỉ vật lý thật), nên TLB miss trong VM đắt hơn và hugepage càng quan trọng. I/O là phần đắt nhất: thiết bị giả lập (chậm), virtio (driver ảo hóa chuyên dụng, ring buffer chia sẻ giữa khách và host), hoặc passthrough/SR-IOV (gán thiết bị thật cho VM qua IOMMU, gần như không mất hiệu năng).

Kernel và system call

01Hệ điều hành làm những việc gì?Hay hỏi

Ảo hóa tài nguyên (CPU thành nhiều process, RAM thành nhiều không gian địa chỉ), quản lý đồng thời, lưu trữ bền vững; cộng với bảo vệ (cô lập process, user/kernel) và trừu tượng hóa phần cứng (file, socket).

02System call là gì, diễn ra thế nào?Hay hỏi

Cách ứng dụng yêu cầu kernel làm việc đặc quyền. glibc đặt số hiệu và tham số vào thanh ghi, chạy lệnh syscall (x86-64) / svc (ARM); CPU chuyển sang chế độ kernel tại điểm vào cố định; kernel xử lý, trả kết quả trong thanh ghi; lỗi thì glibc đặt errno. Chi phí ~100 ns cho syscall rỗng (đo được ~100 lần gọi hàm), hơn nhiều cho syscall thật.

03vDSO là gì?

Trang code kernel ánh xạ sẵn vào mọi process để thực hiện một số "system call" trong user space không cần chuyển mức, như clock_gettime, gettimeofday. ~20 ns.

04Monolithic kernel và microkernel khác nhau thế nào?

Monolithic (Linux): mọi dịch vụ chạy trong kernel, gọi trực tiếp, nhanh, nhưng một driver lỗi làm sập cả hệ. Microkernel (QNX, seL4): kernel tối thiểu (lập lịch, IPC), driver và file system là process user, cô lập lỗi, tốn chi phí IPC. RTOS như FreeRTOS là kernel dạng thư viện, không tách user/kernel.

Process và thread

05Process và thread khác nhau thế nào?Hay hỏi

Process có không gian địa chỉ, bảng fd riêng; thread trong cùng process chia sẻ bộ nhớ và fd, riêng thanh ghi, stack, TLS. Thread tạo và chuyển rẻ hơn nhưng không cô lập: một thread crash làm chết cả process. Linux coi cả hai là task tạo bằng clone với cờ chia sẻ khác nhau.

06Các trạng thái của process?

Running, ready (runnable), blocked (chờ I/O, khóa, sleep), zombie (đã thoát chờ cha wait), stopped. ps: R, S, D (ngủ không ngắt được, thường chờ I/O đĩa), Z, T.

07fork và exec hoạt động thế nào? Vì sao tách đôi?Hay hỏi

fork nhân bản process (copy-on-write), trả PID con cho cha, 0 cho con. exec thay chương trình của process hiện tại. Tách đôi để con tự cấu hình môi trường (dup2 chuyển hướng, đóng fd, đổi thư mục, đổi user) giữa hai bước; shell dùng để làm redirect và pipe.

08Copy-on-write sau fork là gì?

Cha và con dùng chung trang vật lý, đánh dấu chỉ đọc; bên nào ghi thì page fault và kernel sao chép riêng trang đó. Đo được: đọc sau fork 0 fault, ghi 64 MB tốn 16.384 fault (mỗi trang một lần).

09Vì sao output printf bị in hai lần sau fork?Hay hỏi

Khi stdout không phải terminal, stdio dùng full buffering; dữ liệu chưa xả nằm trong bộ nhớ process và bị fork sao chép sang con; cả hai xả khi thoát. Sửa: fflush trước fork, dùng _exit trong con.

10Zombie và orphan là gì?Hay hỏi

Zombie: con đã thoát, cha chưa wait, kernel giữ PID và mã thoát; nhiều zombie làm cạn PID. Sửa bằng waitpid, xử lý SIGCHLD hoặc đặt SIG_IGN. Orphan: cha chết trước, con được PID 1 (hoặc subreaper) nhận nuôi và wait. Trong container, PID 1 phải tự dọn zombie (dùng tini).

11Vì sao không nên fork trong process nhiều thread?

Con chỉ có một thread (thread gọi fork); mọi khóa do thread khác giữ (kể cả khóa trong malloc) bị khóa vĩnh viễn trong con. Chỉ an toàn nếu ngay sau đó gọi exec, hoặc dùng posix_spawn.

12Context switch gồm những gì, tốn bao nhiêu?Hay hỏi

Vào kernel, lưu thanh ghi thread cũ, scheduler chọn thread mới, nếu khác process thì đổi bảng trang (có thể mất TLB), khôi phục thanh ghi, quay về user. Trực tiếp ~1–3 µs, gián tiếp thêm do cache/TLB/predictor bị bẩn. Đo được ~1,2 µs mỗi lần trên cùng nhân; đánh thức thread ở nhân khác ~10 lần đắt hơn trong VM.

13Thread-per-connection và event loop: chọn khi nào?Hay hỏi

Thread-per-connection đơn giản, hợp số kết nối nhỏ; vài nghìn trở lên thì tốn stack, chuyển ngữ cảnh (C10K). Event loop với epoll phục vụ hàng trăm nghìn kết nối bằng vài thread; việc nặng đẩy sang thread pool; mỗi nhân một loop để dùng hết CPU.

14Mô hình 1:1, N:1, M:N?

1:1: mỗi thread ứng dụng là một thread kernel (pthread, std::thread). N:1: nhiều green thread trên một thread kernel, một syscall chặn cả nhóm. M:N: nhiều thread ứng dụng trên ít thread kernel (goroutine, coroutine + pool, Seastar).

Lập lịch

15Kể các thuật toán lập lịch và ưu nhược điểm.Hay hỏi

FIFO (đơn giản, convoy effect), SJF/STCF (tối ưu turnaround nhưng cần biết trước, có thể đói), Round Robin (response tốt, slice quá nhỏ tốn overhead), priority (đói, chữa bằng aging), MLFQ (nhiều hàng ưu tiên, hạ hàng việc nặng CPU, học hành vi, định kỳ boost).

16Scheduler của Linux hoạt động thế nào?Hay hỏi

Các class theo thứ tự: Deadline (SCHED_DEADLINE, EDF) > RT (SCHED_FIFO/RR, ưu tiên 1–99) > Fair (SCHED_OTHER). Fair dùng CFS (tới 6.5) rồi EEVDF (từ 6.6): mỗi task có vruntime tăng theo CPU đã dùng chia trọng số nice, chọn task bị thiệt nhất, cây đỏ đen O(log n).

17SCHED_FIFO và SCHED_RR khác nhau thế nào? Nguy hiểm gì?

Cả hai ưu tiên tĩnh, luôn chạy trước task thường. FIFO chạy tới khi chặn hoặc bị ưu tiên cao hơn chiếm; RR thêm time slice giữa task cùng ưu tiên. Vòng lặp vô hạn ở FIFO chiếm trọn nhân, bỏ đói kernel thread; RT throttling mặc định giới hạn 95%.

18Priority inversion là gì, chữa thế nào?Hay hỏi

Task ưu tiên cao H chờ khóa do task thấp L giữ, trong khi task trung bình M chiếm CPU của L, nên H bị chặn gián tiếp bởi M không giới hạn (Mars Pathfinder 1997). Chữa: priority inheritance (L tạm lên ưu tiên của H), priority ceiling, hoặc tránh chia sẻ khóa giữa các mức ưu tiên.

19Rate Monotonic và EDF?

RMS: ưu tiên cố định, chu kỳ ngắn hơn ưu tiên cao hơn; lập lịch được chắc chắn nếu U ≤ n(2^(1/n) − 1) (~69% khi n lớn). EDF: ưu tiên động theo hạn gần nhất; lập lịch được tới U ≤ 100%.

20isolcpus, nohz_full, CPU affinity dùng làm gì?Hay hỏi

Affinity (taskset, pthread_setaffinity_np) ghim thread vào nhân. isolcpus loại nhân khỏi cân bằng tải để chỉ thread ghim tường minh chạy ở đó. nohz_full tắt tick định kỳ khi nhân chỉ có một task. Cùng rcu_nocbs và IRQ affinity, dùng để cô lập nhân cho data plane DPDK.

21Real-time nghĩa là gì?

Đúng hạn và dự đoán được, quan tâm độ trễ tối đa chứ không phải trung bình. Hard real-time: trễ hạn là lỗi; soft: giảm chất lượng. Linux PREEMPT_RT (mainline từ 6.12) cho độ trễ tối đa vài chục µs, đo bằng cyclictest.

Đồng bộ

22Race condition và data race khác nhau thế nào?

Race condition: kết quả phụ thuộc thứ tự xen kẽ (logic sai, kể cả với atomic, ví dụ load rồi store riêng mất 27% cập nhật). Data race: hai truy cập đồng thời không đồng bộ tới cùng vị trí, ít nhất một là ghi, trên biến không atomic, là UB trong C/C++.

23Mutex và spinlock khác nhau thế nào?Hay hỏi

Spinlock chờ bằng cách quay vòng, hợp vùng găng rất ngắn và chủ khóa không ngủ (kernel, ngắt đa nhân). Mutex cho thread chờ ngủ, nhường CPU; trên Linux dựng trên futex: không tranh chấp chỉ là CAS trong user space, tranh chấp mới gọi syscall futex.

24Futex là gì?Hay hỏi

Fast userspace mutex: biến nguyên trong bộ nhớ user + syscall futex(WAIT/WAKE). Đường nhanh (không tranh chấp) chỉ dùng atomic, không vào kernel; chỉ khi phải chờ hoặc đánh thức mới gọi kernel. Nền của pthread mutex, condvar, semaphore trên Linux.

25Mutex và semaphore khác nhau thế nào?Hay hỏi

Mutex có chủ sở hữu (ai khóa người đó mở), dùng cho loại trừ lẫn nhau, có thể có priority inheritance. Semaphore là bộ đếm không chủ, thread này wait thread khác post; dùng đếm tài nguyên (pool N) hoặc báo hiệu (ISR → task).

26Vì sao condition variable phải dùng trong vòng lặp?Hay hỏi

Có thể thức dậy giả (spurious wakeup), và điều kiện có thể đã bị thread khác thay đổi giữa lúc được báo và lúc khóa lại mutex. Luôn while (!cond) cv.wait(lk) hoặc cv.wait(lk, pred). Dữ liệu phải sửa dưới mutex để tránh lost wakeup.

27RCU là gì, dùng khi nào?

Read-copy-update: người đọc không khóa; người ghi tạo bản sao, sửa, đổi con trỏ nguyên tử, giải phóng bản cũ sau grace period khi mọi người đọc cũ đã xong. Cho dữ liệu đọc cực nhiều ghi rất ít: bảng định tuyến, cấu hình; DPDK có rte_rcu_qsbr.

28Reader-writer lock có luôn nhanh hơn mutex khi đọc nhiều không?

Không. Mỗi lần khóa đọc vẫn ghi vào bộ đếm người đọc (một cache line chung), với vùng găng ngắn chi phí này lớn hơn lợi ích. Chỉ có lợi khi vùng đọc dài và đọc áp đảo; nếu không, cân nhắc RCU hoặc dữ liệu theo nhân.

29Producer–consumer với buffer giới hạn giải thế nào?

Mutex + hai condition variable (not_full cho producer, not_empty cho consumer), hoặc hai semaphore đếm ô trống và ô đầy + mutex. Với một producer một consumer có thể dùng ring buffer lock-free với chỉ số atomic.

Deadlock

30Bốn điều kiện của deadlock?Hay hỏi

Mutual exclusion, hold and wait, no preemption, circular wait (Coffman). Phá một điều kiện là tránh được.

31Phòng tránh deadlock trong code thực tế thế nào?Hay hỏi

Thứ tự khóa toàn cục (lockdep kiểm tra trong kernel); std::scoped_lock cho nhiều mutex; không gọi callback hay I/O khi giữ khóa; try_lock có thời hạn rồi nhả và thử lại; một chủ sở hữu dữ liệu + message thay cho khóa; hệ phân tán dùng timeout.

32Livelock và starvation là gì?

Livelock: các thread vẫn chạy nhưng phản ứng lẫn nhau mãi không tiến triển (cùng try_lock, cùng nhả); chữa bằng backoff ngẫu nhiên. Starvation: một thread không bao giờ được tài nguyên vì người khác luôn được ưu tiên; chữa bằng aging, hàng đợi công bằng.

33Debug một chương trình bị treo nghi deadlock thế nào?

CPU 0% gợi ý deadlock (100% gợi ý livelock/vòng lặp). gdb -p pid, thread apply all bt để xem thread nào chờ khóa nào; trường __owner của pthread mutex cho TID đang giữ. Phòng ngừa: TSan phát hiện lock-order inversion.

34Thuật toán Banker là gì?

Thuật toán tránh deadlock của Dijkstra: mỗi tiến trình khai báo nhu cầu tối đa; trước mỗi lần cấp, hệ thống kiểm tra sau khi cấp vẫn còn một thứ tự cho mọi tiến trình hoàn thành (trạng thái an toàn). Ít dùng thực tế vì cần biết trước nhu cầu.

Bộ nhớ và file

35Các thuật toán thay trang? Nghịch lý Belady?Hay hỏi

OPT (đẩy trang dùng lại xa nhất, chuẩn lý thuyết), FIFO, LRU, Clock (xấp xỉ LRU bằng bit Accessed), LFU. Nghịch lý Belady: với FIFO, thêm khung có thể tăng số fault (chuỗi 1 2 3 4 1 2 5 1 2 3 4 5: 9 fault với 3 khung, 10 với 4). LRU không bị.

36Thrashing là gì?

Tổng working set vượt RAM, hệ thống liên tục đẩy trang rồi cần lại ngay; đĩa 100%, CPU rảnh, mọi thứ chậm hàng trăm lần. Giảm tải, thêm RAM, hoặc tắt swap để thất bại sớm.

37Overcommit và OOM killer?Hay hỏi

Linux cho tổng bộ nhớ ảo cấp vượt RAM + swap vì cấp phát lười; malloc gần như không trả NULL. Khi trang thật sự chạm vượt RAM, OOM killer giết process có oom_score cao nhất. Điều chỉnh bằng oom_score_adj; cgroup memory.max kích hoạt OOM trong container (OOMKilled).

38Buddy allocator và slab allocator?

Buddy quản lý khung vật lý theo khối lũy thừa 2, gộp hai khối bạn khi trống. Slab (SLUB) chia trang từ buddy thành cache đối tượng cùng kích thước (task_struct, sk_buff), cấp/giải phóng nhanh, ít phân mảnh.

39malloc hoạt động thế nào? Vì sao đổi sang jemalloc/tcmalloc?

Xin vùng lớn từ kernel (brk, hoặc mmap cho khối ≥128 KB), tự chia theo size class, cache theo thread (tcache), nhiều arena. jemalloc/tcmalloc/mimalloc giảm tranh chấp đa thread và phân mảnh cho process chạy lâu; tốt nhất vẫn là tránh cấp phát trên đường nóng.

40Inode là gì? Hard link và symlink khác nhau thế nào?Hay hỏi

Inode chứa metadata và vị trí khối dữ liệu, không chứa tên; thư mục ánh xạ tên → inode. Hard link: thêm tên cho cùng inode (dữ liệu còn tới khi hết tên và hết fd mở). Symlink: file chứa đường dẫn, có thể treo, qua được file system khác.

41File descriptor, open file description, inode quan hệ thế nào?

fd là chỉ số trong bảng của process; trỏ tới open file description (offset, cờ) trong kernel; description trỏ tới inode. fork và dup chia sẻ description (chung offset); hai lần open riêng có hai description.

42write() thành công có nghĩa dữ liệu đã an toàn trên đĩa không?Hay hỏi

Không. write chỉ chép vào page cache và đánh dấu bẩn; writeback ghi sau vài giây. Cần fsync/fdatasync (hoặc O_SYNC/O_DSYNC). Ghi file nguyên tử: file tạm → fsync → rename → fsync thư mục. Lỗi fsync phải coi là nghiêm trọng.

43Journaling là gì?

Ghi mô tả thay đổi vào journal và commit trước khi sửa cấu trúc thật; sau sự cố replay giao dịch đã commit, bỏ giao dịch dở. ext4 ordered (mặc định) journal metadata, ghi dữ liệu trước khi commit metadata. Cùng ý tưởng với WAL của database.

44Flash khác đĩa từ thế nào?

Không ghi đè tại chỗ, phải xóa cả erase block; số lần xóa giới hạn. FTL ánh xạ logic → vật lý, wear leveling, garbage collection; gây write amplification; TRIM báo khối không dùng. File system cho flash: F2FS, UBIFS, LittleFS.

I/O và container

45select, poll, epoll khác nhau thế nào?Hay hỏi

select: tập bit giới hạn 1024 fd, truyền lại và quét O(n) mỗi lần. poll: mảng không giới hạn nhưng vẫn O(n). epoll: đăng ký fd một lần, kernel duy trì danh sách sẵn sàng, epoll_wait trả về O(số fd sẵn sàng).

46Level-triggered và edge-triggered trong epoll?Hay hỏi

Level: báo chừng nào fd còn sẵn sàng, dễ dùng. Edge (EPOLLET): chỉ báo khi chuyển trạng thái; phải đọc/ghi tới EAGAIN với fd non-blocking, nếu không sẽ không được báo lại và kết nối "treo".

47io_uring khác epoll thế nào?Hay hỏi

epoll là readiness: báo fd sẵn sàng, ứng dụng tự gọi read/write (một syscall mỗi thao tác). io_uring là completion: hai ring chia sẻ (SQ, CQ), nộp nhiều thao tác một lần, kernel thực hiện và báo kết quả; SQPOLL không cần syscall; dùng cho cả file và mạng.

48Xử lý tín hiệu an toàn trong chương trình nhiều thread?

Chặn tín hiệu ở main trước khi tạo thread (pthread_sigmask), nhận đồng bộ bằng signalfd (đưa vào epoll) hoặc thread riêng gọi sigwait. Handler truyền thống chỉ được gọi hàm async-signal-safe. Server mạng bỏ qua SIGPIPE.

49Các cơ chế IPC trên Linux? Nhanh nhất là gì?

Pipe, FIFO, Unix domain socket (truyền được fd bằng SCM_RIGHTS), TCP/UDP, shared memory (shm_open/memfd + mmap), POSIX message queue, signal, eventfd. Shared memory nhanh nhất vì không chép, nhưng phải tự đồng bộ (atomic, futex, ring lock-free, eventfd để báo).

50Zero-copy trên Linux có những cách nào?

sendfile (page cache → socket), splice/tee/vmsplice, MSG_ZEROCOPY (buffer lớn), mmap file, io_uring registered buffers và zero-copy send, AF_XDP UMEM, kernel bypass DPDK.

51Container khác VM thế nào? Được xây từ gì?Hay hỏi

VM có kernel riêng trên hypervisor, cô lập mạnh, nặng. Container là process chung kernel host, cô lập bằng namespace (pid, net, mnt, uts, ipc, user, cgroup) và giới hạn bằng cgroup (cpu, memory, io, pids, cpuset), cộng overlayfs, seccomp, capabilities. Nhẹ, khởi động nhanh, cô lập yếu hơn.

52CPU throttling trong Kubernetes là gì?Hay hỏi

limits.cpu được thực hiện bằng quota cgroup (cpu.max) theo chu kỳ 100 ms; dùng hết quota thì mọi thread của pod bị dừng tới chu kỳ sau, gây gai độ trễ hàng chục ms. Với data plane: pod Guaranteed + CPU Manager static để có nhân độc quyền; kiểm tra nr_throttled trong cpu.stat.

53Linux và RTOS khác nhau thế nào?Hay hỏi

Linux: đa dụng, thông lượng, cần MMU, process cô lập, cấp phát động, đầy đủ driver/mạng/file; độ trễ tối đa ms (vài chục µs với PREEMPT_RT). RTOS: nhỏ (KB), chạy trên MCU, task chung không gian địa chỉ, ưu tiên cố định preemptive, độ trễ µs xác định, cấp phát tĩnh.

Networking và 5G

54Vì sao data plane mạng tránh system call và ngủ?Hay hỏi

Syscall ~100 ns trở lên, đường qua stack kernel vài trăm ns tới µs; ngủ rồi được đánh thức tốn µs tới chục µs. Ở hàng triệu gói mỗi giây, mỗi gói chỉ có vài chục tới vài trăm ns. Dùng gom lô (recvmmsg), busy poll, io_uring, AF_XDP, DPDK.

55Cấu hình OS điển hình cho một UPF dựa trên DPDK?

Tham số kernel: isolcpus, nohz_full, rcu_nocbs cho nhân data plane, hugepage 1 GB, intel_iommu=on iommu=pt; NIC gắn vfio-pci; IRQ affinity ra nhân housekeeping; thread lcore ghim nhân; mlockall; trên Kubernetes: Guaranteed, CPU Manager static, Topology Manager single-numa-node, SR-IOV + Multus, hugepages resource.

56Control plane 5G dùng mô hình I/O nào?

Event loop (epoll hoặc io_uring), thường mỗi nhân một loop hoặc loop + thread pool. Giao diện: SCTP cho N2 (NGAP), UDP cho N4 (PFCP), HTTP/2 trên TCP cho SBI. Mọi chờ đợi giữa NF đều bất đồng bộ có timeout.

57Một container 5G chạy tốt trên máy dev nhưng bị OOMKilled trên cụm. Hướng điều tra?

So sánh RSS thật dưới tải với limits.memory; kiểm tra cache nội bộ không giới hạn, phân mảnh allocator (allocated vs resident), bộ nhớ socket kernel tính vào cgroup, hugepage có bị tính nhầm không; đọc memory.events và memory.stat của cgroup.
