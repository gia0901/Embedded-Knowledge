Một type để quan sát mọi thứ

Nhiều ví dụ trong module dùng một type in ra mỗi thao tác vòng đời. Đây là công cụ tốt nhất để tự trả lời các câu hỏi "chỗ này copy hay move?", "đối tượng chết lúc nào?" thay vì đoán:

#include <cstdio>
// In ra mọi thao tác vòng đời để quan sát
struct Tracer {
    const char* name;
    explicit Tracer(const char* n) : name(n) { std::printf("  ctor  %s\n", name); }
    Tracer(const Tracer& o) : name(o.name) { std::printf("  copy  %s\n", name); }
    Tracer(Tracer&& o) noexcept : name(o.name) { std::printf("  move  %s\n", name); }
    Tracer& operator=(const Tracer& o) { name = o.name; std::printf("  copy= %s\n", name); return *this; }
    Tracer& operator=(Tracer&& o) noexcept { name = o.name; std::printf("  move= %s\n", name); return *this; }
    ~Tracer() { std::printf("  dtor  %s\n", name); }
};

Tất cả kết quả in trong module là kết quả chạy thật với GCC 13, -std=c++20 -O2.

Bài 1 · Đối tượng, vòng đời và khởi tạo

Bốn loại thời gian lưu trữ

Storage duration Ví dụ Sống từ … tới …
Automatic Biến cục bộ, tham số Khi khai báo → hết khối {} (hủy theo thứ tự ngược)
Static Biến toàn cục, static trong namespace/class/hàm Trước main (hoặc lần đầu đi qua, với static cục bộ) → sau main
Thread thread_local Theo vòng đời thread
Dynamic new, make_unique Từ lúc cấp phát → khi delete / smart pointer hủy

Vòng đời (lifetime) của đối tượng bắt đầu khi khởi tạo xong và kết thúc khi destructor bắt đầu chạy. Truy cập đối tượng ngoài vòng đời là undefined behavior, kể cả khi bộ nhớ vẫn còn đó (Bài 2, Bài 8).

Các dạng khởi tạo

int a;            // default-init: biến cục bộ → giá trị KHÔNG xác định; biến static → 0
int b{};          // value-init: 0
int c = 5;        // copy-init
int d(5);         // direct-init
int e{5};         // direct-list-init: cấm thu hẹp kiểu (narrowing)
int f{5.7};       // LỖI biên dịch: double → int bị thu hẹp
std::vector<int> v1(3, 7);   // 3 phần tử, mỗi phần tử 7
std::vector<int> v2{3, 7};   // 2 phần tử: 3 và 7 (ưu tiên constructor initializer_list)

struct Config { int baud = 115200; bool parity = false; int retries = 3; };
Config cfg{.baud = 9600, .retries = 5};   // C++20 designated init cho aggregate

Những điểm hay bị hỏi:

  • Biến cục bộ kiểu cơ bản không có giá trị khởi tạo nếu không viết gì. Đọc nó là UB. Mặc định hãy khởi tạo bằng {}.
  • {} cấm thu hẹp kiểu, nhưng với type có constructor nhận std::initializer_list thì {} ưu tiên constructor đó (ví dụ v2 ở trên). B01 Item 7 phân tích kỹ.
  • Most vexing parse: Timer t(); khai báo một hàm tên t trả về Timer, không phải đối tượng. Dùng Timer t; hoặc Timer t{};.

Thứ tự khởi tạo đối tượng static

  • Trong một file: theo thứ tự khai báo.
  • Giữa các file: không xác định. Một đối tượng toàn cục ở a.cpp dùng đối tượng toàn cục ở b.cpp trong constructor có thể gặp đối tượng chưa được dựng: static initialization order fiasco.
// logger.cpp
Logger g_logger("app.log");
// config.cpp
Config g_config;      // Config::Config() gọi g_logger.write(...)  → có thể chạy TRƯỚC khi g_logger được dựng

Cách sửa:

Logger& logger() {
    static Logger instance("app.log");   // dựng ở lần gọi đầu tiên, thread-safe từ C++11
    return instance;
}

Hoặc với dữ liệu khởi tạo được lúc biên dịch: constinit (C++20) đảm bảo biến được khởi tạo tĩnh (không chạy code lúc khởi động), loại bỏ hoàn toàn vấn đề thứ tự. Trên MCU, đây cũng là cách giảm thời gian khởi động và tránh constructor chạy trước khi clock và RAM được thiết lập (M02 Bài 4).

Thứ tự hủy ngược thứ tự dựng: đối tượng static được hủy sau main theo thứ tự ngược; thành viên của class được hủy theo thứ tự ngược với thứ tự khai báo (M14 Bài 4 về thread là thành viên cuối).

Thứ tự khởi tạo thành viên theo thứ tự khai báo trong class, không theo thứ tự viết trong danh sách khởi tạo. -Wreorder cảnh báo khi hai thứ tự khác nhau, vì dùng thành viên khai báo sau để khởi tạo thành viên khai báo trước là đọc giá trị chưa khởi tạo.

Tự kiểm tra`struct S { int size; std::vector data; S(int n) : data(n), size(data.size()) {} };` có vấn đề gì?

Không có vấn đề: size được khai báo trước nên được khởi tạo trước data bất kể thứ tự trong danh sách khởi tạo… và đó chính là vấn đề: size(data.size()) chạy khi data chưa được dựng, gọi hàm thành viên trên đối tượng chưa tồn tại (UB). Sửa: khởi tạo từ tham số (size(n)), hoặc đổi thứ tự khai báo; bật -Wreorder (có trong -Wall).

Ý chínhÝ chính của Bài 1
  • Bốn storage duration; vòng đời bắt đầu khi khởi tạo xong, kết thúc khi destructor bắt đầu.
  • Biến cục bộ cơ bản không khởi tạo là rác: dùng {}; {} cấm thu hẹp nhưng ưu tiên initializer_list.
  • Static giữa các file: thứ tự không xác định → static cục bộ trong hàm hoặc constinit.
  • Thành viên khởi tạo theo thứ tự khai báo, hủy ngược lại.

Bài 2 · Value category và tham chiếu

lvalue, prvalue, xvalue

Mỗi biểu thức (không phải mỗi biến) có một value category:

Category Ý nghĩa Ví dụ Lấy địa chỉ được? Move từ nó?
lvalue Có danh tính, tồn tại sau biểu thức x, *p, v[0], std::cout, hàm trả T& Có Không (trừ khi std::move)
prvalue Giá trị thuần, tạm thời 42, x + 1, make(), Tracer("a") Không Có (thực ra C++17: không có đối tượng tạm, khởi tạo thẳng đích)
xvalue Có danh tính nhưng sắp hết hạn std::move(x), hàm trả T&& Không Có

glvalue = lvalue + xvalue (có danh tính); rvalue = prvalue + xvalue (move được). Một quy tắc dễ nhớ: có tên thì là lvalue, kể cả khi kiểu của nó là tham chiếu rvalue. Trong void f(Widget&& w), biểu thức w bên trong hàm là lvalue; muốn move tiếp phải viết std::move(w).

Quy tắc gắn tham chiếu

Tham chiếu Gắn được với
T& lvalue (không const)
const T& Mọi thứ (lvalue, rvalue), nên dùng cho tham số chỉ đọc
T&& (T cụ thể) rvalue
T&& với T được suy luận (template, auto&&) Mọi thứ: forwarding reference (B01 Item 24)

Kéo dài vòng đời đối tượng tạm, và khi nó không áp dụng

Gắn một prvalue vào const T& hoặc T&& cục bộ kéo dài vòng đời đối tượng tạm tới hết phạm vi của tham chiếu. Nhưng quy tắc này không truyền qua lời gọi hàm. Chạy thật:

Tracer make(const char* n) { return Tracer(n); }
const Tracer& pick(const Tracer& a) { return a; }

{ const Tracer& r = make("tmp"); /* ...dùng r */ }        // (4)
{ const Tracer& d = pick(make("x")); /* ...dùng d */ }    // (5)

4) const Tracer& r = make("tmp"); (kéo dài vòng đời)
  ctor  tmp
  ...dùng r
  dtor  tmp                      ← hủy khi r hết phạm vi: an toàn
5) const Tracer& d = pick(make("x")); (dangling)
  ctor  x
  dtor  x                        ← hủy ngay cuối câu lệnh
  ...d đã chết ở đây              ← d là tham chiếu treo

Ở (5), đối tượng tạm chỉ được gắn vào tham số a của pick; vòng đời của nó kết thúc ở cuối biểu thức đầy đủ, d tham chiếu vào vùng nhớ đã chết. GCC 13 có cảnh báo -Wdangling-reference cho một số trường hợp như vậy, nhưng không bắt được tất cả.

Các dạng tham chiếu treo hay gặp

const std::string& name() { std::string s = "x"; return s; }      // trả tham chiếu tới biến cục bộ
std::string_view sv = std::string("abc") + "def";                   // view vào chuỗi tạm đã chết
auto& first = get_vector()[0];                                       // vector tạm chết cuối câu lệnh
for (auto& x : make_config().items()) { ... }                        // trước C++23: Config tạm chết trước vòng lặp
struct Holder { const Widget& w; };  Holder h{Widget{}};             // thành viên tham chiếu gắn vào đối tượng tạm
auto f = [&local]() { ... };  return f;                              // lambda bắt tham chiếu tới biến cục bộ

Vòng for trên phần tử của đối tượng tạm là trường hợp tinh vi nhất: make_config() trả đối tượng tạm, .items() trả tham chiếu vào bên trong nó; chỉ đối tượng mà tham chiếu ẩn của vòng for gắn vào (kết quả của .items()) được kéo dài, còn Config tạm thì chết. C++23 sửa riêng trường hợp này (kéo dài mọi đối tượng tạm trong biểu thức khởi tạo của range-for); code cần chạy với chuẩn cũ hơn thì giữ đối tượng trong một biến có tên.

Công cụ bắt lỗi: -fsanitize=address (với detect_stack_use_after_return=1) bắt phần lớn trường hợp dùng vùng nhớ đã chết khi test.

Tự kiểm traTrong `void consume(std::string&& s) { store(s); }`, `store` có hai overload `store(const std::string&)` và `store(std::string&&)`. Overload nào được gọi và vì sao?

store(const std::string&): biểu thức s có tên nên là lvalue, dù kiểu khai báo là std::string&&. Chuỗi bị copy chứ không move. Muốn move phải viết store(std::move(s)).

Ý chínhÝ chính của Bài 2
  • lvalue (có danh tính), prvalue (giá trị tạm), xvalue (sắp hết hạn: std::move(x)).
  • Có tên là lvalue, kể cả biến kiểu T&&.
  • const T& gắn được mọi thứ; T&& suy luận là forwarding reference.
  • Kéo dài vòng đời chỉ áp dụng khi gắn trực tiếp vào tham chiếu cục bộ, không qua lời gọi hàm.
  • Cảnh giác: trả tham chiếu tới cục bộ, view vào tạm, range-for trên phần tử của tạm, lambda bắt tham chiếu.

Bài 3 · RAII và các hàm thành viên đặc biệt

RAII

Resource Acquisition Is Initialization: gắn vòng đời của tài nguyên (bộ nhớ, file, khóa, ngắt bị tắt, chip select) vào vòng đời của một đối tượng. Lấy tài nguyên trong constructor, trả trong destructor. Vì destructor của đối tượng automatic luôn chạy khi ra khỏi phạm vi (kể cả qua return sớm hay exception), tài nguyên không bao giờ bị quên. Đây là ý tưởng quan trọng nhất của C++; M14 Bài 4 áp dụng cho tài nguyên Linux, M08 Bài 6 cho firmware.

Sáu hàm đặc biệt và quy tắc 0/3/5

Compiler có thể tự sinh: default constructor, destructor, copy constructor, copy assignment, move constructor, move assignment.

  • Rule of Zero: class chỉ chứa thành viên tự quản lý tài nguyên (std::string, std::vector, unique_ptr, unique_fd…) không viết hàm đặc biệt nào; các hàm compiler sinh ra tự làm đúng. Đây là mặc định nên hướng tới.
  • Rule of Five: class trực tiếp quản lý một tài nguyên thô (con trỏ new, handle C) phải tự viết đủ năm: destructor, copy ctor, copy assignment, move ctor, move assignment (hoặc = delete những cái không hỗ trợ). Rule of Three là phiên bản trước C++11 (chưa có move).

Viết đúng một class quản lý tài nguyên

#include <algorithm>
#include <cstddef>
#include <cstdint>
#include <utility>

class Buffer {
public:
    explicit Buffer(std::size_t n) : size_(n), data_(n ? new std::uint8_t[n]{} : nullptr) {}
    ~Buffer() { delete[] data_; }

    Buffer(const Buffer& o) : Buffer(o.size_) {                    // copy: cấp phát mới, chép nội dung
        std::copy(o.data_, o.data_ + size_, data_);
    }
    Buffer(Buffer&& o) noexcept                                     // move: lấy tài nguyên, để o rỗng
        : size_(std::exchange(o.size_, 0)), data_(std::exchange(o.data_, nullptr)) {}

    Buffer& operator=(Buffer o) noexcept {                          // copy-and-swap: nhận THEO GIÁ TRỊ
        swap(o);                                                    // (o đã được copy hoặc move vào)
        return *this;                                               // tài nguyên cũ hủy theo o
    }
    void swap(Buffer& o) noexcept { std::swap(size_, o.size_); std::swap(data_, o.data_); }

    std::size_t size() const noexcept { return size_; }
    std::uint8_t& operator[](std::size_t i) { return data_[i]; }
    const std::uint8_t& operator[](std::size_t i) const { return data_[i]; }
private:
    std::size_t size_;
    std::uint8_t* data_;
};

Những điểm thường bị hỏi:

  • Copy-and-swap: một toán tử gán nhận tham số theo giá trị phục vụ cả copy (người gọi truyền lvalue → tham số được copy) lẫn move (truyền rvalue → tham số được move). Tự gán (b = b) an toàn mà không cần kiểm tra this == &o, và có strong exception guarantee: nếu copy ném (hết bộ nhớ), *this không bị đụng tới.
  • Move để lại đối tượng nguồn ở trạng thái hợp lệ (size_ = 0, data_ = nullptr) để destructor của nó không giải phóng hai lần.
  • noexcept trên move để container dùng move khi phát triển (Bài 4).
  • Đã kiểm tra với AddressSanitizer: copy, move, tự gán, gán chéo, không rò và không giải phóng hai lần.

So với Rule of Zero cùng chức năng:

class Buffer0 {
public:
    explicit Buffer0(std::size_t n) : data_(n) {}
    std::size_t size() const noexcept { return data_.size(); }
    std::uint8_t& operator[](std::size_t i) { return data_[i]; }
private:
    std::vector<std::uint8_t> data_;      // vector đã đúng sẵn cả 5 hàm
};

Chỉ viết Rule of Five khi có lý do (giao diện với C API, cấu trúc dữ liệu tự cài đặt, yêu cầu bố cục bộ nhớ đặc biệt).

Tự kiểm traMột class có `std::vector data;` và `virtual ~Base() = default;`. Trả về đối tượng đó theo giá trị từ hàm trong một vòng lặp chậm hơn dự kiến. Vì sao?

Khai báo destructor (dù là = default) làm compiler không sinh move.   • Rule of Zero mặc định; Rule of Five khi quản lý tài nguyên thô trực tiếp.
  • Copy-and-swap: một toán tử gán cho cả copy/move, an toàn tự gán, strong guarantee.
  • Move để nguồn ở trạng thái hợp lệ; noexcept.
  • Khai báo destructor làm mất move tự sinh.

Bài 4 · Move semantics và copy elision

std::move không di chuyển gì cả

std::move(x) chỉ là một cast sang rvalue reference (static_cast<T&&>(x)): nó cho phép overload nhận T&& được chọn. Việc di chuyển thật sự (lấy tài nguyên) do move constructor/assignment của type làm. Hệ quả:

  • std::move trên đối tượng const không move được: const T&& không gắn vào T&&, overload copy được chọn (B01 Item 23).
  • Sau khi bị move, đối tượng ở trạng thái hợp lệ nhưng không xác định (valid but unspecified): chỉ được hủy, gán giá trị mới, hoặc gọi hàm không có tiền điều kiện (clear(), size()). Thư viện chuẩn đảm bảo vậy cho type của nó; type của bạn nên làm tương tự.

Copy elision: nhiều khi không có copy lẫn move

Chạy thật với Tracer:

Tracer make(const char* n)       { return Tracer(n); }            // trả prvalue
Tracer make_named(const char* n) { Tracer t(n); return t; }       // trả biến có tên
Tracer make_moved(const char* n) { Tracer t(n); return std::move(t); }

1) Tracer a = make("a");          2) Tracer b = make_named("b");     3) Tracer c = make_moved("c");
  ctor  a                           ctor  b                            ctor  c
  dtor  a                           dtor  b                            move  c
                                                                       dtor  c
                                                                       dtor  c
  • (1) Trả prvalue: từ C++17, elision là bắt buộc: đối tượng được dựng thẳng vào biến của người gọi, không copy/move nào, kể cả khi type không copy/move được.
  • (2) NRVO (named return value optimization): compiler được phép (không bắt buộc) dựng t thẳng vào chỗ của người gọi. GCC/Clang làm khi chỉ có một biến được trả về trên mọi nhánh.
  • (3) return std::move(t) chặn NRVO và ép một lần move. GCC cảnh báo -Wpessimizing-move. Quy tắc: không bao giờ std::move khi return biến cục bộ; ngôn ngữ đã tự coi nó là rvalue nếu không elide được.

push_back, emplace_back và noexcept

6) vector push_back lvalue / rvalue / emplace_back       (đã reserve trước)
  ctor  t
  copy  t      ← push_back(t): t là lvalue → copy
  move  t      ← push_back(std::move(t)) → move
  ctor  r
  move  r      ← push_back(Tracer("r")): dựng tạm, rồi move vào

Khi vector hết chỗ và phải cấp phát lại, nó chuyển các phần tử cũ sang vùng mới. Để giữ đảm bảo "nếu ném exception thì vector như cũ", nó chỉ move nếu move constructor là noexcept; nếu không, nó copy. Đo thật, thêm 1000 phần tử (chứa std::string) không reserve:

noexcept move    copies=0     moves=1023
move có thể ném  copies=1023  moves=0

Chỉ khác nhau ở một từ khóa noexcept, nhưng phiên bản thứ hai copy mọi chuỗi mỗi lần vector lớn lên. Move constructor do compiler sinh tự động là noexcept nếu mọi thành viên đều move noexcept.

Perfect forwarding (tóm tắt)

Hàm template nhận T&& (forwarding reference) và chuyển tiếp nguyên value category bằng std::forward<T>(arg): lvalue vẫn là lvalue, rvalue vẫn là rvalue. Đây là cách emplace_back, make_unique truyền tham số tới constructor. Chi tiết và bẫy: B01 Item 24–30.

template <class... Args>
std::unique_ptr<Widget> make_widget(Args&&... args) {
    return std::make_unique<Widget>(std::forward<Args>(args)...);
}
Tự kiểm tra`std::vector v; std::string s = "hello"; v.push_back(std::move(s)); std::cout << s.size();` in ra gì?

Không xác định theo chuẩn (trạng thái hợp lệ nhưng không xác định); với libstdc++ thực tế là 0 vì bộ nhớ đã được chuyển đi (với chuỗi ngắn trong SSO thì nội dung được chép rồi chuỗi nguồn được đặt rỗng). Đoạn code hợp lệ (gọi size() không có tiền điều kiện), nhưng dựa vào giá trị đó là sai thiết kế. Sau khi move, hãy gán giá trị mới trước khi dùng lại.

Ý chínhÝ chính của Bài 4
  • std::move chỉ là cast; move thật do move constructor/assignment.
  • Moved-from: hợp lệ nhưng không xác định; chỉ hủy, gán lại, hoặc gọi hàm không tiền điều kiện.
  • C++17: trả prvalue elision bắt buộc; NRVO tùy compiler; không return std::move(local).
  • emplace_back dựng tại chỗ; move noexcept để vector move thay vì copy khi lớn lên.
  • std::forward giữ nguyên value category trong template.

Bài 5 · Smart pointer

std::unique_ptr: sở hữu độc quyền, chi phí bằng 0

  • Không copy được, chỉ move: đúng một chủ tại mỗi thời điểm.
  • Kích thước bằng con trỏ thô (đo được 8 byte trên x86-64) khi deleter không có trạng thái; hủy bằng delete (hoặc delete[] với unique_ptr<T[]>).
  • Deleter tùy chỉnh cho tài nguyên không phải bộ nhớ: dùng struct không trạng thái để giữ kích thước 8 byte (unique_ptr<FILE, decltype(&fclose)> phải lưu thêm con trỏ hàm, 16 byte). M14 Bài 4 có ví dụ.
  • Là kiểu trả về tự nhiên cho factory; chuyển sang shared_ptr được nếu sau này cần chia sẻ.

std::shared_ptr: đồng sở hữu

 shared_ptr<T> (16 byte)                      control block
 ┌───────────────┬──────────────────┐         ┌───────────────────────────┐
 │ T* (đối tượng)│ con trỏ ─────────┼────────▶│ strong count (atomic)     │
 └───────────────┴──────────────────┘         │ weak count (atomic)       │
                                              │ deleter, allocator        │
                                              │ [T nằm ngay đây nếu dùng  │
                                              │  make_shared]             │
                                              └───────────────────────────┘
  • Hai con trỏ (16 byte): một tới đối tượng, một tới control block chứa bộ đếm.
  • Mỗi lần copy/hủy là một thao tác atomic trên bộ đếm: rẻ nhưng không miễn phí, nhất là khi nhiều thread cùng chạm (cache line của bộ đếm bị giành giữa các nhân).
  • make_shared cấp phát đối tượng và control block trong một lần (nhanh hơn, ít phân mảnh). Đổi lại: vùng nhớ của đối tượng chỉ được trả khi cả weak_ptr cuối cùng cũng hết, vì chúng nằm chung khối; với đối tượng lớn có weak_ptr sống lâu, đây là bộ nhớ bị giữ lại.
  • Thread-safety: bộ đếm được cập nhật atomic, nên các thread giữ các bản sao khác nhau của cùng một shared_ptr là an toàn. Nhiều thread cùng đọc/ghi một biến shared_ptr thì không (cần mutex hoặc std::atomic<std::shared_ptr<T>> C++20). Đối tượng được trỏ tới không tự trở nên thread-safe (M05 Bài 9 có cài đặt bộ đếm).

Chu trình và std::weak_ptr

Hai đối tượng giữ shared_ptr tới nhau thì bộ đếm không bao giờ về 0. Chạy thật:

struct Node { std::shared_ptr<Node> next; std::weak_ptr<Node> prev; ~Node() { std::puts("  ~Node"); } };

{ auto a = std::make_shared<Node>(); auto b = std::make_shared<Node>(); a->next = b; b->next = a; }
{ auto a = std::make_shared<Node>(); auto b = std::make_shared<Node>(); a->next = b; b->prev = a; }

weak_ptr quan sát mà không giữ sống; dùng phải lock() để lấy shared_ptr (rỗng nếu đối tượng đã chết). Dùng cho: con trỏ ngược (cha ← con), cache, observer, callback không muốn kéo dài vòng đời đối tượng (M14 Bài 5).

enable_shared_from_this

Một hàm thành viên cần đưa shared_ptr tới chính mình ra ngoài (đăng ký callback bất đồng bộ) không được viết std::shared_ptr<Widget>(this): việc đó tạo control block thứ hai, đối tượng bị xóa hai lần. Kế thừa std::enable_shared_from_this<Widget> và gọi shared_from_this() (hoặc weak_from_this()). Điều kiện: đối tượng phải đang được một shared_ptr sở hữu; gọi trong constructor hoặc trên đối tượng tạo trên stack ném std::bad_weak_ptr (C++17).

Tự kiểm traVì sao `std::make_unique(...)` được khuyên dùng thay vì `std::unique_ptr(new T(...))`?

  • shared_ptr: 16 byte, control block, đếm atomic; make_shared một lần cấp phát nhưng giữ bộ nhớ tới weak cuối.
  • Bản sao khác nhau an toàn giữa thread; một biến dùng chung thì không.
  • Chu trình rò bộ nhớ: phá bằng weak_ptr.
  • enable_shared_from_this thay cho shared_ptr(this).

Bài 6 · Mô hình đối tượng: bố cục, vtable, slicing

Bố cục và padding

Thành viên được đặt theo thứ tự khai báo, mỗi thành viên căn theo yêu cầu căn chỉnh (alignment) của kiểu nó; compiler chèn padding khi cần. Đo thật trên x86-64:

struct Padded    { char a; double b; char c; };   // 1 + 7 pad + 8 + 1 + 7 pad = 24
struct Reordered { double b; char a; char c; };   // 8 + 1 + 1 + 6 pad          = 16

sizeof Padded=24 Reordered=16

Sắp thành viên từ lớn tới nhỏ tiết kiệm bộ nhớ, đáng kể khi có mảng hàng triệu phần tử hoặc trên MCU ít RAM. alignof(T) cho yêu cầu căn chỉnh; offsetof(T, m) cho vị trí thành viên (chỉ đảm bảo với kiểu standard-layout).

Lớp rỗng và EBO

sizeof Empty=1 WithEmpty=8 WithNUA=4
  • Đối tượng rỗng vẫn có kích thước tối thiểu 1 byte (mỗi đối tượng phải có địa chỉ riêng).
  • Làm thành viên, nó chiếm 1 byte cộng padding: struct { int x; Empty e; } thành 8 byte.
  • Empty base optimization: kế thừa từ lớp rỗng thì không tốn byte nào. C++20 có [[no_unique_address]] cho thành viên, đạt cùng hiệu quả (4 byte ở trên). Thư viện chuẩn dùng kỹ thuật này để allocator, deleter, comparator rỗng không làm container và unique_ptr to ra.

Hàm ảo và vtable

 ┌──────────────┐                          ┌──────────────────────────────┐

  • Class có ít nhất một hàm ảo: mỗi đối tượng có thêm một con trỏ ẩn vptr (sizeof(Poly) = 16 thay vì 4); mỗi class có một vtable chứa địa chỉ các hàm ảo.
  • Gọi hàm ảo qua con trỏ/tham chiếu: đọc vptr → đọc mục trong vtable → gọi gián tiếp. Chi phí trực tiếp nhỏ (vài nano giây), chi phí thật nằm ở chỗ không inline được và khó dự đoán nhánh khi kiểu thay đổi liên tục. Compiler devirtualize được khi biết chắc kiểu (đối tượng cục bộ, class final).
  • Trên MCU: vtable nằm trong Flash, mỗi đối tượng thêm 4 byte RAM; chấp nhận được trong đa số trường hợp (M04 Bài 4 so sánh với CRTP).

Gọi hàm ảo trong constructor và destructor

struct Base    { Base() { hello(); } virtual void hello() { std::puts("  Base::hello"); } virtual ~Base() = default; };
struct Derived : Base { Derived() { hello(); } void hello() override { std::puts("  Derived::hello"); } };
Derived d;

  Base::hello
  Derived::hello

Trong khi constructor của Base chạy, phần Derived chưa tồn tại; vptr đang trỏ vào vtable của Base, nên lời gọi ảo đi tới Base::hello. Tương tự trong destructor (phần dẫn xuất đã bị hủy). Gọi hàm thuần ảo trong constructor là UB (thường crash với "pure virtual method called").

Destructor ảo

Base* p = new Derived;
delete p;     // Base không có destructor ảo → UB: chỉ ~Base chạy, phần Derived không được hủy

Quy tắc: class được thiết kế để xóa qua con trỏ lớp cơ sở phải có destructor public virtual. Class không dùng đa hình kiểu đó thì để destructor protected không ảo (không thể xóa nhầm qua lớp cơ sở) hoặc đánh dấu class final. -Wnon-virtual-dtor và -Wdelete-non-virtual-dtor cảnh báo.

Object slicing

void log(Base b) { b.hello(); }   // nhận THEO GIÁ TRỊ
Derived d;
log(d);                            // chỉ phần Base được copy vào b: "cắt lát"; gọi Base::hello

Truyền đối tượng đa hình theo giá trị (hoặc lưu vào std::vector<Base>) làm mất phần dẫn xuất. Truyền bằng tham chiếu/con trỏ, lưu std::vector<std::unique_ptr<Base>>. Có thể chặn slicing bằng cách xóa copy ở lớp cơ sở đa hình.

Đa kế thừa và điều chỉnh con trỏ

struct A { int a = 1; }; struct B { int b = 2; }; struct C : A, B { int c = 3; };
C c;  B* pb = &c;

&c=0x7ffe7fc2f370  (B*)&c=0x7ffe7fc2f374  chênh 4 byte

Đối tượng C chứa phần A rồi phần B; chuyển C* sang B* đổi giá trị con trỏ (cộng offset của phần B). Vì vậy không được ép con trỏ đa kế thừa bằng reinterpret_cast hay qua void* rồi ép ngược sang kiểu khác: địa chỉ sẽ sai. static_cast/dynamic_cast tính đúng offset. Kế thừa hình kim cương với virtual base thêm một tầng gián tiếp nữa; trong code nhúng nên tránh.

RTTI và dynamic_cast

dynamic_cast và typeid dùng thông tin kiểu lúc chạy lưu cùng vtable. Chi phí: tốn Flash cho typeinfo, dynamic_cast duyệt cây kế thừa (có thể chậm). Code nhúng thường tắt bằng -fno-rtti (M04 Bài 0). Nhu cầu "hỏi đối tượng là kiểu gì" thường là dấu hiệu nên thêm một hàm ảo, hoặc dùng std::variant.

Tự kiểm tra`sizeof` của `struct S { char c; int i; virtual void f(); };` trên hệ 64-bit là bao nhiêu? Trên Cortex-M (32-bit)?

64-bit: vptr 8 byte (đặt đầu đối tượng trong Itanium ABI), char 1 + 3 padding, int 4 → 16 byte (đã căn theo 8). Cortex-M 32-bit: vptr 4 + char 1 + 3 padding + int 4 = 12 byte. Câu trả lời tốt nêu rõ phụ thuộc ABI và có thể đổi thứ tự thành viên để giảm padding.

Ý chínhÝ chính của Bài 6
  • Bố cục theo thứ tự khai báo + padding; sắp từ lớn tới nhỏ.
  • Đối tượng rỗng 1 byte; EBO và [[no_unique_address]] để không tốn chỗ.
  • Hàm ảo: vptr mỗi đối tượng, vtable mỗi class; chi phí chính là không inline.
  • Trong constructor/destructor, gọi ảo đi tới phiên bản của class đang dựng/hủy.
  • Xóa qua con trỏ cơ sở cần destructor ảo; truyền đa hình theo giá trị gây slicing.
  • Đa kế thừa đổi giá trị con trỏ khi cast; chỉ dùng static/dynamic_cast.

Bài 7 · Kiểu, auto, const và constexpr

auto và decltype

Strict aliasing và type punning

Compiler được giả định: truy cập một đối tượng qua con trỏ của kiểu khác (không tương thích) không bao giờ xảy ra, trừ khi qua char, unsigned char hoặc std::byte. Nhờ giả định này nó tối ưu mạnh hơn; vi phạm thì code có thể chạy sai ở -O2.

float f = 1.0f;
uint32_t bad = *reinterpret_cast<uint32_t*>(&f);    // UB: strict aliasing
uint32_t u1;  std::memcpy(&u1, &f, sizeof f);        // đúng: compiler tối ưu thành một lệnh mov
uint32_t u2 = std::bit_cast<uint32_t>(f);            // C++20: đúng, constexpr được
// union { float f; uint32_t u; } — hợp lệ trong C, là UB trong C++ (đọc thành viên không phải thành viên được ghi gần nhất)

Ví dụ thực tế trong nhúng: parse gói tin nhận được trong buffer uint8_t[]. Ép reinterpret_cast<const Header*>(buf) vi phạm cả aliasing lẫn có thể không căn chỉnh (HardFault trên Cortex-M0, M02 Bài 9). Cách đúng: memcpy từng trường (hoặc cả struct) ra biến cục bộ, đổi thứ tự byte theo giao thức.

Những UB hay gặp và compiler khai thác chúng

UB Ví dụ
Tràn số nguyên có dấu INT_MAX + 1
Dịch bit quá độ rộng hoặc số âm 1 << 32 với int 32-bit, x << -1
Truy cập ngoài biên mảng a[n] với mảng n phần tử
Đọc biến chưa khởi tạo int x; return x;
Dùng đối tượng ngoài vòng đời Tham chiếu treo, use-after-free (Bài 2)
Vi phạm strict aliasing Ở trên

Con trỏ null bị giải tham chiếu *p khi p == nullptr

UB không có nghĩa là "chạy ra kết quả lạ"; nó có nghĩa là compiler được giả định điều đó không bao giờ xảy ra và tối ưu theo giả định ấy. Ví dụ thật, g++ -O2:

bool will_overflow(int x)        { return x + 1 < x; }
bool will_overflow_u(unsigned x) { return x + 1 < x; }

will_overflow(int):              will_overflow_u(unsigned int):
    xor  %eax,%eax                   cmp   $0xffffffff,%edi
    ret                              sete  %al
                                     ret

Với int, tràn là UB nên compiler kết luận x + 1 < x không bao giờ đúng và trả false cố định: phép kiểm tra tràn biến mất. Với unsigned, tràn là phép quay vòng có định nghĩa, phép so sánh được giữ (trở thành x == UINT_MAX). Cách kiểm tra tràn đúng: so sánh trước khi tính (x > INT_MAX - 1) hoặc dùng __builtin_add_overflow.

Công cụ: UBSan (-fsanitize=undefined) khi chạy test; -Wall -Wextra; static analyzer (clang-tidy, cppcheck); -fwrapv (định nghĩa tràn có dấu là quay vòng) chỉ nên dùng như lưới an toàn, không thay cho code đúng.

Tự kiểm traVòng lặp `for (int i = 0; i >= 0; ++i) { ... }` dùng để "chạy tới khi tràn". Có vấn đề gì?

Tràn số có dấu là UB, compiler được suy ra i >= 0 luôn đúng (vì i bắt đầu từ 0 và chỉ tăng, không được phép tràn) và biến vòng lặp thành vô hạn. Muốn đếm vòng quanh thì dùng kiểu không dấu, hoặc viết điều kiện dừng rõ ràng.

Ý chínhÝ chính của Bài 8
  • Dùng cast có tên; reinterpret_cast chỉ cho địa chỉ thanh ghi và các trường hợp thật sự cần.
  • Strict aliasing: chỉ char/unsigned char/std::byte được đọc mọi thứ; type punning bằng memcpy hoặc std::bit_cast; union punning là UB trong C++.
  • Parse buffer bằng memcpy (tránh cả aliasing lẫn truy cập không căn chỉnh).
  • Compiler tối ưu dựa trên giả định không có UB: kiểm tra tràn phải làm trước phép tính.
  • UBSan, ASan, cảnh báo, static analysis.

Chuỗi và kiểu bao

  • std::string: libstdc++ giữ chuỗi tới 15 ký tự ngay trong đối tượng (SSO), không cấp phát. std::string_view cho tham số chỉ đọc (M14 Bài 1, cẩn thận vòng đời).

  • std::any: kiểu bất kỳ, có thể cấp phát; hiếm khi cần.
  • std::expected<T, E> (C++23): giá trị hoặc lỗi (M14 Bài 2).

Lambda

int threshold = 10;
auto by_val  = [threshold](int x) { return x > threshold; };   // copy lúc tạo lambda
auto by_ref  = [&threshold](int x) { return x > threshold; };  // tham chiếu: phải sống lâu hơn lambda
auto init    = [buf = std::move(buffer)]() { /* sở hữu buf */ }; // init capture (C++14): move vào
auto counter = [n = 0]() mutable { return ++n; };               // mutable: được sửa bản copy của mình
auto generic = [](const auto& a, const auto& b) { return a < b; }; // generic lambda
  • Lambda là một đối tượng của class ẩn danh có operator(); các biến bắt được là thành viên. Lambda không bắt gì chuyển được thành con trỏ hàm (dùng làm callback C, ISR, M04 Bài 9).
  • [=] trong hàm thành viên bắt this (con trỏ), không copy đối tượng; từ C++20 việc bắt this ngầm qua [=] bị coi là lỗi thời. Viết rõ [this] hoặc [*this] (copy cả đối tượng).
  • Bắt tham chiếu tới biến cục bộ rồi lưu lambda lại (thread, callback, trả về) là nguồn tham chiếu treo kinh điển (Bài 2; M14 Bài 5).
  • std::function có thể cấp phát khi lambda bắt nhiều dữ liệu; dùng tham số template khi chỉ gọi ngay.
Tự kiểm traĐoạn code xóa phần tử thỏa điều kiện trong `std::vector` bằng vòng lặp `for (auto it ...)` và `v.erase(it)`. Có lỗi gì và viết lại thế nào?

Sau erase(it), it (và mọi iterator phía sau) mất hiệu lực; ++it là UB; ngoài ra mỗi lần erase dịch các phần tử phía sau nên tổng là O(n²). Viết lại: std::erase_if(v, pred) (C++20), hoặc erase-remove idiom, hoặc nếu phải dùng vòng lặp: it = v.erase(it) và chỉ ++it khi không xóa.

  • vector và array là mặc định; độ phức tạp lý thuyết thua bố cục bộ nhớ.
  • Biết bảng iterator invalidation; std::erase_if; tham chiếu vào vector treo khi cấp phát lại.
  • SSO 15 ký tự (libstdc++); optional, variant, expected thay giá trị đặc biệt.
  • Lambda là đối tượng; init capture để move; [this]/[*this] rõ ràng; cẩn thận bắt tham chiếu.

Vòng đời và khởi tạo

01Static initialization order fiasco là gì và cách tránh?Hay hỏi

Thứ tự khởi tạo đối tượng static giữa các file không xác định; constructor của đối tượng ở file này có thể dùng đối tượng ở file khác chưa được dựng. Tránh bằng static cục bộ trong hàm (dựng ở lần gọi đầu, thread-safe từ C++11) hoặc constinit/constexpr để khởi tạo lúc biên dịch.

02Thành viên được khởi tạo theo thứ tự nào?Hay hỏi

Theo thứ tự khai báo trong class, không theo thứ tự trong danh sách khởi tạo; hủy theo thứ tự ngược. Dùng thành viên khai báo sau để khởi tạo thành viên khai báo trước là đọc giá trị chưa khởi tạo; -Wreorder cảnh báo.

03{} khởi tạo khác () thế nào?

{} cấm thu hẹp kiểu (narrowing) và tránh most vexing parse, nhưng ưu tiên constructor nhận initializer_list (std::vector<int>{3, 7} là 2 phần tử, (3, 7) là 3 phần tử giá trị 7). T x{} value-init (số về 0).

04Most vexing parse là gì?

Widget w(); được hiểu là khai báo hàm w trả Widget, không phải đối tượng. Dùng Widget w; hoặc Widget w{};.

Value category và tham chiếu

05lvalue, prvalue, xvalue khác nhau thế nào?Hay hỏi

lvalue có danh tính và tồn tại sau biểu thức (biến, *p); prvalue là giá trị tạm thuần (42, f() trả theo giá trị); xvalue có danh tính nhưng sắp hết hạn (std::move(x)). rvalue = prvalue + xvalue, move được. Có tên thì là lvalue, kể cả biến kiểu T&&.

06Khi nào đối tượng tạm được kéo dài vòng đời? Khi nào không?Hay hỏi

Khi prvalue gắn trực tiếp vào const T& hoặc T&& cục bộ (hoặc thành viên tham chiếu trong aggregate init): sống tới hết phạm vi tham chiếu. Không áp dụng khi đi qua lời gọi hàm (const T& r = pick(make()) treo), khi trả tham chiếu từ hàm, khi gắn vào tham số.

07Nêu các dạng tham chiếu treo hay gặp.

Trả tham chiếu/con trỏ tới biến cục bộ; string_view vào chuỗi tạm; tham chiếu vào phần tử của vector tạm hoặc vector sau khi cấp phát lại; range-for trên phần tử của đối tượng tạm (trước C++23); thành viên tham chiếu gắn vào tạm; lambda bắt tham chiếu được lưu lại sau khi biến cục bộ chết.

RAII và hàm đặc biệt

08Rule of 0, 3, 5 là gì?Hay hỏi

Rule of Zero: class chỉ chứa thành viên tự quản lý tài nguyên không viết hàm đặc biệt nào (mặc định nên hướng tới). Rule of Five: class trực tiếp quản lý tài nguyên thô tự viết destructor, copy ctor, copy =, move ctor, move = (hoặc xóa những cái không hỗ trợ). Rule of Three là bản trước C++11.

09Copy-and-swap là gì và được gì?Hay hỏi

Toán tử gán nhận tham số theo giá trị rồi swap với *this. Một hàm phục vụ cả copy và move, tự gán an toàn không cần kiểm tra, strong exception guarantee (copy ném thì *this không đổi). Giá: thêm một lần move/swap.

10Khai báo destructor ảnh hưởng gì tới move?Hay hỏi

Khai báo destructor (kể cả = default, virtual) làm compiler không sinh move constructor/assignment; yêu cầu move âm thầm thành copy. Muốn giữ move phải = default tường minh.

11Khai báo move constructor ảnh hưởng gì tới copy?

Copy constructor và copy assignment bị xóa ngầm; muốn copy được phải tự khai báo. Default constructor cũng không còn được sinh (move ctor là một constructor).

Move

12std::move làm gì?Hay hỏi

Chỉ là cast sang rvalue reference để chọn overload nhận T&&; không di chuyển gì. Việc di chuyển do move constructor/assignment. std::move trên đối tượng const sẽ chọn copy.

13Trạng thái của đối tượng sau khi bị move?

Hợp lệ nhưng không xác định: hủy được, gán lại được, gọi được hàm không có tiền điều kiện (clear, size). Không dựa vào giá trị cụ thể.

14Copy elision và NRVO khác nhau thế nào? Có nên return std::move(local)?Hay hỏi

Trả prvalue: từ C++17 elision bắt buộc, không copy/move. NRVO (trả biến có tên): được phép, không bắt buộc, GCC/Clang làm khi chỉ một biến được trả. return std::move(local) chặn NRVO, ép một lần move; không nên (GCC cảnh báo -Wpessimizing-move). Biến cục bộ trong return đã tự được coi là rvalue khi không elide được.

15Vì sao move constructor nên noexcept?Hay hỏi

std::vector khi cấp phát lại chỉ move phần tử nếu move là noexcept (để giữ strong guarantee), nếu không thì copy. Đo được: 1000 phần tử chứa chuỗi, move noexcept: 0 copy; move không noexcept: 1023 copy.

16push_back và emplace_back khác nhau thế nào?

push_back(T) nhận đối tượng đã có (copy hoặc move vào); emplace_back(args...) dựng tại chỗ trong bộ nhớ của vector từ tham số, tránh đối tượng tạm. Với đối tượng đã có sẵn thì tương đương; emplace_back có thể gọi constructor explicit ngoài ý muốn.

Smart pointer

17unique_ptr có tốn chi phí gì so với con trỏ thô?

Không, với deleter không trạng thái: cùng kích thước (8 byte trên 64-bit), hủy là một lời gọi delete. Deleter là con trỏ hàm thì thêm 8 byte; dùng struct deleter để tránh.

18Cấu trúc của shared_ptr và chi phí?Hay hỏi

Hai con trỏ (đối tượng, control block); control block chứa strong/weak count atomic, deleter. Copy/hủy là thao tác atomic. make_shared cấp phát một lần cho đối tượng và control block, nhưng bộ nhớ đối tượng giữ tới khi weak_ptr cuối cùng hết.

19shared_ptr có thread-safe không?Hay hỏi

Bộ đếm atomic: các thread giữ các bản sao khác nhau an toàn. Nhiều thread đọc-ghi cùng một biến shared_ptr thì không (mutex hoặc std::atomic<std::shared_ptr> C++20). Đối tượng được trỏ tới không tự thread-safe.

20Khi nào cần weak_ptr?

Phá chu trình sở hữu (cha-con, đồ thị), cache, observer/callback không muốn giữ sống đối tượng. Dùng lock() để lấy shared_ptr (rỗng nếu đã chết).

21enable_shared_from_this giải quyết vấn đề gì?

Lấy shared_ptr tới chính mình từ hàm thành viên mà không tạo control block thứ hai (shared_ptr<T>(this) gây xóa hai lần). Đối tượng phải đang được shared_ptr sở hữu; gọi trong constructor ném bad_weak_ptr.

Mô hình đối tượng

22vtable và vptr hoạt động thế nào? Chi phí?Hay hỏi

Mỗi class có hàm ảo có một vtable (mảng địa chỉ hàm, trong vùng chỉ đọc); mỗi đối tượng có vptr trỏ tới vtable của kiểu động. Gọi ảo: đọc vptr, đọc mục, gọi gián tiếp. Chi phí chính: không inline được và dự đoán nhánh; thêm một con trỏ mỗi đối tượng.

23Gọi hàm ảo trong constructor thì sao?Hay hỏi

Gọi phiên bản của class đang được dựng (phần dẫn xuất chưa tồn tại, vptr trỏ vtable của lớp cơ sở). Tương tự trong destructor. Gọi hàm thuần ảo khi đó là UB ("pure virtual method called").

24Khi nào cần destructor ảo?Hay hỏi

Khi đối tượng dẫn xuất có thể bị xóa qua con trỏ lớp cơ sở; thiếu thì UB (phần dẫn xuất không được hủy). Class không dùng kiểu đó: destructor protected không ảo hoặc final.

25Object slicing là gì?

Copy đối tượng dẫn xuất vào biến/tham số kiểu lớp cơ sở theo giá trị: chỉ phần cơ sở được giữ, mất hành vi đa hình. Truyền bằng tham chiếu/con trỏ; lưu unique_ptr<Base>; có thể xóa copy ở lớp cơ sở.

26Vì sao sizeof của class rỗng là 1? EBO là gì?

Mọi đối tượng phải có địa chỉ riêng. Khi kế thừa từ lớp rỗng (EBO) hoặc dùng [[no_unique_address]] (C++20), phần rỗng không chiếm byte; thư viện chuẩn dùng cho allocator/deleter/comparator.

Kiểu, cast, UB, STL

27Strict aliasing là gì? Type punning đúng cách?Hay hỏi

Compiler giả định không truy cập đối tượng qua con trỏ kiểu không tương thích (trừ char/unsigned char/std::byte) và tối ưu theo đó. Đọc bit của float dưới dạng uint32: std::memcpy hoặc std::bit_cast (C++20); reinterpret_cast hay union punning là UB trong C++.

28Vì sao x + 1 < x với int bị compiler bỏ đi?Hay hỏi

Tràn số có dấu là UB, compiler được giả định không xảy ra nên biểu thức luôn false (GCC -O2 sinh return false). Với unsigned, tràn là quay vòng có định nghĩa nên phép so sánh được giữ. Kiểm tra trước phép tính hoặc dùng __builtin_add_overflow.

29Bốn cast của C++ dùng khi nào?

static_cast: chuyển đổi có nghĩa kiểm tra lúc biên dịch; dynamic_cast: ép xuống trong cây đa hình có kiểm tra lúc chạy (cần RTTI); const_cast: bỏ const (ghi vào đối tượng vốn const là UB); reinterpret_cast: diễn giải lại bit (địa chỉ thanh ghi), dễ vi phạm aliasing. Tránh C-style cast.

30Xóa phần tử khỏi vector trong vòng lặp thế nào cho đúng?Hay hỏi

std::erase_if(v, pred) (C++20) hoặc erase-remove idiom; nếu dùng vòng lặp thì it = v.erase(it). erase làm mất hiệu lực iterator từ điểm xóa; ++it sau đó là UB.

31Khi nào iterator của vector mất hiệu lực?

Cấp phát lại (push_back/insert vượt capacity, reserve, shrink_to_fit): tất cả iterator, con trỏ, tham chiếu. Không cấp phát lại: từ điểm chèn/xóa trở đi.

32[=] trong hàm thành viên bắt gì?

Bắt con trỏ this, không copy đối tượng; lambda sống lâu hơn đối tượng sẽ treo. C++20 coi bắt this ngầm qua [=] là lỗi thời; viết [this] hoặc [*this] (copy đối tượng).
